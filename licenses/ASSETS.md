# 资产类第三方登记表（`licenses/ASSETS.md`）

> 本文件是 `tools/check-license-policy.py --assets` 的**第三方资产登记表**（唯一来源）。
> **第一方文件（GZ-AG）不进这张表**：它们登记在 `licenses/FIRST-PARTY.md`（440 起的名册），
> 门禁对 `app/src/main/assets/` 做双向校验 —— 文件在名册或在表里，两处都没有 ⇒ 红（漏登记）；
> 同一文件不许同时在两表（两表冲突 ⇒ 红）。
> 本批（433）只建立表头，**没有填任何条目**；模型 / 字体 / rootfs 这类资产由 414 解冻时逐条登记。

## 为什么单独一张表

`423` 的门禁只看**代码依赖**（Maven / Rust），义务形态是「许可 + 随包正文」。
资产类第三方（模型权重、字体、rootfs 镜像）的义务形态不一样：**许可、署名、可再分发**
三件事各自成立，而且往往没有 POM 可查、没有 `licenses/*.txt` 可对。
所以登记字段也不同，不能塞进 `EXCEPTIONS.md`（那张表是「豁免签字」，这张是「资产台账」）。

## 政策：与代码依赖**同一套**

许可判定共用门禁脚本里的 `ALLOWED` / `DENY_FAMILIES` / `classify()`，**不另立一份表**：

| 类别 | 许可 |
| --- | --- |
| **允许** | Apache-2.0 / MIT / BSD-2-Clause / BSD-3-Clause / ISC / Zlib / 0BSD / Unlicense / MPL-2.0 |
| **禁止** | GPL-2.0 / GPL-3.0 / AGPL / LGPL-2.1 / LGPL-3.0 / SSPL（按家族判，任意版本） |
| **未登记** | 既不在允许表也不在禁止表的（例如字体常用的 OFL-1.1）⇒ 判红 |

⚠️ 两点必须记住：

1. **这张表不是豁免表**。`EXCEPTIONS.md` 里的 Maven 坐标豁免**不覆盖**资产；
   资产要放行，只有「许可在允许表内」或「改政策（改脚本＋过评审）」两条路。
2. **「许可允许」不等于「义务已履行」**。署名要求、随包正文、可再分发是另外三件事，
   由 `署名要求` / `随包？` 两列登记，门禁只查**有没有登记**，不替人核对正文。

## 怎么登记一条

在下面的表格里加一行，六列**缺一不可**（空格子那一行不算登记，门禁会红）：

| 列 | 写什么 | 例子 |
| --- | --- | --- |
| 资产名 | **相对 `app/src/main/assets/` 的精确文件路径**（正斜杠；可用反引号包裹；不许目录、通配、`..`） | `models/tiny.onnx` |
| 版本 | 上游版本号；查不到就填 `—` 并在来源里说明 | `1.0` |
| 许可 | SPDX id（`MIT` / `Apache-2.0` / `OFL-1.1`…），多许可用 `,` 分隔 | `Apache-2.0` |
| 随包？ | 只填 `是` 或 `否`（`否`＝不进 APK，仅开发期用） | `是` |
| 署名要求 | 一句话写清要署什么名／附什么正文；**确实没有就填 `无`**（空着判红） | `随包附 NOTICE` |
| 来源 | 上游地址（能核到版本与许可的那一页） | `https://example.org/model` |

三条容易踩的规矩：

1. **一文件一行**。`models/` 这种目录、`*.onnx` 这种通配都不算登记；目录里每个文件各自一行。
2. **删了资产就删行**。登记了但 `assets/` 里没有对应文件时，门禁只给「提醒」，不改判；
   但留着过期行会让下一个人以为它还在包里。
3. **许可写法要对得上**。写 `OFL-1.1` 就是 OFL-1.1；政策没收录的许可会被判「未登记」而红，
   这是**要人拍板**的事，不要在表里改写一个相近的允许类许可糊过去。
