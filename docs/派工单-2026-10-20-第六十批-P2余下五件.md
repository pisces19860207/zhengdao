## 1. P2-7 · `cleanupPartial` 在 `onCreate` 主线程递归删大目录

**现状**：`TerminalActivity.kt:121` `RootfsInstaller.cleanupPartial(applicationContext)` 在 `onCreate` 同步执行；它是递归删残留，最坏 1.5–2 GB，主线程可掉帧/ANR。

**改法**：挪出主线程（后台线程/协程，或放到 `Application`/专门初始化器），并与「起会话/安装置位」保持互斥（`RootfsInstaller` 已有锁，别绕过）；失败落 RunLog，不静默。

**测试**：源码门禁——`cleanupPartial` 不得直接出现在 `onCreate` 同步段，必须在 IO/后台入口；负例改回 ⇒ 红。若能把「是否可清理」抽纯函数测更好；真机可选。

## 2. P2-8 · `PreviewServer` 接到的 socket 不设 `soTimeout`

**现状**：`preview/PreviewServer.kt` 的 `accept()` 有 `soTimeout`，但 `accept` 到的 `sock` 没设；`handle(sock)` 里 `reader.readLine()` 读请求行。一个连上但不发数据的客户端能把**单线程**串行循环永远卡住。

**改法**：在 `handle` 之前（或 `handle` 开头）对 `sock` 设 `soTimeout`（复用/新增一个明确的超时常量）；超时当坏请求：关连接、记一行日志，循环继续。别把 `accept` 的 timeout 常量直接当请求超时用，若语义不同就单列。

**测试**：`SilentClientTest`——本地起 server，连上不发数据，断言在超时内连接被关、server 仍能处理下一条正常请求（只用 `java.net`，不新增依赖）；负例去掉 `soTimeout` ⇒ 用例超时/红。

## 3. P2-10 · `ConfirmFlow` 的 `pending`/`deferred` 无 `@Volatile`

**现状**：`baopu/agent/ConfirmFlow.kt:81-82` `private var pending` / `private var deferred` 无 `@Volatile`；引擎线程写、UI 主线程读。

**改法**：加 `@Volatile`（或换成 `AtomicReference`/线程安全容器）；`note`/`abandoned` 同理按实际跨线程读的字段处理。不要改变确认制状态机语义。

**测试**：源码门禁——跨线程字段必须有 `@Volatile`/原子类型；负例去掉 ⇒ 红。

## 4. P2-11 · `SessionManager.startedAtMs` 无 `@Volatile`

**现状**：`terminal/SessionManager.kt:79` `var startedAtMs` 无 `@Volatile`；30 秒巡检/其他线程可能读到 0。

**改法**：补 `@Volatile`（`session` / `usesTmux` / `isFallback` 已有同款）；不改变写入点。

**测试**：源码门禁——`startedAtMs` 必须带 `@Volatile`；负例 ⇒ 红。

## 5. P2-12 · 三处 `PendingIntent` 请求码都是 0

**现状**：`CacheNotifier.kt:29` / `InstallNotifier.kt:34` / `SessionService.kt:361` 都是 `PendingIntent.getActivity(ctx, 0, MainActivity... , UPDATE_CURRENT)`；component/filter 相同 ⇒ 同一个 PendingIntent，`UPDATE_CURRENT` 互改 extras（缓存通知可能清掉「回到终端」的 `open_terminal`）。

**改法**：三处给**不同 requestCode**（常量命名，如 `REQ_CACHE=…`/`REQ_INSTALL=…`/`REQ_KEEPALIVE=…`），保持各自 extras/flags；不要改通知 id 与点击语义。

**测试**：源码门禁——三处 requestCode 不得相同，且必须是命名常量；负例改回同一个 0 ⇒ 红。真机可选：分别点三条通知，落点正确。
