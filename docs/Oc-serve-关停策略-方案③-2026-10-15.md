## 0. 一句话

给 `opencode serve`（太极宿主进程）补一个**受控回收出口**：只在「App 真的走了」时收；UI 导航（切 Tab）与会话生命周期（结束会话）一律不碰。**与第⑱刀 `BrowserHolder` 的受控回收出口同型**（有守卫、单出口、只在特定时机真回收）。

## 1. 问题（原文 + 现状，代码级证据）

**问题原文**（台账 §B 顺序 4 / §A #86 遗留项）：

> **P1-6** `serve` 进程没人关：全仓唯一调用点 `ui/HomeScreen.kt:119 if (restart) OcManager.stopServe()`、`ui/taiji/TaijiScreen.kt` 内 0 命中 —— 落点在太极面板生命周期里 …… **要先定「什么时候该关」再动**，否则会把用户正在跑的会话打断。

**现状核实**（本刀开工时逐条 grep）：

| 事实 | 证据 |
|---|---|
| `OcManager.stopServe()` 定义 | `oc/OcManager.kt:604` |
| 全仓 `stopServe()` 调用点 | **只有** `ui/HomeScreen.kt:179`（「重启 serve」流：`if (restart) OcManager.stopServe()` 后紧接 `startServe()`） |

## 2. 策略③（用户 2026-10-15 拍板）

### 2.1 收（Abort 时机）

| # | 时机 | 语义 | 落点 |
|---|---|---|---|
| **T1** | 主页 Activity「正在结束」（`isFinishing == true`） | 用户按返回 / 划掉任务把主页 finish 掉 ⇒ App 真的走了 | `ZhengdaoApp` 的 `ActivityLifecycleCallbacks.onActivityDestroyed` |
| **T2** | 任务被划掉（`onTaskRemoved`） | 从最近任务里划走 | `SessionService.onTaskRemoved` |
| **T3** | 服务销毁（`onDestroy`）——**且**销毁原因是 T2 | 兜一层（个别 ROM 只给 `onDestroy`，不给 `onTaskRemoved`） | `SessionService.onDestroy`（`taskRemoved` 守卫） |

### 2.2 不收（负例，必须保持）

| 场景 | 为什么不收 | 代码位置 |
|---|---|---|
| 切走 / 切回太极 Tab | UI 导航，App 没走（台账原话「不因切 Tab 就关」） | `MainActivity` 的 `when (tab)` / `onTabClicked` |
| **结束本次会话**（太极抽屉） | 会话结束 ≠ App 退出；serve 留着下次重挂 | `TaijiScreen.onCloseSession`：`repo.close()` + `OcRuntime.shutdown()` + `onExit()`（`:392-404`，本就**没有** `stopServe`） |
| 通知栏**停止会话** | 同上，且用户还在 App 里 | `SessionService` 的 `ACTION_STOP_SESSION` → `SessionManager.kill` + `stopSelf`；以及 `SessionManager.kill` → `SessionService.stop()` |
| 转屏 / 配置变更 | `isFinishing == false` ⇒ T1 不触发 | 系统回调 |
| 单纯退到后台（Home 键） | 保活服务仍在前台、agent 还在跑 | — |

### 2.3 天然成立的一条

**进程被系统回收** ⇒ App 进程死，serve 是它 spawn 的子进程，随之消亡（`stopServe` KDoc 原话）。**不需要额外钩子**。若真机发现 serve 会遗留成孤儿，另立一刀（即便遗留也不致命：孤儿分支能重挂）。

## 3. 为什么 T3 必须带守卫（本方案唯一的判断点）

`SessionService.onDestroy()` **不只在任务划掉时跑**：

- `ACTION_STOP_SESSION`（通知栏「停止会话」）→ `stopSelf()` → `onDestroy`；
- `SessionManager.kill()` → `SessionService.stop(ctx)` → `onDestroy`（`SessionManager.kt:225 / :234 / :267`）。

若在 `onDestroy` 里**无条件**收 OC，上面几条就把「**结束会话不关**」踩了 —— 用户点一下「停止会话」，正在跑的 serve 被一起带走。
守卫取 **`taskRemoved`**（T2 置位）⇒ T3 只对「任务被划掉」这条销毁原因生效；其余销毁原因一律**不动** OC。`OcManager.stopServe()` 本身幂等（`serveProcess?.destroy()` 空安全 + `/proc` 扫描命中不到即无操作），所以 T2/T3 重复调用无害。

> ⚠️ 口径说明：本方案把「结束会话」按**最严**解释处理 —— 无论走太极抽屉的「结束本次会话」还是通知栏的「停止会话」，都**不停** serve。若你要的是「通知栏停止会话时顺手收 serve」，那只改一处（去掉 `taskRemoved` 守卫），门禁 G2 会同步翻面。

## 6. 边界与取舍（照实说）

1. **主线程**：`onActivityDestroyed` / `onTaskRemoved` / `onDestroy` 都在主线程；`stopServe()` 含一次 `/proc` 扫描 + `Process.destroy()`，量级约 1–5 ms（hidepid 下只列本 UID 进程）。本刀按**同步调用**处理（teardown 是罕见路径），列为**真机观察项**；若真机发现卡顿，改后台线程（会 +1 条裸 Thread 对账单条目）。
2. **「进程死 ⇒ 子进程亡」是项目既有假设**（`stopServe` KDoc），本刀**不改**。
3. **Release 行为不额外验证**：`stopServe()` 无 `BuildConfig` 分支，debug/release 同路径。
4. **真机读数**（用户/蓝总管）：切 Tab 后 `ps -A | grep -i serve` 仍在；划掉任务后 `serve` 消失；结束会话后 serve 仍在。
