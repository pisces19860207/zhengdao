## ㊽-B · 桥 `execJS` 含分号的多语句必挂（§B 77 ＝ 报告 N3，P2）

> 来源：第㉟刀报告 §7 N3 —— 真机实测：`execJS '1+1'` 正常、`execJS` 带中文的单表达式正常，**凡含分号的多语句一律超时**（回「JS 执行超时或失败」）。我已把根因读到行。

```
你在证道仓库 C:\Users\guoli\AndroidStudioProjects\zhengdao 干活（硬规矩见末尾）。先读 docs/FEATURE-LEDGER.md 的 §B 顺序 77，以及 证道设计报告/证道-第35刀-真机验收批-2026-10-16.md 的 §7 N3。

已核事实（我逐行核过）：app/src/main/java/com/example/zhengdao/bridge/JsEmbed.kt:41-42

任务：
① 让包装同时容纳「表达式」与「语句序列」两种输入，且**保持既有对外契约**：超时/异常仍回 JSON（不断连）、返回值仍过 `redactPairs(redactText(...))` 管线；
② ⚠️ **不得引入二次 eval** —— 第㊷刀刚把 `String(eval(<code>))` 那类写法拔掉（台账 §B 73），别退回去；
③ 表达式与语句序列的判定要么在包装里天然兼容（例如把 code 放进函数体、用 `return` 只作可选前缀），要么给出明确规则并写进 KDoc；**不许用「猜字符串里有没有分号」这种脆判据**；
④ 顺带确认：`return (…)` 那层括号对**多行**代码、`await`/`function` 声明式 code 的行为，写进报告。

判据：
① 纯函数/JVM 单测（不依赖真机）：至少覆盖 `1+1`、`var a=1; a+1`、`document.title` 三种形态 —— 断言产出的脚本文本可被 JS 引擎解析（可用既有 JVM 侧包装测试的同等手法）；
② 负例自证：把包装改回单表达式 `return (…)` ⇒ 「多语句」那条必红；
③ 全量单测 0 失败，贴 XML 聚合读数。

交付：分支 `fix/bridge-execjs-multistmt` ＋ 工作树 `wt-bridge-execjs-multistmt` ＋ 报告双份（放 证道设计报告/，文件名「证道-第48刀B-桥execJS多语句-2026-10-16」）；末尾给「分支名 ＋ HEAD sha ＋ 未合并」。
```
