## 3. A 段规格：确认制通电

### 3.1 事件协议（唯一真源：`RunEngine.EngineEvent`）

新增：

```kotlin
data class ConfirmRequest(
    val callId: String,        // 稳定 id（= tool 调用的 id；落库用）
    val tool: String,          // 工具名，如 write_file
    val summary: String,       // 一句话人话摘要，如「覆盖 l.txt（1,203 行 → 12 行）」
    val argsJson: String,      // 原样参数（落库、恢复时重放）
) : EngineEvent
```

- `AskUser(message)` **保留不动**（收料提问卡在用，别改坏）。
- 界面文案全部走 `strings.xml`，不许在 Kotlin 里拼中文。

### 3.2 引擎挂起与恢复

- `NeedsConfirm` 分支改为：`settle(AWAIT_CONFIRM)` → 落库 pending 三列 → 发 `ConfirmRequest` → **挂起等待**（不再 `return`）。
- 等待用 `CompletableDeferred<Boolean>` ＋ `withTimeoutOrNull(RunRules.CONFIRM_TIMEOUT_MS)`。
- 超时：`settle(ABORTED)` ＋ 回灌一条系统消息「等了 15 分钟没收到批准，本轮先停」＋ 清 pending 三列。
- 公开方法：`fun resumeWithApproval(callId: String, approved: Boolean, note: String?)`；`callId` 不匹配就丢弃（防陈旧点击）。
- 批准：走 `GuardPipeline.executeApproved(spec, call)` —— **跳过权限判定那一段，其余五段（Schema 校验、路径守卫、超时执行、spill＋DataFence）原样保留**。
- 拒绝：不执行，回灌 `用户拒绝：<summary>`，对话继续（`terminateRound = false`）。

### 3.3 落库（跨进程必须能续）

`BaopuDb` 幂等迁移给 `session` 加三列：`pending_tool TEXT`、`pending_args TEXT`、`pending_at INTEGER`。

- 写：进 `AWAIT_CONFIRM` 时同事务写。
- 清：批准/拒绝/超时后清空。
- 读：`BaopuChatController` 构造时若 `pending_tool` 非空 ⇒ 重建 `ConfirmRequest`（`summary` 由工具名 ＋ 参数重新生成，不落库）。

### 3.4 界面

新增 `ui/baopu/BaopuConfirmCard.kt`（形态照 `BaopuAskUserCard`，别另起一套视觉）：

- 一行标题：`要动文件：<路径>`
- 一行摘要：`<summary>`
- 两个按钮：「批准」「拒绝」；忙碌态显示「执行中…」
- 无障碍：两个按钮都要 `contentDescription`（**用 `Modifier.semantics` 或 `Text` 的语义，不要引 `material-icons`**——本项目没这个依赖）

控制器新增 `var confirmCard by mutableStateOf<ConfirmRequest?>(null)`，`onEngineEvent` 接住 `ConfirmRequest`；批准/拒绝调 `engine.resumeWithApproval(...)` 后置空。

### 3.5 红线（A 段最容易破的口子）

1. **批准 ≠ 绕过护栏**：路径守卫、开工闸门、归档闸门、`DataFence`、写前备份一个都不能少。
2. **一次只允许一个 pending**：由 `ActiveSessionGate` 保证；拿到第二个就丢弃并记日志。
3. `executeApproved` **不许**再调 `permission` 判定（否则死循环）。
4. 参数原样落库，但**落库前先过一遍长度上限**（`argsJson` ≤ 8 KB，超了截断并标注），防大参数撑爆表。

## 4. B 段规格：模型契约对齐

> ⚠️ **本节已移出本单**（2026-10-17 19:20）：模型参数相关全部由 **第十四批**（`docs/派工单-2026-10-17-第十四批-抱朴模型参数适配.md`，基线 `775d150`）承接，本单只做 A 段（确认制通电）与 C 段（续跑回灌）。两单都动 `LlmClient.kt` ⇒ 建议先合第十四批。

### 4.1 窗口与输出上限

- `ContextAssembler.DEFAULT_WINDOW_TOKENS`：`128_000` → **`1_048_576`**（理由：deepseek-flash 实测 `context_window=1048576`；用户口径「现在的模型大都 1M 了，谁还用老模型」）。
- `Provider`：flash 内置条目填 `contextWindow = 1_048_576`、`maxOutput = 393_216`（实测 `/models`）。
- 压缩阈值比例（现有 `0.6/0.9`）**不改**，按新窗口自然放大。

### 4.2 请求体（OpenAI 兼容路径 `LlmClient.kt:145-153`）

加三项：

```kotlin
.put("max_tokens", 输出上限)                      // = min(provider.maxOutput ?: 默认, 剩余预算)
.put("stream_options", JSONObject().put("include_usage", true))
.put("reasoning_effort", 档位)                    // none / low / high / max
```

- **不要**发 `effort` 或 `max_reasoning_effort`——实测给非法值也返回 200，属静默忽略的假字段。
- `reasoning_effort` 是**真字段**：非法值返回 422 并列出枚举 `none/minimal/low/medium/high/xhigh/ultra/max`。
- 默认档 = `high`（服务端默认就是 high，显式发出去只为让用户改得动）。

### 4.3 设置页「思考深度」四档

| 界面 | 值 |
|---|---|
| 关 | `none` |
| 低 | `low` |
| 高（默认） | `high` |
| 最高 | `max` |

存 `ProviderPrefs`（沿用现有 key 存储机制，新增一个 `reasoning_effort` 键）；改档位**不需要**重建引擎（每轮读一次即可）。

### 4.4 接住用量与思考内容

- SSE 里 `delta.reasoning_content` 目前被丢弃（`LlmClient.kt:221` 只取 `delta.content`）：**接住但不进正文**——存进 `run_log` 的 `reasoning_chars INTEGER`（只记字数，不落原文，省空间）。
- `usage.prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` / `completion_tokens_details.reasoning_tokens`：落 `run_log` 两列 `cache_hit_tokens`、`reasoning_tokens`，供以后的「缓存账」用。
- 迁移照样走幂等加列。

## 5. C 段规格：续跑回灌工具结果

`RunEngine.loadHistory` 现在只取 `part.kind='text'`（`:826-841`）。改成：

1. 按 `message.id` 升序遍历，每条消息按 `part.sort` 还原；

3. `kind='tool'` → 还原成一条 `ROLE_ASSISTANT` 的 `DataFence.wrap(tool, ts, 结果)`（**保持与在线路径同形**，否则模型会对不上账）；
4. 顺序必须与在线时一致（工具结果紧跟发起它的那轮）。

## 7. 判据（JVM 逐条 ＋ 真机四条）

### 7.1 JVM 单测（每条一例，命名写清断言什么）

| # | 判据 | 断言 |
|---|---|---|
| J1 | 批准后执行器真的跑 | `resumeWithApproval(approved=true)` → 目标文件内容变成期望值 |
| J2 | 拒绝不执行 | 文件 sha256 前后一致，且历史里多一条「用户拒绝」 |
| J3 | 超时自动收尾 | 注入 `foregroundElapsedMs > CONFIRM_TIMEOUT_MS` → 状态 `ABORTED`、pending 三列清空 |
| J4 | 陈旧点击丢弃 | `callId` 不匹配的批准调用不改变任何状态 |
| J5 | 批准不走权限判定但走路径守卫 | 构造越界路径的 pending → 批准后得到 `Rejected`（不是 `NeedsConfirm`，也不是执行成功） |
| J6 | 窗口 1M | `ContextAssembler` 默认窗口 = `1_048_576`；`windowOf(provider 无元数据)` = 1M |
| J7 | 请求体正确 | 纯函数取 body 断言：含 `max_tokens`、`stream_options.include_usage=true`、`reasoning_effort`；**不含** `effort` / `max_reasoning_effort` |
| J8 | 四档映射 | 关/低/高/最高 → `none/low/high/max`，默认 `high` |
| J9 | 续跑回灌 | 造一条含 `kind='tool'` 的历史 → `loadHistory` 结果里含 `DataFence.wrap` 包裹的工具结果，且顺序在发起轮之后 |
| J10 | 迁移幂等 | 连续两次打开库不报错、列不重复、旧数据不丢 |

### 7.2 真机（`adb` 读数 ＋ 截图，缺一条不算交付）

- **T1** 让抱朴把 `资料库/整理/x.txt` 第一行改成 `X` → 出现确认卡（截图）→ 点批准 → `adb shell` 读文件内容确认真改了 → 对话继续往下（截图）。
- **T2** 同样操作点「拒绝」→ 文件 sha256 不变（`adb shell sha256sum`）→ 对话继续。
- **T3** 出卡后 `adb shell am force-stop com.example.zhengdao` 再进 → 卡还在 → 批准仍能改文件。
- **T4** 出卡后不管它，把手机系统时间往前拨 16 分钟（或注入超时）→ 状态变「被中止」、卡消失、有「等了 15 分钟」的人话。

## 追加一 · 输出上限的另一半与参数可见（2026-10-17 19:20 追加）

背景：同目录另有一份《抱朴-模型适配评估-DeepSeek-V4.1-Flash-1017-2026-10-17.md》（112 行），结论与本单 §4 B 段一致（窗口被砍到 128k、OpenAI 分支不发 `max_tokens`、无模型侧 reasoning 处理）。以下**两处以本单为准**，另补两条。

### 11.1 以本单为准的两处

1. **思考模式不关**。评估报告建议 `thinking:{"type":"disabled"}`；实测判据（`D:\zd-tools\ds-effort-probe2.txt`，用非法值探真假）：`reasoning_content` 是**独立字段**、不污染 `content`；`reasoning_effort` 是**真字段**（8 档：`none/minimal/low/medium/high/xhigh/ultra/max`，非法值 422 并把枚举报回来），未传时默认 `high`。抱朴做资料整理是复杂任务，关死思考会丢能力 ⇒ 按 §4 B 段四档（关=`none`／低=`low`／高=`high`／最高=`max`，默认高）实现，**不要写死 disabled**。
2. **`effort` 与 `max_reasoning_effort` 禁发**：两者塞非法值仍 200（静默忽略的假字段），写了等于没写，还会在日志里误导人。

### 11.2 补：Anthropic 分支也要接 `maxOutput`（判据 J11）

- 现状：`app/src/main/java/com/example/zhengdao/baopu/LlmClient.kt:94` `ANTHROPIC_MAX_TOKENS = 4096` 写死，`:162` 直接放进请求体；`Provider.kt:59` 的 `maxOutput` 只被内部预算用，没进任何请求。
- 要求：请求体的 `max_tokens` 取 `provider.maxOutput`；Anthropic 分支 `null` 时回落 `4096`，OpenAI 分支 `null` 时回落 `8192`。
- **J11**：单测断言「显式 `maxOutput=393_216` ⇒ 请求体 `max_tokens` 等于 393216；`maxOutput=null` ⇒ 用各自回落值」。

### 11.3 补：设置页只读展示两个参数（判据 J12）

- 不设可编辑输入框（用户手填 baseUrl / 窗口只会更糟）；只在「抱朴设置」里加一行只读摘要：`上下文 1,048,576 · 输出上限 393,216`。
- **J12**：切到 flash 预设时该行显示上述数字；切到未声明窗口的通道时显示「未声明」，**不许显示 0 或 128,000 假装知道**。

### 11.4 门禁与红线不变

J11/J12 并入 §7 判据表；§6 白名单、§8 负例、§9 门禁一字不动。
