# 已知限制：targetSdk 28 结构性边界

> **记录时间**：2026-10-06（初版基于第 0 步诊断；同日经 E-005 重大反转勘误，本文已按反转重写）

> **关联文档**：`安卓AgentApp-设计方案-v3.md`（架构前提，v3.10 存储反转）、`PROVENANCE.md`（合规底线）、`M1.1-开发任务书.md`（proot 接入约束）、`docs/ERRATA.md`（E-005 反转定案）

## 1. 一句话结论

**证道依赖 targetSdk 28 才能从 App 数据目录 exec proot 二进制（W^X 豁免）。这个约束是架构级的、不可修改的；抬高 targetSdk 会导致整个 Linux 环境变成一堆无法执行的死文件。**

> 【警告】**存储结论已于 2026-10-06 反转（E-005）**：此前「/sdcard 直连不可用、必须走 SAF」的判断**错误**。经 App 真身实测，`/sdcard` 列目录 / 读 / 写**全部可用**；~~SAF 镜像同步降级为**备用方案**（个别 ROM 兜底）~~ → **⚠️ 2026-10-07 进一步更正：不存在什么"备用方案"——SAF 镜像同步已由 `4bbfd21 refactor(P1.5): 删除 SAF 镜像同步` 整体删除，`mirror/PhoneMirror.kt` 已不在版本库，设置页入口也已移除（`ui/SettingsScreen.kt:1177` 明写「不用 SAF」）。本句的"备用方案"表述与本文第 3 节自相矛盾，以第 3 节为准。** 详见第 3 节与 `docs/ERRATA.md` E-005。

## 2. targetSdk 28 约束（架构前提，不受 E-005 影响）

- Android 10 起 SELinux 禁止 targetSdk ≥ 29 的应用从**可写数据目录**执行文件（W^X）。
- 证道的整个 rootfs（`/usr/bin` 下成千上万个二进制）都在 App 数据目录里，必须靠 targetSdk 28 豁免才能 exec。
- **抬高 targetSdk = proot 执行链崩溃 = 整个 Linux 环境不可用。这是不可谈判的架构前提。**

## 3. 存储可用性（E-005 反转后的真身实测结论）

第 0 步「sdcard 读缺陷」诊断于 2026-10-06 经 App 真身重新验证，**结论反转**。原「全拒」证据来自 `run-as` 探针（域为 `runas_app`），不是 App 真身（`untrusted_app`），属方法论错误。真身实测结论：

| # | 诊断项 | 真身实测结论（E-005 修正后） |
|---|---|---|
| 1 | guest readdir `/sdcard` | **成功**（文件管理器可见） |
| 2 | 写己文件读回 | 成功（写路径一直通） |
| 3 | **读用户拷入的已有文件（关键判别）** | **成功**——此前失败根因是 manifest `READ_EXTERNAL_STORAGE` 带 `maxSdkVersion=32` 帽子，Android 13+ 永远无法持有 READ；`d414dca` 摘帽 + 补 READ 运行时授权后已修复 |
| 4 | `run-as` 对照 | `run-as` 域（runas_app）被 FUSE 拒绝，**不能代表 App 真身**；真身（untrusted_app）读写全通 |
| 5 | MANAGE_EXTERNAL_STORAGE | **与本问题无关**——appops 默认状态下真身读写即通，无需「所有文件访问」授权 |

**核心判别**：`/sdcard` 直连在 App 真身下可用，仅需 `READ_EXTERNAL_STORAGE` / `WRITE_EXTERNAL_STORAGE` 的**运行时授权**（Android 13+ 上 READ 须摘掉 manifest 的 `maxSdkVersion=32` 帽子才能持有）。**这不是平台存储视图失效，而是权限声明问题，已修复。**

## 4. 存储方案定位

> ⚠️ **本节已过时（2026-10-07 更新）**：SAF 镜像同步已按 P1.5 决策**整体删除**
> （commit 4bbfd21：PhoneMirror 引擎、设置页入口、/mnt/phone bind 全部移除；
> 用户数据策略见 docs/ERRATA.md E-005 修订段与 docs/acceptance/android16-compat.md）。
> 保留本节仅作决策历史记录——**当前代码中不存在镜像同步**。

- 主路径（现行）：`/sdcard` 直连（真身验证可用），Agent/工具在 guest 内直接读写共享存储。
- 已删除：SAF 镜像兜底（原 `mirror/PhoneMirror.kt` + `/mnt/phone` bind + 设置入口——文件均已不存在）。
- **2026-10-10 定案：不需要 SAF 改造**（`docs/知识库-收工条件.md` §C 的 C1 拍板「不成立」）——① `targetSdk 28` 是架构生死线（§2），为 SAF 动它等于自断命门；② 本 App **不走 Google Play**（GitHub 直发），Play 的 target API 强制与它无关。⇒ 资料库继续用 `File` 直读 `/sdcard`。**真正要盯的不是 SAF，而是最低安装门槛**：见 §6 / §7。

> ✅ **2026-10-10 定案（存亡级）**：**Android 17（API 37）的最低安装门槛仍为 24，未上调**。证道 `targetSdk = 28 > 24` ⇒ **装得上**。详见 §9.1。
> ⚠️ **由此，风险位置转移**：存亡级担忧（装不上）已解除，**当前该盯的变成 §9 的「App Memory Limiter」**——它**不看 targetSdk，对所有应用一律生效**，会让后台长跑的 Debian + tmux + agent 在 Android 17 上被悄悄终止。**这不是装不上的问题，是"切出去一会儿回来环境没了"的问题。**

## 5. 关于「为什么不可修复」（指 targetSdk 28 本身）

| 尝试方向 | 结果 |
|---|---|
| `requestLegacyExternalStorage="true"` | Android 16 平台无视（与存储可用性无关，存储靠运行时授权即可） |
| `pm grant READ` 手动授权 | 授权成功、访问仍拒——**根因是 manifest 带了 `maxSdkVersion=32` 帽子**，Android 13+ 永远无法持有 READ；摘帽（`d414dca`）+ 补运行时授权后真身读恢复。此行记录的是**摘帽前的历史现象**，勿误读为"授权本身无效" |
| 去掉 manifest `maxSdkVersion="32"` | 已做（`d414dca`），解决「永远无法持有 READ」的帽子问题，真身读恢复 |
| 抬高 targetSdk | **绝对禁止**——W^X 豁免丢失，proot 无法 exec |

## 6. 长期风险与跟踪机制

### 政策方向

- **最低安装门槛**（2026-10-06 核验修正；**2026-10-10 补 Android 17**）：**Android 14 = 23；Android 15 起提高到 24；Android 16 维持 24；Android 17 维持 24（未上调，★本次定案，依据见 §9.1）**。targetSdk 28 高于四者，仍有 2 个 API 级余量，风险等级不变，但"仅 23"的说法已过时。
  > ⚠️ **定案依据为间接证据（★★ 多源互证，非一手常量）**：Android 17 官方「行为变更：所有应用」页目录**无**"最低 target SDK"条目（而 Android 15 该页明确写"从 23 提高到 24"）；官方汇总表只列到 15→24；三方综述亦写"旧 target 应用在 17 上基本照跑"。**每季度复查仍需按最新大版本重新核对**，并优先找 AOSP 常量一手出处。
- **Play 侧强制 target API 36**：**2026-08-31 起新应用与更新必须 target API 36（Android 16）**；既有应用低于 API 35 则对新用户不可见。只约束 Play 上架，与 GitHub 直发无关，但为门槛上抬信号。（核验日 2026-10-06，来源：Play 官方 target API 要求页）
- **AOSP 对 untrusted_app 域的策略动向**：proot 依赖的 exec 豁免是否被进一步收紧（直接影响 rootfs 能否 exec，与存储无关）。
- **侧载身份验证政策**：GMS 认证设备上 APK 须来自已验证身份开发者，2026-09-30 起首批执法，2027 全球推行。本项目主要人群（国行无 GMS 设备）不受影响，但需每月核对。

## 8. PRoot 运行期环境坑（运行期，非架构约束）

> 以下属 **PRoot 运行期固有限制**，与第 2 节 targetSdk 28 架构约束层级不同：targetSdk 28 是"动代码改不了"的硬前提；此处是"运行期可规避/自愈"的环境行为。完整诊断与一键自救见 `证道-故障排查手册.md`。

- **硬链接被 SELinux 拦截**：PRoot guest 内 `link()` 系统调用被拒（`Operation not permitted`）。典型触发——Hermes PM 内嵌的 uv 默认硬链接模式装包失败。解法：原位置包装内嵌 uv，加 `--link-mode copy`（详见故障排查手册 坑 #1）。
- **DNS 解析超时**：`/etc/resolv.conf` 配了仍解析超时。三条归因（PRoot 用户空间拦 socket、Android DNS 走 `netd`、VPN 隧道不被继承）**目前均属推测、无实测证据**，详见故障排查手册坑 #2 的审核说明。解法：用宿主 DNS 写死 `/etc/resolv.conf` + 必要时 `/etc/hosts` 写死域名。
  > 🔺 **待裁决（2026-10-06 审核，最高优先级）**：本文旧版写"VPN 隧道不被 PRoot 容器继承"，但 v3 §6 与 M5 §6 均写"proot 子进程与 App 同 UID、同路由表，**天然被 VPN 覆盖**"。两条互斥，且是 DNS 坑归因与"软件源不预置国内镜像"红线的前提。**须裁决后全库统一**，在此之前 DNS 坑根因不作定论。
  > 另注：commit `c7ac1dc`（resolv.conf 加 DNS 重试参数——移动网络丢包快速换源）反证真实成因更可能是**丢包/超时**而非"拦截不到"。
- 这两个坑 **2026-10-06 真机实测**所得，应固化进 P7 的 `agent fix hardlink` / `agent fix network` 一键命令。
  > ⚠️ **更正（2026-10-07 核对）**：`agent-helper` 组件与 `agent fix …` 命令**全仓 0 命中、至今未实现**，这句"应固化进…"没有落地。两坑的**真实解法**是：硬链接坑由 `terminal/EnvSelfHeal.kt:205 ensureHermesUvWrappers`（`:212` 定位 `uv.real`、`:215-219` 写包装、`:220` chmod、`:222` 日志）＋ `terminal/EnvSelfHeal.kt:182 ensureUvConfig`（`:186` 写文件、`:188-191` 写 `link-mode = "copy"`，系统级 `/etc/uv/uv.toml`）＋ `terminal/ProotLauncher.kt:441` 的 `UV_LINK_MODE=copy` 解决；DNS 坑由 `terminal/EnvSelfHeal.kt:84 ensureDnsFiles`（`:87-88` 判缺 `223.5.5.5`/`options timeout`、`:89-100` 重写、`:105-108` 锁 0444）解决，调用点 `terminal/ProotLauncher.kt:201`。

## 9. Android 17 / MagicOS 11：能装、能跑，但新增「后台内存限制」风险

> **记录时间**：2026-10-10 ｜ **性质**：**运行期风险新增**（非架构约束）＋ **存亡级担忧解除**（安装门槛定案）
> **证据等级说明**：★★ = 官方文档/多源一手互证 ｜ ★ = 二手 ｜ ○ = 推断或未实测。**本节省内所有 Android 17 行为均未在证道真机实测**（记录时手机未连接），升级后须按 §9.2 判据复核。

### 9.1 安装门槛定案：**Android 17 未上调，证道装得上**（★★）

**先定版本**：**MagicOS 11 ＝ Android 17（API 37）**。项目内已留此更正——`app/build.gradle.kts:111-112` 注：「原注释写 MagicOS 11 实测对不上，MagicOS 10 才基于 Android 16，MagicOS 11 对应 Android 17」。

| 系统 | 设备侧最低可安装 targetSdk |
|---|---|
| Android 14 | 23 |
| Android 15 | 24（由 23 提高） |
| Android 16 | 24（未上调） |
| **Android 17** | **24（未上调）★ 2026-10-10 定案** |

**证道 `targetSdk = 28 > 24` ⇒ 装得上。**（配置出处：`app/build.gradle.kts`，`minSdk = 36`、`targetSdk = 28`）

**定案依据（三条互证，但属间接证据）**：
1. Android 17 官方「行为变更：所有应用」页的**目录中不存在**「最低 target SDK」条目——而 Android 15 的同一页面**明确写有**"从 23 提高到 24"。官方若上调，惯例会在该页写出。
2. 官方 targetSdk 门槛汇总表**只列到 Android 15→24**。
3. 三方综述写"旧 target 应用在 Android 17 上基本照跑"。

> ⚠️ **证据等级诚实标注**：以上为 **★★（多源互证）**，**不是** AOSP 常量的一手出处。这与 §6 的"每季度复查"不冲突——**门槛是存亡级变量，复查时优先找 AOSP 常量**。

**proot 地基也没动**：证道在 Android 17 上的实际行为 = `min(设备 API 37, targetSdk 28)` = **28**，即按 Android 9 规则运行 ⇒ legacy 共享存储 + 可写数据目录 exec **继续有效** ⇒ §2 的 W^X 豁免与 §3 的存储直连**均不受影响**。

**实测机与升级时间**：荣耀 Magic 5 Pro（PGT-AN10），当前 MagicOS 10.0.0.175 / Android 16。MagicOS 11 分批推送：**第一批**（9/15 已发）Magic8 全系、Magic V6/V5、Magic7、荣耀 600 系；**第二批** Magic6、Magic V3、500/400 系（内测）；**第三批含 Magic5 全系（标准 / Pro / 至臻），10–11 月**（★ 荣耀官方适配名单，二手转述）。

### 9.2 真正的新风险：App Memory Limiter（**不看 targetSdk，所有应用一律生效**）

**这条是 Android 17 里对证道威胁最大的一项，且不能靠 targetSdk 躲开。**

- **机制**（★★ 官方文档）：基于 **cgroup v2** 的 `memory.high` + `memory.swap.max`，按**设备总 RAM** 与**进程可见性**设定额度；**后台 / 不可见进程的限额更严**。
- **表现链条**：超限 → 匿名页被换出到 **zRAM** → 明显卡顿 → 继续增长则**直接终止进程，且没有正常崩溃堆栈**。
- **判据（排查抓手）**：`ApplicationExitInfo` 中 reason = `REASON_OTHER` 且描述含 **`MemoryLimiter:AnonSwap`**；API 37 起有专门的 `REASON_MEMORY_LIMITER`。
- **覆盖面**（★）：Google 于 **2026-08-19** 宣布从 Pixel 扩展到更多厂商，覆盖 **4GB–16GB+ RAM** 的设备。
- **证道正撞这一类**：它是**在后台长时间跑着 Debian + tmux + agent** 的应用。升级后用户可能遇到的现象是——**「切出去一会儿回来，环境没了」**，且日志里找不到常规崩溃原因。
- **逃生舱（调试期可用）**：`adb shell am memory-limiter ignore <UID>` 可将该 UID 豁免。

> ⚠️ **未实测**：以上全部来自官方文档，**未在证道真机上验证**。这正是 §6 新增核对项的用途。

### 9.3 反直觉的红利：`targetSdk 28` 在 Android 17 上是「护身符」

Android 17 多数新限制 **gated on `targetSdk 37`**，证道（28）**全部躲过**：

| Android 17 新限制 | 触发条件 | 证道（targetSdk 28） |
|---|---|---|
| 证书透明度（CT）默认开启 | target 37 | ✅ 不受影响 |
| **Safer DCL 扩展到 native 库**（`System.load()` 的文件须**只读**，否则 `UnsatisfiedLinkError`） | target 37 | ✅ 不受影响 |
| Keystore key 上限 5 万（其余 20 万） | target 37 | ✅ 仍为 20 万 |
| 局域网访问需 `ACCESS_LOCAL_NETWORK` | target 37 | ✅ 不受影响 |
| **App Memory Limiter**（§9.2） | **所有应用，不看 targetSdk** | ❌ **躲不过** |

⇒ **Safer DCL 那条尤其关键**：证道要加载自己的 `libzhengdao_core.so`，若 target 37 则要求该文件只读，很可能直接 `UnsatisfiedLinkError`。**这是"绝对不得上调 targetSdk"的又一条独立理由**，与 §2 的 W^X 并列。

### 9.4 待核：跨资料环回流量（○）

Android 17 另有「**阻止跨资料环回流量**」（cross-profile loopback）一项。字面针对跨用户 / 工作资料，**单资料场景大概率不受影响**；但证道 guest 内会访问 `127.0.0.1`（`ProotLauncher` 中设了 `NO_PROXY`，说明 guest 会访问本地服务）⇒ **存在理论上的交集，未实测，列为待核**。

### 9.5 优先级：这件事比「换 proot」重要一个量级

| | 换 proroot（见 `证道设计报告/证道-proroot替代性实测-2026-10-10.md`） | MagicOS 11 / Android 17 |
|---|---|---|
| 性质 | 可能快一点 | **后台可能被杀** |
| 现状 | 参数对不上（`--kill-on-exit` 缺失、`-b` 不支持单参数简写），**换不了** | **10–11 月就会到本机** |
| 是否需真机验证 | 是（手机未连） | 是（升级后首次） |

⇒ **结论：proot 不用换（参数层面就不成立）；该盯的是 Android 17 的内存限制。** 本文件 §6 已新增对应核对项。
