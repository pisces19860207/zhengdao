# 已知限制：targetSdk 28 结构性边界

> **记录时间**：2026-10-06（初版基于第 0 步诊断；同日经 E-005 重大反转勘误，本文已按反转重写）
> **性质**：架构级不可改约束。本文件是「为什么证道钉死 targetSdk 28、/sdcard 存储真身可用性、SAF 定位」的权威说明。实现方（Zcode / 任何协作者）改代码前先读本文件。
> **关联文档**：`安卓AgentApp-设计方案-v3.md`（架构前提，v3.10 存储反转）、`PROVENANCE.md`（合规底线）、`M1.1-开发任务书.md`（proot 接入约束）、`docs/ERRATA.md`（E-005 反转定案）

## 1. 一句话结论

**证道依赖 targetSdk 28 才能从 App 数据目录 exec proot 二进制（W^X 豁免）。这个约束是架构级的、不可修改的；抬高 targetSdk 会导致整个 Linux 环境变成一堆无法执行的死文件。**

> 【警告】**存储结论已于 2026-10-06 反转（E-005）**：此前「/sdcard 直连不可用、必须走 SAF」的判断**错误**。经 App 真身实测，`/sdcard` 列目录 / 读 / 写**全部可用**；SAF 镜像同步降级为**备用方案**（个别 ROM 兜底）。详见第 3 节与 `docs/ERRATA.md` E-005。

## 2. targetSdk 28 约束（架构前提，不受 E-005 影响）

- Android 10 起 SELinux 禁止 targetSdk ≥ 29 的应用从**可写数据目录**执行文件（W^X）。
- 证道的整个 rootfs（`/usr/bin` 下成千上万个二进制）都在 App 数据目录里，必须靠 targetSdk 28 豁免才能 exec。
- **抬高 targetSdk = proot 执行链崩溃 = 整个 Linux 环境不可用。这是不可谈判的架构前提。**

## 3. 存储可用性（E-005 反转后的真身实测结论）

第 0 步「sdcard 读缺陷」诊断于 2026-10-06 经 App 真身重新验证，**结论反转**。原「全拒」证据来自 `run-as` 探针（域为 `runas_app`），不是 App 真身（`untrusted_app`），属方法论错误。真身实测结论：

| # | 诊断项 | 真身实测结论（E-005 修正后） |
|---|---|---|
| 1 | guest readdir `/sdcard` | **成功**（文件管理器可见） |
| 2 | 写己文件读回 | 成功（写路径一直通） |
| 3 | **读用户拷入的已有文件（关键判别）** | **成功**——此前失败根因是 manifest `READ_EXTERNAL_STORAGE` 带 `maxSdkVersion=32` 帽子，Android 13+ 永远无法持有 READ；`d414dca` 摘帽 + 补 READ 运行时授权后已修复 |
| 4 | `run-as` 对照 | `run-as` 域（runas_app）被 FUSE 拒绝，**不能代表 App 真身**；真身（untrusted_app）读写全通 |
| 5 | MANAGE_EXTERNAL_STORAGE | **与本问题无关**——appops 默认状态下真身读写即通，无需「所有文件访问」授权 |

**核心判别**：`/sdcard` 直连在 App 真身下可用，仅需 `READ_EXTERNAL_STORAGE` / `WRITE_EXTERNAL_STORAGE` 的**运行时授权**（Android 13+ 上 READ 须摘掉 manifest 的 `maxSdkVersion=32` 帽子才能持有）。**这不是平台存储视图失效，而是权限声明问题，已修复。**

## 4. 存储方案定位

**SAF 镜像同步 = 备用方案（非官方主路径）**。

- 主路径：`/sdcard` 直连（真身验证可用），Agent/工具在 guest 内直接读写共享存储。
- 备用：个别 ROM 存储策略异常、直连不可用时，SAF 选文件夹 → 镜像到 `~/mnt/phone/`（guest 内路径）兜底。代码保留，设置页标注「手机文件夹同步（备用）」。
- 镜像目标不是工作区——工作区仍是 `/workspace`（= 手机 `Download/证道`）。
- 第一版做**最小可用**：不递归、不删同步、文件数量上限 1000，跑通再扩（仅备用场景触发）。

### 实现参考（Zcode 已落地）

- `app/src/main/java/com/example/zhengdao/mirror/PhoneMirror.kt` —— 镜像同步核心（复制语义，非挂载；镜像落点 guest `/mnt/phone`），**仅备用场景启用**
- `ProotLauncher.kt` —— 启动时绑定 `phoneMirror: /mnt/phone`
- `SettingsScreen.kt` —— 「手机文件夹同步（备用）」设置入口（SAF 选文件夹）

## 5. 关于「为什么不可修复」（指 targetSdk 28 本身）

| 尝试方向 | 结果 |
|---|---|
| `requestLegacyExternalStorage="true"` | Android 16 平台无视（与存储可用性无关，存储靠运行时授权即可） |
| `pm grant READ` 手动授权 | 授权成功，访问仍拒 —— **前提：manifest 未带 `maxSdkVersion=32` 帽子**；摘帽后（d414dca）真身读正常 |
| 去掉 manifest `maxSdkVersion="32"` | 已做（`d414dca`），解决「永远无法持有 READ」的帽子问题，真身读恢复 |
| 抬高 targetSdk | **绝对禁止**——W^X 豁免丢失，proot 无法 exec |

## 6. 长期风险与跟踪机制

### 政策方向

- **最低安装门槛**：Android 14+ 仅禁止安装 targetSdk < 23 的应用，28 有安全边际，但需持续关注是否上调。
- **Play 侧强制 target API 36**：只约束 Play 上架，与 GitHub 直发无关，但为门槛上抬信号。
- **AOSP 对 untrusted_app 域的策略动向**：proot 依赖的 exec 豁免是否被进一步收紧（直接影响 rootfs 能否 exec，与存储无关）。
- **侧载身份验证政策**：GMS 认证设备上 APK 须来自已验证身份开发者，2026-09-30 起首批执法，2027 全球推行。本项目主要人群（国行无 GMS 设备）不受影响，但需每月核对。

### 每季度核对机制

- [ ] 每季度复查一次：Android 新版本是否上调最低安装 targetSdk 门槛
- [ ] 每季度复查一次：AOSP untrusted_app 域策略是否有变化（proot exec 豁免）
- [ ] 每季度复查一次：侧载身份验证政策的地区推进与豁免细则
- [ ] 每季度在真机以** App 真身**重跑一次存储可用性（readdir/读/写 `/sdcard`），确认直连仍可用、SAF 备用兜底仍有效（**禁止用 run-as 当结论**）

## 7. 备选形态（长期）

- **`system_linker_exec` 灰区方案**：只做技术储备评估，**不实现**（Termux 官方自述违反 Play 政策可能下架，不走这条路）。
- **云机瘦客户端**：复用终端渲染层做 SSH/Mosh 瘦客户端连云机（见设计方案 §10 v2 路线）。作为 targetSdk 28 彻底失效时的终极备选。
