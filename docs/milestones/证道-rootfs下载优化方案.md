# 证道 · RootFS 下载优化方案（调研）

> 调研日期：2026-10-07 · 前置：v1.2 已加 gh-proxy.com 镜像兜底（解决"能不能下"）；
> 本方案解决"下得快不快"。基线实测：311MB 归档 ≈ 4 分钟 @ ~1.3MB/s（5G，GitHub 资产直链）。
> 性质：**调研 + 方案设计，不含代码**。执行批次另行排期。

---

## 0. 一个决定边界的事实

**rootfs 是证道自建包**（`rootfs/build-rootfs.sh`：debootstrap 定制——Debian 13.7 + NodeSource
Node 26 + uv + 精简结构，产物 `debian-13.7-base-arm64.tar.zst` + `.sha256`，由 CI 构建后
发布到 GitHub Releases）。

**直接推论**：USTC / 阿里云 / 网易等 Debian 镜像站镜像的是**官方发行文件**
（.iso / pool 仓库），**不可能镜像证道的自建包**——"换国内 Debian 镜像源"对本问题
不成立。国内加速只有两条真路：**自建国内源**（对象存储）或**优化 GitHub 链路本身**。

---

## 1. 基线与瓶颈定位

| 环节 | 现状 | 实测/估算 | 占比 |
|---|---|---|---|
| 下载 311MB | GitHub 资产直链（Fastly CDN），单连接 1.3MB/s；gh-proxy 兜底 | ~4 分钟 | **~95%** |
| SHA256 校验 | MessageDigest 流式读归档 | ~0.16s（5ms/10MB 外推） | <1% |
| 解压+落盘 | commons-compress 纯 Java zstd + tar 逐 entry | 2.07s（基线实测，5601bb4） | ~1% |

**结论：优化只该花在下载环节。** 解压/校验已不是瓶颈（详见证道-Rust迁移模块评估.md）。

架构利好：`RootfsDownloader.download(urls: List<String>, ...)` **天生多源列表、逐源
重试**——插入任何新源 = 列表头加一个 URL，失败自动回落。工程契合度极高。

---

## 2. 方案一（主推）：国内对象存储做主下载源

### 原理
CI 构建完成后，把 `tar.zst + .sha256` **同步推一份到国内对象存储**；下载源列表头部
插入该 URL（`urls = [ossUrl, githubUrl, ghProxyUrl]`），失败自动回落——现有机制零改动。

### 三家对比（价格为 2026-10 官方定价页量级，执行前复核）

| 项 | 阿里云 OSS | 腾讯 COS | Cloudflare R2 |
|---|---|---|---|
| 国内速度 | **快**（10-50MB/s 常见） | **快** | 中等偏不稳定（海外 POP，无国内节点除非企业版） |
| 存储费 | ~0.12 元/GB/月 | ~0.10 元/GB/月 | $0.015/GB/月 |
| 流出费 | ~0.50 元/GB | ~0.50 元/GB | **免费**（最大卖点） |
| 311MB 单次下载成本 | ~0.16 元 | ~0.16 元 | 0 元 |
| 100 用户/月 | ~16 元 | ~16 元 | 0 元 |
| 实名/门槛 | 需实名，OSS 默认域名无备案要求 | 同左 | 注册即用 |
| 密钥管理 | GitHub Secrets | 同左 | 同左 |

**选型建议**：用户量小（<50 活跃/月）→ **R2**（零成本，速度中等可接受）；
用户量上来或速度投诉 → **阿里云 OSS**（快但 ~0.16 元/次下载）。两者可并存为
`urls = [ossUrl, r2Url, githubUrl, ghProxyUrl]`。

### CI 侧改动（build.yml 加一步）
```yaml
- name: 同步 rootfs 到国内对象存储
  env: { OSS_KEY: ..., OSS_SECRET: ... }   # GitHub Secrets
  run: ossutil cp -f rootfs-out/debian-13.7-base-arm64.tar.zst oss://bucket/... &&
       ossutil cp -f rootfs-out/debian-13.7-base-arm64.tar.zst.sha256 oss://bucket/...
```
⚠️ 注意：CI 每次构建 rootfs **字节都不同**（debootstrap 时间戳/熵）→ 最新构建覆盖
上一版，`.sha256` 同步更新——App 端 manifest 的 url/sha 本就从 latest release 动态
获取（SettingsScreen.kt:554-570），链路自洽。

### 失败模式与回退
- OSS 欠费/限流/删桶 → `RootfsDownloader` 自动回落 GitHub → gh-proxy（现有逻辑）✓
- .sha256 取不到 → v1.2 已改为**必须报错**（5cf218e），不会裸奔 ✓
- 回退路径：删除列表头的 OSS URL 即回到现状（一行改动）

### 维护成本
- 一次性：注册 + 建桶 + CI 同步步骤 + Secrets（半天）
- 持续：盯费用账单（月度 <1 分钟）；无其他维护

## 3. 方案二：流式安装（边下载边解压）

### 原理与收益
现状三步串行：下载写盘(311MB) → 校验整读(311MB) → 解压读(311MB)写(1.5GB)。
流式后：下载流 → 边解压边写 → 边算 SHA256，**解压与下载尾部重叠**。

**收益量化（诚实版）**：省 311MB×2 次读 + 归档落盘，并把解压的 ~2s 隐藏进下载尾部——
**总计约 15~30 秒**（叠加方案一后，下载只剩 10-30s，流式的绝对收益更小）。

### 设计要点（若做）
1. **分段 frame**：CI 打包改用 zstd 多 frame（定期 reset 或 `--rsyncable`），
   使任意 frame 边界可独立解压——这是中断恢复的前提
2. 下载器按 frame 边界喂解压流；进度 = 已解压 entry 数
3. SHA256 流式边下边算，最终比对；不匹配 → 已解压目录作废，回退完整下载路径
4. 原子性保持：解压目标仍是 tmpDir → rename 原子替换 ✓（现有机制）

### 失败模式与代价
- **断点续传复杂化**（最大代价）：现状 Range 续传对 .part 精确恢复；流式后中断 =
  已解压文件树无法对应归档偏移 → 只能按"段"恢复（段内重传）。弱网下体验可能
  **劣于**现状（现状 311MB .part 可无限续）
- 校验失败时已写的 1.5GB 作废（现状：校验在解压前，不浪费解压）
- RootfsDownloader + RootfsInstaller 两文件合并重构，测试面扩大

**裁定：P2 可选**——收益 15~30s，代价是恢复语义复杂化。建议方案一落地、下载时间
压到 1 分钟内之后，**流式的收益进一步缩水，大概率永久不值得做**。除非用户反馈
"峰值空间不足"（311MB 包 + 1.5GB 解压并存）才重新评估。

## 4. 方案三：分块多线程下载

### 原理
GitHub 资产走 Fastly CDN，支持 Range——现状单连接 1.3MB/s 是 per-connection 限速；
8 线程并发 Range 请求通常能到 4~10MB/s（国内对 GitHub 场景实测常见 3~5 倍）。

### 实现要点
- 预分配目标文件大小（setLength），每线程按 offset 写，完成前不发整包校验
- 每 chunk 独立重试；某线程连续失败 → 降级单线程补齐
- gh-proxy 兜底源**可能不支持 Range** → 探测（HEAD Accept-Ranges）后才启用分块

### 收益与互斥
- 仅对 GitHub 直链有意义：4 分钟 → **1~1.5 分钟**
- 与方案一**互斥**：上了国内 OSS（单连接 10-50MB/s）后多线程无必要
- 成本：中（offset 写、chunk 重试、降级逻辑）——RootfsDownloader.downloadOne 需重构

**裁定：P3 备选**——作为"不上对象存储"前提下对 GitHub 源的提速手段；
方案一落地后此方案作废。

### 失败模式
- 并发写同一文件的完整性（offset 隔离，风险低）
- 部分 CDN 对同 IP 并发限流（Fastly 一般不限；gh-proxy 类公益源可能封）
- 线程数激进触发源站风控 → 限速更狠（保守 4 线程起步）

## 5. 明确排除的方案

| 方案 | 排除理由 |
|---|---|
| USTC/阿里云/网易 Debian 镜像站 | 镜像的是官方发行文件，**不自建包**（§0）——除非改用官方 rootfs，见下 |
| 改用官方 Debian rootfs tarball | 策略级重构：失去定制（NodeSource Node 26/uv/精简结构/proot 适配），体积也更大；长期可评估，短期不动 |
| jsDelivr | 单文件 ≤20MB 硬限制，311MB 超限——不可行 |
| HTTP/3 (QUIC) | OkHttp 4.12 不支持（OkHttp 5 才有）；且 H3 解决的是连接建立与队头阻塞，对单流吞吐提升有限——不值当 |
| cloudflare worker 反代 GitHub | 与 gh-proxy 同类（公益/自建反代），稳定性同风险；已有 gh-proxy 兜底，不再叠加同类 |

## 6. 实施顺序与预期收益总表

| 优先级 | 方案 | 工程量 | 预期下载耗时 | 回退 |
|---|---|---|---|---|
| **P1** | 国内对象存储主源（R2 起步 → 用户量上来加 OSS） | 半天（CI 同步步 + urls 插入） | 4 min → **10~30s** | 列表删除该项，自动回落现状 |
| P3 | 分块多线程（仅 GitHub 源语境） | 中（downloadOne 重构） | 4 min → 1~1.5 min | 降级单线程（现有） |
| P2 | 流式安装（边下边解） | 中高（双文件合并重构 + CI 打包格式） | 再省 15~30s | 回退完整归档路径（现有） |

**建议节奏**：P1 一次做完即收——预期"装环境 4 分钟 → 1 分钟内"已解决 95% 的痛点；
P3/P2 仅在 P1 不可行（如不愿注册云账号）或用户反馈仍有痛点时再启动。
