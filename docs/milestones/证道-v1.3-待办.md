## B2 · 删除 agents.json 里的 opencode 条目 —— ✅ **已完成**（`9b70e1b`）

> ✅ **销账（2026-10-07）**：已由
> `9b70e1b feat(v1.3 B2): 移除终端 npm 版 opencode 条目——agents.json 重签 + 出厂卡片删除`
> 完成。`rootfs/agents.json` 已无 opencode 条目（`git grep -i opencode -- rootfs/agents.json` 为空），
> 签名同步更新为 `rootfs/agents.json.sig`。下方原文保留，作为当时"为什么卡住"的决策记录。

**背景**：终端（洞天）里的 npm 版 OpenCode 已从环境移除（v1.2 卸载），但
`AgentRepository` 的清单（`rootfs/agents.json`）里仍留着 opencode 条目，
丹房/清单接口仍会把它当成一个可安装 Agent。

**为什么不做**：该清单是 **ed25519 验签**的（`AgentManifestVerifyTest` 会校验
真实 manifest 与签名）。改条目必须重新签名，而签名私钥/流程不在这边的处理范围内——
**改了不重签 = CI 必红**（ci #2 就是因为验签失败红的，见下）。

**做之前要先解决**：
1. 确认签名密钥的持有与重签流程（谁签、怎么签、密钥放哪）；
2. 改完后 `AgentManifestVerifyTest` 必须仍然通过（该用例在 CI 是硬门禁）。

**验收**：丹房 Agent 列表不再出现 opencode；CI 验签用例仍绿。

## D2 · 待机 CPU 上升，原因未定位

**现象**：环境装好后，静置状态下 CPU 占用高于预期。

**已排除 / 已做的**：
- v1.2 A 类补了资源监控（`ResMonitor`，按 UID 聚合 RSS/CPU，剔除 App 自身进程），
  **观测手段已经有了**——真机实测太极运行时 RSS 363MB / CPU 4.3% / 1 个进程，与 `top` 一致。
- 但"待机"时的上升来源仍未定位：是 tmux 保活轮询、SSE/REST 轮询、
  还是 PRoot 内的某个常驻进程，尚未区分。

**下一步建议**：用 ResMonitor 在**静置 5 分钟**内取多个采样窗口，
按进程维度拆分（而不只看 UID 聚合），先定位到具体 pid 再谈优化。

**为什么不在 v1.2 做**：不影响可用性，且根因未明时任何"优化"都是猜。

**风险等级**：理论风险，真机未复现出实际问题。

**为什么不在 v1.2 做**：v1.2 的范围是"终端环境优化"，此项属于权限判定的一致性清理，
且改它牵涉首装路径（v1.2 C 类刚动过欢迎页与工作区选择），**不宜在同一版内叠加改动**。

**下一步建议**：先厘清两套口径各自的使用场景，统一为一个判定函数并补单测。
