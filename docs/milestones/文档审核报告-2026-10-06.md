## 一、P0 必修（会导致功能失效或必然踩坑）

### P0-1 WebView 访问 `localhost` 会被 cleartext 策略阻断（P3 必踩，无任何文档提及）

- **位置**：执行路线图 §2 P3 第 1 条「WebView 加载 `localhost` 的 OpenCode Web UI」
- **问题**：Android 9（API 28）起，`targetSdk >= 28` 的应用**默认禁止明文 HTTP**（`usesCleartextTraffic` 默认为 false）。本项目 `targetSdk 28`，恰好落在行为变更生效线上。`opencode serve` 只提供 HTTP，WebView 加载 `http://localhost:PORT` 会被系统直接拦掉（`net::ERR_CLEARTEXT_NOT_PERMITTED`）。
- **依据**：Google 官方《行为变更：Android 9 开发者注意事项》——从 API 28 起默认禁止明文流量，`targetSdk=28` 适用。
- **最小修复**：加 `res/network_security_config.xml`，仅对 `localhost` / `127.0.0.1` 开cleartext，其余保持禁止：
  ```xml
  <network-security-config>
    <domain-config cleartextTrafficPermitted="true">
      <domain includeSubdomains="false">localhost</domain>
      <domain includeSubdomains="false">127.0.0.1</domain>
    </domain-config>
    <base-config cleartextTrafficPermitted="false" />
  </network-security-config>
  ```
  注意 `127.0.0.1` 与 `localhost` 在 `domain` 里是两条，不通配。
- **附带**：P3 还需在 WebView 侧处理 `WebView` 客户端混合内容与 `mixedContentMode`，同样没有文档覆盖。

### P0-2 「tmux 兜底恢复现场」是伪确定性承诺——进程树被杀时现场必丢

- **位置**：设计方案 §5 防杀矩阵第 6 行「内存枯竭强杀 / 厂商深度清理 → 无解，tmux 兜底恢复现场」；M2 §8 `SessionRecovery.onAppLaunch()` 注释「tmux server 若还活着则恢复现场」
- **问题**：proot 与 tmux server 都是 App 派生的子进程，共享同一 UID。Android 的 LMK / 用户清理 / 厂商清理是**按 UID 杀整棵进程树**的，不是杀单进程。一旦进程树被整体清除，tmux server 已死，**App 重进只能"重新拉起一个新环境"，不可能恢复现场**——用户正在跑的Agent 任务、日志、临时文件一律丢失。
- **真实兜底边界**：保住现场的**唯一**手段是让整棵进程树不被杀（FGS + 通知可见 + 电池白名单 + ROM 后台锁），tmux 只是"用户手动清理后不必重装 Agent"的便利层。
- **最小修复**：把 §5 该行的「结果」列改为「**无解，现场必丢；仅保住已装 Agent 不需重装**」，并在 M2 §8 顶部加一句红线：`SessionRecovery` 不得对外宣称"恢复现场"，UI 文案改为「已重建运行环境」。这一条还反向强化了 M4 砍掉的合理性——被砍的 Phantom 修复其实是唯一能降低"整树被杀"概率的手段，值得在文档里记一句决策权衡。

### P0-3 16KB 对齐漏掉了 proot 自带的两份 `.so`

- **位置**：设计方案 §4 表格 16KB 行、M1.1 顶部提示块——两者都只强调「别只对齐 proot 而漏掉 `libtermux.so`」
- **问题**：proot 分发包有 **4 个文件**（M1.1 §模块 3 第 1 点）：`proot`、`loader`、`**libtalloc.so**`、`**libandroid-shmem.so**`。后两个是**动态库**，由 proot 运行时加载。当前文档的 16KB 检查清单**完全没提它们**。Android 15 的 16KB 设备上，未对齐的 `.so` 由 bionic linker 直接拒绝加载（`CANNOT LINK EXECUTABLE: unsupported page size`），proot 起不来，M1.1 全部门禁连带失败。
- **注意**：这两个文件放在 `assets/` 而非 `lib/`，`zipalign -P 16` **不处理 assets**，所以不存在打包对齐问题，只需保证文件本身 ELF 对齐 —— 但也意味着"用 APK Analyzer 检查"这条路径**查不到 assets 里的文件**，必须手工 `readelf`。
- **最小修复**：M1.1 与 v3 §4 各加一条验收项：
  ```bash
  for f in proot loader libtalloc.so libandroid-shmem.so; do
    echo "== $f"; readelf -l "assets/proot/$f" | grep -A1 LOAD | grep -o '0x[0-9a-f]*$'
  done
  ```
  所有 LOAD 段的 align 均需 ≥ `0x4000`（16384）。

### P0-4 `AgentHelperUpdater` 把"网络失败"当成"验签失败"→ 静默降级掉好版本

- **位置**：M5 §2 `AgentHelperUpdater.update()`
- **问题**（两处）：
  1. `manifestClient.fetch().getOrNull() ?: run { rollbackToGoldenImage(); return }` —— `Result` 为 null 有**两种**语义：验签失败（安全事件）与网络不可达（普通故障）。当前代码对两者执行同一个动作：**删掉当前正在使用的 activeDir，换回 APK 内置出厂版**。结果：用户飞行模式下打开 App，正在用的热更新 agent-helper 被降级。
  2. `downloadAndVerify(comp)?.let { apply(it) } ?: rollbackToGoldenImage()` —— 同理，下载中断（弱网）也会触发降级。
- **最小修复**：把"安全回退"与"故障保留"拆成两条路径，并在接口上体现：
  ```kotlin
  sealed class FetchOutcome {
      data class Ok(val manifest: Manifest) : FetchOutcome()
      data object SignatureInvalid : FetchOutcome()      // 安全事件 -> 回退
      data class Unreachable(val cause: Throwable) : FetchOutcome() // 故障 -> 静默保留当前版本
  }
  ```
  `Unreachable` 分支只记日志 + 走 §6 的连接失败智能引导，**不动 activeDir**。另加一条：`本地版本 > manifest 版本` 时跳过更新（防manifest 回滚导致降级），当前只判了相等。

### P0-5 `scripts/sign-manifest.sh` 缺公钥导出步骤，首次执行必然中断

- **位置**：M5 §5 离线签发脚本
- **问题**：脚本注释写了前置 `openssl genpkey ... -out ~/.zhengdao/private.key`，但**没有任何生成 `public.key` 的命令**；紧接着的自检步骤 `openssl pkeyutl -verify -rawin -pubin -inkey "$HOME/.zhengdao/public.key"` 会因文件不存在报错，在 `set -euo pipefail` 下直接退出。注释说"公钥从私钥导出后固化进 APK"，但这一步的时机/命令写在了 APK 侧而非脚本里。
- **最小修复**：在 `genpkey` 之后、`sign` 之前插入：
  ```bash
  # 首次执行时导出公钥（后续可跳过；此文件不外传，仅本地核对用）
  [ -f "$HOME/.zhengdao/public.key" ] || \
    openssl pkey -in "$KEY" -pubout -out "$HOME/.zhengdao/public.key"
  chmod 600 "$HOME/.zhengdao/public.key"
  ```
  `openssl pkeyutl -sign -rawin -inkey <ed25519私钥>` 写法本身**正确**（Ed25519 内部自带摘要，`-rawin` 必需），与 Android `Signature.getInstance("Ed25519")` 兼容，无需改动。

## 四、值得肯定的部分（审核中确认有效、无需改动）

- **红线体系一致性**：五条红线（`PROOT_NO_SECCOMP=1` 禁令、proot 必用Termux fork + GPL 聚合分发登记、manifest 先验签后解析、私钥离线不进 CI、targetSdk 28 钉死）在 M1.1/M2/M3/M5/设计方案 中表述一致，且每份都给了"为什么"，没有出现互相矛盾的反例。
- **勘误机制**：E-005 从「全拒」到反转的完整过程被留档（方法论错误= 用 `run-as` 探针代替 App 真身），并沉淀成 §6 红线 ⑤ + 每季度复核清单。这套机制本身是资产。
- **故障与架构的层级区分**：手册 §坑 #1/#2 明确声明属"运行期可规避"、`已知限制.md` §2 属"动代码改不了"，两者不混为一谈——这是很多同类项目会犯的错，这里做对了。
