# 证道 · v2.0 架构设计（Rust Core 部署形态 + 宿主/guest 通信机制）

> 定稿日期：2026-10-07 · 前置：rust/sha256poc 链路 PoC（dc268ea）、解压基线（5601bb4）、
> Rust 迁移模块评估（89d1776）、下载优化方案（1d910ff）
> 本文回答两个问题：① Rust 核心以什么形态部署；② 宿主与 guest 之间用什么机制通信。
> 两者共同约束一条铁律：**数据常驻 native 的收益模型（89d1776 §0）不容被部署形态破坏。**

---

## 1. 现状盘点（设计输入）

### 1.1 运行位置地图（坑 #0，故障排查手册置顶条）

| 组件 | 运行位置 | 父进程 | 文件系统视图 | 解析器 |
|---|---|---|---|---|
| 太极 serve（opencode） | **宿主 bionic** | App 本身 | Android 宿主根 | Android netd |
| 终端（tmux/bash/Agent） | **PRoot guest**（Debian 13.7） | proot | rootfs 目录 + bind | rootfs resolv.conf |
| App 本体 | 宿主 | — | Android 根 | Android netd |
| Rust PoC（libsha256poc.so） | **App 进程内**（嵌入） | — | 同 App | — |

### 1.2 已实证的通信事实

1. **guest 可直连宿主 127.0.0.1:14000**：本会话在洞天终端 `curl http://127.0.0.1:14000/api/event`
   收到 `server.connected` + heartbeat（PRoot 不虚拟化网络，guest 与宿主共享内核网络命名空间；
   手册"不在同一网络栈"指的是 **DNS/配置解析路径不同**（netd vs resolv.conf），不是包路由隔离）
2. App ↔ serve：TCP 回环 REST/SSE + Basic auth（现有，稳定）
3. 状态通知：文件标记 + 进程内 StateFlow（RootfsState，v1.2 引入）
4. JNI 链路：libsha256poc.so 嵌入 App 进程，真机对拍 5/5（dc268ea）

### 1.3 收益模型（不可破坏的铁律）

JNI 边界搬大块数据永远亏（10MB = 27ms vs 计算 5ms）。划算形态 = **数据常驻 native、
Java 只收小结果/进度事件**。任何让"数据跨进程/跨边界搬运"的部署选择都直接违背 v2.0 的立项前提。

## 2. 决策一：Rust 核心部署形态

### 2.1 候选对比

| 维度 | A. 嵌入式 .so（App 进程内） | B. 独立进程（Rust 守护进程） |
|---|---|---|
| 崩溃隔离 | ❌ 无——native panic/段错误杀整个 App | ✅ 守护进程崩了 App 无感，可重启 |
| 内存开销 | ✅ 增量 ~0.3–1MB RSS（.so + 工作缓冲） | ❌ 完整重复一套运行时（数 MB）+ IPC 缓冲 |
| JNI 边界次数 | ✅ 同进程函数调用，**零序列化** | ❌ 每次交互都要 IPC 序列化（边界成本 ×N） |
| 数据常驻 | ✅ **可行**——缓冲区留在 native，Java 只收进度 | ❌ **被杀死**——跨进程必经序列化，收益模型失效 |
| 与 libsha256poc.so 关系 | ✅ 直接演化为统一 core .so | ❌ 另起炉灶 |
| 复杂度 | 低（现有 CMake/jniLibs 路径已验证） | 高（进程生命周期/看护/协议设计） |

### 2.2 裁定：**嵌入式 .so（方案 A）**——这不是偏好，是被收益模型决定的

决定性论据：v2.0 的立项前提是"数据常驻 native 的流水线"。独立进程形态下，
数据要么跨 IPC 序列化（收益模型失效），要么共享内存（复杂度远超省下的东西）。
**进程隔离与数据常驻不可兼得；而 v2.0 要的是后者。**

崩溃隔离的替代方案（采纳 A 后的配套纪律）：
1. Rust 侧**错误不跨 FFI panic**（PoC 规范 #1，返回 null/错误码）——panic 跨 FFI 在
   `extern "system"` 下行为未定义，这是硬性红线
2. panic = abort 编译选项**不开**（panic=unwind 默认，unwind 到 JNI 边界被吞掉并返回 null）
3. 真正可能有 UB 风险的代码（unsafe 块）集中隔离在 `mod raw` 里，CI 加 `cargo clippy`
   对 unsafe 的告警门槛
4. Kotlin 侧**永远有平台回退**（规范 #2）——.so 崩了功能降级不中断

### 2.3 与 libsha256poc.so 的关系：**演化，不并存**

现状 `libsha256poc.so`（sha256 + 流式）是种子。v2.0 演进路径：

```
rust/sha256poc（现在）          rust/core（v2.0）
├── sha256 模块            →    ├── sha256 模块（平移）
├── extract 模块（P1 新增） →    ├── extract 模块（归档→解压→落盘流水线）
└── （新）fs 模块          →    ├── fs 模块（dirSizeMb 等）
                               └── 统一 JNI 薄层 + 进度回调协议
```

- 目标形态：**单一 `libzhengdao_core.so`**（共享 sha2/zstd 依赖、一次 loadLibrary、
  多模块注册），避免每模块一个 .so 的加载/体积碎片化
- 迁移方式：`cargo workspace` 收编 sha256poc → 改名 core；Kotlin 侧
  `Sha256Native` 迁到 `rust.CoreNative`，**旧调用点保留回退**（规范 #2）
- proguard keep 规则同步迁移；.so 入库策略不变（llvm-strip 后入库，CI 免装 Rust）

### 2.4 明确不做

- **独立进程**：除非未来出现"必须在 App 死后继续跑的重活"（目前没有——rootfs
  安装/校验都随 App 生命周期），否则不引入
- **系统级 Rust 守护进程 / root helper**：与本 App 免 root 定位冲突

## 3. 决策二：宿主 / guest 通信机制

### 3.1 通信需求矩阵（谁需要跟谁说什么）

| 通信对 | 需求场景（v2.0 视角） | 现有机制 |
|---|---|---|
| App ↔ 太极 serve | REST/SSE 对话流 | TCP 127.0.0.1:14000 + Basic auth ✅ |
| App ↔ 终端 | pty 输入输出 | 进程内 JNI（libtermux）✅ |
| App ↔ Rust core | 解压/校验/统计流水线 | 嵌入式函数调用（本文 §2）✅ |
| 状态通知（环境装好/卸了） | RootfsState 标记 + StateFlow | 文件标记 + 进程内状态 ✅ |
| **guest 工具 ↔ 宿主 serve** | **潜在**：guest 内 Agent 想调太极的 opencode 能力 | **未使用**（终端 opencode 已卸载） |
| guest ↔ App 通用 IPC | 潜在：guest 内工具上报结果/请求任务 | 无 |

### 3.2 机制裁定表

| 机制 | 用在哪 | 不用在哪 | 理由 |
|---|---|---|---|
| **TCP 127.0.0.1（现状保留）** | App ↔ 太极 serve | — | 已稳定、Basic auth/REST/SSE 全链路验证；换 UDS 无收益（回环 TCP 延迟本就微秒级） |
| **Unix domain socket（文件式）** | **仅当** guest 内进程需要与宿主 App/serve 通信时启用：socket 文件落在 App files 目录（proot bind 覆盖范围内，如 `files/home/.zhengdao/socks/`），guest 经 bind 路径连接 | App ↔ serve（TCP 已足够） | UDS 相比 TCP 回环的优势是 **SO_PEERCRED 对端凭证**（可验证 uid）与文件权限控制——guest 与 App 同 uid，凭证校验意义有限，故默认 TCP，UDS 留给需要权限边界的场景 |
| **抽象命名空间 UDS（@name）** | **不用** | — | Linux 抽象套接字无文件系统路径，proot 拦截语义未验证（PRoot 转换的是路径型 syscall）；不拿未验证机制进架构 |
| **文件标记 + 轮询** | 状态类通知（环境装好、任务完成标记）——**保持现状** | 高频数据流（文件轮询延迟与 IO 代价不适配） | 零协议成本、崩溃安全（文件即状态）、已在用（RootfsState/RunLog） |
| **guest 直连 127.0.0.1:14000** | guest 内进程要调 opencode 能力时（能力已实证可达） | — | 共享内核回环，天然可用 |

### 3.3 为什么"继续文件轮询"在状态类场景是正确选择（回应"是否升级 UDS"）

- 状态类通信的频率是**事件级**（装好/卸了/完成），不是数据流级——文件标记的
  轮询延迟（秒级）完全匹配
- 文件即状态：崩溃后重启读文件自动恢复真相，无需"重放事件"或"状态对账"
- UDS 引入的新失败面：socket 文件残留/权限/生命周期绑定——对状态通知是纯增负

## 4. v2.0 落地路线（按本文裁定的形态）

| 阶段 | 内容 | 验收 |
|---|---|---|
| R1 | cargo workspace 收编 sha256poc → rust/core，改名 libzhengdao_core.so；Kotlin 侧迁移 + 回退保持 | 真机对拍 5/5（现测平移） |
| R2 | extract 模块：归档路径进 → 解压/校验/落盘 + onEntry 进度回调（JNI 边界只跨一次） | 同一 311MB 包 vs Java 基线 2.07s 对拍；正确性对拍 20k+ 条目 |
| R3 | fs 模块：dirSizeMb 下沉 | 设置页数值与 Java 版一致 |
| R4 | （可选）UDS 通道：仅当出现 guest→宿主的真实 IPC 需求 | 真机 guest 连接 + 权限验证 |

每阶段独立 commit + 推送；任一阶段失败可回退到纯 Kotlin 路径（规范 #2 回退纪律）。

## 5. 风险登记

| 风险 | 缓解 |
|---|---|
| native panic 杀 App（嵌入形态的固有代价） | §2.2 纪律：FFI 边界 null 化、unsafe 隔离、clippy 门槛 |
| .so 体积增长（sha2+zstd+jni 全量） | llvm-strip + lto（PoC 实测 325KB 起步）；按需 feature 裁剪 |
| NDK 版本绑定（27.2 / API 35 链接器） | 与现 libtermux 同链路；NDK 升级为独立批次 |
| 手册"不在同一网络栈"被误读为"guest 连不上宿主回环" | 本文 §1.2 已实证澄清；建议故障排查手册坑 #0 补一行注记（另行提交，非本文范围） |
| 与另一 agent 的 v1.2/v1.3 工作撞车 | Rust core 全部在 `rust/` 与 `com.example.zhengdao.rust` 包内，不交叉 |
