# 证道 · Rust 改造可行性裁定与演进计划审核

> **裁定时间**：2026-10-06
> **裁定依据**：仓库代码实况（`app/build.gradle.kts`、`app/src/main/cpp/`、`RootfsDownloader.kt`、`RootfsInstaller.kt`）+ `docs/milestones/证道-性能演进路线图.md` 逐条比对
> **结论摘要**：现有演进计划的方向（先诊断后动刀、不为"感觉更快"重写）**是对的**，但**技术选型层面有一处根本性误判**：把 `MessageDigest`（SHA256）和 `zstd-jni`（解压）当成"Kotlin 实现"来评估，而这两个**本来就已经是 C/硬件加速的原生实现**。按计划推进 SHA256 PoC 会得到一个技术上无意义的结果。

---

## 0. 一句话结论

**当前代码里没有任何一个模块"值得为了性能改写成 Rust"。** 计划中三个候选迁移对象（SHA256 / 下载引擎 / 解压引擎）中，两个已是原生实现、一个是 I/O bound 而非 CPU bound——**真正值得做的是把 v1.0 的诊断做完并修正评估口径，而不是启动 SHA256 PoC**。

## 1. 仓库原状事实（裁定的地基）

| 事实 | 证据 | 对演进计划的影响 |
|---|---|---|
| **零 Rust 代码** | `find . -name "*.rs"` / `Cargo.toml` 均无结果 | 引入 Rust 是**从零建工具链**，成本被计划严重低估（见 §4） |
| **已有 C 原生层** | `app/src/main/cpp/`（Termux PTY JNI + CMake 3.22.1）+ `externalNativeBuild` 已配置 | cargo-ndk 可复用现有 CMake 接入点，**不是完全从零** |
| **SHA256 已是原生实现** | `RootfsDownloader.verifySha256()` 用 `java.security.MessageDigest.getInstance("SHA-256")` | ⚠️ **这是 JDK/ART 的原生实现，不是 Kotlin 循环**。计划误判 |
| **解压已是 C** | `RootfsInstaller` 用 `commons-compress` + **zstd-jni 1.5.6-4（`libzstd-jni-*.so` 已在 jniLibs）** | ⚠️ **zstd 是 C 实现的 zstd 库**，计划误判 |
| **NDK 版本偏低** | `ndkVersion = "27.2.12479018"` | **r27 不是 r28+**——16KB 对齐需手动加两个 linker flag（计划未提） |
| **`useLegacyPackaging = true`** | `app/build.gradle.kts` | 压缩式so 打包，会**规避** 16KB ZIP 对齐问题（但 ELF 对齐仍要管） |
| **全量代码 6460 行 Kotlin** | 最大的三个文件是 `SettingsScreen`(1127)、`TerminalActivity`(759)、`ProotLauncher`(602) | 规模适中，**不存在"编译期太长"这类需要 Rust 解决的问题** |
| ~~**ABI 双架构**~~ **已消解** | ~~`abiFilters += listOf("arm64-v8a", "x86_64")`~~ | **2026-10-06 用户定案砍掉 x86_64**（定位手机 / 平板，不做模拟器支持），收敛为 arm64 单架构。Rust 交叉编译只需一个目标，16KB 只需验一套——**这原本是最大的一笔额外成本，现已归零** |

## 2. 逐模块裁定：可改 / 不可动 / 维持现状

### 2.1 ❌ 不可动（结构性天花板，改写无意义）

| 模块 | 为什么不能动 | 依据 |
|---|---|---|
| **PRoot syscall 拦截** | **第三方 C 二进制**，证道无法重写；且它是**GPL**（Termux fork），重写等于重新实现一个 ptrace 拦截器——这不是性能问题，是重写 proot 本身 | 性能路线图 §5.1 已自认🔴 高瓶颈，本裁定确认：**只能规避（userns / bubblewrap / 真 root）或功能上接受** |
| **OpenCode 运行时内存** | 第三方 TS/Bun 进程，Rust 只能管它的**生命周期**，改不了它自身的内存占用。降内存只能靠配置与 prompt 层 | 性能路线图 §5.2 判断正确，予以确认 |
| **终端渲染（TerminalView / TerminalEmulator）** | 已是 Java 实现的成熟终端模拟器，**渲染热点在 Android 的文本布局与 Canvas**，不在计算。换 Rust 重写 = 重写整个终端模拟器，收益远小于风险 | v3.9 刚为此付出切换成本（WebView → 原生），不应再引入第二种实现 |
| **Compose UI / Android 平台集成** | Kotlin 最优：与 AndroidX 生命周期、Compose 编译器、状态管理深度耦合 | 计划 §6 已列为不迁移红线，正确 |
| **rootfs 构建管线（CI）** | 在 GitHub Actions 上跑，不在手机上。CI 的"性能"不是用户可感知的 | — |

### 2.2 ⚠️ 技术上可做，但**现在不该做**（计划的核心误判在此）

| 模块 | 计划怎么说 | 实际情况 | 裁定 |
|---|---|---|---|
| **SHA256 校验** | 列为"中严重度"，计划"先做 PoC 验证 JNI" | **已是 `MessageDigest` 原生实现**。ARM64 上 Android 的 SHA256 走的是 **ARMv8 crypto 扩展（`sha256` 指令）或 OpenSSL BoringLib 汇编**，不是 Java 循环。1.5GB 文件的 SHA256 在现代 ARM64 上是 **I/O 瓶颈（读盘速度），不是 CPU 瓶颈** | ❌ **PoC 无意义**。重写为 Rust 最多省掉 JNI 调用开销（纳秒级），而瓶颈在磁盘 I/O。**建议从计划中删除**，改为"实测 SHA256 耗时，若确实超阈值再重新评估（但几乎不会超）" |
| **RootFS 解压（tar.zst）** | 列为"中严重度"，可迁 Rust | **解压本身是 C 的 zstd**，Kotlin 只做 tar 遍历（commons-compress `TarArchiveInputStream`）。zstd 压缩比/速度是 **C 库的实现水平**，Rust 重写 zstd 只能做到"同样水平"（除非换算法，如 zstd → lz4，收益是压缩比下降） | ❌ **维持现状**。真要优化，方向是"**减少解压量**"（更小的 rootfs / 分层按需解压），不是"更快的解压器" |
| **下载引擎** | 列为"中严重度"，触发条件"速度 < 带宽 50%" | OkHttp 已是**高度优化的异步 HTTP 栈**（连接池、HTTP/2、多路复用）。且 M1.1 已实现 Range 断点续传。**下载速度瓶颈在网络与 CDN，不在解析** | ❌ **维持现状**。真要优化 = 多连接分块并发（Kotlin 层 `Range` 切片即可，**不需要 Rust**） |

### 2.3 ✅ 真正值得考虑 Rust 的（唯一一个，但要等数据）

| 模块 | 候选理由 | 前置条件 |
|---|---|---|
| **PTY 桥（`app/src/main/cpp/`）的数据搬运** | 唯一有真实 CPU 热点嫌疑的地方：大输出时 PTY read → TerminalEmulator 的字节处理是高频 JNI 往返。**但当前是 Java 层ByteQueue + C 层 read** | 必须先有 **Perfetto trace 证明 JNI 往返是热点**，而不是"大输出感觉卡"。若热点确在 JNI 往返，可考虑 Rust 重写数据通道（**但这是唯一值得起Rust 的地方，且收益上限有限**——终端卡顿的主因历史上是渲染，不是搬运） |
| （备选）`libtalloc.so` / `libandroid-shmem.so` | proot 运行时依赖 | ❌ 第三方预编译二进制，**不得替换** |

## 4. 若将来真要引入 Rust：成本与门槛（供决策参考）

**一次性成本（从零起步，项目当前状态）**：
1. Rust 工具链安装 + `cargo-ndk` 配置 + 与现有 `externalNativeBuild`（CMake）对接
2. CI 增加 Rust 构建环节~~（两套 ABI）~~ —— **已消解**：2026-10-06 定案单 arm64 架构，只有一套
3. JNI 边界设计（Kotlin ↔ Rust 的对象传递、生命周期、错误传播）——**这是最容易出 bug 的地方**
4. ~~16KB 对齐在两套 ABI 上分别验证~~ → **单 arm64 架构，只需验一套**（2026-10-06 定案）
5. R8/ProGuard 对 JNI 入口方法的 keep 规则

**收益上限的诚实估计**：即使 Rust 迁移完美，**只能改善"CPU 密集型"路径**。而当前已识别的热点中：
- SHA256 = I/O bound → 迁移无收益
- 解压 = 已是 C → 迁移无收益
- 下载 = 网络 bound → 迁移无收益
- PRoot = 第三方 C → 不可动
- OpenCode = 第三方 → 不可动

**唯一可能有收益的**：PTY 数据搬运的 JNI 往返（需 Perfetto 证明）。这是一个**收益上限有限、投入成本明确**的赌注。

**建议**：把"是否引入 Rust"这个决策**推迟到 v1.0 诊断数据出来之后**，且只在 Perfetto 明确指出"某模块 CPU 热点且非 I/O、非第三方"时才启动。**当前阶段（v1.0）的正确动作是：把 Perfetto 基线做完，不动语言。**

## 5. 修订后的演进路线（建议替换原§2/§3/§4）

| 阶段 | 内容 | 明确**不做**的事 |
|---|---|---|
| **v1.0 诊断**（不变） | Perfetto 冷启动 trace、`dumpsys meminfo` 基线、下载/解压/SHA256 耗时测量 → `docs/performance-baseline.md` | ❌ 不碰语言、不引Rust、**不把"已是原生的模块"列为迁移候选** |
| **v1.x 优化**（Kotlin） | ① OkHttp **多连接分块并发**（纯 Kotlin `Range` 切片，不需 Rust）② zstd 复用上下文 ③ App Startup 延迟初始化 ④ Baseline Profile（**前提：先核对 AGP ≥ 8.0**）⑤ **减少 rootfs 解压量**（比"更快解压"收益大得多） | ❌ 不动 proot / OpenCode / 终端渲染 |
| **v2.0 Rust**（条件触发，门槛抬高） | **仅当Perfetto 证明某模块 CPU 热点、且该模块是自研代码（非第三方、非已是 C 实现）时**启动评估。**当前唯一候选 = PTY 数据搬运的 JNI 往返** | ❌ 不迁移 SHA256（已是原生）、❌ 不迁移 zstd 解压（已是 C）、❌ 不迁移下载引擎（I/O + 网络 bound） |

## 6. 给决策者的一句话

**这份计划最值得肯定的地方是它说"先诊断后动刀"；最需要修正的地方是诊断前就该知道的常识——SHA256 和 zstd 本来就不在 Kotlin 里跑。** 现在最该做的事是把 v1.0 的 Perfetto 基线跑出来，而不是启动一个技术上注定无收益的 SHA256 PoC。
