## 2. 候选方案对比

| 维度 | **A. mikepenz** `multiplatform-markdown-renderer` 0.38.1 | **B. jeziellago** `compose-markdown` 0.7.2 | **C. 自研** |
|---|---|---|---|
| 渲染方式 | 纯 Compose（AST → @Composable） | **AndroidView 包 TextView** | 手写解析 + 排版 |
| 分发仓库 | **Maven Central**（项目已配） | JitPack（**须改 settings**） | — |
| 代码语法高亮 | ✅ 内置 `-code` 模块（`dev.snipme:highlights`） | ❌ 无 | 自己接 |

| 表格 / 任务列表 | ✅ GFM 内建 | ✅ | 自己写 |

| 维护活跃度 | 活跃（0.45.0 @2026-08） | 活跃（0.7.2 @2026-04） | — |
| 许可 | Apache-2.0 | MIT | — |

**为什么选 A 而非 B**：B 是 **TextView 包装**，本质是「在 Compose 里塞一个 AndroidView」，与项目已裁定的「Compose 原生 UI 直连」方向相反；且它**不提供代码高亮与复制按钮**（计划里复制按钮优先级最高），还要引入 coil3、并需要改 `settings.gradle.kts` 加 JitPack 源。

**为什么不用 C（自研）**：Markdown 解析 + GFM 表格 + 代码高亮，自研成本远高于 635 KB 的体积代价，且易有边界 bug。

## 3. 版本选型的关键依据（**这是本次调研最重要的发现**）

mikepenz 各版本**编译所用 Kotlin 版本**（各版本 POM 实拉）：

| 库版本 | 编译用 Kotlin | JetBrains markdown | 发布日 |
|---|---|---|---|
| 0.45.0 / 0.44.0 | 2.4.10 | 0.7.9 | 2026-08 |
| 0.43.0 / 0.42.0 | 2.4.0 | 0.7.5 | 2026-06 |
| 0.41.0 | 2.3.21 | 0.7.3 | 2026-05 |
| 0.40.2 | 2.3.20 | 0.7.3 | 2026-04 |
| 0.39.2 | 2.3.0 | 0.7.3 | 2026-01 |
| **0.38.1** | **2.2.21** | 0.7.3 | **2025-11** |
| 0.35.0 | 2.1.21 | 0.7.3 | 2025-05 |

项目 Kotlin 为 **2.2.10**。Kotlin 编译器的 metadata 只保证读「同线或更旧」的产物，**用 2.2.10 消费 2.3/2.4 编译的库存在 metadata 不兼容风险**（可能报 "compiled with a newer Kotlin"）。

→ **0.38.1（Kotlin 2.2.21，同 2.2 线）是当前唯一有实测把握的版本**，且功能完备（表格、任务列表、代码高亮、复制、retainState 均已具备）。

⚠️ 代价：0.38.1 发布于 2025-11，距今约一年。**这是「不升级项目 Kotlin」约束下的必然取舍**——升级库版本 = 同步升级 Kotlin/AGP，属架构级改动，不应混在 v1.1 里做。

### 5.2 渲染改造（`FinalAnswerText`）

```kotlin
@Composable
private fun FinalAnswerText(text: String) {
    if (text.isEmpty()) return
    val state = rememberMarkdownState(text, retainState = true)   // 流式更新不闪 loading
    Markdown(
        markdownState = state,
        modifier = Modifier.fillMaxWidth(),                        // ⚠️ 必须覆盖：库默认是 fillMaxSize()
        colors = markdownColor(text = MaterialTheme.colorScheme.onSurface),
        typography = markdownTypography(text = MaterialTheme.typography.bodyLarge, …),  // 对齐第二阶段视觉
        components = markdownComponents(
            codeFence = { MarkdownHighlightedCodeFence(it.content, it.node, it.typography.code, showHeader = true) },
            codeBlock = { MarkdownHighlightedCodeBlock(it.content, it.node, it.typography.code, showHeader = true) },
        ),
    )
}
```

### 5.3 渲染范围（建议）

- **最终回答** → Markdown 化（本条是第四阶段的目标）
- **思考过程（ReasoningBlock）** → **保持纯文本**（灰小字）：思考过程常含非规范 Markdown，渲染成本高且视觉噪音大
- **工具调用卡片（ToolCallCard）** → **保持等宽纯文本**：入参/结果是日志性质，不需要 Markdown

## 6. 风险与注意点

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| R1 | **流式重解析开销（⚠️ 上游长期限制，非临时问题）** | 0.38.1 **无** `rememberStreamingMarkdownState()`（0.43+ 才有，需 Kotlin 2.4）。流式追加时每次内容变化都会全量异步重解析。**更关键**：增量解析是 mikepenz **明确拒绝**的功能 —— Issue #315 作者原话：「The currently used markdown parser **does not support incremental parsing**，please report the issue upstream.」「…would **effectively require incremental parsing**…**difficult to make correct for all Markdown cases**.」该 Issue 自 2025-02 挂至 2026-05，社区多次请求未改口。**→ 结论：这不是「暂时没优化」，是「上游不打算优化」，缓解方案是长期策略。** | 用 `retainState=true` 先观察；若真机卡顿，做**节流**（仅当内容稳定或距上次 >150ms 才更新 state），或流式中用纯文本、仅完成后 Markdown 化。**节流是长期策略，不是临时 workaround。** |
| R7 | **流式闪烁**（Markdown 组件反复出现/消失） | Issue #457：0.37.0 在 LLM 流式场景下会闪烁。作者给的官方解法：① 把解析移到 ViewModel，只把结果状态暴露给 Compose；② **传递一个状态对象并设为 `immediate`**（有用户实测确认「passing a state object set to `immediate` resolves the flicker」） | **真机若出现闪烁，优先试「状态设为 `immediate`」，而不是直接加节流** —— 节流是「卡了再加」，`immediate` 是「闪了先试」。两者不冲突，可叠加。 |
| R2 | **视觉回归** | 库自带 typography / padding 与第二阶段「大字号 + onSurface」不一致 | 用 `markdownColor()/markdownTypography()` 显式对齐；**必须真机验收**字号与留白 |
| R3 | **默认 `Modifier.fillMaxSize()`** | 库默认 modifier 是撑满，直接用在消息列表会出错 | 一律显式传 `Modifier.fillMaxWidth()`（已在 5.2 写明） |
| R4 | **R8 / release** | debug ✅实测通过 ≠ release 通过 | release 构建后做一次冒烟测试；如遇 keep 问题，在 `proguard-rules.pro` 补规则 |
| R5 | **图片不显示** | 默认 `NoOpImageTransformerImpl`，Markdown 里的图片不加载 | 视为**优点**（不引入 coil3）；确需图片再单独评估 |
| R6 | **版本锁死** | 库升版需同步升 Kotlin（架构级） | 本次锁 0.38.1；升 Kotlin 作为独立议题，勿混入 v1.1 |
