## 坑 #0：**先确认作用域** —— 太极（宿主）与终端（PRoot guest）不在同一个网络栈

> **为什么置顶**：这是本手册里唯一一条**架构级认知**。任何网络相关排查，
> **先读这条再动手**——它决定你接下来要改的那份配置**到底在不在生效路径上**。
> （2026-10-07 真机实测所得；原编号 #5，因价值高于单点故障而提为 #0 置顶。）

### 现象

在终端（Debian guest）里改了 `/etc/resolv.conf` 或 `/etc/hosts`、装了 dnsmasq、
加了代理环境变量，期待「太极」Tab 的网络行为跟着变——结果**一点没变**。
（或反过来：设置 / 插件页里改了东西，终端里的行为照旧。）

> 本轮若不是先查了「太极到底跑在哪」，就会一直在 PRoot 里调 hosts、调 resolv.conf、
> 调 `rotate`，调半天才发现**调的东西根本不在同一条路径上**。
> **先确认作用域，再优化参数** —— 这个顺序比任何单点优化都重要。

### 根因

App 里跑 OpenCode 的**两个位置不在同一个网络栈**：

| | 「太极」Tab 的 serve | 终端（洞天）里的进程 |
|---|---|---|
| 运行环境 | **宿主 bionic**（Android），**不经 PRoot** | PRoot 内的 Debian 13.7 |
| 父进程 | **App 自己**（`com.example.zhengdao`） | `proot` |
| 看到的根 | Android 宿主根（mounts 首行 `dm- / erofs`） | rootfs 目录 |
| 配置文件 | `files/oc/xdg/config/opencode/`（**宿主路径**） | `~/.config/opencode/`（guest 内） |
| DNS 走谁 | **Android netd**（系统解析器） | rootfs 的 `/etc/resolv.conf` |
| `/etc/hosts` 生效吗 | **不生效** | 生效 |

### ★ 两个 OpenCode 是**完全独立的两份资产**（不是同一份的两处入口）

> **为什么单列**：v1.1.1 曾把两者当成"一套东西的两个实例"，于是太极的配置被写到了
> 终端 taiji 脚本的 XDG 目录（`files/home/.zhengdao/taiji/config/opencode`）——
> **没有人读那份文件**，导致插件开关、人设 AGENTS.md 一直没生效（v1.2 阶段 2.0 才发现）。
> **它们之间没有任何共享文件、没有版本联动、删掉一个不影响另一个。**

| | **太极的 OpenCode**（宿主） | **终端的 OpenCode**（已卸载） |
|---|---|---|
| 二进制 | `files/oc/usr/bin/opencode`（bionic 原生，~65MB 包） | 曾为 `rootfs/usr/lib/node_modules/opencode-ai`（npm） |
| 配置真相源 | `files/oc/xdg/config/opencode/opencode.json` | 曾为 guest `~/.config/opencode/` |
| 安装方式 | App 内下载 GitHub release 包 + SHA 校验 | 曾在 guest 里 `npm i -g opencode-ai` |
| 卸载方式 | 删 `files/oc/` | 曾 `npm uninstall -g` |
| **需要 Debian/PRoot 吗** | **完全不需要**（跑在宿主 bionic 上） | 需要（只在 PRoot 里存在） |
| 谁负责写配置 | `OcManager.updateConfig()`（**唯一写入口**） | 无（已随 v1.2 卸载消失） |
| 现状 | **在用，主打功能** | **v1.2 已卸载**（用户重新裁决） |

⚠️ **推论（新用户体验相关）**：太极**不依赖 Debian 环境**。用户没装 326MB 的 rootfs
也能正常用太极；反过来，装了 Debian 也不会让太极多出任何能力。
（serve 的 `PATH` 被显式设为 `/system/bin`，从不进 PRoot。）

### 怎么确认（真机）

```bash
SPID=$(ps -A | grep -iE " opencode$" | awk '{print $2}')
run-as com.example.zhengdao cat /proc/$SPID/environ | tr '\0' '\n' | grep -iE "proxy|xdg|home"
cat /proc/$SPID/mounts | head -1        # 首行是 dm- / erofs ⇒ 宿主，不在 proot 里
```

### 自救

- 改**太极**的网络行为 → 改 **App 侧**：`OcManager.startServe` 注入的环境变量
  （`NO_PROXY` / `BUN_FEATURE_FLAG_DISABLE_IPV6` 在此），或 Android 系统网络设置；
- 改**终端**的网络行为 → 改 rootfs 内的 `/etc/resolv.conf` / `/etc/hosts`，
  或 `ProotLauncher` 注入的 guest 环境变量；
- **别指望改一边能影响另一边。**

### 附：曾在这里踩过的坑（给未来的自己留证据）

2026-10-07 为"优化网络延迟"，我们**在 rootfs 的 `/etc/hosts` 里把 `opencode.ai`
钉死到 `172.65.90.21`**（P0，规避 IPv6 黑洞下的长超时）。**已撤除，不要再往回加。**

撤除理由（真机实测）：

1. **收益 ≈ 0** —— 按上表，太极 serve 跑在宿主、**不读 rootfs 的 hosts**，
   这项优化对主产品**完全无效**；终端里的 opencode 同日已卸载；guest 内即便有进程，
   curl 拆解显示也只省**首次请求 8–25 ms**（连接复用后 DNS 成本归零）。
   端到端由 TLS + 跨境 RTT（~1.7 s）主导，DNS 只占 ~1%。
   ⇒ **省的是"问路"的时间，不是"走路"的时间。**
2. **风险是硬故障，不是性能波动** —— Cloudflare 前置、4 个轮换 IP
   （`172.65.90.20`–`.23`），IP 一旦轮换就是**直接连不上**，不可控、不可预测、不可自愈。

保留下来的三项**均不依赖外部 IP**，无轮换风险：遥测 `0.0.0.0` 屏蔽、
`NO_PROXY` / `no_proxy`、`BUN_FEATURE_FLAG_DISABLE_IPV6=1`。

> ⚠️ **代码证据（2026-10-07 核对）**：撤除逻辑已在 `terminal/EnvSelfHeal.kt` 落地——
> `:62 private val HOSTS_UNPINS = listOf("opencode.ai")`；
> `:70-77 internal fun stripObsoletePins(text: String): Pair<String, Int>`（**按精确域名匹配**，只删 hosts 里 `opencode.ai` 那一行，不会误伤 `telemetry.opencode.ai`），
> 由 `:119-153 ensureHosts` 在每次启动时调用（`:130-136` 撤除历史遗留钉 IP）。
> 上句"保留下来的三项"与代码一致：遥测四条 `0.0.0.0` 屏蔽在 `terminal/EnvSelfHeal.kt:41-46 HOSTS_PINS`；
> `NO_PROXY` / `no_proxy` 与 `BUN_FEATURE_FLAG_DISABLE_IPV6=1` 在 `terminal/ProotLauncher.kt:455/464/465`（另有 `oc/OcManager.kt:250-254`）。

> 若将来 guest 里**真的**需要优化 DNS，正确方向不是 hosts 钉 IP，而是：
> ① 在 guest 内跑**本地 DNS 缓存**（dnsmasq / systemd-resolved 最小配置），上游指向国内可达 NS；
> ② 或让 guest 复用宿主已解析的结果，而不是各自查 DNS。
> 若目标是"减少跨境 RTT"，**DNS 完全不是抓手** —— 要么换 CDN 节点、要么上代理、要么接受 1.7 s。

## 坑 #1：Hermes 硬链接失败（`hermes pm repair` 反复报 Operation not permitted）

### 现象

`hermes pm repair` 反复卡在同一个位置，报 `failed to hardlink file ... Operation not permitted (os error 1)`。

### 根因

**Hermes 的 PM（包管理器）内嵌了一个自己的 uv**（路径：`/root/.hermes/tools/uv-0.12.3-linux-arm64/uv`），这个内嵌 uv 绕过了所有系统级防御：

1. **剥离所有 `UV_*` 环境变量** → `export UV_LINK_MODE=copy` 无效
2. **重定向 `XDG_CONFIG_HOME`** → `~/.config/uv/uv.toml` 读不到
3. **记住自己的 uv 安装路径** → `/usr/local/bin/uv` 的 wrapper 被绕过

Android 的 PRoot 环境不允许硬链接（SELinux 拦截），uv 默认的硬链接模式必然失败，但前面三层防御全被 PM 绕过了。

### 临时自救（原位置包装内嵌 uv）

```bash
cd /root/.hermes/tools/uv-0.12.3-linux-arm64/
mv uv uv.real
cat > uv <<'EOF'
#!/bin/sh
case "$1" in
  sync|pip|venv|install)
    exec "$(dirname "$0")/uv.real" "$@" --link-mode copy
    ;;
  *)
    exec "$(dirname "$0")/uv.real" "$@"
    ;;
esac
EOF
chmod +x uv
export UV_LINK_MODE=copy
hermes pm repair
```

**关键点**：shebang 用 `#!/bin/sh`（不是 `/system/bin/sh`）；`case` 判断子命令（`uv python install` 不接受 `--link-mode`）；`--link-mode copy` 放最后（clap 取最后值）。

## 坑 #2：终端 DNS 解析超时（resolv.conf 有，但 curl 超时）

### 现象

```bash
$ cat /etc/resolv.conf
nameserver 223.5.5.5
nameserver 119.29.29.29
...

$ curl -I --max-time 5 https://www.baidu.com
curl: (28) Resolving timed out after 5001 milliseconds
```

DNS 配置完整，但解析超时。

### 根因

> ⚠️ **审核标注（2026-10-06，以下三条均为推测，非实测结论）**：这三条根因**没有一条有实测证据**（无 `getprop net.dns`、无抓包、无`curl --resolve` 对照）。按项目自己的 E-005 纪律「真机验证优先于文档推断」，本节属"文档推断"，不能当定论。
> 另：**根因三与 v3 §6 / M5 §6 直接冲突**——那两处写"proot 子进程与 App 同 UID、同路由表，天然被 VPN 覆盖"，本节写"不走 VPN 隧道"。两者不能并存，**须裁决后统一**。
> 反向线索：commit `c7ac1dc` 给 resolv.conf 加 DNS 重试参数（移动网络丢包快速换源）后症状缓解，说明真实成因更可能是**丢包/超时**而非"拦截不到"。
> **正确的诊断动作**（替代推测）：① 宿主 Termux 与guest 内分别 `cat /etc/resolv.conf` 对比；② guest 内 `nslookup`/ `getent hosts` 与 `curl --resolve`（绕 DNS）分别测；③ 宿主 `ping` 网关与 guest `ping` 网关对照，定位断点在 DNS 层还是链路层。

**根因一（推测）：PRoot 无法正确拦截 DNS 系统调用**
PRoot 在用户空间拦截系统调用，但 DNS 解析不走普通文件系统调用，而是通过 socket 发送查询。PRoot 对 socket 相关系统调用的拦截不完整，导致 `/etc/resolv.conf` 配置了 DNS 但查询发不出去。

**根因二（推测）：Android 的 DNS 解析走 netd，PRoot 拦截不到**
Android 系统的 DNS 解析通过 `netd` 守护进程处理，而 PRoot 在用户空间拦截系统调用，两者不在同一层面。PRoot 容器内发送的 DNS 查询可能被网关静默丢弃，而宿主 Termux 环境却正常。

**根因三（推测，且与 v3 §6 冲突待裁决）：VPN/代理客户端与 PRoot 不兼容**
用户连接 VPN 后，宿主 Termux 中网络正常，但进入 PRoot 容器后连接失败。PRoot 容器内的网络请求不走 VPN 隧道，而是以"商业 IP"直接发出，导致被远程服务器拒绝。

### 临时自救（五步）

**第一步：测基础连通性（绕过 DNS）**

```bash
# ⚠️ 循环依赖：网络正是故障本身，apt 未必可用。ping 已内置则直接跑，
#否则先试 guest 内已有的连通性手段（如 curl --resolve、getent hosts），别卡在 apt 上。
ping -c 2 223.5.5.5
```

- **通** → 基础网络层没问题，是 DNS 查询被阻
- **不通** → PRoot 网络栈或代理彻底断了

**第二步：用 IP 直接测（绕过 DNS 解析）**

```bash
curl -I --max-time 5 http://223.5.5.5
```

- **通** → 网络层通，只是 DNS 查询被阻
- **不通** → 网络整体断了

**第三步：重新写 resolv.conf（用宿主正在用的 DNS）**

如果宿主手机用的是路由器 DNS（如 `192.168.1.1`），可以把它写进去：

```bash
echo "nameserver 192.168.1.1" > /etc/resolv.conf
```

**第四步：在 /etc/hosts 里写死常用域名**（**应急手段，需先现查 IP**）

既然 DNS 查询发不出去，可把域名和 IP 写死在 `/etc/hosts` 里。⚠️ **下面的 IP 仅作格式示例，不可直接用**——CDN 节点会变动，写死过期 IP 会静默连到错误节点：

```bash
# ⚠️ 步骤：先在宿主能联网的地方 `ping google.com` 拿到当前 IP，再写死
# echo "<现查到的IP> google.com" >> /etc/hosts
```

长期方案应避免维护 IP 清单（见上文"长期修复"第5 条：启动时从宿主获取当前 DNS 并注入）。

**第五步：检查代理 App 的规则模式**

如果代理 App 是「全局模式」，国内流量也走代理，节点一断全断。改成「规则模式」或「绕过大陆」模式。

## 坑 #3：改了 opencode 的配置，「太极」里却不生效（配置到底在哪）

> **v1.2 重写（2026-10-07）**：本条原先讲的是"两份 opencode 互不相通"。
> v1.2 已**卸载终端里的 npm 版 opencode**（用户裁决反转），现在 App 里**只有太极这一份**；
> 但"改了配置不生效"这个现象**依然存在**，真因也变了——见下面「根因」。

### 现象

- 插件管理页开了 / 关了开关，太极里的行为没变化；
- 或者手动改了某份 `opencode.json`，重启 App 后**改动被抹掉**（只剩 `$schema` + `permissions`）；
- 或者 Agent 表现得"不知道自己在手机里""找不到文件"（人设没喂进去）。

### 根因

太极的 OpenCode（宿主 bionic 版 `files/oc/usr/bin/opencode`，**不经 PRoot**）真正读取的配置只有一个：

| 用途 | 路径（App 私有目录内） |
|---|---|
| 配置文件 | **`files/oc/xdg/config/opencode/opencode.json`** ← 唯一真相源 |
| 人设文件 | `files/oc/xdg/config/opencode/AGENTS.md` |
| 插件缓存 | `files/oc/xdg/cache/opencode/packages` |

> ⚠️ **补充（2026-10-07）**：上表只覆盖 **opencode 配置**。另有两条独立的"真相源"链同样值得知道：
> ① **Agent 热更新清单** = `rootfs/agents.json` + `rootfs/agents.json.sig`（ed25519 验签，`ui/AgentManifest.kt`：公钥 `:35 PUBLIC_KEY_B64`、先验签 `:50 verify` → `:61 parse`、三通道 `:164-191`、`TTL_MS` 6h `:28`）；
> ② **验签缓存**（SharedPreferences `zhengdao-agents-manifest`）在建卡片时被读：`ui/AppState.kt:107 AgentManifest.cached(ctx)`；manifest 拉取失败时沿用最近一次验签通过的版本（`ui/AgentManifest.kt:97 cached(ctx)`）。
> ⇒ 排查"Agent 卡片内容不对/关不掉"时，除上表的 opencode 配置外，还要看这条 `agents.json` 链。

历史坑（v1.2 已修）：`PluginManager` 曾指向 `files/home/.zhengdao/taiji/...`——那是**已废弃的
终端 taiji 脚本**的 XDG 目录，与 serve 读的不是同一个文件 ⇒ 插件开关改的配置没人读，
太极的 `AGENTS.md` 也从未被写进正确目录。同时 `OcManager.ensurePermissionPolicy()` 是
**整文件覆盖写**，冷启动一次就会把它不认识的字段（`plugin` / `snapshot` / `watcher`）全部抹掉。

### 自救

1. 要改太极的行为 → 改**上表那个路径**，或直接用**设置 → 插件管理**；
2. 改完重启 App 发现被抹 → 说明写方没走 merge；现在所有写方已统一走
   `OcManager.updateConfig()`（读-改-写），正常情况下不会再被抹；
3. 终端里现在**没有 opencode 了**（v1.2 卸载）。想用 CLI 可自行 `npm i -g opencode-ai`，
   但那是你自己装的第二份，App 不为它管配置、也不为它管插件。

## 坑 #4：【已撤除】hosts 钉 IP 导致连不上 opencode.ai —— 本条留作历史档案

> **状态：已撤除（2026-10-07）**。当前版本**不再**往 `/etc/hosts` 写任何 `opencode.ai` 的
> IP 钉住项。本条只保留"这个故障模式长什么样、当初为什么撤"，供日后有人想重新钉 IP 时参考。
> **结论先说：不要再钉。** 完整论证见 **坑 #0** 的附记。

### 曾经的现象

太极 / 终端里访问 `opencode.ai` 失败（连接超时 / TLS 握手失败），但访问别的站点正常。

### 曾经的根因

为规避 IPv6 黑洞网络下的长超时，v1.2 一度把 `opencode.ai` **钉死到一个 IPv4**
（`172.65.90.21`）写进 `/etc/hosts`，并给 Bun 加了 `BUN_FEATURE_FLAG_DISABLE_IPV6=1`。
但 `opencode.ai` 由 **Cloudflare 前置、解析出 4 个轮换地址**（实测 `172.65.90.20`–`.23`，
两次 curl 分别命中 `.21` 与 `.23`）。**一旦钉住的那个 IP 被轮换掉就是硬故障**——
而且因为 IPv6 也被禁了，没有备用路径。

### 为什么撤（不是"先观察"）

1. **收益 ≈ 0**：太极 serve 跑在宿主 bionic，**不读 rootfs 的 `/etc/hosts`**（见坑 #0），
   对主产品完全无效；终端 opencode 已卸载；guest 内只省首次请求 8–25 ms，
   连接复用后 DNS 成本归零。端到端由 TLS + 跨境 RTT（~1.7 s）主导，DNS 占 ~1%。
2. **风险是硬故障而非性能波动**：IP 轮换即连不上，不可控、不可预测、不可自愈。

### 现在怎么做的（自愈会主动清理）

`EnvSelfHeal.ensureHosts()` 每次启动会**主动摘除**历史遗留的 `opencode.ai` 钉住行
（幂等；按**精确域名**匹配，不会误伤 `telemetry.opencode.ai`）。
已装环境升级 App 后那行会自动消失，无需手工处理；单测 `EnvSelfHealTest` 锁住了这个行为。

### 若日后仍要排查 opencode.ai 连不上

按 **坑 #0** 先确认作用域，再看这三件事：
① guest 内 `getent ahostsv4 opencode.ai` 能否解析；
② `/etc/resolv.conf` 内容（应为国内源在前 + `options timeout:1 attempts:3 rotate`）；
③ 是否走了代理（真机实测 serve 进程**无** `HTTP_PROXY`/`HTTPS_PROXY`）。
