## 坑 #1：Hermes 硬链接失败（`hermes pm repair` 反复报 Operation not permitted）

### 现象

`hermes pm repair` 反复卡在同一个位置，报 `failed to hardlink file ... Operation not permitted (os error 1)`。

### 根因

**Hermes 的 PM（包管理器）内嵌了一个自己的 uv**（路径：`/root/.hermes/tools/uv-0.12.3-linux-arm64/uv`），这个内嵌 uv 绕过了所有系统级防御：

1. **剥离所有 `UV_*` 环境变量** → `export UV_LINK_MODE=copy` 无效
2. **重定向 `XDG_CONFIG_HOME`** → `~/.config/uv/uv.toml` 读不到
3. **记住自己的 uv 安装路径** → `/usr/local/bin/uv` 的 wrapper 被绕过

Android 的 PRoot 环境不允许硬链接（SELinux 拦截），uv 默认的硬链接模式必然失败，但前面三层防御全被 PM 绕过了。

### 临时自救（原位置包装内嵌 uv）

```bash
cd /root/.hermes/tools/uv-0.12.3-linux-arm64/
mv uv uv.real
cat > uv <<'EOF'
#!/bin/sh
case "$1" in
  sync|pip|venv|install)
    exec "$(dirname "$0")/uv.real" "$@" --link-mode copy
    ;;
  *)
    exec "$(dirname "$0")/uv.real" "$@"
    ;;
esac
EOF
chmod +x uv
export UV_LINK_MODE=copy
hermes pm repair
```

**关键点**：shebang 用 `#!/bin/sh`（不是 `/system/bin/sh`）；`case` 判断子命令（`uv python install` 不接受 `--link-mode`）；`--link-mode copy` 放最后（clap 取最后值）。

### 长期修复（给 Zcode，P7 固化）

1. ~~**RootFS 构建脚本**：预设 `/etc/environment` 的 `UV_LINK_MODE=copy` + `~/.config/uv/uv.toml` 的 `link-mode = "copy"`~~ —— ⚠️ **对内嵌 uv 无效**（本节根因已自述内嵌 uv 会剥离环境变量 + 重定向 `XDG_CONFIG_HOME`）。这两项只对**系统 uv** 有效，别误以为已解决坑 #1。真正的长期解是第2 条。
2. **`agent-helper` 加命令 `agent fix hardlink`**：扫描所有 Agent 的内嵌 uv/npm，原位置包装
3. **终端启动 banner 提示**："若装 Agent 遇到 hardlink 报错，敲 `agent fix hardlink`"
4. **文档附录 A 加坑 #12**：Agent 内嵌工具绕过系统级 wrapper

## 坑 #2：终端 DNS 解析超时（resolv.conf 有，但 curl 超时）

### 现象

```bash
$ cat /etc/resolv.conf
nameserver 223.5.5.5
nameserver 119.29.29.29
...

$ curl -I --max-time 5 https://www.baidu.com
curl: (28) Resolving timed out after 5001 milliseconds
```

DNS 配置完整，但解析超时。

### 根因

> ⚠️ **审核标注（2026-10-06，以下三条均为推测，非实测结论）**：这三条根因**没有一条有实测证据**（无 `getprop net.dns`、无抓包、无`curl --resolve` 对照）。按项目自己的 E-005 纪律「真机验证优先于文档推断」，本节属"文档推断"，不能当定论。
> 另：**根因三与 v3 §6 / M5 §6 直接冲突**——那两处写"proot 子进程与 App 同 UID、同路由表，天然被 VPN 覆盖"，本节写"不走 VPN 隧道"。两者不能并存，**须裁决后统一**。
> 反向线索：commit `c7ac1dc` 给 resolv.conf 加 DNS 重试参数（移动网络丢包快速换源）后症状缓解，说明真实成因更可能是**丢包/超时**而非"拦截不到"。
> **正确的诊断动作**（替代推测）：① 宿主 Termux 与guest 内分别 `cat /etc/resolv.conf` 对比；② guest 内 `nslookup`/ `getent hosts` 与 `curl --resolve`（绕 DNS）分别测；③ 宿主 `ping` 网关与 guest `ping` 网关对照，定位断点在 DNS 层还是链路层。

**根因一（推测）：PRoot 无法正确拦截 DNS 系统调用**
PRoot 在用户空间拦截系统调用，但 DNS 解析不走普通文件系统调用，而是通过 socket 发送查询。PRoot 对 socket 相关系统调用的拦截不完整，导致 `/etc/resolv.conf` 配置了 DNS 但查询发不出去。

**根因二（推测）：Android 的 DNS 解析走 netd，PRoot 拦截不到**
Android 系统的 DNS 解析通过 `netd` 守护进程处理，而 PRoot 在用户空间拦截系统调用，两者不在同一层面。PRoot 容器内发送的 DNS 查询可能被网关静默丢弃，而宿主 Termux 环境却正常。

**根因三（推测，且与 v3 §6 冲突待裁决）：VPN/代理客户端与 PRoot 不兼容**
用户连接 VPN 后，宿主 Termux 中网络正常，但进入 PRoot 容器后连接失败。PRoot 容器内的网络请求不走 VPN 隧道，而是以"商业 IP"直接发出，导致被远程服务器拒绝。

### 临时自救（五步）

**第一步：测基础连通性（绕过 DNS）**

```bash
# ⚠️ 循环依赖：网络正是故障本身，apt 未必可用。ping 已内置则直接跑，
#否则先试 guest 内已有的连通性手段（如 curl --resolve、getent hosts），别卡在 apt 上。
ping -c 2 223.5.5.5
```

- **通** → 基础网络层没问题，是 DNS 查询被阻
- **不通** → PRoot 网络栈或代理彻底断了

**第二步：用 IP 直接测（绕过 DNS 解析）**

```bash
curl -I --max-time 5 http://223.5.5.5
```

- **通** → 网络层通，只是 DNS 查询被阻
- **不通** → 网络整体断了

**第三步：重新写 resolv.conf（用宿主正在用的 DNS）**

如果宿主手机用的是路由器 DNS（如 `192.168.1.1`），可以把它写进去：

```bash
echo "nameserver 192.168.1.1" > /etc/resolv.conf
```

**第四步：在 /etc/hosts 里写死常用域名**（**应急手段，需先现查 IP**）

既然 DNS 查询发不出去，可把域名和 IP 写死在 `/etc/hosts` 里。⚠️ **下面的 IP 仅作格式示例，不可直接用**——CDN 节点会变动，写死过期 IP 会静默连到错误节点：

```bash
# ⚠️ 步骤：先在宿主能联网的地方 `ping google.com` 拿到当前 IP，再写死
# echo "<现查到的IP> google.com" >> /etc/hosts
```

长期方案应避免维护 IP 清单（见上文"长期修复"第5 条：启动时从宿主获取当前 DNS 并注入）。

**第五步：检查代理 App 的规则模式**

如果代理 App 是「全局模式」，国内流量也走代理，节点一断全断。改成「规则模式」或「绕过大陆」模式。

### 长期修复（给 Zcode，P7 固化）

1. **`prepareNetwork()` 每次启动会话前都重写 `/etc/resolv.conf`**，不依赖上次的残留
2. **`ProotLauncher` 启动参数加 `--bind /etc/resolv.conf`**，避免 guest 内被意外覆盖
3. **终端启动 banner 加一句**："网络不通？先 `cat /etc/resolv.conf` 看 DNS"
4. **`agent-helper` 加命令 `agent fix network`**——一键重写 DNS 配置
5. **启动时从宿主获取当前 DNS，注入 guest 的 resolv.conf**（参考 PAUXB 修复方案：从 Termux 环境解析 Debian 镜像域名，注入 IP 到 `/etc/hosts`）

## 共性分析

| 维度 | 坑 #1（Hermes 硬链接） | 坑 #2（网络断连） |
|---|---|---|
| **表象** | 装 Agent 失败 | DNS 解析超时 |
| **真因** | PM 内嵌 uv 绕过系统 wrapper | PRoot 无法正确拦截 DNS 系统调用 + VPN 不兼容 |
| **层次** | 应用层工具行为 | 系统层网络栈限制 |
| **短期解** | 原位置包装内嵌 uv | 写死 IP 到 hosts / 用宿主 DNS |
| **长期解** | `agent fix hardlink` | `agent fix network` |

**共性**：都是"环境看起来正常，但某层被绕过/限制"。证道的长期方案是把这些坑**固化成 `agent-helper` 的一键修复命令**，让用户一条命令自救。
