| **C** | 增量下发（省"每次更新重下"） | **zstd `--patch-from` 实测不可用**，须改文件级增量 | — | 用户 + 端侧改造 |

**四句话**：

1. **不删任何东西，只换压缩级别，包就小 24.8%**（326.6 → 245.7 MB）。这是零风险、
   零兼容性代价的一步（端侧解码器本来就支持 -19；代价只是 CI 打包时间，多线程可控）。
2. **FFmpeg 一棵树就是半个包**（−168.3 MB / −51.5%）。它不是设计文档里估的"数十 MB"，
   因为在 Debian 13 上 ffmpeg 会拖进 LLVM（`libLLVM.so.19.1` 123 MB）、mesa/libgallium、
   flite 语音库、pocketsphinx、X11/GL/cairo/pango/SDL2 一整套。
3. **换解压器一个字节都不省**——包大小只由**压缩端**的算法与参数决定。
   解压器（Java/Rust）负责的是解压速度与容错，与体积无关。
4. **zstd 的 `--patch-from`（差分）算法有效，但端侧用不了**：官方 CLI v1.5.7 实测，
   32 MB 基线在"内容完全一致"时补丁只有 **5,298 B**（普通 -19 = 5,260,466 B），128 MB 基线 = **31,104 B**
   ⇒ 算法本身没问题；**但补丁不自包含**——解码必须同时拿到**同一份基线原文**，
   且**解码窗口要开到基线大小**（128 MB 基线 ⇒ 帧声明 128 MB 窗口，`--memory=64MB` 直接解不动）。
   即手机要为一个 480 MB 基线备好原文 + 512 MB 窗口（峰值近 1 GB）⇒ **结构性不可行**。
   "每次更新省 90% 流量"要靠**文件级增量**（清单 + 变更文件包），见 §4 C。

### 两条反直觉的实测结论（值得单独记住）

1. **node 头文件 63.5 MB 原始字节几乎不占包**（只省 0.8 MB）：它是 3,428 个纯文本头文件，
   压缩率极高，而且和别的文本高度相似。→ **删它没有收益，只伤害 `npm` 原生编译**，
   **建议保留**（此前我按字节占比估过"能省 20 MB"，实测证明是错的）。
2. **ffmpeg 的"几十 MB"是十倍的误判**：设计文档写的是"体积数十 MB，保留理由待复核"，
   实际是 **397.8 MB 安装体积 / 158.4 MB 包体积**。

### 压缩参数（同一份 tar，级别/窗口对照；全部实测）

| 配置 | 原包（1,017.1 MB 文件内容） | 瘦身包（470.6 MB 文件内容） |
|---|---|---|
| zstd 默认（级别 3，现网） | 326,606,222 B = 326.6 MB | 147,325,507 B = 147.3 MB |
| **zstd -19** | **245,658,431 B = 245.7 MB（−24.8%）** | **106,557,407 B = 106.6 MB（−27.6%）** |
| zstd -19 + `window_log 27` + LDM | 239,651,672 B = 239.7 MB（比 -19 再省 2.4%，**但解码要 128 MB 窗口**） | 102,891,194 B = 102.9 MB（比 -19 再省 3.4%，同样要 128 MB 窗口） |
| zstd -22 + `window_log 27` + LDM | —（先那次被我掐断，产物不可信，不采用） | 102,015,852 B = 102.0 MB（比 -19 再省 4.3%，同样要 128 MB 窗口） |
| xz -9e（等价对照，端侧**不支持**） | 211,110,992 B = 211.1 MB（比 -19 再省 14.1%） | **90,439,092 B = 90.4 MB（−38.6%）** |

> **`--long` / `window_log 27` 的结论：不值得**。它只再省 2.4%（原包）～4.3%（瘦身包），
> 代价是端侧解压必须分配 **128 MB 窗口**内存（低端机上就是一次 OOM 风险），
> 而手机上下载省下来的那 4 MB 远不如"别让用户在低端机上崩"重要。
>
> 说明：`xz` 只作为"压缩上限"的参照系。真要用它，Java 侧与 Rust 侧**都要**加解码分支
> （`RootfsInstaller.kt:139` 的 `Format { ZSTD, GZIP }` 只认 zstd/gzip 魔数），
> 而收益比 zstd -19 多 16.2 MB ⇒ **不推荐**（省 5% 的流量，换两端格式改造 + 解压更慢）。
>
> 结论：**zstd -19 是"免费的一半"**——不动内容、不动格式、不动端侧，直接省 24.8%。

## 4. 方案（分三阶段落地）

### 阶段 A —— 零功能取舍，可立即做（实测收益最大的一步）

1. **打包参数改为 `zstd -19 -T0`**（多线程，CI 时间可控）：**实测 326.6 → 245.7 MB（−24.8%）**，
   内容一字不改、格式不变、端侧不用改一行代码。这是全案里**性价比最高**的一步。
2. **不要开 `--long` / `window_log 27`**（实测：原包再省 2.4%、瘦身包再省 4.3%，
   代价是端侧解压要 128 MB 窗口内存）——低端机上"崩一次"比"多下 4 MB"贵得多。
3. `rootfs/build-rootfs.sh` 末尾补清理：`rm -f usr/bin/qemu-aarch64-static`
   （构建期 chroot 用的 qemu，属残留；脚本已有 `rm -rf "$ROOTFS_DIR/debootstrap"`，漏了它）、
   以及 `usr/share/gitweb`、`var/cache/debconf`、`var/log/*`。
   实测这四项合计只值 **−3.8 MB（−1.2%）** ⇒ 顺手做，别指望它省流量。
4. `usr/lib/python3.13/__pycache__`（157 个 `.pyc`）：按 node 头文件那条教训，
   字节码对包体积贡献接近零（已包含在上面那 3.8 MB 里），而删掉会让每个模块首次导入重新编译
   ⇒ **保留**。
5. 断言与门禁更新：`build-rootfs.sh:204` 的「ffmpeg 必须存在」断言**保留**（B1 已否）、
   `:211-220` 的落盘体积断言不变，**新增"包体积上限"门禁 = 280 MB**
   （`build-rootfs.sh` 打包后立即 `stat -c%s` 比对，超限即红并提示"历史最大项是 ffmpeg 那棵树"；
   基线 245.7 MB、留了约 35 MB 余量，能挡住"某个预装包又把大依赖整棵拖回来"这类回归）。

### 阶段 B1 —— 剔除 ffmpeg 整棵闭包（主杠杆）❌ **已拍板：保留 ffmpeg（2026-10-08）**

> **决定（用户 2026-10-08，原话要点）**：「ffmpeg 是 hermes agent 要用的，不然 hermes 会自己下载的，
> 更拖慢整个进度，本来 hermes 下载就慢了。」
> ⇒ **不删**。ffmpeg 留在预装清单里，`build-rootfs.sh:103` 的安装项与 `:204` 的断言都保留。
> 代价换来的价值是：Hermes 的多媒体能力（tts / vision / image_gen 等）在环境里开箱可用，
> 不会在用户侧触发"Agent 自己 apt/pip 下一整套多媒体栈"——那种下载比多下 100 MB 环境包慢得多，
> 而且会失败在用户的网络环境上。**下节内容保留为"如果哪天又要删"的施工图。**

- 收益：**326.6 MB → 151.0 MB（−51.5%）**
- 代价：环境里不再有 `ffmpeg` / `ffprobe` 命令
- 补救（按推荐顺序）：
  1. **另发一个 extras 包**（如 `extras-ffmpeg-arm64.tar.zst`，约 150 MB），需要的用户按需下载；
     这是"默认小 + 功能不丢"的正解，代价是多一条发布产物与一份安装 UI
  2. `apt-get update && apt-get install -y ffmpeg`（联网从 Debian 镜像取，落盘约 400 MB）
  3. 自编静态最小 ffmpeg（只留需要的 codec）——工作量大，暂不考虑
- 实现（若将来要执行）：`build-rootfs.sh:99-105` 去掉 `ffmpeg`；删 `:204` 断言；
  新增"闭包剔除后不得影响保留集合"的自检（本方案已提供工具，见 §6）

### 阶段 B2 —— locale 只留常用 4 种（−18.8 MB / −5.8%）

- 保留 `zh_CN`、`zh_TW`、`en`、`en_GB`（+ `locale.alias`），C.UTF-8 由 glibc 内置；
  其余 `usr/share/locale/*` 全部删掉，`usr/share/i18n`（charmaps/locales 源，15.7 MB）一并删。
- 代价：其他语言（日/韩/法/德…）不再有本地化提示文本；删了 `usr/share/i18n` 之后
  `locale-gen` 无法再生成新语言（当前已按 4 种语言预生成，够用）。
- 若想更保守：只删 `usr/share/locale`，保留 `usr/share/i18n`（少省约 5 MB）——**不推荐**，
  因为 `usr/share/i18n` 里绝大多数内容（charmaps 各语言）本来就是浪费。

### 阶段 C —— 增量下发（真正解决"每次更新都重下 300 MB"）

**先给一个否定结论：zstd 的 `--patch-from` 在这份包上走不通（已实测）。**

- **实测（用官方 zstd CLI v1.5.7，不是 python 绑定）**：
  1. 32 MB 基线、新包与基线**内容完全一致** → `--patch-from` 补丁 **5,298 B**
     （同一份内容的普通 `-19` 是 5,260,466 B）；128 MB 基线同样条件 → **31,104 B**。
     ⇒ **算法本身完全有效**（差三个数量级）。
  2. 但补丁**不是自包含的**：解码必须让**同一份基线原文**参与
     （`zstd -d --patch-from=<基线> -o out patch.zst`；不加基线直接解 → `Decoding error (36) : Data corruption detected`），
     并且**解码窗口必须开到基线大小**：128 MB 基线的补丁帧声明窗口 128 MB，
     `--memory=64MB` 解码报 `Window size larger than maximum : 134217728 > 67108864 /
     Use --long=27 or --memory=128MB`；放宽到 `--memory=256MB` 才解码成功，
     产物与原文件**逐字节一致** ✓。
  3. ⇒ 端侧代价 = **基线原文（480 MB，且必须是"上一版未压缩的 tar"）+ 解码窗口（512 MB）**，
     峰值近 1 GB。而 App 手里只有**已安装的 rootfs**（uid/gid/mtime/成员顺序都变了），
     想在端上重建出逐字节相同的 tar 不可靠 ⇒ **结构性不可行**，不是"参数没调对"。
- **一次自我更正（值得记下）**：我最初用 python-zstandard 的 `dict_data`（raw-content dictionary）
  当 `--patch-from` 的等价物，得到"零变化也压不出小补丁"（480 MB 基线：147,326,517 B ≈ 无字典的
  147,325,507 B），据此写过"窗口覆盖不了基线"的结论。**那是错的**：python 绑定的 `dict_data`
  与 CLI 的 `--patch-from` 语义不等价——32 MB 切片上即便给到 `window_log 25` + LDM 也只省约 3%
  （6,933,160 / 6,828,969 B vs 无字典 7,060,109 B），而 CLI 在同样条件下是 1000 倍。
  **判据以 CLI 为准**，本节数字全部来自 CLI 实测。
- 结论没变，但理由更硬：**差分不是"算法问题"，是"内存 + 基线副本"问题**。基线越大越不可行。

**推荐形态：文件级增量**（不依赖任何大窗口）

1. CI 每版多产出两件资产：
   - `manifest`：每行 `sha256 \t size \t path`；
   - **只含变更文件**的补丁包 `patch-<old>-<new>.tar.zst`。
2. 清单开销实测（瘦身包口径）：10,399 个文件、9,475 种唯一内容，清单原文 1.24 MB，
   **zstd-19 后 441,331 B = 0.44 MB** ⇒ 每版额外下载不到半兆。
3. 端侧拿**已经装好的 rootfs** 当基线（不必额外留一份旧 tar）：按清单逐文件比
   `sha256`，未变的原地复用、变的从补丁包取、本地缺的或校验不过的**回退全量下载**。
4. 为什么它比 patch-from 强：
   - 只按**内容 sha256** 判定 ⇒ mtime / 权限扰动不会造成"全量重下"（重建环境免疫）；
   - 不需要基线副本（省 480 MB 存储，也不需要 480 MB 内存窗口）；
   - 失败可回退，清单即校验依据，不像差分帧"错一个字节全废"。
5. 代价：要设计"包版本 + 清单 + 补丁包 + 回退"整条链路，App 与 CI 都要改；
   但它是唯一能把"老用户更新一次"从 100+ MB 降到几 MB 的办法。

> 附注：zstd 的 dictionary 解码 Java 侧（`commons-compress` 的 `ZstdCompressorInputStream`）
> 本来就不支持，这条能力只在 Rust 侧有——**但既然 patch-from 已被实测否掉，
> 这条路就不必再走了**（与 §8 的排序相应下调）。

## 8. 往 Rust 方向的进化（第二问）

### 8.1 现状：已经做对的部分

- 单一 `libzhengdao_core.so`（入库 808,704 B），三个模块：
  `sha256.rs`（纯逻辑）、`extract.rs`（SHA 流式校验 → zstd/gzip 解压 → tar 落盘）、
  `jni_bridge.rs`（仅 android，两个符号，JSON 出参 + 限频进度回调）。
- 六条 JNI 规范已固化：错误不跨 FFI panic（`catch_unwind`）/ Kotlin 侧永远有平台回退 /
  proguard keep / `.so` 入库 CI 免装 Rust / 不用 cargo-ndk 直配 NDK clang /
  逻辑层与 JNI 薄层分离（PC 可 `cargo test`，现 8 例，已进 `ci.yml`）。
- 16KB 页对齐门禁（每个 LOAD 段 `p_align ≥ 0x4000`）+ **静默降级靠 readelf 验收**
  （因为回退纪律让"加载失败"表现为"Rust 路径永远不执行"，跑起来不崩）。
- 体检第 10 项把 native 层的可用性显示出来（⚠ 而非 ✗），降级可见。

### 8.2 收益模型的铁律（所有"要不要用 Rust 重写"的判断都从这条出发）

> **瓶颈在 JNI 边界，不在算法。**
> 真机实测：sha256 无论开不开 asm，Rust/JNI 都比平台 `MessageDigest` 慢约 5 倍
> （10 MB 数组拷进 native + hex 字符串封送回 JVM）；解压 Rust 3611 ms vs Java 3668 ms（<2%）。
> ⇒ 划算的形态只有一种：**整条流水线一次跨边界、数据常驻 native**。

### 8.3 下一步候选（"一次跨边界"是硬门槛；Rust 契合度与用户收益分开看）

| 用户/项目收益 | 候选 | 为什么值得 | Rust 契合度 | 代价/风险 |
|---|---|---|---|---|
| ★★★ | **文件级增量下发**（阶段 C：清单 + 变更文件包 + 回退） | 更新一次从 100+ MB 降到"变更文件 + 0.44 MB 清单" | 低（Java 就能做：比对 sha256 / 重组 / 解包）——只有把"比对→重组→解包"合成一条 native 流水线时才需要 | 协议 + 回退设计；要真机对拍 |
| ★★☆ | **下载 → 校验 → 解包 一条流水线** | 现在是"OkHttp 落盘（Java）→ 再读一遍解包（Rust）"，两趟 IO、两份 SHA、两次跨边界 | **高**（正是"整条流水线一次跨边界"的标准形态） | 网络栈搬进 native（TLS/代理/重定向/DNS 行为必须与现在的 OkHttp 一致）——**取舍要先谈清楚** |
| ★★☆ | 解包路径继续加固（symlink 越界、路径穿越、稀疏文件等 `core/README.md` 列的 v2.0 候选项） | 正确性收益，风险低，且解包本来就在 native | **高** | 要同步改 Kotlin 版语义并保留对拍 |
| ★☆☆ | 清单/补丁包生成（CI 侧） | 让 CI 产出 §4 C 需要的两件资产 | 低（CI 脚本用 python/shell 更省事） | 与端侧同一套哈希口径即可 |
| ✗ | ~~zstd `--patch-from` 差分帧~~ | **实测否掉**（窗口覆盖不了基线，见 §4 C） | — | — |
| ✗ | 单函数下沉（sha256、小文件 IO） | — | — | 铁律已证必亏，**不要做** |
| ✗ | 端侧压缩、换压缩算法 | — | — | 体积由压缩端决定；端侧换算法还要两端同步改格式 |

### 8.4 落地纪律（沿用现有规范，不改）

1. 只下沉"整条流水线"，不下沉"单个函数"
2. 任何 native 路径必须有平台回退，回退必须能在**体检**里看见
3. `.so` 入库、CI 免装 Rust；逻辑层保持 PC 可测（`cargo test`，现已进 `ci.yml`）
4. 16KB 页对齐是发布门禁，靠 `llvm-readelf` 验收，不靠"跑起来没崩"
5. 每次下沉都要有**同口径真机对拍**（同一份输入、同一份输出、逐条比对）
