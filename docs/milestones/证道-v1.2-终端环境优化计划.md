且顺带查出两个更根本的问题。

**① 真实进程环境（不是调试脚本）**——`run-as` 读 `/proc/<serve_pid>/environ`：

```
PATH=/system/bin                     ← 宿主 bionic，非 Debian
NO_PROXY=localhost,127.0.0.1,::1     ✅   no_proxy=...  ✅
BUN_FEATURE_FLAG_DISABLE_IPV6=1      ✅

```

同时 `/proc/<pid>/mounts` 显示其根是 `dm-15 / erofs`（Android 宿主根），  
父进程是 **App 自己**（`com.example.zhengdao`）而非 proot。  
⇒ **太极的 serve 跑在宿主 bionic 上，根本不读 rootfs 的 `/etc/hosts`。**  
hosts 钉住只对 **PRoot guest 内**的进程有效；而终端里的 opencode 在阶段 1 已卸载，  
所以**这项钉住对当前产品的实际收益 ≈ 0**。

**② curl 拆解（guest 内，`%{remote_ip}` 已确认直连、无中间代理）**

| 阶段                               | 钉住 `.21`             | 未钉住（DNS 选 `.23`）           | 结论                                     |
| -------------------------------- | -------------------- | -------------------------- | -------------------------------------- |
| `time_namelookup`                | 0.006–0.007 s        | 0.015–0.030 s（冷启最高 0.43 s） | **DNS 确实快了**，但只有 8–25 ms（冷启最多 ~420 ms） |
| `time_connect` − dns（真实 TCP RTT） | ~3 ms                | ~3 ms                      | **完全没变**                               |
| `time_appconnect` − tcp（TLS 握手）  | ~1.73 s              | ~1.69–1.74 s               | **完全没变**，且是耗时主体                        |
| `time_total`                     | 2.86 / 2.97 / 5.47 s | 2.96 / 3.16 / 3.72 s       | 区间重叠，**无显著改善**                         |

- 对照组 `https://www.baidu.com`：total **0.31 s**、TLS 0.26 s ⇒ 那 1.7 s 是**到 Cloudflare 的跨境  
  RTT**，不是 DNS 能优化掉的。
- 钉的 `.21` 与 DNS 自选的 `.23` **同属 `172.65.90.0/24`**，TLS 耗时相同 ⇒  
  「钉错节点导致路绕远」在本机**未发生**（但仍是长期隐患）。
- **连接复用时 DNS 成本归零**：同进程第二次请求 `dns=0.000 tcp=0.000 tls=0.000 total=0.951 s`  
  （首次 2.98 s）。⇒ 长连接客户端（如 serve 的 keep-alive）只在**第一次**请求受益。

**③ `resolv.conf` 的 `rotate` 到底该不该留？**（交替对照，各 12 次 `getent`）

|              | 中位数     | 最大值                                                   |
| ------------ | ------- | ----------------------------------------------------- |
| `rotate`（现状） | ~106 ms | **1110 ms**（随机落到国际 NS 后 `timeout:1 × attempts:3` 才回退） |
| 去掉 `rotate`  | ~110 ms | 124 ms                                                |

⇒ **中位数无差异（噪声内），但尾部明显更紧**。样本量小（12×2），  
可作为「可选优化」而非结论；已恢复原状待用户定夺。

**结论：本次只降低了 DNS 解析延迟，没有降低网络延迟。**  
端到端耗时由 TLS 握手 + 跨境 RTT 主导（~1.7 s），DNS 只占 ~1%。

### 阶段 2.6（追加）：撤除 opencode.ai 的 IP 钉住（用户 2026-10-07 拍板）

**决策：撤。** 依据三条，按权重：

1. **收益趋近于零**
   - 太极 serve 跑宿主 bionic，不读 rootfs 的 `/etc/hosts` → 对主产品**完全无效**；
   - 终端 opencode 阶段 1 已卸载 → 对 guest 也**没有当前用户**；
   - 即便 guest 里有进程，也只省**首次请求 8–25 ms**（连接复用后 DNS 成本归零）；
   - 端到端由 TLS + 跨境 RTT（~1.7 s）主导，DNS 占 ~1%。
2. **风险是硬故障，不是性能波动**  
   IP 轮换 = **直接连不上**，不是"慢一点"。Cloudflare 的 `172.65.90.0/24` 段何时换、  
   换到哪个段，不可控、不可预测、不可自愈。用零收益换硬故障风险，不划算。
3. **保留的三项零风险且有效**  
   遥测 `0.0.0.0` 屏蔽（不依赖外部 IP、不会轮换）、`NO_PROXY`/`no_proxy`（环境变量层旁路）、  
   `BUN_FEATURE_FLAG_DISABLE_IPV6=1`（Bun 行为修正，非网络硬编码）。

**落地（三处一并清）**

| 位置                            | 处理                                                              |
| ----------------------------- | --------------------------------------------------------------- |
| `rootfs/build-rootfs.sh` §2.7 | 删掉 `echo '172.65.90.21 opencode.ai' >> /etc/hosts`，并把"为什么撤"写进注释 |

抽出的纯函数 `EnvSelfHeal.stripObsoletePins(text)` + 单测 `EnvSelfHealTest`

**未来 guest 里真需要优化 DNS 的正确方向**（不是 hosts 钉 IP）：
