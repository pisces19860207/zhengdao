## 0. 一句话

**全局只有一条 tmux 会话；点同一个 Agent 就接回去，点别的（或点安装）就把这整条换掉。**

```
decide(本次带命令? 本次是"启动"?, 本次属谁的, 当前会话里是谁, 会话还在?)
  ├─ 没带命令           → KEEP_SESSION    （洞天 / 通知栏 / 「安装中」入口：会话原样不动）
  ├─ 同一个 Agent 且会话还在 → ATTACH_CURRENT（不重启、不新增、不注入）
  └─ 其余一切           → REPLACE_SESSION （整条 kill 掉再起一条新的）
```

决策函数是**纯逻辑**：`terminal/SessionRouter.kt`（`SessionRouter.decide`），
决策表由 `app/src/test/java/com/example/zhengdao/terminal/SessionRouterTest.kt` 逐格钉住（11 条用例）。
`TerminalActivity.routeSessionIfNeeded()` 只负责把决策落到会话上。

## 1. 状态定义

| 状态 | 位置 | 说明 |
|---|---|---|
| `currentAgentId: String?` | `SessionManager`（唯一真相源） | 这条会话里跑的是谁。`null` = 裸 bash / 不适用 |
| 落盘副本 | `zhengdao-session` prefs 的 `current_agent` | **进程被杀时唯一能活下来的东西**，用于"回来还是它"（见 §5） |
| tmux 会话名 | `SessionManager.TMUX_SESSION = "zhengdao"`（常量，不做参数化） | 终端里 `tmux ls` 永远只该有一行 |
| 分屏 | tmux **pane**（`C-b "` 上下分） | 同一会话内的两块，**不是两个会话、不是两个窗口** |

**不再需要**"同名进程有几个"这种计数——单会话下不可能并存，要判断的只是"这条会话里是谁"。

## 2. 为什么换方向（多窗口 → 单会话）

旧实现是**多窗口并存**：每点一次「启动」就 `C-b c` 开一个**新窗口**再注入命令，
再用「扫 `/proc` 数同名进程」+「20 秒启动窗口守卫」来压重复实例。
用户 2026-10-07 判定：**方向反了**。

- 旧方向把问题当成"**怎么管住好几个实例**"，于是要判重、要守卫、要窗口列表；
- 实际需要的是"**根本不存在并存**"——手机上一条 tmux 会话已经占满一屏，
  并存只会让用户在两份东西之间来回找（实测窗口积到 `5:bash`，用户不知道安装跑在哪一屏）。

改成单会话后，"判重"这件事**自然消失**：旧的已经被 kill，不可能有两个。

## 3. 实现落点

| 动作 | 位置 |
|---|---|
| 决策 | `terminal/SessionRouter.kt` |
| 应用决策 | `TerminalActivity.routeSessionIfNeeded()` |
| 新请求的读取 | `TerminalActivity.readRequestFromIntent()`（`onCreate` 与 `onNewIntent` 共用） |
| killCurrentSession | `SessionManager.kill()`（连带清 `currentAgentId`） |
| startNewSession | `SessionManager.start()`（**不**清 `currentAgentId`——调用方已登记好） |
| 命令注入 | `TerminalActivity.injectPendingAutocmd()`（写**当前 pane**，不开新窗口） |
| 崩溃/被杀后的接回 | `TerminalActivity.restoreLastAgentIfAny()` |

### 两处容易看错、但必须这个方向的地方

1. **`SessionManager.start()` 内部调 `killInternal(clearAgent = false)`**
   ——`start()` 的语义是"给**当前** Agent 起一条干净会话"，调用方已经登记过 id 了，
   这里再清一次会让"杀 App 再开"找不到人。`kill()` 会清、`start()` 不会清，是刻意的。
2. **`SessionManager.hasSession()` 而不是 `isAlive()`**
   ——Termux 引擎的 `isRunning` 在进程 spawn **之前**是 false。
   `onNewIntent`（复用实例）会立刻走一遍 attach，紧接着 `onResume` 又走一遍；
   只认 `isAlive` 会把刚建好的会话判成"没有会话"，于是 kill 一遍重来
   ——同一句启动命令被注入两次、正要启动的 Agent 被自己的第二次启动顶掉。

## 4. 删掉了什么

- `TerminalActivity.countProcesses()`（扫 `/proc` 数同名进程）
- `TerminalActivity.Companion.recentLaunches` + `launchGuardMs`（20 秒"启动中"窗口守卫）
- `injectPendingAutocmd()` 里的启动幂等守卫块
- 所有走 `C-b c` 开新窗口的注入路径（v1.3 早期已改，本次确认无残留）

> ⚠️ **别把 `AgentRepository.installProcessAlive()` 一起删了**：它也扫 `/proc`，
> 但问的是**另一个问题**——"安装这个长任务还有没有在跑"（安装器在非 TTY 下不输出，
> 没有别的信号可用）。终端侧的进程计数是"判重"，安装侧的是"判活"，不是一回事。

## 5. 「回来还是它」的两种情况（**必须分开说**）

| 情况 | tmux 还在吗 | 怎么回来 | 上下文还在吗 |
|---|---|---|---|
| 切后台 / 关页面 / 断线重连 | **在**（进程没死） | 真 attach：同一个 pty、同一块画面 | **在** |
| **App 进程被杀**（用户杀、系统回收） | **不在**（proot 与 tmux 都是 App 的子进程） | 重新执行该 Agent 的 `launchCmd` | **不在** |

第二行以前被写成"tmux 兜底"，是错的（见 `ERRATA.md` E-018）。
现在的实现是**重放启动命令**：落盘的 `current_agent` 还在 → 新会话起来且本次请求不带命令时，
自动再跑一遍。用户观感与"接回来"一致，但不能承诺对话上下文保留。

## 7. 本次一并踩到、值得记住的三个坑

### 7.1 Compose 看不见 `AgentRepository` 的状态（卡片"要手抖一下才刷新"）

`AgentRepository.stateOf()` 的输入是 **SharedPreferences + `/proc`**，对 Compose 不可见；
而卡片的按钮形态（安装 / 安装中 / 启动）全靠它。旧代码的"5 秒轮询"重新赋值 `agents`，
指望它带出重组——**没用**：`AgentInfo` 是 data class，前后内容相等 ⇒ `mutableStateOf`
判定"没变" ⇒ 不重组。真机症状：点完「安装」回到丹房，卡片仍写着「安装」，
**切一下 tab 才变「安装中」**。

修法第一版：把 `stateOf` 的结果灌进 `mutableStateMapOf`（对 Compose 可见的镜像），
卡片读镜像（第一次组合时镜像还没灌，退回实时查一次）。

**第一版不够，第二版才是对的**（2026-10-07 二次实测）：

镜像灌进 snapshot **只是必要条件**——还得有人**按节拍去灌**。第一版写成条件式轮询：

```kotlin
LaunchedEffect(agents, stateTick) {
    agents.forEach { installStates[it.id] = AgentRepository.stateOf(context, it) }
    if (installStates.values.any { it == Installing }) { delay(2000); stateTick++ }  // ← 缺口在这
}
```

缺口是：**条件式轮询需要有东西先把它叫醒**。而"点了「安装」"在 Compose 眼里什么都没发生
——没有 state 变化 ⇒ 不重组 ⇒ `LaunchedEffect` 的 key 不变 ⇒ effect 不重启 ⇒
**连第一轮都没跑起来**，镜像永远是空/旧值。旧版之所以看起来"有时能刷新"，
正是切 tab 把整个 `HomeScreen` 拆掉重建、歪打正着跑了第一轮。
这就是用户那句"**要手抖一下才刷新**"的病因，也解释了为什么它像"偶发"。

第二版改成**常驻循环**，外加 `ON_RESUME` 时立刻重灌一次（不等 2 秒）：

```kotlin
LaunchedEffect(agents, stateTick) {          // 进页面先读一次
    while (true) {
        agents.forEach { installStates[it.id] = AgentRepository.stateOf(context, it) }
        delay(2000)
    }
}
```

开销：一次读 = SharedPreferences（内存缓存）+ 几个 `File.exists()`，只有"安装中"才多扫一次
`/proc`。半赫兹，且只在丹房 tab 处于组合时跑，可忽略。

> 教训：**轮询的"条件"不能依赖它本要去发现的那个变化**。
> 触发器本身就是被观测对象时，就会形成死锁式的静默——状态永远停在旧值，还不报错。

#### 这一条怎么在**不装 326MB 环境**的前提下真机验证（可复用）

`AgentRepository.stateOf()` 判「失败」靠读一个文件：`files/home/.zhengdao/install-<id>.rc`
（guest 侧 `/root/.zhengdao/…`）。这个文件**能从宿主侧直接造**，于是不需要真跑安装：

```bash
# 1) 停在丹房页，dump 一次基线（Claude 卡片只有名字+描述）
# 2) 造结局文件（id 是 claude-code，不是 claude！见 AppState.factoryAgents）
echo 1 | MSYS_NO_PATHCONV=1 adb shell run-as com.example.zhengdao \
    tee files/home/.zhengdao/install-claude-code.rc
# 3) 手不动手机，等 5 秒，再 dump
```

实测结果（2026-10-07 23:03–23:05）：

- 基线：Claude 卡片无状态行。
- 写入 rc 后静置：卡片自己多出红字「上次安装失败（退出码 1）。终端往上翻就是原因；点「安装」可重试。」，
  下方三张卡片整体下移（y 从 1765 → 1961）。
- 删掉 rc 再静置：红字自己消失、布局回位。

**全程没有触屏、没有切 tab、没有生命周期事件** ⇒ 只可能是常驻轮询在刷新。
这一轮还顺带验了卡片按钮的 `envReady` 守卫：`failedInstall` 为真但环境未装时，
按钮仍是「先装环境」而不是点了只会报错的「重试安装」。

> 教训：**判据落在文件上，就等于给了自己一个可控的测试把手**。
> 遇到"要真跑一遍长任务才能验"的 UI 状态，先问一句：它的判据能不能被单独构造出来。

> 教训：**"状态放哪"决定它能不能驱动 UI**。放在 prefs / `/proc` 里的东西，
> 必须有人把它搬进 snapshot 状态，否则 UI 永远不会自己跟上。

### 7.2 长命令的 `echo` 会把整屏糊掉

hermes 的 uv 包装器是 1.5KB base64，原先写在注入命令里 `echo … | base64 -d > …/uv`。
bash 会**回显整行** ⇒ 点一次「安装」先糊满一屏 base64，用户看不到任何进度。
改到宿主侧落盘（`filesDir/home` ⇄ guest `/root` 同一个 bind），终端里只留可读输出。
（用户报的"hermes 安装有问题"里最直观的一条。）

### 7.3 「安装中」按钮不能杀掉安装

丹房点「安装中」是 `onOpenTerminal(null, agentId)`——**不带命令**，
决策表里对应 `KEEP_SESSION`。若它落到 `REPLACE_SESSION`，
用户只是想看一眼进度，就会把正在跑的安装整条杀掉。
`readRequestFromIntent()` 里"`agent_id` 只在带命令时才算一次请求"就是为这个。
