# 证道 · 环境包增量下发协议（v1，2026-10-08）

> 目的：把"每次更新环境都重下 200+ MB"降到"只下变更文件"。
> 背景与实测取证见 `docs/milestones/证道-环境包瘦身与压缩方案-2026-10-08.md` §4 C
> （其中已实测否掉 zstd `--patch-from`：补丁不自包含 + 解码窗口须等于基线大小）。
>
> 本文件是 **CI 侧（`tools/rootfs-manifest.py`）与 App 侧（`rootfs/RootfsDelta.kt`）共同遵守的格式契约**。
> 任何一侧改动格式，必须同时改这里与另一侧。

---

## 0. 三个概念

| 名字 | 是什么 | 谁产生 |
|---|---|---|
| **清单**（manifest） | 一棵 rootfs 树里**每个文件/软链/目录**的类型、权限、大小、SHA256 | CI（从构建出的树直接生成） |
| **env id** | 一棵树的内容指纹，16 位十六进制。**与 mtime 无关**，内容一样就是同一个 id | CI（对清单正文求哈希） |
| **补丁包**（patch） | 只含"从 env A 到 env B 变了的文件"的 tar.zst，内含删除清单 | CI（对比上一版的清单得到） |

**端侧不需要下载清单**：补丁包 + "我装的是哪个 env"（标记文件）就够。
清单资产是给 **CI 自己下一次算差分**用的（也是将来"环境体检"的校验依据）。

---

## 1. env id

```
env = sha256( 清单正文（去掉所有以 '#' 开头的行）以 LF 连接、末尾 LF )[0:16]
```

- 逐行按字节比较，行序固定（见 §2 排序规则），因此**同样的树 → 同样的 env**，重建（mtime 变化）不影响。
- 清单文件头里的 `# env=` 只是**缓存**，权威算法是上面这条；CI 两侧都重算，不信任头里的值。

## 2. 清单格式（`rootfs-manifest.txt`）

UTF-8、LF 换行、**按 path 的字节序升序**排序。前若干行是注释头，其余每行一条：

```
# zhengdao-rootfs-manifest v1
# env=<16 hex>
# distro=debian-13.7
f	0644	12345	<sha256(64 hex)>	./usr/bin/node
d	0755	0	-	./usr/share/doc
l	0777	0	./usr/bin/node	./usr/bin/nodejs
```

字段顺序 = `type \t mode(八进制) \t size \t digest \t path`：

| type | 含义 | mode | size | digest |
|---|---|---|---|---|
| `f` | 普通文件 | 权限位（如 `0644`） | 字节数 | 内容 SHA256 |
| `d` | 目录 | 权限位 | `0` | `-` |
| `l` | 符号链接 | `0777`（tar 惯例） | `0` | **链接目标**（不是哈希） |

- path 一律以 `./` 开头（与包内 tar 的成员名一致），不含尾随 `/`（目录也不含）。
- 正文行内**不出现制表符以外的空白**；path 里若含制表符或换行，CI 侧直接**报错退出**（宁可没有清单，也不要一份会错位的清单）。
- 大小写：digest 小写十六进制。

## 3. 补丁包（`rootfs-patch-<baseEnv>-to-<newEnv>.tar.zst`）

一个普通 tar.zst，成员名与**完整包完全同构**（`./usr/bin/foo` 这种），因此 App 侧复用同一套解包代码：

1. 第一个成员固定是 `./.zhengdao-patch-info`（**不是树里的文件，App 不落地它**），内容：

```
zhengdao-patch v1
base=<baseEnv>
new=<newEnv>
deletes=<n>
<相对 path 1>          ← 无 ./ 前缀，一行一个；n=0 时此段为空
<相对 path 2>
```

2. 其余成员 = **变更文件**，判定规则（对清单逐行比较）：

| 情况 | 是否进补丁 |
|---|---|
| 新树有、旧树没有 | ✅ |
| 类型变了（f↔l↔d） | ✅ |
| mode 变了 | ✅ |
| `f` 的内容 SHA256 变了 | ✅ |
| `l` 的链接目标变了 | ✅ |
| 其余（完全一致） | ❌ 不进（端侧原地保留） |

3. **删除清单**（`deletes`）= 旧清单里有、新清单里**没有**的 path（目录也算，App 侧按递归删）。

## 4. 索引（`rootfs-index.json`）

App 唯一需要读的入口。放在**滚动版 Release `latest`** 的资产里
（`https://github.com/<owner>/<repo>/releases/download/latest/rootfs-index.json`，`withMirrorFallback` 可加 gh-proxy 兜底）。
**不再依赖 `raw.githubusercontent.com/.../rootfs/manifest.json`**（那是"仓库里没人更新的死文件"，见 ERRATA E-033）。

```json
{
  "schema": 2,
  "distro": "debian-13.7",
  "version": "13.7",
  "env": "8f3c1a2b9d4e5f60",
  "builtAt": "2026-10-08T06:12:00Z",
  "url": "https://github.com/pisces19860207/zhengdao/releases/download/latest/debian-13.7-base-arm64.tar.zst",
  "sha256": "<完整包 sha256>",
  "size": 217000000,
  "manifestUrl": "https://github.com/pisces19860207/zhengdao/releases/download/latest/rootfs-manifest.txt",
  "patch": {
    "from": "1a2b3c4d5e6f7081",
    "url": "https://github.com/pisces19860207/zhengdao/releases/download/latest/rootfs-patch-1a2b3c4d5e6f7081-to-8f3c1a2b9d4e5f60.tar.zst",
    "sha256": "<补丁 sha256>",
    "size": 3145728
  }
}
```

- `patch` 可以为 `null` / 缺省（没有上一版清单时的首次构建）。
- 老 App（v1.3.0 及以前）读的是 `rootfs/manifest.json`（只有 `version/url/sha256`）——
  那份文件**保持原样不动**，新 App 也不再读它（`RootfsCache.MANIFEST_URL` 改指索引，旧地址降级为兜底）。

## 5. 端侧标记文件（`<filesDir>/rootfs/.zhengdao-rootfs-ok`）

`ProotLauncher` 只判断"存在与否"；增量要再加两行（旧安装没有 `env=` ⇒ **第一次更新走全量**，之后才有增量）：

```
distro=debian-13.7
env=8f3c1a2b9d4e5f60
installed-by=zhengdao
installed-at=2026-10-08T14:20:00+08:00
```

## 6. 端侧应用算法（`RootfsDelta.apply`）

```
前置：标记里的 env == 补丁的 from（否则不做增量，直接全量）
1. 建 rootfs.tmp/：把当前 rootfs/ 树整棵搬过去（同内容文件优先硬链接，失败退复制；软链重建软链）
2. 解补丁包到 rootfs.tmp/（复用 RootfsInstaller 的解包代码；跳过 .zhengdao-patch-info）
3. 按删除清单递归删 rootfs.tmp/ 里的 path（仍然受"路径必须在 tmp 内"约束）
4. 写标记（新 env），原子替换：删旧 rootfs/ → rename tmp（失败退复制）
5. 任何一步抛错 → 调用方**回退全量下载**（RootfsInstaller.install）
```

- **不做"全树逐文件校验"**：补丁资产本身有 SHA256 边车；`from` 匹配保证基线正确。
  用户本地跑过 `apt upgrade` / 装过 Agent 造成的漂移，表现为"补丁没碰的文件保持本地版本"——
  这是**有意为之**（否则每次更新都会把用户装的东西删回去）。
- 增量路径的存储需求 ≈ 当前树的体积（临时多一份）+ 补丁体积；峰值与全量解压同级，无需新增门槛。

## 7. CI 侧产出（`rootfs/build-rootfs.sh` + `tools/rootfs-manifest.py`）

| 资产 | 何时产出 |
|---|---|
| `debian-13.7-base-arm64.tar.zst`（+`.sha256`） | 每次重建 |
| `rootfs-manifest.txt`（+`.sha256`） | 每次重建 |
| `rootfs-patch-<base>-to-<new>.tar.zst`（+`.sha256`） | 拿得到上一版清单时 |
| `rootfs-index.json` | 每次重建 |

上一版清单从 `latest` 的资产里取（工作流在构建前 `curl` 到 `rootfs-base/rootfs-manifest.txt`，
取不到就只产全量包 + 清单 + 索引，**不产补丁**，构建不因此失败）。

正式 tag 的 Release 也**同步一份**滚动版的 rootfs 资产（历史 tag 只有 APK，
导致"差分包无从累积"——见方案 §7-3；同步是"下载 latest 资产再上传到 tag"，不重跑构建）。
