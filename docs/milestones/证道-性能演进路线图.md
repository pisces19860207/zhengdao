## 0. 可行性评估结论（2026-10-06）

**总体方向正确，但候选设定需重大修正**（同日代码实况核查，详见 §5.7 与 `证道-Rust改造可行性裁定.md`）。

✅ **对的部分**：数据驱动、渐进式、设高门槛（Rust 仅在实测确认瓶颈后触发）的方法论，与证道"真机验证优先"的纪律一致。

❌ **需修正的核心**：旧版把 **SHA256（`MessageDigest`）与 RootFS 解压（`zstd-jni`）** 列为 Rust 迁移候选并评估为"中严重度"，但代码核查证明——**这两个本来就已经是 C / 原生实现，不在 Kotlin 里跑**，且 SHA256 是 **I/O bound**（读盘速度）而非 CPU 瓶颈。**迁移无收益**。当前唯一值得考虑 Rust 的候选是 **PTY 数据搬运的 JNI 往返**（且需先有 Perfetto 数据支撑）。

**修正后的行动结论**：v1.0 只诊断不动刀，**不要启动 SHA256 PoC**；引入 Rust 的决策推迟到 v1.0 诊断数据出来之后。

## 4. Rust 迁移触发条件

> ⚠️ **2026-06 裁定：下表中 SHA256 / 下载引擎 / 解压引擎三行已作废**——它们都**不是 CPU 热点**（SHA256 与 zstd 本就是C/原生实现，下载是网络 bound），迁Rust 无收益。详见 §5.7。

| 模块 | 触发条件（须实测） | 裁定状态 |
|---|---|---|
| **PTY 数据搬运 JNI 往返** | Perfetto trace 证明大输出时 JNI 往返占比显著（如 > 10% 帧时间） | ✅ **当前唯一有效候选** |
| 下载引擎 | 下载速度 < 网络带宽 50% | ❌ 作废——网络 bound，非 CPU 瓶颈。优化走**多连接分块并发（纯 Kotlin）** |
| 解压引擎 | RootFS 解压 > 60s，或解压期间 UI 卡顿 > 3s | ❌ 作废——zstd 已是 C。优化走"**减少解压量**" |
| OpenCode 进程管理 | **持续**内存 > 4GB且无法靠配置优化，或被 LMK 频繁杀 | ❌ 第三方 TS/Bun，Rust 只能量化进程生命周期，改不了它自身内存 |
| SHA256 校验 | ~~1.5GB 文件校验 > 15s~~ | ❌ **作废**——`MessageDigest` 已原生，且 SHA256 是 **I/O bound**，改Rust 无收益 |

> **通用门槛（五者同时满足才启动评估）**：① 实测确认为**CPU** 热点（不是 I/O、不是网络、不是内存分配）；② 该模块是**自研代码**（非第三方、非已是 C 实现）；③ Kotlin 层优化已穷尽；④ 预期收益 ≥ 30%；⑤ JNI 桥接复杂度可控。
>
> **另需先满足的工程前提**：NDK 升级到 r28+（当前项目是 r27，见 §5.7）。~~ABI 双架构各自验证 16KB~~ —— **已不适用**：2026-10-06 用户定案砍掉 x86_64，**单arm64 架构**，16KB 只需验一套，Rust 交叉编译也只需一个目标。

## 5. 评估注记（需补强 / 修正，供 zcode 注意）

1. **PRoot 是最大瓶颈却不在迁移列表**——proot 是第三方 C 二进制，证道无法 Rust 重写。但它是 🔴 高瓶颈（ptrace 44% I/O 下降）。路线图须明确：该瓶颈**只能靠替代方案规避**（如评估 unprivileged userns / bubblewrap / 真 root），或功能上接受。本路线图不把它列为 Rust 目标，但单列"结构性瓶颈，待专项评估"。
2. **OpenCode 内存是第三方限制，Rust 只能治标**——证道只能管进程生命周期（监控/重启/提示释放），降不了 OpenCode 自身内存。v1.x 的"资源监控+超阈值提示"是主要手段，Rust 迁移仅强化进程管理，非根治。
3. ~~**targetSdk 28 对现代性能工具链的兼容性需确认**~~ —— **该归因错误，已撤销**（2026-10-06 审核）：Macrobenchmark / Baseline Profile / Perfetto 是**构建期工具，取决于 AGP 版本与 minSdk，与 targetSdk 无关**。且 targetSdk 28 意味着**更少**的行为变更（API 29+ 兼容性开关不生效），对混淆与基线 profiling 反而友好，"支持度有限、收益打折"不成立。**真正需确认的是 AGP 版本**：`androidx.benchmark` 宏基准需 **AGP 8.0+**；请先核对项目当前 AGP 版本能否在 targetSdk 28 + Compose ~~+ Hilt~~ 组合下正常跑起基准。（⚠️ **项目并没有 Hilt**：`app/build.gradle.kts` 无 `hilt` / `dagger` 依赖，原文的"Hilt 组合"是想象的）
4. **关键数字标注为"假设值，待实测"**——44% I/O 下降、3.5GB 峰值、P99 94μs JNI 延迟等均引用自外部，**v1.0 必须重测**，数据以 ~~`docs/performance-baseline.md`~~ → **`docs/acceptance/compose-perf-baseline.md`** 为准（**原文路径不存在**），不得直接当事实写进代码注释。
5. **§5.1 "APK 体积可减少 52%" 存疑**——该句与"Rust 编译产物 1-3MB"自相矛盾：引入 Rust `.so` 只会增体积，除非替换了原本很大的 Kotlin/Java 依赖（计划书 Rust 仅覆盖 3 个小模块，不足以减 52%）。**该数字待 v1.x 实测澄清，勿轻信。**

**核查发现三个根本性事实，推翻旧计划的候选设定**：

| 事实 | 证据 | 后果 |
|---|---|---|
| ~~项目**当前零 Rust 代码**~~ → **❌ 已被推翻（2026-10-07）** | ~~`find . -name "*.rs"` / `Cargo.toml` 无结果~~ → **实际有**：`rust/Cargo.toml`（workspace，成员 `sha256poc`、`extract`）+ 9 个 `.rs` + 入库的 `libextract.so` / `libsha256poc.so`，且 `RootfsInstaller.kt:76` 已调用 | 引入 Rust **不再是"从零建工具链"**；但本节其余诸条（JNI 边界设计、16KB、CI）的工程量判断仍然有效 |
| **SHA256 本来就不在 Kotlin 里跑** | `RootfsDownloader.verifySha256()` 用 `java.security.MessageDigest` | ART/BoringLib 在 ARM64 上走 **crypto 扩展指令**。且SHA256 是 **I/O bound**（读盘速度），重写 Rust 最多省纳秒级 JNI 开销 → **迁移无收益，旧计划的 SHA256 PoC 应删除** |
| **zstd 解压本来就是 C** | `RootfsInstaller` 用 `libzstd-jni-1.5.6-4.so`（已在 jniLibs） | Rust 重写 zstd 只能做到同等水平。真要优化应走"**减少解压量**"（更小 rootfs / 分层按需解压）。⚠️ **但事实上解压仍被 Rust 化了**（R1 收编，见上方更正）——**理由不是性能**，而是验证 native 流水线与 16KB 对齐 |
| 下载引擎是**网络 bound** | OkHttp 已优化，M1.1 已实现 Range 续传 | 优化方向是多连接分块并发——**纯 Kotlin Range 切片即可，不需 Rust** |

**❌ 不可动（第三方/结构性天花板）**：PRoot syscall 拦截（第三方 C，GPL，重写=重写 proot）、OpenCode 运行时（第三方 TS/Bun）、终端渲染（已是 Java 模拟器，热点在 Android 文本布局与 Canvas）、Compose UI 与平台集成、rootfs 构建管线（在 CI，不是手机）。

**✅ 唯一值得考虑 Rust 的候选**：**PTY 数据搬运的 JNI 往返**（`app/src/main/cpp/`，大输出时 read → TerminalEmulator 的高频 JNI 往返）。
⚠️ 但必须先有 **Perfetto trace 证明** JNI 往返真是热点——历史上终端卡顿的主因是**渲染**而非搬运。且收益上限有限。**这是唯一值得起 Rust 的地方，也是个收益有限的小赌注。**

**⚠️ 引入 Rust 前必须先解决的两个工程前提（旧计划未提）**：
1. **NDK 版本**：`app/build.gradle.kts` 当前 `ndkVersion = "27.2.12479018"`（**r27，非 r28+**）。r27 需手动加两个 16KB linker flag。建议引入任何原生代码前先确认是否升级到 **r28+**（默认 16KB 对齐）。
2. ~~**ABI 双架构**：Rust 需交叉编译**两套**并各自验证 16KB，工作量 ×2。~~ —— **已消解**：2026-10-06 用户定案砍掉 x86_64（定位是手机 / 平板，不做模拟器支持），`abiFilters` 收敛为 `arm64-v8a` 单架构。这原本是引入 Rust 最大的一笔额外成本，现已归零。

**📌 反向证据**：旧计划提到的"P99 94μs JNI 延迟"——94μs 对终端数据搬运**完全可接受**（远低于 60fps 的 16.7ms 帧预算）。这个数字应当作"**JNI 延迟不构成瓶颈**"的依据，而非启动 Rust 的理由。

**结论**：**当前代码里没有任何一个模块值得为了性能改写成 Rust。** v1.0 的正确动作是把 Perfetto 基线做完，不要启动技术上注定无收益的 SHA256 PoC。引入 Rust 的决策**推迟到 v1.0 诊断数据出来之后**。
> 📌 **后续实际发生（2026-10-07）**：Rust **确实被引入了**，但**不是**因为性能——是作为「native zstd + 进度回调 + 文件树处理」的**架构验证**（`rust/extract/README.md` 明写"基线已证解压仅 2 秒，不是性能任务"；真机 Rust 3611ms vs Java 3668ms）。**本节结论（迁 Rust 无性能收益）依然正确**；被推翻的只是"项目零 Rust"这个事实前提。若将来有人拿"Rust 都上了"来论证迁 PTY/其它模块，请先回到本节的门槛表。

## 6. 给 zcode 的纪律

- 所有性能结论以 Perfetto / Macrobenchmark / `dumpsys meminfo` **实测**为准，不许用文档推断替代真机测量（同 E-005 精神）。
- 先写 ~~`docs/performance-baseline.md`~~ → **`docs/acceptance/compose-perf-baseline.md`** 基线，再谈任何优化。
- 引入 Rust 工具链（cargo-ndk / JNI 桥接）增加维护负担，须**用户拍板**。⚠️ **2026-10-06 裁定更新**：原"先在 SHA256 小模块 PoC 验证"的建议**已撤销**——SHA256 是 `MessageDigest` 原生实现且 I/O bound，PoC 必然得出"无收益"的技术性结论，白费一轮工。若将来真要验证 Rust，唯一合理的 PoC 对象是 **PTY 数据搬运**（且需先有 Perfetto 数据支撑）。
- **不动 targetSdk 28**（已知限制.md 硬约束）。
- 不迁移红线：UI 层（Compose）、Android 平台集成（Activity/Service/权限/通知）、业务逻辑编排（ViewModel）——Kotlin 最优。
