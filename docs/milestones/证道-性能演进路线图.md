| 阶段 | 语言 | 关键动作 | 红线 |

## 3. 瓶颈评级（⚠️ 表中数字为计划书假设值，须 v1.0 实测验证）

| 模块 | 瓶颈类型 | 当前语言 | 严重度 | 假设依据 |
|---|---|---|---|---|
| PRoot syscall 拦截 | CPU/IO | C（proot 二进制，第三方） | 🔴 高 | ptrace 致 I/O 下降约 44% |
| OpenCode 运行时 | 内存 | TS/Bun（bionic，第三方） | 🔴 高 | 初始化内存峰值 ~3.5GB，触发 LMK |
| RootFS 解压 | CPU/IO | Kotlin + zstd-jni | 🟡 中 | ARM 上 zstd 未充分优化 |
| 下载引擎 | IO | Kotlin + OkHttp | 🟡 中 | 大文件 Range + SHA256 边下边算 |
| SHA256 校验 | CPU | Kotlin + MessageDigest | 🟡 中 | 1.5-2GB 全量读取 |
| 终端渲染 | 渲染 | TerminalView（C） | 🟢 低 | 已从 WebView 切原生，瓶颈消除 |
| Compose UI | 渲染 | Kotlin | 🟢 低 | 常规 UI 负载 |

---

## 4. Rust 迁移触发条件

| 模块 | 触发条件（须实测） |
|---|---|
| 下载引擎 | 下载速度 < 网络带宽 50%，或 SHA256 校验耗时 > 10s |
| 解压引擎 | RootFS 解压 > 60s，或解压期间 UI 卡顿 > 3s |
| OpenCode 进程管理 | 内存 > 2GB 且无法靠配置优化，或被 LMK 频繁杀 |
| SHA256 校验 | 1.5GB 文件校验 > 15s 且流式优化无效 |

> **通用门槛（四者同时满足才启动评估）**：① 实测确认为真实瓶颈；② Kotlin 优化已穷尽；③ 预期收益 ≥ 30%；④ JNI 桥接复杂度可控。

## 5. 评估注记（需补强 / 修正，供 zcode 注意）

1. **PRoot 是最大瓶颈却不在迁移列表**——proot 是第三方 C 二进制，证道无法 Rust 重写。但它是 🔴 高瓶颈（ptrace 44% I/O 下降）。路线图须明确：该瓶颈**只能靠替代方案规避**（如评估 unprivileged userns / bubblewrap / 真 root），或功能上接受。本路线图不把它列为 Rust 目标，但单列"结构性瓶颈，待专项评估"。
2. **OpenCode 内存是第三方限制，Rust 只能治标**——证道只能管进程生命周期（监控/重启/提示释放），降不了 OpenCode 自身内存。v1.x 的"资源监控+超阈值提示"是主要手段，Rust 迁移仅强化进程管理，非根治。
3. **targetSdk 28 对现代性能工具链的兼容性需确认**——`已知限制.md` 钉死 targetSdk 28（W^X 豁免硬前提，动不得）。Macrobenchmark / Baseline Profile / Perfetto 的 AGP 版本要求可能偏高，v1.0 诊断前先确认工具链可用；Baseline Profile 在 targetSdk 28 下支持度有限，预期收益需打折。
4. **关键数字标注为"假设值，待实测"**——44% I/O 下降、3.5GB 峰值、P99 94μs JNI 延迟等均引用自外部，**v1.0 必须重测**，数据以 `docs/performance-baseline.md` 为准，不得直接当事实写进代码注释。
5. **§5.1 "APK 体积可减少 52%" 存疑**——该句与"Rust 编译产物 1-3MB"自相矛盾：引入 Rust `.so` 只会增体积，除非替换了原本很大的 Kotlin/Java 依赖（计划书 Rust 仅覆盖 3 个小模块，不足以减 52%）。**该数字待 v1.x 实测澄清，勿轻信。**

## 6. 给 zcode 的纪律

- 所有性能结论以 Perfetto / Macrobenchmark / `dumpsys meminfo` **实测**为准，不许用文档推断替代真机测量（同 E-005 精神）。
- 先写 `docs/performance-baseline.md` 基线，再谈任何优化。
- 引入 Rust 工具链（cargo-ndk / JNI 桥接）增加维护负担，须**用户拍板**且先在 SHA256 小模块 PoC 验证。
- **不动 targetSdk 28**（已知限制.md 硬约束）。
- 不迁移红线：UI 层（Compose）、Android 平台集成（Activity/Service/权限/通知）、业务逻辑编排（ViewModel）——Kotlin 最优。

## 7. 一句话

**v1.0 只诊断不动刀，v1.x 先做 Kotlin 优化，v2.0 只把实测确认的瓶颈模块换成 Rust（先 SHA256 PoC）。** 不要为"感觉 Rust 更省内存"提前重写——先用 Perfetto 和 Macrobenchmark 证明它是瓶颈。
