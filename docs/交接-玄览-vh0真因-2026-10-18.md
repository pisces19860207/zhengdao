> ## ⚠️ 更正（2026-10-18 13:4x，蓝总管）

> **真因（qoder 同包对照 + 我亲手反证）**：Compose `AndroidView` 的宿主 `ViewFactoryHolder` 调 `addView(child)` 时不传 LayoutParams ⇒ WebView 拿到 **WRAP_CONTENT** ⇒ `onMeasure` 的 heightMeasureSpec 不是 EXACTLY ⇒ Chromium 改走「按网页内容高度给自己定尺寸」，而内容高度又由这个塌成 0 的视口算出 ⇒ 自锁。修法 = 建 WebView 时给它自带一份 MATCH_PARENT 的 `FrameLayout.LayoutParams`（4 行代码）。两个 `useWideViewPort`/`loadWithOverviewMode` 开关与本病**无因果**（各开一版真机实测仍 0）。

## 0. 一句话

`100vh` 恒为 0 的根因是 **`WebSettings.useWideViewPort` 是 false**（WebView 146 在这个配置下把「布局视口高度」算成 0）。
把它打开后，`100vh` 立刻从 0 变成 662、`matchMedia('(min-height:1px)')` 从 false 变 true、必应主容器 `#hp_app` 从 0 变成 662、搜索框从 `top=-22`（屏外）回到 `top=64`（屏内）。

**但还有一层没解**：同一个时刻，屏幕上画的还是旧画面（只有背景图），而 CDP 驱动的那个 WebView 的 DOM 已经是好的。见 §4。

## 3. 真因的最短表述

- 屏幕宽高、可视视口、ICB 全是对的，**唯独「布局视口高度」是 0**；
- 布局视口高度由 WebView 的 `AwSettings.useWideViewPort` 决定（false ⇒ 走「宽视口/桌面式」那一套，高度算成 0）；
- 站点拿 `100vh` 定高 + `overflow:hidden` ⇒ 整层被裁光 ⇒ 只剩 `position:fixed` 的背景图。**这就是「白屏／显示不完整」。**

## 4. 还没解开的一层（接手时优先看这个）

打开视口设置后，**DOM 全对、画面不动**：

- 同一时刻截图：仍只有背景图；
- CDP `Page.captureScreenshot` **超时**（渲染器不响应这条命令，但 `Runtime.evaluate` 是通的）；
- 用 CDP 把页面导航到 `example.com`，DOM 已变（`deOH=895`）、**画面还是必应的图**；
- `/json` 同时有 **5 个 page target，其中 4 个 `url` 为空**。

**我的推断**：屏幕上挂着的那个 WebView，和 CDP 驱动的那个**不是同一个实例**。
`BrowserScreen` 这一行嫌疑最大：

```kotlin
factory = { BrowserTabManager.view() ?: WebView(it) }
```

`view()` 返回 null 时会**裸建一个没有引擎、没有设置、不会加载**的 WebView 挂在界面上。4 个空 target 很可能就是这么来的。

**建议先查**：每个 WebView 建实例时打 `identityHashCode` ＋ 是否挂载 ＋ 是否有引擎，把「5 个实例」对上号；再判「冷启动首屏（杀进程→启动→玄览→必应）画面是否正确」。
- 冷启动首屏正确 ⇒ 冻结是二次导航/多实例的问题；
- 冷启动首屏也不对 ⇒ 还有第二层。

## 5. 改法与副作用（必须分开验）

`useWideViewPort` 与 `loadWithOverviewMode` 是两个开关，**我只测了「两个都开」**。请分两版测：

1. 只开 `useWideViewPort = true`；
2. 两个都开。

注意两个都开时，必应的 DOM 结构会变（从 `#img_cont` 那套变成 `#bnp` / `#scroll_cont` / `.header_shadow`），说明站点走了**另一套布局**；`innerHeight` 从 551 变成 662（≈缩放 0.83）。**这一层要看视觉：字会不会变小、桌面版排版能不能接受。** 如果只开 `useWideViewPort` 就够，优先只用它。
