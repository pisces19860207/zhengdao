## 二、根因（逐条，含反编译源码的发现）

### 1. 顶栏被长模型名挤没 —— 布局算术，不是渲染 bug

v1.0 任务一把「模型池入口」做成 `TextButton` **直排顶栏主行**，而标题列是 `Modifier.weight(1f)`。
实测模型名 **`opencode/longcat-2.5-preview-free`（31 字符）** 在 560dpi 下宽度远大于可用空间，
`Row` 先满足非 weight 子项 → **标题列被压到 0 宽**（整段不可见），`ConnectionLabel` 被挤成一字一行
（`已` / `连` / `接`），顶栏因此从单行变成多行、整条高度被撑高。

真机坐标佐证：修复前 `☰` 在 **y≈302**，修复后回到 **y≈204**（同一元素，纯因顶栏不再被撑高）。

### 2. BACK 键退出 App —— predictive back 在本工程不生效

material3 `ModalNavigationDrawer` **确实内置**了返回处理。反编译 1.4.0 `NavigationDrawer.kt` 确认：

```
939:  internal fun DrawerPredictiveBackHandler(
943:      val drawerPredictiveBackState = remember { DrawerPredictiveBackState() }
955:      PredictiveBackHandler(enabled = drawerState.isOpen) { progress -> ...
```

`ModalNavigationDrawer`（第 643 行）与 `DismissibleNavigationDrawer`（第 732 行）都调用它 —— **代码在**。

但本工程 `targetSdk 28`，`AndroidManifest.xml` **未声明** `android:enableOnBackInvokedCallback="true"`，
`PredictiveBackHandler` 走的是新的 back 分发通道，**在该配置下不触发** → BACK 直接冒泡到 Activity → 退到桌面。

**性质**：这不是 material3 的 bug，是「库用了新 back 机制、而工程仍是旧 targetSdk/未开开关」的配置错配。

### 3. insets 二次叠加 —— Scaffold 不消费 inset（反编译确认）

反编译 material3 1.4.0 `Scaffold.kt`，其 KDoc（**第 75–78 行**）原文：

> `Any insets consumed by other insets padding modifiers or [consumeWindowInsets] on a parent layout will be excluded from [contentWindowInsets].`
> `... The lambda receives a [PaddingValues] that should be applied to the content root via [Modifier.padding] and [Modifier.consumeWindowInsets] to properly offset top and bottom bars.`

即：**Scaffold 自己不消费 window insets**，它要求内容根**成对使用** `Modifier.padding(innerPadding)`
**和** `Modifier.consumeWindowInsets(innerPadding)`。本工程 `MainActivity` 的 `HomeTabs` 内容根**只用了前者**。

**后果**：inset 未被消费 → 内部任何 `statusBarsPadding()` / `navigationBarsPadding()` 都会把状态栏 / 导航条
**再垫一次**（顶层整体下移、底部多一条空档）。这正是「顶栏固定 + 输入框避让」这次改动会踩到的坑。

> ⚠️ 注意区分：**IME inset 不在 `contentWindowInsets` 内**，因此 `imePadding()` 的键盘避让**不受本项影响**。

### 4. 删除后列表不同步 —— 乐观更新缺回源

初版删除后只做本地 `sessions.filterNot { it.id == target.id }`。当删的是**当前会话**时，
代码会另起一个新会话，但本地列表不会因此新增该项 → 「当前」徽章消失、找不到刚建的会话。

## 三、修法

### 1. 顶栏布局：标题回主行独占，模型退副行限宽

`TaijiComponents.kt::SessionBar` 重构为两行：

- **主行**：`☰ 历史` — **标题（`weight(1f)`，独占剩余空间）** — `＋ 新会话` — `◼ 停止`
- **副行**：`● 已连接 · <模型胶囊>`；模型胶囊**限宽 176dp**，长名最多牺牲自己尾部（省略号），不再抢标题空间

新增纯函数 `shortModelName()`（`provider/model` → 取 `model` 段）+ 6 例 JVM 单测。
修复后实测：标题 `新会话` 在 `y 169–253`，`● 已连接` 与模型胶囊横排在 `y 260–316`，`☰` 在 `y 204–288`。

### 2. insets：宿主消费 + 顶栏/抽屉避让

- `MainActivity.kt`：`HomeTabs` 内容根在 `Modifier.padding(padding)` 之后补 **`Modifier.consumeWindowInsets(padding)`**
  （严格按 Scaffold KDoc 的成对要求），声明「系统栏内边距已由本层应用」。
- `TaijiComponents.kt`：`SessionBar` 与抽屉头部加 `statusBarsPadding()`（在宿主已消费的前提下为正确 no-op，
  且宿主若变化仍自洽）；`ComposerBar` 保留 `navigationBarsPadding().imePadding()`。

**真机验证（像素级）**：

| 测量项 | 结果 |
|---|---|
| 内容区起始 y（状态栏下方） | 太极页 = **141px**，丹房页 = **141px** → **两页一致，无遮挡、无重复内边距** |
| 状态栏高度 | 141px ÷ 3.5 ≈ **40dp**（正常值） |
| 底部导航栏 | 白色导航区从 **y=2568** 起，至 2848 = **280px = 80dp** |
| 输入框 | 占位符 `描述你的任务…` 位于 `y 2400–2484`，**完全落在导航栏之上，无重叠** |

### 3. BACK 键兜底

`TaijiScreen.kt` 显式注册：

```kotlin
BackHandler(enabled = drawerState.isOpen) {
    scope.launch { drawerState.close() }
}
```

语义与「点遮罩关闭」一致：**抽屉开着 → 先关抽屉；抽屉关着 → 不拦截（正常返回）**。

### 4. 删除后回源刷新

`onDelete` 改为：执行删除 → 若删的是当前会话则另起新会话 → **`refreshSessions()` 回源对齐**
（而非仅本地 `filterNot`）。保证列表与真实状态一致（含「当前」徽章归位）。

## 五、本轮**主动不做**的项（决策记录）

| 项 | 结论 | 理由 |
|---|---|---|
| 左缘滑开抽屉（`Modifier.systemGestureExclusion()`） | **不做** | ① 风险收益不对等——为「多一个打开方式」去和系统返回手势博弈，可能在部分 ROM 上误伤用户返回操作；② 已有替代路径（顶栏 `☰` 一点即开）；③ 工程判断上「不确定能稳」的手势 = 不做。若未来用户反馈「☰ 太小不好点」，应做**更大的按钮**，而不是抢边缘。 |

真机实测数据（留档，供将来复评）：从 x≈4px 起手右滑会被**系统返回手势**抢走；从 x≈120px（≈34dp）起手则正常开抽屉。这是 Android 手势导航的通用行为，不是本项目缺陷。
