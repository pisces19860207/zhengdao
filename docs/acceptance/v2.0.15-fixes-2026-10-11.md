## ① 清理「Agent 缓存包」不再卡界面

**改了什么**：`app/src/main/java/com/example/zhengdao/terminal/CacheCleaner.kt` 新增
`internal data class DeleteStat(files, dirs, bytes)` 与 `internal fun deleteTreeCounted(root: File): DeleteStat`
（`walkFileTree` 不跟随软链；`visitFile` 删文件并累加 `attrs.size()`（软链不计字节）、`postVisitDirectory` 删目录并计数；
`deleteTree()` 改为 `deleteTreeCounted(root).any`）；`cleanAgentCaches` 改为 `val st = deleteTreeCounted(dir); if (st.any) { freed += st.bytes; count++ }`。
`app/src/main/java/com/example/zhengdao/ui/SettingsScreen.kt` 新增页级 `cleaning` 状态与 `fun runClean(work, toast)`
（`withContext(IO)` 执行、重入守卫 `if (cleaning) return`、结束 toast + `storageTick++`），五处清理入口
（脚本缓存 / 可选工具 / 临时文件 / Agent 缓存包 / 旧依赖代）全部改走它，清理期间按钮文案变「清理中…」且 `enabled = !cleaning`。

**怎么验的**：

- 造量：`adb shell` 在 `/storage/emulated/0/Download/证道/cache/npm` 建 **4000 个 1,024 B** 文件（`printf "%01024d"` 走 mksh 内建，耗时 136 s，`du -sk` = 16,188 KB）。
- 设置页「清理 Agent 缓存包」显示 **3 MB**（`agentCacheMb` 走 `dirSizeMb`＝真实字节 4,096,000 ÷ 1,048,576 取整 ⇒ 3）。
  **口径差不是路径错**：同一批数据下 `du`/存储卡按块计费显示得大得多（1500 个 64 B 文件时 `du` 报 6 MB、App 报 0 MB）。
- 点「清理」后**立刻**在同一条 `adb shell` 里跑 `uiautomator dump`（端到端 2.35 s）⇒ **抓到了按钮文案「清理中…」**，
  同一次 dump 里页面其余元素照常返回 ⇒ 清理期间**主线程没被堵**（改前是 Compose `onClick` 里同步删）。
- 清理后 `cache/npm` = **0 个文件**；运行日志逐字：
  `[10-11 20:51:17] 缓存清理(Agent 包缓存): 删除 1 项 Agent 包缓存，释放 3MB`
  （前一轮 1500 个小文件那笔 = `[10-11 20:48:12] … 删除 5 项 Agent 包缓存，释放 0MB`）⇒ 「边删边数」的项数与字节数与实际删除量对得上。

**没验的**：没有在「缓存特别大（GB 级）」的极端量下计时；五处清理入口只实测了其中这条（Agent 缓存包），
其余四处共用同一个 `runClean`，属**同源**改动。

## ② 换工作区会先问一句 + 资料库不会"悄悄换一份"

**改了什么**：`app/src/main/java/com/example/zhengdao/terminal/Workspace.kt` 新增 `KEY_PREV = "workspace_prev_host"`
与 `prevHostDir(ctx)`，三个切换入口（`setDefault` / `setCustom` / `setPrivate`）开头调用 `rememberCurrent(ctx)` 记住旧工作区；

`otherPopulated(ctx)`（候选 = 旧工作区 / 默认工作区 / 私有工作区各自的「资料库/原始」，排除当前，返回带文件数的那份）、
`copyRawInto(ctx, srcRaw)`（跳过同一路径与嵌套路径、按序、限 `MAX_SCAN`、跳过软链、**同名不覆盖**）与 `rebuildAfterCopy(ctx)`；

资料库卡的「另外发现一份带资料的资料库：…（N 个文件）」提示与「把那份复制过来（N 个文件）」按钮。

**验到的（真机，uiautomator 文本逐字）**：

- 点「恢复默认」⇒ 弹出确认框：标题 **「换工作区后，资料库也跟着换」**、**「当前资料库：/storage/emulated/0/Download/男性/资料库（19 个文件）」**、
  「资料库挂在「工作区」下面，所以换工作区就等于换了一份资料库。这一份会原样留在原地、不再被读（不会被删）。」、
  「要不要把这些文件一并复制到新工作区的资料库里？原件不动、同名不覆盖。」、
  按钮 **「复制过去并切换」** / **「只切换，资料留在原地」**。
- 用 `input keyevent 4` 关掉确认框 ⇒ 工作区**仍是** `/storage/emulated/0/Download/男性`（未切换）。

**「另外发现一份」+ 一键复制（端到端，真机实测通过）**：

- 造场景（可逆、不动任何文件内容）：`mv '…/男性/资料库/原始' '…/男性/资料库/原始_临时验证'` ⇒ 资料库状态变未挂载。
- 回到 App（HOME + `am start`）后，资料库卡逐字出现：
  **「另外发现一份带资料的资料库：/storage/emulated/0/Download/证道/资料库（19 个文件）。资料库是跟着「工作区」走的——换过工作区之后，旧那份还留在原地，但 App 只读上面这个路径。」**
  ＋按钮 **「把那份复制过来（19 个文件）」**。检测到的正是**默认工作区**那份（当时 `KEY_PREV` 还没写过，走的是默认工作区候选）。

  原件一份不动；同名的文件不覆盖（当前这份优先）。」＋ 取消 / 复制。

  与源目录做 `{size,relpath}` 列表 `diff` = **IDENTICAL**；随后删掉我自己造的临时目录 `原始_临时验证` 并复核通过。

**没验的**：两个切换按钮（「复制过去并切换」/「只切换，资料留在原地」）**本次没有真按**——按了就会改变工作区状态与
资料库指向，本轮只验证到"对话框出现、文案正确、取消后状态不变"；跨工作区的整条切换链路留给下次真机或用户实际操作时复验。

## ③ 回到设置页即自动重新整理资料库

**改了什么**：`SettingsScreen.kt` 的 `ON_RESUME` 观察者里调用 `KnowledgeBase.autoRefresh(ctx)`
（`autoRefresh` 判「开关开着」且「资料库目录在」，然后在后台线程重建索引，失败只写日志不抛）。

**验到的（真机）**：`adb shell rm -f '…/男性/资料库/整理/00-目录.md'`（App 生成物，可重建）
→ `input keyevent 3`（HOME）+ `am start` 把任务带回前台（= 触发 `ON_RESUME`）
⇒ 清单**被重新生成**：`整理/00-目录.md` 1599 B、mtime **20:41**；
而该时刻的运行日志里**只有** `[10-11 20:41:18] 路由 → settings（来自 home）`、**没有**「会话启动 / 资料库已预置」
⇒ 自动刷新**只靠回到设置页**就完成了，不需要进终端。

**没验的**：冷启动路径（App 从未打开过、进程被杀后直接进设置页）没单独跑；开关关闭时不刷新这条只做了代码复核。

## ④ 渲染层两处（台账 §B-补-47）

**改了什么**：

- 选词中不滚动：`app/src/main/java/com/termux/view/TerminalGestureController.java` 的 `onScroll()`
  （**第一方文件**，头注释即"独立开发声明"）顶部加 `if (mView.isSelectingText()) { mScrollRemainder = 0.0f; return true; }`
  —— 与同文件 `onUp()`（`:77`）、`onScale()`（`:153`）同判据，改前只有这一处漏判。
- 判据收敛 + 修缺陷：新增第一方类 `app/src/main/java/com/termux/view/textselection/DisplayColumnIndex.java`
  （`public static int validCursorColumn(CharSequence line, int column)`，纯计算、无 Android 依赖），
  `app/src/main/java/com/termux/textselection/TextSelectionCursorController.java`（**衍生文件**）的
  `getValidCurX()` 改为调用它（同时移出已无用的 `com.termux.terminal.WcWidth` 导入，并在 `PROVENANCE.md` 的
  「Apache-2.0 修改通知」表里补记这一处修改）。

**验到的**：单测 `app/src/test/java/com/example/zhengdao/terminal/DisplayColumnIndexTest.kt` **8 例全绿**
（半宽边界 / 宽字符内部贴右侧 / 混排 `中a文b` / 零宽组合字符 / ZWJ 开头 / 代理对 emoji / 空串与 null / 行内 NUL 截断）；
全量单测 **68 suite / 619 例 / 0 失败 / 0 错误 / 1 跳过**。

**修掉的那条旧毛病（读码推得 + 单测钉住）**：上游内联实现遇到零宽字符（组合字符、ZWJ、变体选择符）时
**无条件 `return col`** ⇒ 行内只要有零宽字符，无论手柄在哪一列都会被夹回该字符的起始列（`"a\u0301b"` 上第 2 列算成第 1 列），
选区末端因此少一列、手柄往左跳。新实现改成「只有手柄**确实**停在该字符起始列时才返回它」。

**没验的（诚实标注）**：两个症状**都没能在真机复现**——adb 合成手势（`input swipe` 原地长按 1–2 s、
`input motionevent DOWN/UP`、拖拽选择）都唤不起 Termux 的文字选择工具条，选词链路无法自动化验收。
`TextSelectionCursorController` 与上游的差异比对（`git diff --no-index`）本轮未跑。
真机复现步骤：终端里长按选中一段**含中文**的文字 → 拖动手柄 → 观察 (a) 终端内容是否跟着滚、(b) 手柄停在字符边界是否偏差一列。
