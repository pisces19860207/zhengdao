## 1. P2-1 · `BaopuChatController.refresh()` 主线程读库

**现状**：`refresh(force)` 直接 `readMessages(sid)` / `readStepRows(sid)`（`db.read {}` 在调用线程执行）；它由引擎事件回到主线程后调用 ⇒ 每个事件都可能主线程读库，消息多时掉帧。

**改法**：把库读取挪到 `Dispatchers.IO`（控制器已有 `scope` 与 `withContext(IO)` 的用法，照 `refreshBackupStats` 房型）；`refresh(force)` 的对外语义（force 时重算中断标记、刷新消息/步骤卡）保持不变，更新顺序不要乱。若改成 suspend/异步，注意组合层调用点与 `force` 的时序。

**测试**：源码门禁——`readMessages` / `readStepRows` 必须出现在 `withContext(Dispatchers.IO)` 段内；负例改回主线程直读 ⇒ 红。行为级若可做（假 db 记录调用线程）更好。

## 2. P2-2 · `forgetMemory` 的 `db.write` 丢弃 Future

**现状**：`forgetMemory` 里 `db.write { … }` 不 `.get()`；失败被吞，`refreshMemory()` 照常按成功刷新。

**改法**：`runCatching { db.write { … }.get() }`，失败走 `onFailure`（RunLog + 用户可见一句话）；成功后再 `refreshMemory()`；不要用「提交未完成就刷新」。

**测试**：源码门禁——该路径必须 `.get()` 或有等价等待；负例去掉 ⇒ 红。可加假 db 抛错用例。

## 3. P2-3 · 消息落库丢弃 Future ＋ 事件在提交前发

**现状**：`RunEngine` 的 `persistUserMessage` / `persistAssistantMessage` / `persistToolExchange`（`:1433` / `:1455` / 工具交换）都是 `db.write { … }` 不 `.get()`；`onEvent?.invoke(EngineEvent.MessagePersisted(...))` 在事务 `endTransaction()` 之前就发。⇒ UI 可能先收到事件、库里还没有；写失败也静默。

**改法**：三处 `.get()`（或 `Future` + `onFailure`）后再发 `MessagePersisted`；事件移到 `endTransaction()` 之后；失败落 RunLog 并让本轮有明确结果（不静默丢消息）。注意 `settle` 的「先落库再切状态」原则不变。

**测试**：源码门禁——三处 `db.write` 后必须有 `.get()`/等待，`MessagePersisted` 不得出现在事务体内；负例逐条红。

## 4. P2-4 · 每个 `LlmClient` 新建 OkHttpClient

**现状**：`LlmClient.kt:644` `private val http: OkHttpClient = defaultHttp()`；`defaultHttp()` 每次 new（`:867`），`:809` 还有一处直调。每轮对话/每个客户端都新建连接池与线程池。

**改法**：提成**进程级单例**（companion `by lazy`），流式/非流式共用同一个 client；超时口径不变；若个别请求需要不同超时，用 `newBuilder()` 派生、仍共享连接池。不要改成全局可变 client。

**测试**：源码门禁——`LlmClient` 不得再持 `private val http = defaultHttp()`，`defaultHttp()` 只在 companion 单例初始化处调用；负例改回 ⇒ 红。

## 5. P2-5 · 流式 Call 无取消入口 ＋ `latch.await()` 无超时

**现状**：`LlmClient.streamAsync`（`:671`）用本地 `Call`，不返回句柄；`RunEngine.kt:1132/1156` 用 `CountDownLatch` 无限 `await()`；`stop()` 只置 `stopRequested`，最长要等 readTimeout（60s）。

**改法**：`streamAsync` 返回可取消句柄（`Call` 或包装），`RunEngine` 保存它；`stop()` 里 `cancel()`；`latch.await(timeout)` 加总上限（常量进 `RunRules`/`BaopuKernel`，别写死 60s 以外的新魔数），超时按失败处理并取消 Call。保证取消后不再回调成功、不吞异常。

**测试**：源码门禁——`latch.await()` 不得无参；`stop()` 必须取消；行为级用本地慢速 ServerSocket / 假 LlmClient 验证超时与取消（不新增依赖）。负例：去掉超时/取消 ⇒ 红。

## 6. P2-6 · `TerminalActivity.onDestroy` 漏清 `onSessionDied`

**现状**：`onCreate` 里 `SessionManager.onSessionDied = { code -> handleSessionFinished(code) }`（`:239`），`onDestroy` 只清 `onViewUpdate` / `onCopyText` / `onPasteRequest`（`:1930` 附近）⇒ 单例钉住已销毁 Activity。

**改法**：`onDestroy` 补 `SessionManager.onSessionDied = null`；若本批新增了别的全局回调，一并列入清单清理。不要动会话本身（`SessionManager` 的 kill/attach 语义不变）。

**测试**：源码门禁——`onDestroy` 必须包含 `onSessionDied = null`；负例删掉 ⇒ 红。
