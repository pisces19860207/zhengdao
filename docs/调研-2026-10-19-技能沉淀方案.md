## 2. Q1–Q7 逐条

### Q1 技能正文放哪 —— 推荐 ①`<工作区>/技能/<名字>/`；**结论：待用户拍板**

| 选项 | 依据（文件:行号） | 代价 |
|---|---|---|
| ① `<工作区>/技能/<名字>/`（如 `技能/整理书稿/SKILL.md`） | 工作区根＝`Workspace.hostDir`（`Workspace.kt:41-55`），`LibraryPaths.kt:61` 已把它定为唯一真相源；read_file 的根就是它（`BaopuRuntime.kt:132`）⇒ 模型按索引 `read_file 技能/…` 天然够得着 | 换工作区＝换一套技能（与资料库同题，先例：`Workspace.kt:90-106` 的 prevHostDir 提示机制可复用）；**仅私有模式**下工作区是 App 外部目录，随卸载删除（`Workspace.kt:82`、`:61-66` 注释） |
| ② 复用 `抱朴记忆/` 子目录 | 全局记忆已在 `<App私有>/抱朴记忆/记忆/`、项目记忆在 `<工作区>/记忆/`（`MemoryStore.kt:120-124,233`） | 记忆条目是 500 字符上限＋front-matter 校验的形态（`Memory.kt:62`、`MemoryStore.kt:33-100`），真技能包几十 KB 塞不进；混进记忆目录会让 validate/去重/reindex 的语义变混；loadAll 非递归（`:186-189`）虽不会误收子目录，但「记忆」与「技能」两种寿命两种体量的东西同居一目录，审阅界面难分 |
| ③ App 私有目录（filesDir/技能/） | —— | 文件管理器看不见；**read_file（工作区根）够不着** ⇒ 直接违反母单红线 4（技能必须是工作区内普通文件）。**不可行** |

推荐 ①，理由：立项单 §2-1 已定方向「工作区里的文件」，① 是唯一同时满足「read_file 够得着＋文件管理器可见＋跟 C 层『跟工作区』口径一致」的选项；换工作区行为与资料库一致（旧工作区的技能原样留在原地，用 prevHostDir 先例提示）。**待用户拍板**（含：要不要给全局技能留位置——B 层口径的技能放哪，本调研建议第一版只做 C 层，查不到用户对「全局技能」的需求强度，需要用户决定）。

### Q2 谁能写索引 —— 推荐 ③「模型提案＋用户明说＋手动编辑」三路，全部过确认；**结论：待用户拍板**

现状先说清：**改 C 层的唯一合法通道**已经是「提案 → 人确认 → 落盘」（`PersonaFiles.kt:105-106,143-151`），技能索引写进 C 层天然继承这条链，**不需要发明新机制**。三条发起路：

| 方案 | 依据 | 代价 |
|---|---|---|
| ① 只模型提案＋用户确认 | 提炼已有纯函数先例：`MemoryRefine.refine`（`MemoryRefine.kt:104-113`，不跑模型、从会话事实确定性推导）；产出候选等用户过目（`BaopuChatController.kt:377-392` 的确认/丢弃对） | 用户不主动说的经验提炼不出来 |
| ② 用户说「记住」也算提案 | 现状**查不到**「对话里说记住 → 产生提案」的链路：标记词只产记忆候选（`MemoryRefine.kt:42-49`）。「记住」按钮只服务已提炼候选（`strings.xml:875-876`） | 要新增「用户明说 → 高置信提案」的识别；误识别会弹多余确认卡 |
| ③ 手动编辑（审阅界面直接改 C 层） | 立项单 §2-3 点名的审阅界面（进抱朴设置页）；现状**无处查看/编辑 B/C**（立项单 §1 末行 ❗） | 用户本人编辑＋显式保存＝用户自己确认，可以不走提案卡（用户是确认制的最高一级）；模型产出的一律照走确认卡 |

推荐 ③＝①＋②＋手动编辑（与母单建议一致）：模型产出的一律走提案卡（红线 2 确认制不降级）；用户本人「说记住」走**高置信提案**（还是要卡，但卡上写明「这是你说的」）；审阅界面手动编辑即时保存（用户操作即确认）。**待用户拍板**。

### Q3 一次收尾最多提炼几条 —— 推荐 3 条（对齐现状先例）＋技能索引设总数上限；**结论：待用户拍板**

预算算术（全部现值）：
- 索引住在 **C 层人设**（上限 8000 tokens，`PersonaFiles.kt:44`），**不占**记忆召回预算（记忆段与人设段分开装，`ContextAssembler.kt:252-261`；召回 2000 tokens 是 `Memory.kt:74`，管的是 MemoryEntry）。
- 一句索引按记忆渲染房型（`Memory.kt:303-307`）估 **40–80 tokens/条** ⇒ 纯算术上 C 层要 100+ 条才会触顶；**瓶颈不在 token，在质量**。
- 质量的现状先例：一次收尾提炼记忆候选 **≤3 条**（`MemoryRefine.kt:33` MAX_CANDIDATES=3），且只认用户原句（`:57-59`）——会话事实有限，多提必出噪声。
- 待过目同屏上限：maxPending=6（`BaopuChatController.kt:218`）。

| 选项 | 代价 |
|---|---|
| ① 3 条（推荐） | 与记忆提炼同口径，用户审卡负担最小 |
| ② 5 条 | 待过目卡更挤；3→5 没有数据支撑优劣（**查不到，需要用户决定**） |
| ③ 不限＋超限提示 | 确认卡刷屏；与 maxPending=6 的现有 UI 容量冲突 |

无论选几条，技能**索引总量**建议另设上限（如 20 条）：超限时**提示用户先删旧索引**，而不是靠截断兜底（见 Q6——截断是异常兜底，不该当常态入口）。**待用户拍板**。

### Q5 「会话关闭时」的代码落点（关键）——推荐 A＋D 组合；**结论：待用户拍板**

「会话关闭」在代码里**没有一个现成的钩子**，四个候选逐个说：

| 候选 | 落点 | 可靠性 / 漏算风险 |
|---|---|---|
| A. `newSession()` | `BaopuChatController.kt:336-347`（清视图态＋重置提炼游标）；调用点：抽屉 `BaopuScreen.kt:160`、顶栏 `:214` | **可靠性最高**：用户主动动作，时机语义与「会话关闭」完全一致（账本只增不删，新会话＝旧会话封卷）。漏算：用户不点新会话直接杀 App |
| B. Settled 事件（扩展现有提炼） | `BaopuChatController.kt:631-679`（refineOnSettle，本轮 Done/Aborted 时已在提炼**记忆**候选） | 语义是「**轮**结束」不是「会话关闭」：一轮刚完用户可能马上继续 ⇒ 每轮都弹技能提案太吵；且 run_log 只有轮级 state（`:661-666`），**查不到「会话级收敛」信号** |
| C. 进程退出前 | —— | **查不到可靠落点**：Android 无可靠的进程退出回调（Activity onDestroy / Service onTaskRemoved 均不可靠）。不编 |
| D. 下次开工时补算（兜底） | 游标已在内存：`BaopuChatController.kt:342-343`（refineMarkSession/refineMarkUserCount）、`:636-640`（按游标取增量）；**持久化后**即可在新会话开始/控制器构造时对比补算。先例：压缩摘要的跨进程恢复 `RunEngine.kt:234-236`（restoreCompression）、控制器构造即 refresh（`BaopuScreen.kt:100`） | 可靠性最好（杀进程也补得回来）；代价：游标要落库或 SP，补算逻辑要在构造路径上跑 |

推荐 **A＋D 组合**：用户点「新会话」⇒ 对本会话未提炼的增量提炼一次并弹提案；用户没点就杀掉 ⇒ 下次进来构造时按持久化游标补算。漏算风险趋近于零。**待用户拍板**（含游标存 SP 还是库——建议库，与 restoreCompression 同房型）。

### Q6 索引怎么写才不超 8000 tokens —— 推荐形态＋超限行为；**结论：形态待用户过目，机制已定**

推荐的一句索引（照 `Memory.kt:303-307` 的渲染房型举例，不落代码）：

> 【技能】整理书稿：遇到拆章、转编码、导出书稿类任务，先 read_file `技能/整理书稿/SKILL.md` 按它做。

约 60 tokens/条；上限 8000（`PersonaFiles.kt:44`）÷ 60 ≈ 130 条才触顶，**按算术不紧张**，风险全在「正文本体＋索引合计」。超限时的确切行为（现机制）：`PersonaRules.clip` 按字符比例保留 90% 再拼 `TRUNCATION_MARK`（`PersonaFiles.kt:72-82`）——**截的是段尾** ⇒ 索引小节若放 C 层末尾，最新的索引最先被截掉；标记「…（人设超长，已截断；完整内容在文件里）」进上下文，模型与用户都看得见（截断可见，不静默）。对策（不新增机制）：索引条数上限（Q3）＋超限提示先删旧索引；截断标记只当异常信号。立单判据 K2（超限提案截断可见）用现有 TRUNCATION_MARK 断言即可。

### Q7 与 MCP（刀 5③）/ 技能包（刀 5①）的边界

一句话：**本批技能＝「工作区里的普通文件 ＋ C 层一句索引」，是进程内的文件约定，零协议、零打包格式**；刀 5①「Skill 包」（台账 `FEATURE-LEDGER.md:783`）才是把技能**产品化成分发格式**（打包/导入/导出），刀 5③「MCP 客户端」（同处：Streamable HTTP 优先＋SSE 回退；`FEATURE-LEDGER.md:740`：不跨 rootfs ⇒ stdio 型 MCP 不在列；`:802`：同机 127.0.0.1 是否真通降级为刀 5 前置实测）是把**外部工具**接进引擎的协议适配。避免做两遍的三条边界：本批**不定义**任何包/导入格式（将来刀 5① 的包导入时应落到同一 `技能/<名字>/` 目录约定上）；本批**不碰**任何网络协议与外部进程；本批的技能**不进**工具表（工具表不可被模型编辑，母单红线 1）——技能只是「教模型先去读哪个文件」。

## 4. 「会让用户难受的点」清单

1. **索引悄悄被截**：技能索引多了之后 C 层触顶，截断按段尾比例吃掉最新索引（`PersonaFiles.kt:76-78`）——虽有可见标记，但「我确认过的技能怎么不灵了」很难排查。对策：索引上限＋超限提示先删旧的（Q3/Q6）。
2. **提炼出废话技能**：每次收尾都弹「要不要存为技能」，弹多了用户会烦——一次 ≤3 条＋「用户明说才高置信」（Q2/Q3）是下限保障；**查不到**更聪明的过滤办法，需要用户决定要不要在提案卡上加「这类以后别问了」。
3. **换工作区技能「丢失」**：技能跟工作区走（Q1①），换工作区后旧技能还在旧目录里但索引（C 层也跟工作区？否——C 层文件在工作区根，换工作区 C 层人设本身就是另一份）——**索引与正文会一起换掉**，但用户感知是「技能全没了」。有 prevHostDir 提示先例（`Workspace.kt:102-106`）可做提醒；仅私有模式还随卸载删除（`Workspace.kt:82`）。
4. **待过目列表是进程内存**：`pendingMemories` 杀进程即丢（`BaopuChatController.kt:340`）——技能提案若同机制，用户没来得及看就没了；补算（Q5-D）可救，但用户仍可能面对「突然冒出三条旧提案」。
5. **「用户说记住」的识别靠标记词**：`MemoryRefine.kt:42-49` 的标记词表会漏（换个说法就认不出）也会误（反话、引用别人的话）——误识别的直接后果是多弹一张确认卡，可接受但要心里有数。
6. **技能文件被手改后索引与正文不一致**：用户在文件管理器里改了/删了 `技能/…/SKILL.md`，索引行不会自动更新（文件是真相、索引是人设文本，没有对账机制）——审阅界面加「校验一下」按钮可缓解（改动清单草案未含，需用户点头）。
7. **记忆与技能的边界模糊**：「这次学到的做法」什么时候是记忆（500 字内的一句话）、什么时候升格成技能（一个目录一篇长文）——本调研的口径建议：**提炼一律先出记忆候选；只有模型或用户明说「这值得做成流程」才出技能提案**——这条需要用户拍板。
