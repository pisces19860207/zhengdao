## 0. 先更正我自己上一轮的四处错误（留痕）

上一轮我基于"存在性"就下了几条结论，其中**四条经复核不成立**。两条是方向性错误。

### 0.1🔴 我说「wgpu / GPU 渲染撞 targetSdk 28 生死线」—— **错了，方向反了**

我上一轮的原话是：

> "GPU 渲染那套 `.so` 正是 Android 17「Safer DCL 扩展到 native 库」（文件须只读，否则 `UnsatisfiedLinkError`）的头号雷区"

**复核结果（② 官方行为变更原文 + 实测博客复现）**：

Android 17 把 Safer DCL 扩展到 `System.load()` 加载的 `.so`，但**门控需要两个条件同时成立**：

1. 设备运行 **Android 17+**
2. **且** 应用的 `targetSdkVersion >= 37`

原文（Mobile Hacking Lab 实测复现，逐字）：
> "The check only fires for apps whose targetSdkVersion is 37 or higher, running on a device whose OS is Android 17 or higher. **Miss either condition and the old, permissive behavior applies.**"

**证道 `targetSdk = 28`**（`app/build.gradle.kts:141`，②）⇒ **这条限制对证道完全不触发**。

**所以事实恰好相反：targetSdk 28 让证道躲过了 Android 17 这一批新限制，而不是撞上它们。** 这是 Android 14 引入 DEX 版 Safer DCL 以来的一贯规律——那次门控是 `targetSdk >= 34`，28 同样躲过。

⚠️ 我上一轮把"躲过"读成了"撞上"，这是**方向性错误**。它影响的是"Warp Mobile 那条路能不能走"的判断，见 §2。

### 0.2 🔴 我说「Forge 是 60fps JNI 传输的已验证参考」—— **它没碰 GPU，而且只花了一天**

我上一轮把 Forge 当成"wgpu/GPU 渲染那一档"的代表。**复核结果完全不是**（② `app/build.gradle.kts` 原文）：

```
compileSdk = 35
targetSdk = 35        ← 不是我以为的高 target
minSdk = 26
ndkVersion = "28.0.13004108"

packaging { jniLibs { useLegacyPackaging = true } }

dependencies {
    implementation(platform(libs.compose.bom))
    implementation(libs.compose.ui)
    implementation(libs.compose.ui.graphics)     ← Canvas 绘制
    ...
    implementation(libs.shizuku.api)            ← 用了 Shizuku
    implementation(libs.shizuku.provider)
}
```

**全文没有一行 Vulkan / wgpu / OpenGL ES。** 它的渲染就是 `Compose Canvas`，和证道的方案文档 P2 设想**完全同一件事**。

⇒ **我上一轮把 Forge 归错档了。** 它不是"GPU 路线"的参考，它是"Compose Canvas 路线"的参考——**而那条路线对证道恰好是安全的那条。**

### 0.3 🟡 我说「CI 不构建 Rust，要重搭构建链」—— **地基已经现成**

我上一轮说"引入 wgpu 要加 NDK + cargo-ndk"。**实测复核（① 本机 cat + grep）**：

| 我以为要新建的 | 实际状态 |
|---|---|
| CI 里装 NDK | ✅ **已有**。`ci.yml:58` 与 `build.yml:120-124` 都执行 `sdkmanager "ndk;27.2.12479018"`，注释写明「与 app/build.gradle.kts 的 ndkVersion 一致」 |
| `cdylib` 产物类型 | ✅ **已配**。`rust/core/Cargo.toml` 的 `crate-type = ["rlib", "cdylib"]` |
| JNI crate | ✅ **已引入**。`[target.'cfg(target_os = "android")'.dependencies] jni = { version = "0.21", default-features = false }` |
| Kotlin 侧 `external fun` | ✅ **已有一整套**。`app/src/main/java/com/example/zhengdao/rust/CoreNative.kt:40/52/71/96/142/149` 共 6 个 native 方法已跑通 |
| `.so` 入库 | ✅ **已入库**。`app/src/main/jniLibs/arm64-v8a/libzhengdao_core.so`（960 KB） |

**唯一真正缺的是**：CI 里那一步 `cargo-ndk`（现在 `.so` 是**人工** build 后拷进来的，`ci.yml:60` 注释原文承认）。

⇒ **修正后的结论：引入 Rust 状态层的构建成本 ≈ 加 1 个 CI 步骤 + 1 个 cargo-ndk，不是"重搭构建链"。** 这条明显比我上一轮说的对你有利。

### 0.4 🟡 我说「Warp Mobile 在 GitHub，方案里写 Codeberg 是错的」—— 结论对，但补一条

方案原文写「**Warp Mobile**（**Codeberg**）」。实际位置（②）：

- 主仓库：`github.com/ImL1s/warp-mobile-android`
- GitLab 镜像：`gitlab.com/aa22396584/warp-mobile-android`
- **Codeberg 上没有**

⇒ 方案的"参考实现"里，**两个项目一个路径是 404、一个托管平台写错**。这不是致命问题，但说明方案的引用是二手的、没有逐条打开过。

## 2. 但两个参考项目的成熟度天差地别，而"高级"的那个恰好不能用

### 2.1 🔴 Warp Mobile：`AGPL-3.0-only` + **targetSdk 31** + 只在 S24 Ultra 验证

它 README 原文（②）：

> **"License: AGPL-3.0-only.** This project is built on: warpdotdev/Warp — parent project; warpui, warp_terminal, warpui_core, and the DCS hook parser are reused and extended. **Also AGPL-3.0.**"

且 F-Droid metadata（②）：

> "**Target SDK 31** ... Requires Android 12 ... **per-cell Vulkan rendering** ... on **Galaxy S24 Ultra** primary"

三条对证道的含义：

| | 后果 |
|---|---|
| **AGPL-3.0-only** | ⛔ 证道是 **GPL-3.0**。GPL-3.0 项目吸收 AGPL 代码，整个许可证被传染成 AGPL。**可以读架构，不能拷代码。** |
| **targetSdk 31 + Vulkan** | ⚠️ 它需要 31 是因为它要 `Memory Limiter` 之外的一堆现代行为。**证道钉死 28 走不了这条路。** |
| **只在 S24 Ultra 验证** | ~~那是 **Adreno** GPU。证道的机器是**荣耀（Mali）**。③ Vulkan 驱动栈两家差异很大，"已验证"不能迁移~~ **2026-10-11 更正（`docs/ERRATA.md` E-110）：这句写错了。** Galaxy S24 Ultra 是 Adreno 750（骁龙 8 Gen 3），本机（荣耀 Magic 5 Pro / PGT-AN10，SoC `kalama` = 骁龙 8 Gen 2）是 **Adreno 740** —— **同厂商、相邻一代**，"荣耀"只是品牌、不是 GPU 厂商。⇒ "只在 S24 Ultra 验证"这条**不成立**，✅ 验证在这一层可以迁移 |

**⇒ 改后是两条独立的否决（`AGPL-3.0-only` ⛔ ＋ `targetSdk 31` 的现代行为要求 ⚠️）；原先第 ③ 条"GPU 型号不同、验证不能迁移"已按 `docs/ERRATA.md` E-110 撤回。**

### 2.2 🟡 Forge：MIT、Compose Canvas、**但只花了一天**

Forge 的许可证是 **MIT**（README 原文 "MIT — do whatever you want with it."），技术栈是 `alacritty_terminal` + `ropey` + `tree-sitter` + `rustix-openpty`，**全部与 GPL-3.0 兼容** ✅。

**但它的 Roadmap（② 原文）**：

| 阶段 | 内容 | 状态 | 计划工时 |
|---|---|---|---|
| 1 | PTY、ANSI 渲染、tabs、scrollback、额外按键行、**60fps** | **done** | **1d** |
| 2 | proot + Alpine + Node.js + git + Claude Code | **active** | 14d |
| 3 | 编辑器 + 文件管理 | planned | 21d |
| 4 | 手势 + 主题 + 会话持久化 | planned | 14d |

**Phase 1 只用了 1 天。**

③ 我的判断：**1 天做不出生产级终端。** 一个能用的终端至少要处理宽字符合并、OSC/CSI 边界、滚动区域、选区跨行、tmux 全屏重绘、IME 预编辑——Forge 把这一整个 Phase 标成 1 天完成，而 Phase 3/4 里**手势和选区根本还没做**（也就是说方案里最让你在意的"交互"，它也还没有）。

它自己的最新 commit 标题还写着：

> "fix: auto-open Claude Code tab after setup completes — **claude command only works in Debian proot session**"

⇒ 它连自己的 proot 会话都在调。而且它用的是 **Alpine**，后来换成了 **Debian**（和证道撞上了同一个问题），说明这条路**没有捷径**。

### 2.3 ⚠️ "60fps binary grid rendering protocol"是 README 的**一行 feature 清单**，不是测量报告

方案把这句当成技术论证。原文（②）：

> Features › Terminal › "60fps binary grid rendering protocol"

**全仓库没有 benchmark 代码、没有 p95 数字、没有 trace。** 这属于「**② 文档自述**」，而且是**营销段**不是工程段。

⇒ **它不能作为"这条路已被验证到 60fps"的证据。** 按我们自己的纪律，这类自述要防"过期/夸大"，这里连测量都没有。

## 3. 方案里唯一真正值钱的东西（而且和你的项目铁律一致）

Forge 的架构里有一条是对的：**"每帧只跨一次 JNI，传打包后的网格"**。

这和你项目里已经用过的经验**方向完全一致**：

> 「整条流水线在 native，边界只跨一次」——证道 2026-10-07 实测 10MB 跨 JNI：平台 5ms vs Rust 27ms，慢 5 倍 ⇒ 划算的形态是**一次跨界**，不是多次。

⚠️ 但**那个 10MB 的数字不能套到终端上**：一帧网格按 80×24 算，一个 cell 打包 8 字节也就 **~15KB**，比 10MB 小三个数量级。③ 所以"跨 JNI 一定亏"在终端场景**可能不成立**——**这也是为什么必须实测，不能靠推理。**

## 4. 一条被方案完全没提、但会绊住任何人的真实坑

`alacritty_terminal` 这个 crate 本身很干净（纯 `vte` + `unicode-width`，② `Cargo.toml`）。**但 Alacritty 整个项目没有 Android 支持**（② 官方 issue #7121）：

> 提问者：Android 没有 fontconfig，"This will cause Alacritty to crash on startup"，他靠把 Ubuntu 的 fontconfig 目录拷到 sdcard 硬编码环境变量绕过去。
> 维护者 chrisduerr 回复（**逐字**）："**There is no chance Android support will be upstreamed if it requires any significant changes.**"

③ 我的判断：**只要只取 `alacritty_terminal`（库）而不取 `alacritty`（主程序），fontconfig 这个坑碰不到。** 证道现在用 Termux 的 `WcWidth.java` 自己算宽度，本来也不依赖 fontconfig。

⇒ **但这意味着你必须严格只引入 `alacritty_terminal`，一旦引入 `alacritty` 主程序就会踩 fontconfig + OpenGL + winit 三连坑。** 方案里没提这条边界。

## 5. 结论（分三档，不含糊）

### 5.1 可行，且成本比上一轮说的低——但只限"换状态层"

| | 判定 |
|---|---|
| 只换**状态层**（`alacritty_terminal` 0.25, Apache-2.0）+ **保留/重写显示层用 Compose Canvas** | ✅ **可行**。许可证兼容、不碰 Vulkan（我上一轮说错的地方）、不碰 fontconfig、**CI 只差一个 cargo-ndk 步骤**、`.so` 打包和 JNI 调用**已有现成范例**（`CoreNative.kt`） |
| 换**渲染层为 wgpu/Vulkan** | ❌ **不建议**（**理由已按 `docs/ERRATA.md` E-110 更正**）。① ~~它在你荣耀的 **Mali** 上没有任何验证（Warp Mobile 只测了 Adreno）~~ → 本机 GPU 同为 **Adreno 740**（骁龙 8 Gen 2 / `kalama`），S24 Ultra（Adreno 750）的验证在这一层可以迁移，**此条撤回**；② 收益无实测支撑（`render()` 一帧 **2.3 ms**，判据 **>16 ms** 才谈换引擎 —— E-086）；③ 相比"只换状态层"多出整套 GPU/native 栈（体积 / 驱动面 / 16 KB 对齐面）而症状不在绘制侧；④ 唯一验证过的参考实现 Warp Mobile 是 AGPL-3.0-only，仍然 ⛔ 吸收不了 |
| 吸收 **Warp Mobile** 代码 | ⛔ **不可以**。AGPL-3.0-only 会污染 GPL-3.0 |

### 5.2 但换状态层解决不了你眼下任何一个问题

10-10 的终端审计出 **9 条问题，0 条是"引擎能力不够"**：

- 主线程搬缓存（`Store.adoptDir:170` → `copyRecursively:180`）
- `Workspace.kt:57` 前缀判断写错
- 网络预检往 pty 注入 `echo`（会喂给正在跑的 agent）
- 光标闪烁 Runnable 停不下来
- 触摸滚轮无 clamp

**这 5 条全出在显示交互层，和状态层用什么无关。** 换成 Alacritty 一条都不解决。

### 5.3 你真正想要的东西，方案里有一半是对的

你说"**很丑很臃肿**"——这是对 `TerminalView.java` **1589 行一个类管 6 类职责**的准确描述（10-10 实测：选区 55 / 闪烁 50 / 手势 44 / IME 43 / 无障碍 39 / 布局 20 处）。

**解法不是换引擎，是拆 + 重写显示层。** 这正是 `docs/archive/证道-终端显示交互层重写方案-2026-10-10.md` 的 P1/P2。

**而 Forge 恰好证明了这条路可行**：它就是 `alacritty_terminal` + **纯 Compose Canvas** + MIT。**方案里"最值得抄"的那个项目，反而是那个看起来最不高级的。**

## 6. 建议的下一步（把 ③ 变成 ①）

**不要再查方案了。方案的真实性已经查完了，剩下全是未知数，而未知数只能靠量。**

10 分钟量三个数：

| # | 量什么 | 在哪加一行 | 判定 |
|---|---|---|---|
| ① | `TerminalRenderer.render()` 每帧耗时 | `TerminalView.onDraw` 前后打点 | >16ms 才谈换引擎；<8ms 连宽度缓存都不用加 |
| ② | 中文屏 vs 英文屏差多少 | 同上，分两次跑 | 差值大 ⇒ 只需 `SparseArray<Float>` 缓存，**十几行，不必上 Rust** |
| ③ | 一帧网格打包后多大 | 算 `cols*rows*8` | **这个数决定 JNI 方案生死**（见§3 的更正） |

**如果 ① 出来 <8ms** ⇒ 换 `alacritty_terminal` 唯一的收益就只剩"宽字符/OSC 边界更准"，那不值得引入第二门语言。
**如果 >16ms** ⇒ 那时换状态层 + 二进制网格协议是成立的，而且我上一轮纠正后的构建成本估算（加 1 个 CI 步骤）说明它比你想的便宜。
