## 0. 一句话结论

**能 Rust 化的"高收益"目标已经没有了。** 项目已完成一轮有效的 Rust 下沉（sha256 / 解压 / Ed25519，统一进 `libzhengdao_core.so`），  
剩下真正还可做的只有 **1 个明确的低风险搭车项**（目录占用统计）和 **2 个"要做也该用 Kotlin、不该用 Rust"的伪候选**。  
**没有发现任何因性能瓶颈而必须 Rust 化的模块。**

> 证据等级说明：本报告每条结论标注 **[实测]** / **[代码走查]** / **[文档自述]** / **[推断]**。

## 1. 现状盘点：Rust 已经吃掉了什么

| 模块                                 | 现状                                                         | 证据                        |
| ---------------------------------- | ---------------------------------------------------------- | ------------------------- |
| SHA-256（一次性 + 流式文件）                | ✅ 已在 Rust（`rust/core/src/sha256.rs`）                       | [代码走查]                    |
| 归档流水线（zstd/gzip → tar → 落盘 + 流式校验） | ✅ 已在 Rust（`rust/core/src/extract.rs`）                      | [代码走查]                    |
| Ed25519 验签（清单 + 环境包索引两条信任链）        | ✅ 已在 Rust（`rust/core/src/ed25519.rs`），Kotlin 平台实现**保留作对拍** | [代码走查]                    |
| 统一产物                               | ✅ 单一 `libzhengdao_core.so`（948KB，已入库 `jniLibs/arm64-v8a/`） | [实测] `ls -la`             |
| PTY 终端读写                           | 已是 native（`libtermux.so`，C/CMake）                          | [文档自述]                    |
| zstd 解压内核                          | 一直是 native（`libzstd-jni-1.5.6-4.so`，C）                     | [代码走查] `build.gradle.kts` |

**Rust 代码规模**：`rust/core/src/` 6 个文件、**1,306 行**（含 253 行测试）。  
**Kotlin 规模**：`app/src/main` **20,369 行** + 测试合计 **26,422 行**。  
⇒ Rust 占比约 **6%**，且集中在"数据常驻 native"的形态上——这正是收益模型认可的形态。

**收益模型的铁律（PoC 实测得出，仍是本审计的唯一标尺）**：

- 单函数跨 JNI 搬大块数据 **永远亏**（10MB：平台 5ms vs Rust 27ms，慢 5 倍）；
- 划算的形态 = **输入输出都在 native、Java 只收小结果/进度**的流水线。

## 2. 本轮新发现：还可做的候选

### 候选 A —— 目录占用统计 `dirSizeMb` ⭐ 唯一明确推荐

| 项     | 内容                                                                                  |
| ----- | ----------------------------------------------------------------------------------- |
| 位置    | `ui/SystemInfoProvider.kt:265`（`walkFileTree`）、`terminal/CacheCleaner.kt:333`       |
| 现状    | 纯 Java `Files.walkFileTree` 遍历 `rootfs`(约 1.6GB) + `home`(可达数 GB)，**每次进设置页/首页全量重算** |
| 调用点   | `SettingsScreen.kt:249-251`、`HomeScreen.kt:824`、`PluginManager.kt:183/227`          |
| 形态契合度 | ✅ **天然适合**——输入是目录路径、输出是一个 Long，**数据全程常驻 native，边界只跨一次**（正是收益模型认可的形态）                |
| 预期收益  | 设置页"存储占用"从"秒级等待"变即时；无正确性风险（纯统计）                                                     |
| 成本    | 低。一个纯函数（`Sha256Stream` 同款模式），PC 上 `cargo test` 可验                                   |
| 回退    | 天然安全——Rust 不可用即走现有 Java 路径，结果一致（可对拍）                                                |
| 状态    | **已被 2026-10-07 评估列为"P2 搭车项"，但至今未实装**（本轮核实：`dirSizeMb` 仍是纯 Java）[代码走查]              |

**裁定：推荐做，但优先级"低"**——理由是**用户体验收益**（即时显示），**不是性能瓶颈**。  
若做，建议一并下沉 `CacheCleaner` 的目录求和（同一套 native 遍历）。

### 候选 B —— 索引 JSON 解析（`RootfsIndex` 的手写 `JsonReader`） ❌ 不建议 Rust 化

| 项                | 内容                                                                                                                                              |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 位置               | `rootfs/RootfsIndex.kt:205`（自写的 RFC 8259 读取器，约 150 行）                                                                                           |
| 为什么看似候选          | "手写 JSON 解析器"天然像 CPU 活                                                                                                                          |
| 为什么**不该** Rust 化 | ① 输入是**一个几百字节的索引文件**，一次解析微秒级——**跨 JNI 边界搬字符串的成本大于解析本身**（收益模型第 1 条直接适用）；② 手写解析器的价值是**容错语义**（半截下载判 null、字段缺失取默认），这套语义用 Rust 重写要**逐条复刻**，收益为零、风险非零 |
| 裁定               | ❌ **维持现状**。若将来真有解析性能需求，正确方向是 Kotlin 侧换 `kotlinx.serialization`（零边界成本），**不是 Rust**                                                               |

### 候选 C —— 资料库 `.docx` 抽取 / 摘要文本处理 ❌ 不建议 Rust 化

| 项                | 内容                                                                                                                                                                         |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 位置               | `terminal/DocxTextExtractor.kt`（212 行）、`terminal/KnowledgeBaseSummarizer.kt`（384 行纯函数）                                                                                     |
| 为什么看似候选          | "解 zip + 解 XML + 正则"像 CPU 活                                                                                                                                                |
| 为什么**不该** Rust 化 | ① **调用频率极低**（P3a 只在补摘要时跑一次，且受 `MAX_FILES_PER_RUN=40` 限制）；② 单文件上限 40MB、正文上限 200K 字符——**绝对量小**；③ 这些是**刚真机验证通过**的纯逻辑（E-063），Rust 化等于**用"已验证的稳定"换"未验证的重写"**，与项目"不在没收益时动刀"的纪律相悖 |
| 裁定               | ❌ **维持现状**                                                                                                                                                                 |

## 3. 明确不该碰的（重申既有红线，本轮复核仍成立）

| 模块                          | 判定    | 理由                                                                              |
| --------------------------- | ----- | ------------------------------------------------------------------------------- |
| PRoot syscall 拦截            | ❌ 不可动 | 第三方 C 二进制（GPL，Termux fork），重写=重写 proot 本身                                       |
| OpenCode 运行时（TS/Bun）        | ❌ 不可动 | 第三方；Rust 只能管生命周期，改不了其内存                                                         |
| 终端渲染（TerminalView/Emulator） | ❌ 不可动 | 热点在 Android 文本布局与 Canvas，不在计算；v3.9 刚付过切换成本                                      |
| Compose UI / Android 平台集成   | ❌ 不可动 | 与 AndroidX 生命周期、Compose 编译器深度耦合，Kotlin 最优                                       |
| 网络下载器                       | ⏸ 不下沉 | 瓶颈是带宽（实测 1.3MB/s 是源站给的）；换 Rust 要重写 TLS/代理/续传，风险 >> 收益                           |
| PTY 数据搬运 JNI 往返             | ⏸ 待数据 | 历史上终端卡顿主因是**渲染**不是搬运；P99 JNI 延迟 94μs 远低于 16.7ms 帧预算 ⇒ **反向证据**。需 Perfetto 证明才启动 |

## 4. 本轮审计的两个新观察（此前文档未提）

### 观察 1：`Ed25519` Kotlin 平台实现可能已可退役（但**建议先别删**）

- **事实**：`AgentManifest.kt:228` 的 Kotlin `Ed25519`（约 140 行 BigInteger 曲线运算）当前作用是  
  **"Rust 优先 + 平台对拍"**（`Ed25519Verify.verify`：两者结论不一致即**拒绝**）。[代码走查]
- **可优化点**：这是**纯计算**且**对拍两颗结果必须一致**，本身没有性能诉求。  
  既然 Rust 已稳定（E-051 起）并已覆盖两条信任链，理论上可以：把 Kotlin 版降级为  
  **"仅 Rust 不可用时才编译/执行"**，甚至完全删除——省 ~140 行 BigInteger 代码。
- **为什么不建议现在删**：
  1. 它是**安全关键路径的唯一独立实现**。删了就失去"双实现对拍"这个**免费的正确性保险**  
     （E-051 的整个价值就是两个独立实现互相印证）；Rust 侧如果哪天因 16KB 对齐静默加载失败，  
     对拍会立刻暴露，而单实现不会。
  2. `BigInteger` **不在 ART 原生加速范围**（与 SHA-256 不同），Kotlin 版确实比 Rust 慢——  
     但**验签每次只在打开清单/索引时跑一次**，慢几毫秒无感。
- **裁定**：**保留现状**。若要减代码，正确的做法是**先补一条断言测试**（Rust 与平台对拍必须一致），  
  确认长期稳定后再议删，**而不是现在为了少 140 行去拆掉保险**。

### 观察 2：Rust 侧 `progress` 回调的 R8 保号规则需长期维持（维护提醒）

- **事实**：`jni_bridge.rs:227` 的 `report_progress` 依赖 Kotlin 静态方法  
  `CoreNative.onProgress` **按名字查找**，而 R8 看不见 JNI 调用点 ⇒ 必须显式 keep  
  （这是 E-022 真机闪退的根因）。[代码走查]
- **风险**：这是**一条"看起来能删、删了就崩"的规则**。本轮核实 `proguard-rules.pro`  
  的 keep 规则存在且正确，但**审计未发现任何"防回归"的门禁**——如果将来有人清理  
  proguard 规则，或 R1 收编后符号名变了，会重新触发 E-022 那类**进程级闪退**。
- **建议**：加一条**静态门禁**（CI 或单测）：断言 `proguard-rules.pro` 里存在  
  `CoreNative` 的 keep 行，且 `jni_bridge.rs` 里引用的类名与之匹配。**成本 10 行，防的是闪退。**

## 6. 给决策者的一句话

**这条线已经很干净了。** 上一轮（2026-10-06/07）的裁定"没有任何模块值得为**性能**改 Rust"至今仍成立，  
且 Rust 该吃的（sha256/解压/验签）已经吃完了。剩下**唯一**名副其实的余地是 **`dirSizeMb` 目录统计**  
——它契合"数据常驻 native"的形态、风险低、可回退，但**买的是体验不是速度**。  
**建议：不新开 Rust 化批次**；若哪天顺手，把 `dirSizeMb` 搭车下沉即可。
