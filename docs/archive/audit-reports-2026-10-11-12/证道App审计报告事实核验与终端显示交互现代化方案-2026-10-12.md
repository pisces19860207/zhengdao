## 一、给用户的结论

**你说“Termux 看起来陈旧、改过之后还是差点意思”，这是合理的体验反馈；但“代码年代久，所以整个终端都要推倒重写”不是代码事实，也不是当前最稳妥的方案。**

当前项目不是原样照搬的 Termux 页面：Termux 上游终端组件基于 `v0.119.0-beta.3`，同时项目已有自己的配色、行间距/键高选项、绘制调整、输入法与手势职责拆分，以及独立终端页面。2026-10-10/11 的提交记录显示这些改动刚完成或继续修复。也就是说，**底层来源较旧和近期有定制并不矛盾**；近期调整改善了一些问题，但它们不等于重新设计了终端的整体视觉、操作模型与可访问性。

可行且相对稳妥的目标是：**重做证道自己的终端显示与交互体验，先保留已工作的终端模拟器、PTY 会话和 Debian 环境。** 不必把“现代化”绑定到换 Rust、换 JNI 或一次性重写全部终端协议实现。本次工作树已加入一个可切换的第一方 View 原型，包含独立 Canvas 网格 renderer 与触摸/滚动控制器；IME/硬件键盘直接复用 `TerminalImeBridge`。它目前只是待设备验收的实验入口，不是已验证可替换生产实现。

## 三、当前终端真实结构

项目中的“终端”不是一个可单独替换的黑盒，至少有以下三层：

| 层 | 当前实际职责 | 关键代码 | 更换影响 |
|---|---|---|---|
| **显示与触摸视图** | Android `View` 管绘制入口、尺寸、焦点、触摸事件、选择、输入法及无障碍代理。 | `com/termux/view/TerminalView.java` 与 `TerminalGestureController`、`TerminalSelectionController`、`TerminalImeBridge` 等 | 可先改，但要保留 IME、硬件键盘、滚动、选区、resize、无障碍等边界。 |
| **终端模拟器/屏幕状态** | 解读 ANSI/VT/xterm 控制序列，维护屏幕格、滚屏缓冲、颜色、光标、宽字符和程序状态。 | `com/termux/terminal/TerminalEmulator.java`、`TerminalBuffer.java` 等 | 替换风险最高之一；vim、tmux、shell 和 Agent TUI 都依赖协议兼容性。 |
| **会话与 PTY** | 启动 Linux 子进程，PTY 收发，线程/队列管理，更新行列尺寸。 | `TerminalSession.java`、`JNI.java`、`app/src/main/cpp/termux/termux.c` | 与视觉现代化关系小。重写会牵涉 proot、SessionManager、进程与会话保活。 |

项目自有的终端工具栏、底部快捷键条是外围 UI；重做它们不能单独解决用户指出的终端内部显示/触摸体验，所以不把它们当成本次主改造对象。

## 四、当前实现证据与“陈旧”判断的边界

### 代码能够确认

- `TerminalView.onDraw()` 调用 `TerminalRenderer.render()`，renderer 使用 Android `Canvas` 绘制固定列/行的字符网格。
- 当前 renderer 遍历可见行和列，并处理 ANSI 样式、光标、选区、合字、宽字符及字体宽度不匹配。项目注释记录的真机实验显示，单纯用 `invalidate(Rect)` 并没有跳过 `onDraw` 中的 Java 网格遍历；这不能推出 Canvas 一定慢，只说明那种局部失效优化没有达到预期。
- `TerminalView` 的多个内部职责已拆到手势、输入法、尺寸、选区、无障碍和光标控制器；这是结构整理，不代表终端交互已全部现代化。
- `TerminalPrefs.kt` 已有 Catppuccin Mocha 调色板、字号和间距选项；项目历史包含舒适行高/键高与配色调整。因此“完全原样 Termux、没有现代定制”不准确。
- 当前上游来源标注为 Termux terminal-emulator/terminal-view `v0.119.0-beta.3`，代码保留了项目修改与来源说明。上游版本号反映来源版本，不等同于该分支当前每项能力都过时。
- 当前 OSC 解析中处理了 OSC 52 等能力，但没有可见的 OSC 8 hyperlink 实现；“终端内链接目前不支持”这一点与源码相符，属于可明确列出的能力缺口。

### 不能仅靠静态源码断言

- 不能断言当前 renderer 在你的手机上卡、耗电或“不够现代”；没有本次性能采样和用户操作观察。
- Canvas 是 Android 正常的绘制 API，不自动等于过时。终端本身是定宽字符网格，Compose `Text` 不是可直接替代品；直接换成普通文本控件会失去终端单元格、ANSI 属性、鼠标报告、选区和 TUI 兼容能力。
- “很多代码多余”不能由 Termux 文件行数、来源年代或模块数量证明。先前 9,216 行的统计已更正为 8,186 行；体量大也不等于能安全删除。要识别冗余，必须追踪调用、协议依赖和测试覆盖。
- 旧报告中“每按键只改一个单元格”“渲染已经增量绘制”的说法不应再引用；当前代码会处理可见网格，设备帧时需另测。

### `terminal-view` 逐路径拆解（本轮源码核查）

把 `terminal-view` 理解成“只负责画字的 View”会低估它的职责。当前实现实际是一组彼此协作的显示、输入和 Android 系统集成代码：

| 路径 | 当前代码如何工作 | 替换时必须保留的行为 |
|---|---|---|
| **PTY 输出 → 屏幕** | `TerminalSession` 收到 PTY 数据后驱动 `TerminalEmulator` 更新屏幕并通知客户端；`TerminalActivity` 把高频屏幕更新合并投递到主线程，再调用 `TerminalView.onScreenUpdated()`。View 处理滚动位置/选区锚点后 `invalidate()`，`onDraw()` 再调用 Canvas `TerminalRenderer`。 | 线程切换与重绘合并、终端滚屏/选区保持、前后台会话更新；不得让输出高峰把主线程队列堆满。 |
| **字符网格绘制** | Renderer 以 emulator 的可见行列为网格，读取 ANSI 属性和颜色，绘制字形、光标、选区，并针对宽字符、合字及字体实测宽度差异做处理。它不是普通多行文本控件。 | 单元格列宽、光标/选区坐标、滚屏、ANSI 属性、宽字符和绘制基线必须与模拟器屏幕状态一致。 |
| **View 尺寸 → emulator/PTy** | `TerminalSizeResolver` 用 View 像素宽高除以字宽/行高，得到行列数，再调用 session 的 `updateSize()`；这会更新 emulator 与 PTY 的终端尺寸。字号/字体/行高变化也可能引发行列变化。 | 键盘弹出、旋转、窗口变化、缩放后要同步更新行列并验证 tmux/TUI resize；初始化时须先建 renderer 再 attach session。当前 Activity 对这个顺序和字号 px 换算有明确依赖。 |
| **触摸与滚动** | `TerminalGestureController` 按 emulator 模式分流：普通 transcript 本地滚动、mouse tracking 转鼠标滚轮、alternate buffer 转方向键；另处理惯性、点击、鼠标事件、双指缩放和长按选择。项目已有选区态滚动保护及每个 `onScroll` 回调最多 10 行的滚轮限幅。 | 不可只复刻“手指上下滑”：tmux mouse mode、全屏 TUI、普通 shell 历史和 alternate buffer 的语义不同；还要防手势与选区手柄/Activity 边缘返回冲突。 |
| **IME 与硬件键盘** | `TerminalImeBridge` 以 `BaseInputConnection` 保留 composing/commit/delete 路径；提交文本按 code point 送入终端，并把 IME 的换行转为回车。硬件按键另走 `KeyEvent`、键盘映射和 `KeyHandler`，修饰键/功能键也会读 Activity 的粘滞键状态。 | 中文输入法组合过程、退格、回车、Ctrl/Alt/Shift/Fn、硬件键盘及 Android 返回键必须分开测；不能把 IME 简化为“拿到字符串后写 PTY”。`onCodePoint()` 还连接证道资料库提示逻辑。 |
| **选择/复制/粘贴** | `TerminalSelectionController` 驱动 `TextSelectionCursorController`；选区通过 `ActionMode` 工具条和 `PopupWindow` 手柄呈现，拖动时按字符列换算坐标并做边缘自动滚动。复制/粘贴再经 session client 回到 Activity 的系统剪贴板实现。 | 触摸坐标、宽字符列、滚动后的选区、手柄拖动、复制/粘贴、更多菜单及 Activity/窗口销毁时关闭 popup，都是显示层替换的一部分。 |
| **光标与 Android 生命周期** | `TerminalCursorBlinker` 用主线程 `Handler` 驱动闪烁，跟随 emulator attach/detach；View 的 attach/detach 还会清理选区 popup/监听。 | 页面暂停/恢复、会话切换、设备息屏/唤醒、视图销毁后不能留定时任务或悬浮窗口；cursor mode 变化也要正确同步。 |
| **Activity 集成与无障碍** | Activity 设置 `TerminalViewClient`，接收缩放、点击、按键、代码点和 emulator-ready 回调；`TerminalSessionClient` 的输出回调再驱动屏幕更新。View 还代理 Autofill，并在无障碍开关启用时更新屏幕文本描述。 | 适配接口需要覆盖输出通知、输入写入、行列尺寸、焦点/键盘、选区/复制、光标状态、日志与生命周期，不能只提供一个 renderer 接口。 |

**耦合结论：** 近期 P1 拆分已把若干职责迁入控制器，但没有把 `TerminalView` 变成可直接插拔的模块。生产 Activity 仍直接设置 `mClient`、读取/比较 `mTermSession`，并使用 `mEmulator`、`mRenderer` 等公开成员；选区控制器也直接读取 emulator 屏幕及 renderer 字体度量。因而“保留 emulator/session，替换 View”在架构上可行，但必须先定义屏幕读取、尺寸更新、输入/回调和选择坐标的稳定适配契约，再逐步迁移。当前不是换一个 Android View 类就能完成的低风险替换。

**本轮发现的待核查代码风险（不是已复现故障）：**

- `TerminalSizeResolver.setTextSize()` 重建 renderer 后调用 `updateSize()`，但当新旧行列数相同时，尺寸更新分支不会 `invalidate()`；Activity 的双指缩放回调可直接调用 `setTextSize()`。若某次字号切换后行列数恰好不变，屏幕可能没有立即重绘到新字形尺寸。应补一个针对同网格字号变化的测试，并决定在字号变更路径显式失效；本轮未改代码、未做设备复现。
- `TerminalView.getCursorY()` 使用固定 `40px` 偏移，而同一类 renderer 的行高、基线和项目可配置行距是动态值；该函数由选区手柄拖动路径调用。它可能是历史坐标约定，也可能在特定字号/密度/行距下造成选区垂直偏差，需用不同密度、字号和行高实测后再判定，不能仅凭常数直接宣布为 bug。
- `TerminalA11yDelegate` 在构造时只读取一次 `AccessibilityManager.isEnabled()` 并缓存。若无障碍服务在 View 存活期间开启/关闭，屏幕描述更新分支可能仍使用旧状态；需要验证应用运行中切换 TalkBack 的行为，并考虑监听状态变更。

**现有回归证据边界：** P1 验收文档记录了特定 Honor Android 16 设备上的中文输入、两种回车、快捷键、复制粘贴和 tmux 滚动等真机检查；输入 `InputConnection` 另有 instrumented 自检。但这不等于全设备、所有输入法、TalkBack、所有 TUI/Unicode 情形都已覆盖。当前结论是“关键路径已有有价值的局部证据”，不是“整套替换已被验证安全”。

### 新视图原型的当前实现

已新增 `ZhengdaoTerminalView`，在独立 View 中绘制 emulator 屏幕网格，并使用自有 Canvas renderer 与触摸/滚动控制；模拟器、session/PTY、终端屏幕状态、尺寸 resolver、IME 桥接与选区基础设施仍复用现有实现。IME/硬件键输入直接委托同包的 `TerminalImeBridge`，没有再复制一份输入逻辑。renderer 对部分等宽 ASCII 字符按 run 批量调用 `drawTextRun()`，宽字符、组合字符及其他不满足安全条件的字形仍逐格绘制。它是**可运行的替代 View 原型**，但像素等价、真实输入法兼容、滚动/选择手感和完整 TUI 行为尚未设备验收；不能视作生产替换已通过。

输入回归页可通过 `modern_terminal_view=true` Intent extra 切换新旧 View，instrumented 自检分别覆盖两者的四个输入场景。启动示例：

```powershell
adb shell am start -n com.example.zhengdao/.ui.ImeRegressionActivity --ez modern_terminal_view true
```

原型采用新旧并行、可回退的方式，当前仅在输入回归页启用。设置 `JAVA_HOME=D:\Program Files\Android\Android Studio\jbr` 后，离线 `:app:testDebugUnitTest --tests com.termux.view.TerminalRenderRunGrouperTest :app:assembleDebug :app:assembleDebugAndroidTest` 已成功；分组 JVM 测试为 5 tests、0 failures、0 errors。真机/模拟器未连接，输入与视觉行为尚未设备验收。

## 五、明确推荐：证道自己的终端体验，保留可靠协议内核

### 目标方案

做一个**证道自有的终端显示与交互外壳**，但不要把它理解为“把一个旧 View 换成一个 Compose Canvas”：

1. **先决定目标体验，而不是先选 UI 框架。** 明确要改善的前三项是观感、读屏、滚动/选择、键盘操作、链接还是性能；选真实 Agent/TUI 建基线。
2. **保留终端模拟器、`TerminalSession` 和 PTY。** 先更新证道可控的呈现和交互：主题/字体/行距、滚动状态、选区与复制、快捷操作、链接交互和无障碍。
3. **若仍需换底层显示交互实现，再建立稳定适配边界并做替代原型。** 让新实现从 emulator 读取屏幕状态、把输入送到 session、把尺寸变化传回 PTY；逐项替换绘制、选择/手势、IME，不以“Compose 化”本身作为目标。
4. **只有协议需求无法由当前 emulator 满足时，才评估替换 emulator。** 单纯字体或视觉不满意，不足以支持重写终端解析器。

### 对仓库里 10 月 10 日 Compose 重写草案的复核

仓库有一份归档草案 [`docs/archive/证道-终端显示交互层重写方案-2026-10-10.md`](../docs/archive/证道-终端显示交互层重写方案-2026-10-10.md)，它提出保留 Termux 状态层/会话层、把 View/Renderer/手势/选区/IME 整体改成 Compose。这个**方向上“分层保留底层”是合理的**，但草案中的若干关键论据/估算现在不能照搬：

- 草案写“渲染慢”的依据已被更正：[`docs/证道-P0渲染层测量-2026-10-10.md`](../docs/证道-P0渲染层测量-2026-10-10.md) 与 ERRATA E-086/E-087/E-088 记录 `TerminalRenderer.render()` framestats draw 相位约 2.3ms、中英无可测差异；旧的 30–48ms 是帧总时长，不是 renderer CPU 耗时。随后“洪水时主线程解析把渲染饿住”的推断也已撤回。因此，**Compose 或 Rust 不能以“已证明渲染太慢”为理由立项**。单机测量也不证明所有设备均没有性能问题；只是目前没有足够证据称换技术栈会更快。
- 草案关于 Compose 可调用 Android Canvas 的思路可行，但它只说明技术上能够复用 `Canvas`/`Paint` 绘字，**不等于视觉会自动变现代、也不等于性能会提升**。Compose Canvas 仍要承接字符网格绘制，IMEs、手势、语义和生命周期仍需实现。
- 草案里 `TerminalView` 一个类承载多项职责的统计对应重构前结构。当前 HEAD 已在近期提交中将手势、IME、选区、尺寸、无障碍、光标职责拆为控制器；P1 重构与真机回归记录可在 [`docs/acceptance/terminal-view-refactor-p1-2026-10-10.md`](../docs/acceptance/terminal-view-refactor-p1-2026-10-10.md) 查看。所以“再做一次职责拆分就能解决大部分问题”和“Compose 是必要下一步”都不再是当前结论。
- 草案给出的 1–2 天 Compose、1 天手势、1 天 IME 等工时只是未经验证的估算；接入成本不只看 emulator/session 的方法数量，还包括屏幕状态观察/重绘、PTY resize、选择坐标、输入法 composition、焦点、无障碍、配置变化和 Activity 会话保活。不能把这份工时当承诺。
- 草案测试时快捷键条标了 18 个 id；当前验收文档已经修正为 17 个键。迁移前应以当前 XML 与 `wireKeyBar()` 为准，而不是复制旧清单。

**更新后的判断：** 不建议现在就把整套显示/交互层一次性 Compose 重写。更稳的工程方案是建立适配边界后，对真正需要改的部分逐个替换；Compose 可以用于外围工具、面板、状态和动画，核心终端字符网格可继续用 Canvas，也可在新原型中承载 Canvas 绘制。是否换框架由原型和维护目标决定，不由“现代”标签决定。

### 方案选项

| 方案 | 做法 | 难度/风险 | 评价 |
|---|---|---|---|
| A. 现有 View 内改善体验 | 保留当前已拆分的 View/控制器和 emulator/session；改视觉系统、交互反馈、链接与已知交互缺陷。 | 低到中；兼容风险最低 | **现在最适合先验证**。能给用户可见改善，不必先承担整层替换成本。 |
| B. 建适配接口后替换绘制器 | 把屏幕快照/行访问、尺寸、字体、选区、光标明确成接口，换 renderer；保留输入控制器和 emulator/session。 | 中到高；需要拆耦合和截图/兼容回归 | 若视觉设计或经实测确认的绘制限制无法在现 renderer 内解决，再做。 |
| C. 自研完整 View/显示交互层 | 第一方 View（可以含 Compose 外壳）承担渲染、滚动、选择、IME、焦点、无障碍；复用 emulator/session。 | 高；体验控制权最大，行为回归面也最大 | **可行的中长期自研目标**；用适配层和可回滚原型推进，不一次性删旧实现。 |
| D. 自研/替换 emulator | 另写或采用其他终端协议核心，再适配现有 PTY/session。 | 很高；TUI/Unicode/协议/维护风险显著 | 只有清晰的协议能力缺口或长期战略需求时立项。 |
| E. 全部重写（View + emulator + Session/PTy） | 重新实现 UI、协议、进程和 I/O。 | 极高；牵动 Linux 启动、进程生命周期和会话保活 | 与“不要太激进”的目标相反，当前没有证据支持。 |

**Compose 和 Rust 是不同层面的选择。** Compose 可用于 Android UI 的声明式布局；Rust 可以实现终端协议/屏幕状态核心。不能把两者合成“Compose/Rust 渲染器”一个决定。普通 Compose `Text` 不适合作为终端网格替代品；Rust 也不会自动改变视觉或交互。若将来选择 Rust emulator，仍由 Android 视图按屏幕状态绘制字符通常更符合 Android 系统输入、Canvas 与无障碍集成；需通过批量快照/事件接口避免每个字符一次 JNI。

## 六、具体改造蓝图

### 阶段 0：冻结行为基线，确认真正的“差点意思”

先从真实使用任务记录问题，而不是继续盲目改参数或直接换框架。用同一组样例运行当前版本并留截图/录屏：

- Agent TUI 的颜色、代码块、光标、选区和提示；
- vim/less/tmux 的全屏刷新、滚动、pane resize、鼠标/滚轮；
- 中英文、emoji、组合字符、宽字符、窄屏和字体放大；
- 中文输入法组合输入、复制粘贴、返回键、软/硬键盘切换；
- 当前主题/字号/行高在白天、低亮度和长时间阅读时的观感。

同时收集用户反馈类别：看不清、太挤、滚动难、选字难、键盘操作多、状态不明、视觉像旧终端、或某个 TUI 显示错误。先确定最影响使用的前三项。

### 阶段 1：不换内核，先做能感知的现代化

- 建立统一终端视觉 token：前景/背景、ANSI 调色板、选区、光标、边框/分隔、字体大小与行高；现有 Catppuccin 作为一个预设，不把单一主题当成全部设计。
- 增加可读的会话/滚动状态、合理的软键盘与快捷操作布局、可发现的选区/复制/粘贴操作。
- 为链接能力优先补 OSC 8：模拟器解析 open/close hyperlink 状态，屏幕行/单元格保存链接范围，视图绘制可见样式并通过长按/点击安全打开；外部 URI 必须做 scheme allowlist 与安全确认，避免终端内容任意跳转。
- 检查终端正文与外围工具栏的视觉层级，不在字符格中插入卡片式组件，不遮盖 TUI。
- 消除可确认的危险操作竞态，如 pane 关闭后固定延时输入确认字符；统一错误结果，不在失败时提前更新本地 pane 状态。

### 阶段 2：建立适配边界，再做绘制原型

- 为显示层提取最小接口：输入 emulator 屏幕状态、可见行列、字体/行距、光标/选区；输入事件输出到既有 session；尺寸变化回传 emulator/PTY。不要让外围业务 UI 依赖 renderer/emulator 内部可变字段。
- 记录这份接口的运行时调用频率与分配量；获取屏幕数据应按一帧/一批提供，避免每个字符或每个 cell 跨 JNI。
- 先以新旧 renderer 并行截图比对网格坐标、颜色、游标和选区；不让两个 View 同时驱动同一 session 输入。
- 做功能开关或可快速回滚分支，只对一组代表性 TUI 和设备启用新 renderer。
- 如性能问题明确，再评估缓存字形/背景、按行脏区或其他优化；每个优化都用帧时、CPU 与内存测量验证，不能仅凭 `invalidate(Rect)` 推断。

### 阶段 3：决定是否替换交互 View

如果用户测试显示滚动、选择、输入法和快捷动作仍是主要痛点，再新建证道 View，复用 emulator/session。按职责验证：

- 文本选择手柄、复制菜单与 TalkBack；
- 双指/单指滚动、鼠标滚轮与终端应用 mouse reporting；
- 中文 IME composing/commit/delete、硬件键盘和功能键；
- 屏幕 resize 时 emulator reflow、tmux pane 与 shell 行列一致；
- 终端焦点、Activity 返回、前后台、会话存活。

只有这些测试稳定后，才逐步移除旧 View 中已经迁出的重复代码。不要先按行数批量删除 vendor 源码。

#### 当前原型状态（2026-10-12）

- `ZhengdaoTerminalView` 在输入回归页中可通过 `modern_terminal_view` Intent extra 选择；不带该 extra 时仍走旧 `TerminalView`。目前没有切换生产页面的默认实现。
- 新 View 自己绘制字符网格，接管触摸/滚动、fling、缩放和鼠标报告；IME/硬件键行为直接由 View 内的 `TerminalImeBridge` 字段处理，不复制第二份输入实现。vendored `TerminalView.java` 只保留继承所需改动：移除 `final`，并抽出选区查询/手柄绘制两个 protected hook。终端模拟器、屏幕行数据、`TerminalSession`/PTY、尺寸 resolver、光标生命周期及选区基础设施仍沿用项目现有实现。
- 自动化输入回归页已分别覆盖新旧 View 的四个 IME 场景（候选拼音上屏、composition 中退格删组合符、提交后退格再输入、连续快速输入）。Android Studio JBR 下 `:app:assembleDebug` 与 `:app:assembleDebugAndroidTest` 成功。
- 当前没有连接设备（`adb devices` 仅列出表头），所以仪器测试没有实际运行；编译成功不等于设备输入/显示行为通过。
- surface 样式开启时，网格被缓存的圆角 `Path` 裁剪；未设置 surface 样式时，renderer 每帧用 emulator 当前背景色（反色模式下用前景色）整幅填充，避免透明背景/旧帧残留。
- renderer 将相邻同样式、同选区/光标状态、单列宽、可直接量度的 ASCII glyph 作为 run，批量调用 `Canvas.drawTextRun()`；宽字符、组合字符、变宽字形和状态边界不合并。背景格仍逐格绘制，稳态 Java renderer 不创建逐帧对象。为避免 shaping 差异，run paint 禁用了 kerning/ligature。新增纯 JVM `TerminalRenderRunGrouperTest` 覆盖同样式、样式边界、宽/组合字符、选区和光标边界；此测试检查分组决策，不是 Canvas 像素截图测试。
- `:app:testDebugUnitTest --tests com.termux.view.TerminalRenderRunGrouperTest` 已通过；测试报告为 5 tests、0 failures、0 errors。测试只依赖 JVM/JUnit，不调用 Android Canvas。
- **像素一致性尚未实测，不能宣称已证明逐像素相同。** 当前批处理限制在等宽 ASCII，并禁用了 run shaping 的 kerning/ligature；背景与装饰仍逐格绘制以尽量保持原几何/绘制行为。仍需在设备上对新旧 renderer 做截图逐像素比较。
- 自研手势控制器和 renderer 还没有新旧截图对照、完整 Unicode/TUI、mouse tracking、resize、TalkBack 或帧时测量；绘制兼容性、输入边界与滚动手感仍需设备验证。不可据此宣称新实现已可稳定使用或性能更好。

### 阶段 4：对 emulator 做基于需求的选择

先定义必需协议能力清单（VT/xterm 控制序列、256 色/真彩、OSC、键盘模式、鼠标、括号粘贴、alternate screen、Unicode 宽度与 reflow），用真实 Agent/TUI 程序建立回归样本。若当前 emulator 的某一项成为无法维护的限制，再评估替代库或上游升级；同时核许可证、Android 兼容性、维护活跃度、性能和 Rust/Java 接入成本。

## 七、项目风险与验收门槛

| 类别 | 必测项 | 通过标准 |
|---|---|---|
| 协议兼容 | shell、tmux、vim/less、主要 Agent TUI；ANSI/真彩、清屏、alternate screen、光标定位、mouse reporting | 无布局破坏、残影、输入错位或无法退出全屏程序 |
| Unicode/字体 | 中文、emoji、组合附加符、宽字符、字体切换、字号/行高切换 | 光标/选区与实际字符列一致；不得吞字、重叠或错列 |
| 输入 | 中文 IME composition、粘贴、多行粘贴、Ctrl/Alt/Shift、硬件键盘 | 不丢字、不重复、不把控制键当普通文本 |
| 尺寸变化 | 横竖屏、分屏、多窗口、软键盘出现/隐藏、tmux pane resize | PTY rows/cols、画面和光标位置一致 |
| 交互/无障碍 | 长按选择、TalkBack、触摸目标、减少动画、系统返回 | 关键动作可发现、可聚焦、可读出，不依赖颜色/长按教程 |
| 性能 | 初次显示、持续输出、光标闪烁、滚动、选择、resize 的帧时/CPU/内存 | 在目标低中高端机上达到事先设定指标；不凭主观“更流畅”验收 |
| 回退 | 新实现异常、终端会话仍运行时切回 | 会话不重启、不丢输入输出；版本升级失败可禁用新实现 |

## 八、报告的可靠性结论

- **可以信任为源码事实：** JNI 方法传递边界、Canvas renderer 与 visible-grid 遍历、主题/间距选项存在、OSC 8 当前未处理、顶部 pane 操作使用固定延迟输入、TerminalSession 的 PID 状态风险代码路径。
- **可以当作需要测试的风险：** pane 确认字符误入程序、终端掉帧、宽字符错位、访问性不足、用户觉得“老”。其中只有代码本身可见的触发/结构，不能替代实际复现。
- **不能沿用为当前事实：** 旧版“690 行死代码”“9,216 行 Termux”“已经 Canvas 增量绘制”“终端目录统计已经 Rust 化”“剩余 Rust 化候选为 0”等说法。
- **本报告建议是工程路径，不是已验证设计稿。** 当前已有可切换代码原型，Debug APK、Android 测试 APK 和 run 分组 JVM 测试已构建/通过；但没有设备测试、像素比较或性能测量。下一步应连接设备完成新旧回归，再用结果决定是否推进。

## 九、最终建议

最符合“不要太激进，但要跟得上”的路线是：**保留终端模拟器与 PTY，以新旧并行的可回滚方式验收证道自己的终端 renderer 与交互原型；修正已验证的协议/交互缺口后，再决定是否替换生产 View。** 目前没有必要全盘重写 Termux，也不应该仅因它来自旧上游版本就认定所有代码多余。

如果用户主观不满意在真实设备上仍然存在，应在回归页先验证当前代码原型，再以真实 TUI/设备结果判断视觉、手势与维护性是否达标；必要时仍可基于反馈制作多个视觉方向，而不是默认这份初稿就是最终设计。每个阶段先做小范围、可回滚、可测试的交付，再决定是否继续替换下一层。当前最明确的优先项是构建恢复、设备兼容验收和性能测量；**不是**承诺 Compose/Rust 后必然更快，也不是立即删除 Termux 派生层。
