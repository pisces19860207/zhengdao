## 2026-10-12 修订结论

Rust 代码确实接入了多个真实生产调用，但旧文档的终端分类、统计数字及“剩余候选为 0”结论不准确或证据不足。

| 能力 | 当前代码核实 | 归属与限制 |
|---|---|---|
| `extract` | `RootfsInstaller.extractArchive` 调用 Rust；rootfs 增量包也复用该入口。失败通常回退 Java，但 SHA 不匹配和空归档会硬失败，不回退。 | 环境安装。Rust 先流式计算归档 SHA，再重新读取归档解包；是一次 JNI 调用，不是一次文件扫描。 |
| `sha256File` | `RootfsDownloader.sha256Of` 调用 Rust 文件哈希，失败回退平台流式哈希；缓冲区为 128 KiB。 | 环境下载/安装校验。 |
| `verifyEd25519` | 环境索引和 Agent 清单均经 `Ed25519Verify` 调用 Rust，并与平台实现对拍；不可用时回退平台验签。 | 同时服务环境索引与 Agent 清单，不应全部归为“环境”。 |
| `dirSizeBytes` | `SystemInfoProvider.dirSizeMb` 调用 Rust，并在失败时回退 Java。 | 通用 UI 目录统计（主页/设置/插件等），**不等于终端缓存统计已 Rust 化**。终端 `CacheCleaner` 仍有独立 Kotlin 递归统计 `fileLengths`。 |

另有 `CoreNative.sha256Hex` 一次性字节数组摘要接口，但当前检索到的生产逻辑没有调用它；仪器测试会调用。旧文档的 4 行能力表因此不应被理解为“终端已有一项 Rust 能力”。

### 旧文档中已更正的事实

- `com/termux/**/*.java` 在旧文档所标记的 `adb9118` 与当前 `aeb2478` 均为 29 个文件、**8,186 行**，不是 9,216 行。`TerminalEmulator.java` 单文件为 2,533 行。
- `RootfsDelta.kt` 在 `adb9118` 与当前版本均为 **267 行**，不是 293 行；其中不只有清单编排，还包含目录树克隆、硬链接/复制、软链接重建及递归删除。
- 终端确实由 Android `Canvas` 绘制，但不能据此称为“每次按键只改一个单元格”或“增量绘制”。当前 `TerminalRenderer.render` 遍历可见行列；源码说明局部 `invalidate(Rect)` 能限制光栅化区域，却不会省去完整 `onDraw`/display-list 录制。GPU 加速与实际收益需要设备实测，旧文档没有提供本次测量证据。
- `dirSizeBytes` 的实现与调用归属是 `SystemInfoProvider`，而非 `terminal/CacheCleaner`。所以“终端 Rust 化 1 项”应撤回。
- `targetSdk=28` 当前配置属实；“是 proot 生死线”是项目设计假设，本次没有独立进行目标 Android 版本实验，不在本报告中确认为普适平台事实。

### Rust 化决策应如何表述

- 已确认以上列出的生产调用存在；这只能证明“已接入”，不能证明“比 Kotlin 快”或“达到收益预期”。没有真机基准数据，不下性能结论。
- “剩余可 Rust 化候选为 0”不是静态搜索可以证明的结论。终端 `CacheCleaner.fileLengths` 有 Kotlin 目录遍历，`RootfsDelta.cloneTree` 有文件树操作；它们是否值得迁移取决于真实耗时、I/O 瓶颈、语义差异与维护成本，当前证据不足以判为该迁或不该迁。
- 下一步应先用代表性大目录/归档做真机基准，并验证 Rust/Java 语义对拍；只有测出明显瓶颈且保持安全边界时，才考虑新增 Rust 批次。

## 三、环境还能再 rust 化吗？——核心已做，剩的是胶水

环境的计算流水线（解包 `extract` + 校验 `sha256File` + 信任根 `verifyEd25519`）已整体 native 化，正是裁定里「整条流水线在 native、边界只跨一次」的赢面样板。

| 环境剩余部分 | 性质 | 判定 |
|---|---|---|
| `RootfsInstaller` 的 Java 解包路径（commons-compress） | 故意留的**兜底**（native 失败时回退） | ✅ 保留，不能删 |
| `RootfsDelta.kt`(293 行，增量差分) | 清单/编排 | ❌ 裁定 ❌，ROI 低 |
| `RootfsDownloader` / `RootfsCache` | 编排 | ❌ 裁定 ❌ |
| `ProotLauncher` 参数组装 | 编排（见上） | ❌ 裁定 ❌ |

> ⚠️ **易混淆点**：你在终端里跑的 agent（Python / Node / Claude / agy）**本来就跑在 Debian guest 里，是原生 Linux 进程**，不在 App 的 Kotlin 层。所以「环境 rust 化」在 App 侧只涉及**安装/校验/解包**环节，已经覆盖。

## 五、建议（证据等级【②】）

- **维持现状**，不为终端/环境新开 Rust 批次。值得做的已做，剩下的都是裁定里明确「不该做」的编排层。
- 唯一 **borderline** 候选：`RootfsDelta` 的差分计算若将来变重（增量包很大），可收编进 `extract` 流水线；但现在是 293 行编排，ROI 低，**不急**。
- ⚠️ 红线照旧：`targetSdk=28` 是 proot 生死线，与 Rust 无关，**别动**。
