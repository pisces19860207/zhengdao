# 证道 App UI/UX、交互与过渡动画审计报告

**审计日期：** 2026-10-12  
**审计基线：** `main`，HEAD `aeb2478`  
**审计对象：** Android App 首页/丹房、太极对话、终端、权限引导、设置与插件等主要界面  
**审计方式：** 静态检查 Compose/Android View 实现、导航、交互状态、动画调用、主题与测试文件。未修改 App 源码。

> **范围说明：** 本报告可以核实代码里有什么交互和状态处理，但没有连接真机、录屏、检查 TalkBack/大字体，也没有做真实用户可用性测试。因此“点击目标是否好够到、页面是否拥挤、动画是否舒服、不同 ROM 上是否一致”等体验判断都列为待验证项，不冒充已复现结论。

## 一、执行摘要

当前 UI 已有不少基于真实使用问题做过的改进：三个主 Tab 的选中态图标有轻微弹动；安装/系统状态可折叠；权限引导集中成一页；重要状态有空态或明确错误提示；太极输入框考虑了软键盘避让、硬件键盘 Enter/Shift+Enter 和停止生成；部分自绘图标补了无障碍描述。整体方向是“浅色、卡片式、少跳转、终端独立全屏”，且注释显示不少调整来自真机问题反馈。

主要改进空间不是“加更多动画”，而是**让重要动作有一致、可预期、可撤销或可确认的结果**：

1. 太极授权审批抽屉已经提供“拒绝/允许”按钮；但外部点击与系统返回不关闭，缺少“稍后处理”语义，需核验返回键行为是否会让用户感觉被困住。
2. 终端分屏关闭操作靠固定延迟补发确认按键，存在输入误入正在运行程序的交互风险。
3. 当前有按钮按压缩放和长按级触感，但动画/触感模式没有统一策略；所有点击都触发 `LongPress` 触感，可能过强或造成无意区分。
4. 主 Tab 页面直接条件切换，没有页面内容转场；这有明确的生命周期理由（避免太极页面重叠打开 SSE），不建议简单加 Crossfade。可以在不重叠页面/不重建 Repository 的前提下，改进状态连续性和轻量反馈。
5. 当前自动化测试几乎没有覆盖主导航、关键对话框、权限引导、终端工具栏与太极输入状态；UI 体验回归更依赖人工。

**建议顺序：** 先修正危险或误导性输入流程与授权退出路径，再统一按压/加载/成功/错误反馈，随后用小范围动效提升页面状态变化可理解性，最后补 Compose UI 测试与真机可用性走查。

## 三、发现与建议（按优先级）

### P2 — 授权审批抽屉阻止隐式关闭，但没有“稍后”语义

- **证据位置：** `app/src/main/java/com/example/zhengdao/ui/taiji/TaijiComponents.kt`，`PermissionSheet`（约 1184–1198 行）。
- **当前实现：** `ModalBottomSheet(onDismissRequest = { /* 不允许点外面关掉——必须显式选择 */ })`，Sheet 内已有“拒绝”和“允许”两个按钮；注释明确不允许点外部关闭，以免用户盲批。
- **UX 风险：** 已有明确拒绝路径，不能称为“无法拒绝”。但如果用户只想暂离或需要先确认目标，系统返回/手势关闭因 no-op 不会退出，缺少“稍后处理”状态，可能让人觉得被困住。另一方面，直接允许外部关闭也可能令 Agent 保持等待，因此不能仅为便利而解除门禁。
- **改善方法：** 保留不允许误批的原则；可新增“稍后处理”按钮，将请求保持为待处理或显式取消等待，并让 Agent/UI 显示这一状态。也可将系统返回映射为一个确认弹层（“拒绝此次请求 / 继续查看请求”），不要静默丢弃或误批准。
- **验收：** TalkBack 可读出工具名、目标以及“拒绝/允许/稍后处理”；点外部不会批准；“拒绝”能解除 Agent 等待；“稍后”状态可恢复或明确取消；旋转/切后台回来状态不丢。

### P1 — 终端关闭 tmux pane 依赖固定 250ms 发送 `y`

- **证据位置：** `app/src/main/java/com/example/zhengdao/TerminalActivity.kt`，`btn_yellow` 点击处理（约 149–162 行）。
- **当前实现：** 发送 `Ctrl-b x` 后 250ms 无条件写入 `y`；本地 pane 计数同时递减。
- **UX 风险：** 这是时间假设，不是确认状态判断。若 tmux 未弹确认、焦点已在运行中的交互程序，或设备负载/终端响应时序不同，`y` 可能成为程序输入；计数也可能与真实 pane 数脱节。该项是交互正确性与潜在数据破坏风险，优先级高于动画。
- **改善方法：** 最优为配置 tmux 的 pane 关闭确认交互，按钮触发具备可靠状态确认的关闭路径；或通过专门的 tmux 命令/控制通道查询真实 pane 数并关闭指定 pane。避免固定 sleep 后盲发按键。关闭前如需二次确认，优先在 App 内呈现可读的明确确认 UI，确认后再发无提示的 tmux 操作。
- **验收：** pane 数为 1、2、未知；焦点在 shell、vim/编辑器、密码/确认输入、长时间运行任务时分别测试。任何场景均不得把确认字符泄漏给活动程序，按钮结果与 tmux 实际 pane 数一致。

### P2 — 触感反馈统一调用 `LongPress`，与普通点击语义不匹配

- **证据位置：** `app/src/main/java/com/example/zhengdao/ui/util/Press.kt`，`pressClickable()`。
- **当前实现：** helper 内每次 `onClick` 都执行 `HapticFeedbackType.LongPress`；同一 modifier 还会将内容缩放至 0.97 并播放 ripple。
- **UX 风险：** 普通点击发出“长按”级反馈，强度和语义可能不符合操作；系统/设备对长按触感的呈现差异较大，频繁点击卡片时可能显得过重。不是所有可点击控件都使用此 helper，反馈因入口而不一致。
- **改善方法：** 普通点击改用轻量、符合 Compose/Android 语义的触感类型；长按动作单独由长按事件触发相应反馈。将触感抽象成明确的反馈策略，避免点击 helper 同时承担普通点击和长按语义。保留缩放与 ripple 前先验证与 Material 默认交互叠加是否必要。
- **验收：** 在支持触感与不支持触感的设备测试；系统触感关闭时功能正常；连续快速点击不产生过强反馈；TalkBack/键盘激活控件仍有正确焦点与状态反馈。

### P2 — 页面切换“无内容转场”虽有合理原因，但页面状态变化反馈有限

- **证据位置：** `app/src/main/java/com/example/zhengdao/MainActivity.kt`，`HomeTabs` 的 `when(tab)` 页面分发和图标动画说明（约 654–805 行）。
- **当前实现：** 页面内容按当前 Tab 条件组合；只对 Tab 图标做 spring 缩放。代码明确不对页面做 Crossfade，因为新旧页面同时存在会让太极页面短暂开启第二条 SSE，并可能重复滚动/会话定位。
- **判断：** 不应把“缺少 Crossfade”简单记为缺陷；生命周期和连接所有权确实是约束。现有图标弹动提供了选中反馈，但切换页面的内容变化本身较突然。
- **改善方法：** 先验证切换时 Repository/SSE 单实例与列表滚动状态保持正确。若要增加过渡，采用不会同时组合两页的单页 `AnimatedContent`/替换式状态过渡，或仅对目标页根容器做短暂淡入；不要让旧太极和新 Tab 在转场时并存。也可保持不做页面动画，仅加强选中 Tab 的颜色、语义选中态与轻量触感。
- **验收：** 快速连点 Tab、太极生成中切换、终端打开后返回、旋转屏幕及后台恢复均无重复连接、重复请求、滚动跳变或页面闪白；在系统“移除动画”打开时动效应减少或关闭。

### P2 — 动画与动效偏好缺少统一规则

- **证据位置：** `MainActivity.kt` 的 `tabIconScale()` 使用 spring；`ui/util/Press.kt` 使用 `animateFloatAsState`；`ui/HomeScreen.kt` 使用 `AnimatedVisibility` 展开状态卡。
- **当前实现：** 已有轻量选中弹动、按压缩放和展开/折叠动画，但从本次搜索范围未发现统一的动效时长/距离 token 或系统移除动画偏好接入。
- **改善方法：** 定义少量动效 token（即时反馈、局部展开、页面替换），统一时长、缓动和位移；重要状态不只靠动画表达，始终同时更新文字/图标/语义。尊重系统减少动画设置；切 Tab 等高频动作避免 overshoot 过强、过长。暂不建议新增共享元素或复杂转场。
- **验收：** 60Hz/低端机上不卡顿；减少动画模式下仍能理解状态变化；动画结束前按钮状态不与真实业务状态矛盾。

### P2 — 交互状态应统一区分“加载、空、成功、失败、不可用”

- **证据位置：** `ui/HomeScreen.kt`、`ui/taiji/TaijiScreen.kt`、`ui/PermissionSetupScreen.kt`、设置和插件页面。
- **观察：** 代码已有多处良好反馈：刷新会话失败会保留旧列表并给重试 Snackbar；权限行解释可选权限；Home 页面包含问题卡和去向动作；按钮有禁用状态。但页面中仍混用 Toast、Snackbar、对话框与内嵌提示。
- **改善方法：** 制定反馈分级：可撤销/需操作错误用 Snackbar（带重试/查看日志）；持久状态显示在页面内；短暂成功用轻反馈；破坏性动作使用明确确认并说明影响。长任务优先显示持续进度及阶段文本，避免只靠 Toast 或旋转指示器。
- **验收：** 断网、权限拒绝、后台返回、重复点击、服务端超时、无数据和真实空列表均有不同且不矛盾的画面；失败不能呈现为零结果或成功。

### P3 — 自适应窗口、字号放大和布局压力需要系统走查

- **证据位置：** UI 页面主体在 `app/src/main/java/com/example/zhengdao/ui/`；有 `res/layout-w600dp/term_keys.xml` 资源变体，但本次检索未发现普遍使用 Compose `WindowSizeClass` 的布局规则。
- **风险/限制：** 静态搜索不能证明布局一定有问题；尚未核查所有组件在 600dp 平板、多窗口、横屏、屏幕缩放和 1.3–2.0 字体缩放下是否可用。
- **改善方法：** 以窗口宽度而非设备型号决定布局：窄屏维持单列与底部导航；宽屏可考虑导航栏/双栏，限制文本列最大宽度；对工具卡、模型名、路径和长错误文案测试换行与溢出。确保底部输入框、主按钮、系统导航栏/IME 不相互覆盖。
- **验收：** 360dp 窄屏、600dp/平板、横屏、分屏、字体放大、键盘弹出逐项截图走查；无横向溢出、被遮挡操作、裁切状态文案。

### P3 — UI 自动化与无障碍回归不足

- **现状：** 本次在 `app/src/androidTest` 中找到的 UI 相关测试主要是 Agent manifest 验签和 IME 回归自检；没有看到覆盖主导航、权限引导、设置返回、弹层、错误状态和终端工具栏交互的成套 Compose UI 测试。
- **改善方法：** 建立关键路径 UI 测试集，使用语义标签与用户可见文案定位控件，避免依赖屏幕坐标。对自绘 Canvas 图标逐个检查父控件语义、选中/禁用状态、触摸面积和焦点顺序。对弹窗加入返回键与 TalkBack 遍历测试。
- **验收：** 最低覆盖首次启动、主 Tab 往返、进入/返回终端、打开/关闭历史抽屉、发送/停止、授权同意/拒绝、设置深层返回、加载/失败/空态。

## 四、推荐的交互与过渡动效准则

1. **动作先反馈，结果再反馈。** 点击后立即有 pressed/ripple；异步任务开始时控件禁用并显示进度；任务结束后明确成功或失败。
2. **动画服务于状态，而非装饰。** 只有展开、选择、页面替换等空间关系变化使用动画；发送、授权、删除等关键动作不能只靠动画说明结果。
3. **避免把输入当控制通道。** 对终端发送确认键、快捷键等不得使用无确认状态的固定延迟；命令类交互应幂等、可取消、可诊断。
4. **保留可撤销性。** 删除、退出会话、关闭 pane 等高影响动作先说明对象和影响；可能时提供撤销，而不是立即执行后用 Toast 告知。
5. **减少动效优先级高于“统一炫酷”。** 先支持系统减少动画设置，再调 spring 参数；避免多个控件同时 overshoot 或重复震动。
6. **语义、视觉、状态一致。** 选中/不可用/进行中状态同时通过颜色、文字/图标、Compose semantics 表达，不能只靠颜色或动效。

## 五、优化实施计划

| 阶段 | 工作 | 交付与验证 |
|---|---|---|
| **0：基线采集** | 在真机记录首页、太极、权限、设置、终端关键路径；收集窄屏/大字号/键盘场景截图与短录屏；统计用户操作步骤与重复点击。 | 建立当前体验基线和截图集；不先改动画参数。 |
| **1：交互正确性** | 设计授权“批准/拒绝”流程；替换终端盲发 `y`；核对加载/失败结果不会伪装成功。 | 关键路径测试 + 真机验证；这是最高优先级。 |
| **2：反馈一致性** | 统一轻触感、按压效果、Snackbar/Toast/内嵌状态使用场景；为长操作补阶段反馈。 | 交互 token/组件清单及状态矩阵；对网络失败/权限拒绝做验收。 |
| **3：轻量转场** | 在不产生双页面组合和重复连接的前提下，试验单页面替换淡入或保持现有页面切换，仅增强 Tab 选中反馈；接入减少动画偏好。 | A/B 截图/录屏与连接数量、帧时验证；如无明确体验收益则维持无页面转场。 |
| **4：可访问性与窗口尺寸** | TalkBack、触摸目标、字体缩放、平板/横屏/分屏、系统返回逐项走查。 | 自动化 UI 回归 + 设备矩阵检查表。 |

## 六、建议的最低 UI 验收矩阵

| 类别 | 场景 |
|---|---|
| 导航 | 首次启动、跳过安装、底部 Tab 快速切换、设置/插件连续返回、终端关闭后返回 |
| 太极 | 空会话、长消息、生成中切 Tab、停止生成、权限请求批准/拒绝、服务断网恢复 |
| 终端 | 软键盘/硬件键盘、分屏创建/关闭、长按工具栏说明、复制粘贴、字号变化、终端保持后台 |
| 权限 | 首次授权、拒绝、系统静默拒绝、从设置返回、稍后再说、之后从设置补授权 |
| 可访问性 | TalkBack 焦点顺序、自绘图标描述、按钮选中/禁用状态、字体缩放、减少动画 |
| 设备适配 | 小屏窄宽、600dp 以上、横屏、分屏、多窗口、键盘弹出、系统导航手势 |

## 七、最终判断

当前 UI 已经包含不少来自真实反馈的修正，不建议整体重做或为了“现代感”统一加页面转场。优先解决**操作安全与结果可理解性**，再补一致的轻反馈和自动化回归。尤其是授权审批退出路径与终端 pane 关闭输入，应作为先于视觉动效的交互问题处理。

本报告是审计与改善建议，不代表以上代码已修改或所有体验问题已被真机确认。建议按实施阶段逐项落地，并用目标设备的录屏、UI 测试和用户任务完成率复核。
