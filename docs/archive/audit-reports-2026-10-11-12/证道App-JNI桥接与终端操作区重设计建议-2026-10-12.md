# 证道 App JNI 桥接与终端操作区重设计建议

**审计日期：** 2026-10-12  
**审计基线：** `main`，HEAD `aeb2478`  
**范围：** Rust `CoreNative` JNI、Termux PTY JNI、终端顶部三点与快捷键条，以及相关变更历史  
**性质：** 只读技术/交互审计与方案建议；未改 App 源码、未运行设备基准。

> 用户提出希望“另外做”一套终端操作 UI，不继续使用现有 Termux 风格的三点控件。本报告将“顶部三件套”按当前实现理解为红色离开终端、黄色关闭当前 pane、绿色创建分屏；若实际想指的是底部快捷键条或整个终端工具区，方案边界需要再调整。
>
> **范围勘误（2026-10-12）：** 用户随后澄清，真正想评估的是终端内部的显示、渲染和交互层，而非顶部红黄绿控件。本报告的 JNI 技术核查仍可参考；第四至第七节的顶部操作区方案不是该需求的解决方案，现由《证道App审计报告事实核验与终端显示交互现代化方案-2026-10-12.md》取代。

## 一、结论摘要

1. **JNI 暂时没有值得为性能而大规模重写的热点。** Rust 桥接主要传文件路径、摘要或一次性字节数组；终端 JNI 负责 PTY 生命周期和窗口尺寸等低频系统操作。解包按路径在 native 侧完成，避免把整份归档经 JNI 传递；终端输入输出主要走 PTY 文件描述符及后台读写线程。
2. **优先级应放在边界正确性而非微优化。** Rust 解包错误 JSON 需要正确转义；已审计出的终端未启动会话 PID 0 结束风险属于更高优先级的生命周期问题。性能优化应等真机基准确认瓶颈。
3. **顶部三点可独立于 Termux 引擎重做。** 当前 `TerminalView`、`TerminalEmulator` 和 PTY JNI 是 Termux 派生层；顶部红黄绿按钮、窗口栏布局和底部快捷键条是证道自己的 Activity/XML UI。重设计顶部操作区不需要重写 Termux，也不需要改 PTY/JNI。
4. **难度：顶部操作区重做为低到中；整套终端工具区重做为中；重写终端引擎或 JNI 为高且当前无必要。**

## 二、当前架构核实

| 层 | 当前实现 | 归属 |
|---|---|---|
| 终端绘制/模拟器 | `TerminalView`、`TerminalEmulator`，Android View/Canvas；由 Termux 上游衍生并由项目维护修改。 | Termux 派生 |
| PTY/子进程 JNI | `com.termux.terminal.JNI` 加载 `libtermux`，创建 subprocess、设置 PTY 尺寸、等待退出和关闭 fd。 | Termux 派生 C/JNI |
| 顶部三项动作 | `activity_main.xml` 中 `btn_close`、`btn_yellow`、`btn_split`；Activity 将其连接到 `finish()`、tmux pane 操作等。 | **证道自有 UI**，不是 Termux 的固定组件 |
| 底部快捷键条 | `term_keys.xml` 与 `layout-w600dp/term_keys.xml` 两种资源布局；17 个按键由 `TerminalActivity.wireKeyBar()` 逐一绑定。 | **证道自有 UI** |
| Rust JNI | `CoreNative` 加载 `libzhengdao_core`；覆盖 extract、文件哈希、Ed25519、目录统计等。 | 证道自有 Rust/JNI |

主要位置：

- `app/src/main/res/layout/activity_main.xml`：顶部红黄绿按钮、标题、复制/粘贴和终端主体。
- `app/src/main/res/layout/term_keys.xml`、`app/src/main/res/layout-w600dp/term_keys.xml`：窄屏/宽屏快捷键条。
- `app/src/main/java/com/example/zhengdao/TerminalActivity.kt`：按钮行为、快捷键发送、粘滞修饰键、tmux pane 计数。
- `app/src/main/java/com/termux/terminal/JNI.java`、`app/src/main/cpp/termux/termux.c`：Termux PTY JNI。
- `app/src/main/java/com/example/zhengdao/rust/CoreNative.kt`、`rust/core/src/jni_bridge.rs`：Rust JNI。

Git 历史显示，这套 UI 之前已经迭代过：三点触摸区曾从 11dp 扩到 30dp 并加涟漪；快捷键条改为窄屏两行、宽屏一行；顶部标题和复制/粘贴也多次为小屏布局调整。因此这不是简单“换颜色”问题，原布局已承担较多行为与历史兼容约束。

## 三、JNI 与桥接优化审计

### 3.1 Rust `CoreNative`：整体桥接形态合理

| 接口 | 当前边界形态 | 判断 |
|---|---|---|
| `nativeSha256File(path)` | 传一个路径字符串；native 以 128 KiB 缓冲流式读文件；返回短摘要。 | 保持即可。不要改成 `readBytes()` 后传整包。 |
| `nativeExtract(archivePath, targetDir, sha)` | 传路径/摘要；解压、落盘及校验在 Rust 内完成；返回短 JSON 结果和限频进度。 | 形态合理；优先改进结果编码可靠性，而不是再合并 JNI 函数。 |
| `nativeVerifyEd25519(pub,sig,msg)` | 一次传入三个字节数组，做一次完整验签并返回 Boolean。 | 对小签名消息属合理边界。调用端为安全对拍还会运行平台实现，CPU 成本可测后再讨论。 |
| `nativeDirSizeBytes(path)` | 一个路径进、一个字节数出。 | 边界简单；真实作用在通用 UI 目录统计，不代表终端 `CacheCleaner` 已改走 Rust。 |
| `nativeSha256Hex(ByteArray)` | 整个字节数组复制到 Rust 后计算摘要。 | 当前仓库生产路径未发现实际调用，仪器测试在用；无需单独优化。 |

### 3.2 值得优先处理：错误 JSON 的转义

- **位置：** `rust/core/src/jni_bridge.rs` 的 `to_json()`；Kotlin 端解析在 `CoreNative.parseExtractReport()`。
- **现状：** Rust 成功/失败结果由字符串格式化直接拼成 JSON；失败消息里的双引号、反斜线或控制字符没有 JSON 字符串转义。
- **影响：** 遇到带特殊字符的底层错误信息时，JSON 可能不符合规范；Kotlin 当前用正则读取 `error`，最可能的结果是错误信息被截断或转义内容失真，而非可靠地保留原始诊断。
- **建议：** 使用成熟序列化器（如 `serde_json`）或一个经过测试的 JSON string escaping helper；为引号、反斜线、换行、控制字符和非 ASCII 错误消息加 Rust 单测及 Kotlin 解析测试。不要只对路径做 ad hoc 替换。
- **优先级：** P2，正确性/诊断完整性修复；不是已测出的性能热点。

### 3.3 进度回调：只在真机证明确有开销后再改

- **位置：** `rust/core/src/jni_bridge.rs` 的 `PROGRESS_STEP` / `report_progress()`；Kotlin 入口 `CoreNative.onProgress()`。
- **现状：** 每累计约 200 个归档条目跨 JNI 通知一次；回调中创建字符串并写日志，不是每个文件一次。
- **建议：** 如果海量小文件归档的基准显示明显成本，再考虑按时间限频、只更新可见安装状态或每阶段回报，而非逐条目回调。普通体量安装包暂不需要为了理论减少 JNI 调用而改。
- **验收数据：** 对比关闭回调/当前回调的解包耗时、进度可感知性和日志量；同时验证取消/失败后状态仍能收尾。

### 3.4 Ed25519 双实现对拍：不要未经度量就删除

- **现状：** `Ed25519Verify.verify()` 调平台验签与 Rust 验签，并在结果不一致时按拒绝处理；Rust 不可用时回退平台。
- **判断：** 这是兼容性/安全对拍，不是多余的 JNI 往返。实际消息很短，一次 JNI 调用的边界成本相对有限；真正额外成本是第二次验签计算。
- **建议：** 先量测索引和 Agent manifest 验签总耗时。若测得启动或刷新成为可感知瓶颈，再比较发布版只用已验证实现、debug/测试版持续双实现的方案，并保留定期/发布验收对拍。不能以“少一次 JNI”作为唯一理由牺牲独立实现校验。

### 3.5 Termux PTY JNI：保留，不为 Rust 化而重写

- **接口：** `createSubprocess`、`setPtyWindowSize`、`waitFor`、`close`。
- **使用形态：** 创建进程和更新尺寸属于低频操作；读写数据主要经 PTY fd 和后台 I/O 队列，不是每按一个字符就跨 JNI 一次。
- **判断：** 当前没有证据表明 PTY JNI 是交互性能瓶颈。将它迁到 Rust 不会消除 PTY，也不会自动改善延迟，还会增加 Termux 派生代码的维护成本。
- **需单列修复的生命周期问题：** `TerminalSession` 的 `mShellPid` 初始为 0，但结束路径可能将未启动会话判为 running 后传给 `Os.kill`；PID 0 在 POSIX 下不是“无效子 PID”。建议结束前严格要求 `pid > 0`，并覆盖“创建后未 spawn 就关闭/重路由”的测试。此项是 JNI/进程边界正确性，不是性能优化。

## 四、终端顶部操作区重设计

### 4.1 问题不是三点大小，而是“视觉隐喻”和动作语义不匹配

当前布局使用 macOS 红黄绿交通灯视觉：

- 红点实际含义是**离开终端 Activity**；PTY 会话由进程级 SessionManager/前台服务保活，因此不是“关闭会话”。
- 绿点是**创建上下分屏**。
- 黄点是**关闭当前 pane**。
- 复制/粘贴是标题栏文字动作；终端快捷键又固定在底部工具条。

红黄绿提供了颜色区分，却没有直观表达三个终端动作；黄色“收回一块”和绿色“分屏”也要求用户先理解 pane 概念。长按查看说明说明视觉本身不够自解释；首次说明/帮助可以补充，但高频控制不应依赖记忆颜色或长按。

当前三项 30dp 热区已比早期版本改善，但标题栏还要容纳标题、复制和粘贴，小屏宽度仍存在争夺；三项操作也放在屏幕顶部，单手握持时不一定容易够到。以上为布局/交互风险，实际可达性需在目标机上试握验证。

### 4.2 推荐方向：证道自己的“终端工作台工具栏”

保留终端画布与会话不变，把 Mac 窗口隐喻替换为具名、可访问的终端操作区：

**顶部（导航与会话状态）**

- 左侧使用明确的“返回”图标/按钮：语义是离开终端页面、会话继续运行；不使用“关闭”来暗示 kill session。
- 中间显示短会话标题/环境状态，空间不足时缩短辅助信息，不挤压操作触摸区。
- 右侧放入“更多”或工具入口，容纳低频的复制整屏、终端重置、说明等；复制选区继续使用系统选择菜单。

**终端操作面板（pane 与会话）**

- 用文字+图标明确表达“分屏”“窗格”“切换窗格/布局”等动作；按钮使用至少约 48dp 可触摸区域，禁用态/未知状态用文字或语义表达，不只靠颜色。
- 将 pane 管理做成一个“布局/窗格”面板：展示当前 pane 数与方向，提供“上下分屏”“关闭当前窗格”“切换焦点”等具体动作。关闭动作要用可靠 tmux 命令/查询状态，不能依赖固定延迟盲发 `y`。
- 将单手高频动作放在拇指容易触及的位置，但避免挤占终端文本高度。是否做底部 dock、可收起工具条或浮动入口，先用静态原型对比单手可达性和终端可视行数，再定实现。

**底部快捷键条**

- 第一阶段先保留现有 17 键的发送语义与布局资源，只重做顶部三项。
- 后续若用户也希望替换快捷键条，再单独梳理高频键、修饰键状态、键盘弹出、横竖屏和 600dp 断点；不应将“换顶部三点”与“重做所有快捷键”绑成一次大改。

### 4.3 可选设计路线

| 方案 | 内容 | 优点 | 代价/风险 | 建议 |
|---|---|---|---|---|
| A. 具名顶部工具栏 | 移除圆点；导航、标题与“分屏/窗格”按钮用标准图标+文字/无障碍标签。 | 改动最小、语义比颜色清楚；保留终端空间；可渐进替换。 | 小屏要控制标题宽度，部分控制仍处顶部。 | **推荐先做原型**。 |
| B. 顶栏导航 + 底部可收起操作 dock | 顶部只放返回和会话信息；pane/复制粘贴等进入底部工具 dock，快捷键条独立保留或由 dock 切换。 | 单手触达好；主动作集中；可逐渐发展为证道自己的终端控制面板。 | 占用垂直空间；与两行快捷键条竞争；工具模式切换需清楚。 | 若实测单手够不到是首要痛点，再选择。 |
| C. 工具入口 + Bottom Sheet | 顶栏去掉三点，仅留返回、标题和一个工具按钮；点击后弹出操作面板。 | 终端视口最大；能放文字说明、pane 数和危险操作确认。 | 高频动作多一次点击；面板打开/返回状态需处理。 | 适合作为 pane 管理与低频工具，不建议把所有高频动作都藏进去。 |

**推荐组合：** 方案 A 先替换三点并保留现有底部键条；对“关闭 pane/切换布局”等较复杂操作使用方案 C 的面板。经过单手实测后，再决定是否把高频动作下移为方案 B。

### 4.4 实施难度与边界

| 改造范围 | 难度 | 主要修改 | 不需要改动 |
|---|---|---|---|
| 只替换顶部三点视觉和文案 | 低 | `activity_main.xml`、`TerminalActivity` 点击绑定、语义描述、触摸反馈。 | `TerminalView`、Termux emulator、Rust/PTY JNI、session 数据路径。 |
| 重做顶部动作交互（pane 面板、状态查询、危险操作反馈） | 中 | 新增 Activity/Compose 或 XML 控件状态、tmux 操作封装、pane 状态同步及测试。 | 仍可保留现有 TerminalView 与底层进程链路。 |
| 顶栏、底部快捷键条整体重做 | 中 | 同步窄屏/`w600dp` 布局或移除资源限定布局、重绑按键、重新适配 IME/横屏/大字号与 17 键语义。 | TerminalEmulator 内核和 PTY fd 通信。 |
| 重写 Termux renderer/emulator/PTY 或把 PTY 换 Rust | 高 | 需要重新实现终端兼容性、IME/选择/滚动/PTY 生命周期。 | 当前没有充分理由进入此范围。 |

因此，**“独立做一套 UI”并不难到需要动 Termux 内核**。更准确地说，顶部外观替换容易，交互可靠性和多尺寸适配需要中等工作；最难的是保证 pane 状态准确以及不破坏现有键盘/会话生命周期，而不是画新图标。

## 五、建议实施顺序

### 阶段 1：先定语义与静态原型

1. 明确红点代表“返回/离开页面，不结束进程”；把视觉文案改成“返回”。
2. 为“分屏”和“窗格操作”写清晰动词与动作后状态。
3. 画 2–3 个黑白/低保真原型，比较单手可达、标题空间和终端可视高度。
4. 不改 SessionManager、TerminalView、JNI，不改变现有快捷键条。

### 阶段 2：顶栏独立替换

1. 只替换 `btn_close / btn_yellow / btn_split` 的显示与布局，保留既有功能接口。
2. 使用清晰语义、焦点顺序、至少 48dp 热区和按压反馈。
3. 明确区分“返回”“创建分屏”“管理窗格”，不依赖红黄绿颜色。
4. 覆盖 360dp 窄屏、横屏、600dp 宽屏、大字体、TalkBack 和系统返回。

### 阶段 3：解决 pane 操作可靠性

1. 移除“发送 `Ctrl-b x` 后固定 250ms 盲发 `y`”。
2. 选择可观察/可查询的 tmux pane 控制方式；按钮展示真实或明确未知状态。
3. 关闭 pane 前对正在运行的任务给可理解的确认；错误时不更新本地 pane 数。
4. 测试焦点在 shell、TUI、vim、密码提示及长任务中的行为。

### 阶段 4：测量与决定是否进一步优化 JNI

分别记录启动终端、键盘输入响应、窗口 resize、解包、文件哈希、目录统计和验签耗时；区分 UI 绘制、文件 I/O、Rust 计算、JNI 和 Android 系统调度。只有测出 JNI/回调占比显著时，再做针对性微优化。

## 六、测试与验收清单

### JNI / native 边界

- 解包错误包含引号、反斜线、换行时，结果可被合法解析且错误可读。
- Rust 不可用时平台回退正确；哈希/验签结果与基准一致。
- 进度回调关闭/失败不留下 pending exception，不导致后续 JNI 调用崩溃。
- 未 spawn 的 TerminalSession 关闭时不向 PID 0 发送信号。
- 有数据的 PTY 会话在输入、resize、返回 Activity、前后台切换时持续正确。

### 顶部操作区

- 用户无需颜色记忆或首次教程即可说出“返回是否保留会话”“如何分屏”“如何关闭当前窗格”。
- 三个以上 pane/未知 pane 数时，界面不会误导用户认为还有容量或可以安全关闭。
- 任何 pane 关闭操作均不会向 shell/TUI 意外输入确认字符。
- 单手握持、左/右手、软键盘弹出、横屏和大字号下关键动作可用。
- TalkBack 读出按钮动作与状态；禁用状态有明确语义；点击与长按不会混淆。

## 七、最终意见

当前 JNI 的整体边界设计已经比较克制：不建议为了 Rust 化或“统一 native”而重写 Termux PTY，也不建议先优化理论上的边界调用次数。可落地的近期事项是：

1. 修好 Rust 解包错误 JSON 的转义。
2. 修复未启动会话的 PID 0 结束风险。
3. 将红黄绿三点从“交通灯隐喻”改成证道自有的具名操作区；先只做顶部，不碰 Termux renderer。
4. 把 pane 关闭从固定延迟盲发按键改为状态可靠、结果可观察的交互。
5. 为终端底栏/快捷键条后续改版保留独立阶段，不一次性重写整个终端。
