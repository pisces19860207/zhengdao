一句话结论
能 Rust 化的「高收益」目标已经没有了。项目已完成一轮有效的 Rust 下沉 （sha256 / 解压 / Ed25519，统一进 libzhengdao_core.so）。 剩下真正还可做的只有 1 个低风险搭车项（目录占用统计）， 以及 2 个「要做也该用 Kotlin、不该用 Rust」的伪候选。 没有发现任何因性能瓶颈而必须 Rust 化的模块。

规模对比

Rust 占比约 6%，且集中在「数据常驻 native」的形态上——正是收益模型认可的形态。
收益模型的铁律（PoC 实测，仍是本审计唯一标尺）
  • 单函数跨 JNI 搬大块数据 永远亏（10MB：平台 5ms vs Rust 27ms，慢 5 倍）。
  • 划算形态 = 输入输出都在 native、Java 只收小结果/进度的流水线。

2. 本轮新发现：还可做的候选

候选 A —— 目录占用统计 dirSizeMb 唯一推荐

位置：ui/SystemInfoProvider.kt:265、terminal/CacheCleaner.kt:333
调用点：SettingsScreen.kt:249-251、HomeScreen.kt:824、PluginManager.kt:183/227
  • 现状：纯 Java Files.walkFileTree 遍历 rootfs(≈1.6GB) + home(可达数 GB)，每次进设置页/首页全量重算。
  • 形态契合：✅ 天然适合——输入是目录路径、输出是一个 Long，数据全程常驻 native，边界只跨一次。
  • 收益：设置页「存储占用」从秒级等待变即时；纯统计，无正确性风险。
  • 成本：低。一个纯函数（Sha256Stream 同款模式），PC 上 cargo test 可验。
  • 回退：天然安全——Rust 不可用即走现有 Java 路径，结果一致（可对拍）。
  • 状态：2026-10-07 已列为「P2 搭车项」，但至今未实装（本轮核实仍是纯 Java）。
裁定：推荐做，但优先级「低」——理由是用户体验（即时显示），不是性能瓶颈。可一并下沉 CacheCleaner 的目录求和（同一套 native 遍历）。

候选 B —— 索引 JSON 解析（手写 JsonReader） 不建议

  • 位置：rootfs/RootfsIndex.kt:205（自写 RFC 8259 读取器，约 150 行）。
  • 看似像候选：「手写 JSON 解析器」天然像 CPU 活。
  • 为什么不该 Rust 化：① 输入是一个几百字节的索引文件，一次解析微秒级——跨 JNI 搬字符串的成本 > 解析本身；② 手写解析器的价值是容错语义（半截下载判 null、字段缺失取默认），Rust 重写要逐条复刻，收益为零、风险非零。
  • 裁定：维持现状 若真有解析性能需求，方向是 Kotlin 侧换 kotlinx.serialization（零边界成本），不是 Rust。

候选 C —— 资料库 .docx 抽取 / 摘要文本处理 不建议

  • 位置：terminal/DocxTextExtractor.kt（212 行）、terminal/KnowledgeBaseSummarizer.kt（384 行纯函数）。
  • 为什么不该 Rust 化：① 调用频率极低（只在补摘要时跑一次，受 MAX_FILES_PER_RUN=40 限制）；② 单文件上限 40MB、正文上限 200K 字符——绝对量小；③ 这是刚真机验证通过的纯逻辑（E-063），Rust 化 = 用「已验证的稳定」换「未验证的重写」。
  • 裁定：维持现状

3. 明确不该碰的（复核既有红线，仍成立）

模块判定理由
PRoot syscall 拦截不可动第三方 C 二进制（GPL），重写=重写 proot 本身
OpenCode 运行时（TS/Bun）不可动第三方；Rust 只能管生命周期，改不了其内存
终端渲染（TerminalView/Emulator）不可动热点在 Android 文本布局与 Canvas；v3.9 刚付过切换成本
Compose UI / 平台集成不可动与 AndroidX 生命周期、Compose 编译器深度耦合，Kotlin 最优
网络下载器不下沉瓶颈是带宽；换 Rust 要重写 TLS/代理/续传，风险 >> 收益
PTY 数据搬运 JNI 往返待数据卡顿主因是渲染；P99 94μs 远低于 16.7ms 帧预算 ⇒ 反向证据。需 Perfetto 证明

4. 本轮两个新观察（此前文档未提）

观察 1 · Ed25519 Kotlin 平台实现「可能可退役，但建议先别删」

  • 事实：AgentManifest.kt:228 的 Kotlin Ed25519（约 140 行 BigInteger 曲线运算）当前作用是 「Rust 优先 + 平台对拍」——两者结论不一致即拒绝。
  • 可优化点：纯计算，无性能诉求；Rust 已稳定（E-051 起）并覆盖两条信任链，理论上可降级为「仅 Rust 不可用时才跑」甚至删除，省 ~140 行。
  • 为什么不建议现在删：
    • 它是安全关键路径的唯一独立实现。删了就失去「双实现对拍」这个免费的正确性保险——Rust 若因 16KB 对齐静默加载失败，对拍会立刻暴露，单实现不会。
    • BigInteger 确实不在 ART 原生加速范围，但验签每次只在打开清单/索引时跑一次，慢几毫秒无感。
  • 裁定：保留现状 若要减代码，先补一条对拍断言测试，长期稳定后再议，而不是现在为了少 140 行拆掉保险。

观察 2 · Rust 进度回调的 R8 保号规则需要「防回归门禁」

  • 事实：jni_bridge.rs:227 的 report_progress 依赖 Kotlin 静态方法 CoreNative.onProgress 按名字查找，R8 看不见 JNI 调用点 ⇒ 必须显式 keep（E-022 真机闪退的根因）。
  • 风险：这是一条「看起来能删、删了就崩」的规则。本轮核实 keep 规则存在且正确，但未发现任何防回归门禁——将来有人清理 proguard 规则、或符号名变了，会重新触发 E-022 那类进程级闪退。
  • 建议：加一条静态门禁（CI 或单测）：断言 proguard-rules.pro 存在 CoreNative 的 keep 行，且与 jni_bridge.rs 引用的类名匹配。成本 10 行，防的是闪退。

给决策者的一句话
这条线已经很干净了。上一轮（2026-10-06/07）的裁定「没有任何模块值得为性能改 Rust」至今仍成立， 且 Rust 该吃的（sha256 / 解压 / 验签）已经吃完了。剩下唯一名副其实的余地是 dirSizeMb 目录统计——它契合「数据常驻 native」的形态、风险低、可回退， 但买的是体验不是速度。
建议：不新开 Rust 化批次；若哪天顺手，把 dirSizeMb 搭车下沉即可。
