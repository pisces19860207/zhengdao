## 0. 范围

UI/UX 评审的「交互三件」（§B 81 的 8 号）：
1. 卸载弹窗一按就跳终端，用户看不到执行了什么；
2. 体检「修复」用裸 `Thread`，没有进行中状态；
3. 下拉刷新是 350ms 假进度。

## 1. 卸载弹窗：让用户看见「要跑什么、删什么」

**现状**：`HomeScreen.kt:1201` 确认卸载 ⇒ `onOpenTerminal(cmd, null)` 直接跳终端执行；`:1209` 彻底删 ⇒ `onOpenTerminal(cmd + " && rm -rf " + wipe.joinToString(" "), null)`。弹窗里虽有说明，但执行内容（尤其 `rm -rf` 的路径）不可见，且「彻底删」只有一次点击。

**要求**：
- 弹窗里**显式列出**将要执行的命令或至少「卸载命令 + 将彻底删除的路径清单」（wipe 列表）；路径为空就不显示「彻底删」。
- 「彻底删」必须**第二次确认**（弹窗内两段式，或再弹一张确认卡）；第一次点击只进入确认态，不许直接跳终端。
- 跳终端前给终端一条**人话回声**（例如命令前加 `echo '证道：正在卸载 X…'`，或等价做法），让用户在终端里看到「在干什么」；不许静默只跑命令。
- 不改卸载命令本身的语义（`npm uninstall -g …`、`rm -rf` 路径集合不变），只改「可见/确认」这一层。

**测试**：源码门禁——彻底删路径必须有二段确认状态；跳终端的命令必须带可见回声/说明；wipe 列表必须进弹窗文案。负例：把彻底删改回一键直跳 ⇒ 红。

## 2. 体检「修复」：裸 `Thread` 改成有状态的 IO

**现状**：`HomeScreen.kt:667` 可修复项点击后 `Thread { EnvHealth.fixDetailed(...) ... }.start()`；按钮不置灰、可连点，进行中没有任何 UI 状态。

**要求**：
- 用现有 `scope`/协程 + `Dispatchers.IO`（或等价后台入口）替换裸 `Thread`；线程体里的 `try/catch`、复检、`IssueCenter` 上报、`healthEpoch++` 语义原样保留。
- 修复进行中：该行按钮禁用/显示「修复中…」，禁止连点；完成后恢复；失败按现有路径上报，不静默。
- 不改 `EnvHealth` 的修复逻辑，只改调用侧的线程与状态。

**测试**：源码门禁——该路径不得再出现 `Thread {`，必须有 `Dispatchers.IO`/协程与进行中状态；负例改回裸线程 ⇒ 红。

## 3. 下拉刷新：去掉 350ms 假进度

**现状**：`HomeScreen.kt:404-410` `onRefresh` 里 `ptrRefreshing = true; stateTick++`，然后 `delay(350); ptrRefreshing = false`；不管真实数据加载是否完成，350ms 后一定收起。

**要求**：
- `ptrRefreshing` 由**真实加载完成**驱动：加载 effect 在 IO 读完、状态写完后再置 false；保留一个**安全超时**（比如 10s）防止永远转圈，但不能用 350ms 假装完成。
- 保留 `stateTick++` 触发重载的机制，不新造第二条刷新路径。
- 若加载失败，也要收起 spinner 并给出已有错误提示，不静默。

**测试**：源码门禁——不得再出现 `delay(350)` 后无条件 `ptrRefreshing = false`；必须有「加载完成/失败/超时」三出口。可用纯函数/状态机测 spinner 的结束条件；负例改回 350ms ⇒ 红。
