## 0. 症状

用户装环境时，「验证 + 解压」阶段体感很慢。当前链路（读代码）：下载（`RootfsDownloader`，下载时算 sha256）→ `RootfsInstaller.installInto`：Rust 快路径单遍解包并校验（失败回退 Java）→ 写 marker → `swapLocked` 换树 → **旧树 `deleteRecursively()` 同步删除**。

**不许先优化**：先量出各阶段耗时，再决定治哪里。

## 1. 必做四件

1. **分阶段计时 + 可读日志**：下载 / 校验（若与下载同遍则记 0 并注明）/ 解包 / 写标记 / 换树 / 清旧树，各阶段耗时写 `RunLog`（一条汇总 + 失败时也写）。日志里带包大小与条目数。
2. **进度可见**：解包阶段 UI 显示「阶段名 + 已解条目数 + 已用秒」（Rust 若已回调 `onEntry` 就直接用；能拿到字节偏移再加百分比，拿不到不编）。用户在等的时候必须知道「在动」。
3. **旧树清理移出关键路径**：`swapLocked` 换树成功、marker 写好后，**先让环境可用/先提示完成**；旧树删除放到后台（失败只 log，留给启动 `cleanupPartial` 下次重试），不再让「安装完成」等到删完 1–2GB 才出现。
4. **去重复校验**：确认「下载时已验 sha256」的包，在 install 阶段**不再整包额外遍历一遍**（Rust 单遍解包同时校验即可）。源码门禁/日志断言：同一次安装对同一包只做一遍哈希。

## 2. 实测与判据

- 真机至少跑两次完整安装（同一包），给**阶段耗时表**（ms）与总时长；有旧树/无旧树各一次（第二次能体现「清旧树挪后台」的差异）。
- 改前/改后对比表；如果量完发现瓶颈是解包本身（CPU/IO 上限），如实写「瓶颈=X，本批不做」，**不许假装变快**。
- 源码门禁：旧树删除不得再出现在「完成提示之前」的同步路径；install 不得对同一包重复整包哈希。
- 全量单测 0 失败 0 错误；lint 预算不升。
