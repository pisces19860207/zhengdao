## 三、★ 那扇"时间锁"的门（为什么 C 是个决策而不是待办）

现在资料库能直接读写 `sdcard` 下的目录，靠的是**两个过期的许可**：

| 依赖 | 现状 | 什么时候会失效 |
|---|---|---|
| `targetSdk = 28` | 很低 | **上架 Google Play** 要求 target API 36（2026-08-31 起） |
| `requestLegacyExternalStorage = true` | Android 10 的临时豁免 | 一旦 targetSdk ≥ 30 就**彻底无效** |

**门一旦关上**：`File` 直接读写共享存储会失效 ⇒ 资料库的路径层要**整体换成 SAF**
（用户手动授权目录 + `DocumentFile` 逐文件读写），那是**另一次的工程量**，不是顺手能改的。

**已经预留的把手**：资料库的根路径收在一个函数里（`KnowledgeBase.root()`），
以后换 SAF 时**改这一处**即可，不必翻遍全项目。

**我的建议**：**现在不动**。理由：① 证道目前不走 Play（自己装）②
targetSdk 28 距离"设备侧最低可安装门槛"还有余量，不影响装机 ③ 现在改 = 白白引入风险和工期。
**只要记住"门在哪、把手在哪"，等真要上架时再开这一仗。**

## 五、明确**不做**的（如实列出，不是遗漏）

| 不做 | 为什么 |
|---|---|
| **P3b：PDF 正文** | **已决策**（2026-10-09 用户拍板）。见下 |
| **扫描版 PDF 的 OCR** | 难度与 PDF 不是一个量级（要引引擎、要下模型），**明确不做** |
| 老式 `.doc`（97-2003） | 格式是另一套（OLE 复合文档），投入产出比低；`.docx` 已覆盖绝大多数 |
| docx 里的图片 / 批注 / 修订 / 公式（OMML） | 摘要只需要正文；抽这些既没必要又容易出错 |
| 自动 / 定时跑摘要 | 等"免费模型不限流"确认后再谈（P2 方案第八节） |
| SQLite / 数据库方案 | 已定案：**给 agent 的知识库一律走"文件"**（见工作区记忆） |

### P3b（PDF）为什么不做（三条理由，已拍板）

1. **代价不对称**：`.docx` 是"顺手就做"（系统自带 zip）；`.pdf` 是"专门打一仗"
   （必须引第三方库 PDFBox-Android，扫描版还要再上 OCR）—— 投入差一个数量级。
2. **需求薄**：手机上看 PDF 的人本就少（正经设备是平板）；且"存在手机里"≠"想让 AI 去读"。
3. **服务"别人"更不划算**：证道是**自己装**的 App，不是给大众发的；
   多数人真正想要的只是**转成文字**——那交给终端 agent 用工具转即可（现有设计：产物放 `改版/`）。

**保留的能力**：`.pdf` **仍会出现在清单里**（只给文件名），**不报错**——
这是"不做"与"做不了"的区别。

**将来想捡起来**：完整方案（含"动工前必须先回答：这批 PDF 有多少是扫描版"）留档在
`docs/知识库-P3设计方案.md` §5，是**开工说明书**，不是待办。
