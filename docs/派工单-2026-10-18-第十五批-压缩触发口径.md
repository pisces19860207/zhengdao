## 0. 一句话

压缩的门槛现在只看「窗口比例」；1M 窗口下这道门等于不存在。本单把触发口径改成**两个条件任一满足就压**：① 估算 token ≥ `min(窗口×0.85, 120_000)`；② 同一会话里「待压的旧消息」超过 60 条。

## 2. 规格（三件，一件都不能省）

### 2.1 A 段：绝对上限（120k）

- 新增常量（放 `RunRules.kt`，纯判据内核）：`const val COMPRESS_ABS_MAX_TOKENS = 120_000`。
- 触发线 = `min(windowOf(provider) * COMPRESS_THRESHOLD, COMPRESS_ABS_MAX_TOKENS)`。
- **1M 窗口** ⇒ 触发线 120k（原来 891k）；**8k 窗口** ⇒ 仍是 6.8k（不变）；**窗口未声明**（回落 1M）⇒ 同上。
- 只改「触发线怎么算」，**不改** `COMPRESS_THRESHOLD` 的语义与取值。

### 2.2 B 段：旧消息条数（60 条）

- 新增判据：同一会话里「可压的旧消息」条数 ≥ 60 也触发。
- **「可压的旧消息」定义**：`history` 里去掉 `Compressor.selectCompressionRange` 保留的最近 `KEEP_RECENT` 条、再去掉 `NEVER_COMPRESS` 段之后的条数（**直接复用选区函数**，不要另写一套口径）。
- 调用点：`RunEngine` 里已经拿到 `history`，把条数传进判据即可（例如 `needsCompressing` 增加一个 `oldMessageCount: Int = 0` 参数，默认 0 ⇒ 老调用不受影响）。

### 2.3 C 段：两条都要有「不压」的反向保证

- 两条触发条件都满足不了 ⇒ 一定不压（不许出现「每轮都压」的抖动）。
- 压完之后**不要立刻再压**：保持现有冷却与「超线才压」语义（本单不改冷却）。

## 4. 判据（JVM，每条一例，测试名写清断言什么）

| # | 判据 | 断言 |
|---|---|---|
| J1 | 1M 窗口用绝对上限 | 窗口 1_048_576 ⇒ 触发线 == 120_000（不是 891k） |
| J2 | 小窗口仍按比例 | 窗口 8_192 ⇒ 触发线 ≈ 6_963（`8192*0.85`） |
| J3 | 未声明窗口回落 | `contextWindow == null` ⇒ 与 1M 同口径（120_000） |
| J4 | 旧消息条数触发 | 估算 token 远低于触发线、但可压旧消息 = 60 ⇒ `needsCompressing == true` |

| J6 | 默认参数不破坏老调用 | `needsCompressing(...)` 不传新参数时行为与改前一致 |
| J7 | 前缀不动 | 压过之后 `NEVER_COMPRESS` 段逐字仍在（回归，复用既有例） |

## 5. 负例（自己造红再改回绿，脚本化）

1. 把 `COMPRESS_ABS_MAX_TOKENS` 改成 `Int.MAX_VALUE` ⇒ **J1 必红**（1M 窗口又回到 891k）。
2. 把 60 改成 600 ⇒ **J4 必红**（60 条不再触发）。
3. 把「可压旧消息」直接用 `history.size` 代替 ⇒ **J4 或 J5 必红**（口径错）。
