## 0. 一句话

会话变长以后，抱朴现在只会进 `COMPRESSING` 然后原地打转；本单让它**真调一次模型把中段旧话压成一段摘要**，摘要落库、被压的消息标出来但不删，重启后摘要还在。

## 3. A 段规格

### 3.1 接线（在 `RunEngine` 里替换桩）

`compressWithFallback(history, provider)` 改成 `runCompression(sessionId, history, provider)`，步骤：

1. `val range = Compressor.selectCompressionRange(history)`；`range.isEmpty()` ⇒ 直接返回 `null`（别发空请求）。
2. `val choice = Compressor.chooseChannel(provider)`：`choice.degraded == true` ⇒ **不压**，记 `run_log` 一行 `compression_skipped_degraded`，返回 `null`（降级通道上压出来的摘要不可信）。
3. `Compressor.buildRequest(range, provider)` → 新增的 `LlmClient.completeOnce(...)`（非流式；`max_tokens ≤ 1024`、`temperature = 0.2`、**不传 tools**）。
4. 成功：`Compressor.parseSummary(text, range.ids, now, model)` 得 `CompressionRecord` → 落库 → 返回 `record.summary`。
5. 失败（超时/非 2xx/解析不出）：**不许把异常抛给整轮**。记 `run_log`（`compression_failed` + 状态码），返回 `null`，本轮按「不压」继续跑。

### 3.2 冷却（防死循环）

- 同一会话「压缩失败」后，**至少隔 10 步**才允许再试（`run_log` 里找最近一次 `compression_failed` 的 step 比较）。
- 成功压缩后，下一次触发必须**确实又超了触发线**（`probe.needsCompressing`），不许主动重压。

### 3.3 `LlmClient.completeOnce`

新增一个**只做一次请求、拿整段文本**的入口（内部可以复用现有 SSE 解析器，把流读完拼起来）：

- 入参：`provider`、`messages`、`maxTokens`、`temperature`、`timeoutMs`（默认 60 s）。
- 出参：`sealed` 结果，`Ok(text, model)` / `Failed(code, message)`。
- 红线：**不许**在压缩请求里带 `tools`／`stream`；**不许**把压缩请求计入用户可见气泡。

## 4. B 段规格（可追溯 + 不删）

### 4.1 落库（幂等迁移，照 `BaopuDb` 既有风格）

```sql
CREATE TABLE IF NOT EXISTS compression (
  id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL,
  summary TEXT NOT NULL,
  compressed_ids TEXT NOT NULL,   -- JSON 数组
  created_at INTEGER NOT NULL,
  model TEXT NOT NULL,
  source_tokens INTEGER NOT NULL,
  summary_tokens INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_compression_session ON compression(session_id, created_at);
```

DAO：`insertCompression(record)`、`latestCompression(sessionId): CompressionRecord?`。

### 4.2 组装侧跳过

`ContextAssembler.assemble(...)` 增加参数 `skipIds: Set<String> = emptySet()`：

- 历史段展开时跳过 `skipIds` 里的消息（**不是删消息，只是不进 prompt**）；
- 返回的 `compressedIds` 仍如实带出（判据 5 要的追溯）；
- **前缀段（`NEVER_COMPRESS`）不许受影响**（`ContextAssembler.kt:74` 那个集合是红线）。

### 4.3 会话恢复

`BaopuChatController` 构造（或 `BaopuRuntime` 加会话时）读 `latestCompression(sessionId)`：

- 有 ⇒ 把 `summary` 与 `compressedIds` 塞进引擎（引擎字段命名与现有 `compressionSummary` 保持一致）；
- 无 ⇒ 现状不变。

### 4.4 界面（只加一条，不做美化）

在消息流里插一张细条：

- 文案：`已压缩 M 条早期消息 · 摘要 x 字`（`strings.xml` 中英各一）
- 点开：展开摘要全文（`labelSmall`，可复制）
- **不给「取消压缩」「删除原始消息」按钮**（本单不做回滚；原始消息仍在库里）

## 6. 判据

### 6.1 JVM（每条一例）

| # | 判据 | 断言 |
|---|---|---|
| J1 | 选区正确 | `selectCompressionRange` 不动最近的 `KEEP_RECENT` 条，且不含 `NEVER_COMPRESS` 段 |
| J2 | 请求体不带 tools | `completeOnce` 组出的 JSON 里无 `tools`、无 `stream` |
| J3 | 成功路径落库 | 假一个 `LlmClient` 返回固定摘要 ⇒ `compression` 表多一行、`summary` 原样、`compressed_ids` 与选区一致 |
| J4 | 跳过生效 | 同一批消息 + `skipIds` ⇒ 组装出的 prompt 里**不再出现**被压消息原文 |
| J5 | 前缀不动 | 被压的会话里，`NEVER_COMPRESS` 段的内容逐字仍在 |
| J6 | 失败不炸 | `completeOnce` 返回 `Failed` ⇒ 本轮照常进入 `THINKING`，`run_log` 有 `compression_failed`，`compression` 表**不新增** |
| J7 | 冷却 | 失败后第 1 步不再发压缩请求，第 11 步才允许 |
| J8 | 重启可恢复 | 关库重开 ⇒ `latestCompression` 拿回同一条摘要与同一批 ids |
| J9 | 幂等迁移 | 旧库连开两次不报错、旧数据不丢 |

### 6.2 真机（缺一不算交付）

- **T1** 造一个长会话（连发 12 条长消息，每条 ≥ 200 字）⇒ 出现「压缩中」后**真的变短**：再发一条，看请求估算不再超线（截图 + `run_log` 里 `compression` 行）。
- **T2** `am force-stop` 重进 ⇒ 细条还在、点开能看摘要全文、对话能接着跑。
