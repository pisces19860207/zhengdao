## 二、重构方案：Hub 目标形态

**设计原则**：Hub 只做"菜单"，不做"仪表盘"；状态一律 ≤6 字；一行一个去向。

```
设置
─────────────────────────
环境
  环境与更新            已安装 ›
  存储与缓存            256 MB  ›
终端与资料
  终端与工作区          default ›
  资料库               12 个文件 ›
后台
  后台保活             指南 ›
─────────────────────────
  帮助                 新手指南 ›
  关于                 v2.0.16  ›
```

> **第二轮反馈修订（2026-10-12，用户原话「hermes那些检查…保留，不用细分那么多」+「插件有一个是太极页的，那个已经合到太极页了，另一个资料库/知识库才是终端用的」）**：
> 1. **删「插件」行**（上一版方案有，此版删除）：插件入口 2026-10-08 已搬进太极页（② `TaijiScreen.kt:134-138` 注释原话“从「设置」页搬进太极”，现为太极抽屉 → 插件面板，:517-518 复用 PluginsScreen），Hub 不再重复。附带清理项：设置侧 `onOpenPlugins` 死参数（② `SettingsScreen.kt:115` 声明未调用）与 MainActivity 不可达的 plugins 路由（② `MainActivity.kt:489/493`，全仓仅此三处引用），实施 P1 时顺手删。
> 2. **Hermes 保留单一入口、不细分**：环境与更新页保持一张「Hermes 依赖环境」卡（② `SettingsEnvActivity.kt:196`），首页体检表里它也是一项（② `EnvHealth.kt:130`），两处都不拆成多行多卡。
> 3. **「资料库/知识库」是终端向入口**：保留在 Hub「终端与资料」区（② `SettingsScreen.kt:204`），它就是终端挂载资料库的那一行。
> 4. 边界判断（③）：首页体检表的「uv 配置」虽涉 hermes 内嵌 uv，但它同时管系统级 `rootfs/etc/uv/uv.toml`（② `EnvHealth.kt:277-288`），并入 Hermes 会把系统配置问题误报成 Hermes 问题，故不合并。

| 变化 | 动作 | 风险 |
|---|---|---|
| 删 Root 行 + 说明 | 从 Hub 移除，内容并入"关于 → 开发路线" | 零（:221 起两段纯展示） |
| 搬三个 MB 数字 | 做成存储页页顶占用总览卡 | 零（数字在 `SettingsStorageActivity` 本来就有） |
| 删权限行 | "终端与工作区"页内"权限"卡已存在；待处理时该行右侧显示橙色"权限待处理"，并把权限卡排到页内第一张 | 低（需在页内做卡片排序） |
| 下沉输入回归页 | 改隐藏入口（如"关于"连点版本号 3 次） | 零（不影响功能） |
| 短状态文字 | 见上行右侧示例 | 零 |
| 行结构统一 | 标签 16sp 主色、状态 13sp 次要色（见第三节） | 低（改 `SettingRow` 一处，全 Hub 生效） |

Hub 加搜索框列为二期：现在 4 分区 + 6 二级页，找个设置要点 3–4 次；iOS 设置有搜索。但不是痛点首位，排 P2。

## 三、排版（Typography）：全 App 最弱的一环

### 3.1 现状（②）

- `ui/theme/Type.kt` 全文 36 行，**只覆盖了 `bodyLarge` 一个样式**（:12-19），其余全靠 M3 默认值。
- 设置行里：标签 = `bodyMedium + Normal + onSurfaceVariant`（:293-294），状态 = `bodyMedium + Medium + onSurfaceVariant`（:301-302）——**同样字号、同样颜色，状态还加粗了**。眼睛先读到状态，后读到设置名称，主次倒挂。
- SectionCard 标题 = `labelLarge + onSurfaceVariant`（:260-261），和行标签只差一个字重——分组标题、设置名、状态三级几乎无差别。

### 3.2 建议 type scale（中文场景）

| 用途 | 现在（②） | 建议 | 说明 |
|---|---|---|---|
| 页面大标题 | M3 默认 titleLarge 22sp | **24sp / 行高 32 / SemiBold**，`onSurface` | 2 倍以上跳跃从标题开始 |
| 分组标题（SectionCard） | labelLarge 14sp 次要灰 | **13sp / Medium**，次要灰，字距 +0.02em | 分组标题要"退后" |
| 行主标签（设置名） | bodyMedium 14sp 次要灰 | **16sp / `onSurface`（主文字黑）** | 设置名是主角 |
| 行状态 | bodyMedium 14sp 加粗次要灰 | **13sp / `onSurfaceVariant`**；就绪态用 `IOSReadyGreen`（已有令牌） | 状态退后为辅助 |
| 正文/说明 | bodySmall 12sp | **14sp / 行高 ×1.6** | 中文行高不低于 1.5 |

- 字体：现在全 `FontFamily.Default`（系统默认，各机型随机型）。**不建议**为此内置字体文件——包体已经很胖（rootfs 245MB），收益偏低；若将来要做"记忆点"，优先用排版处理而非换字体（③ 成本/收益判断）。
- 中文数字与单位：`rootfs 245 MB` 建议数字用等宽呈现或单位降灰度，三个数字改成页内总览卡后用表格对齐，不再挤在行尾。

### 5.4 「慢」与「突然出信息」：成因与无感化方案（2026-10-12 用户反馈）

**成因（② 代码原文）**：

1. 11 项体检**串行**跑在一条 IO 线程上：`EnvHealth.evaluate` 就是 `items.map { … }`（② `EnvHealth.kt:161/169-170`），总耗时 = 各项之和。
2. 慢项分布：`diskCheck` → `StorageAudit.totalCleanableMb` 走 **Java 递归遍历**（② `StorageAudit.kt:132/338` → `CacheCleaner.kt:537-545`，逐文件 `listFiles()`+`length()`），要扫 hermes 工具 / uv 缓存 / Agent 缓存几千个文件；`networkCheck` 在系统未标记验证时有 **1.2 秒 TCP 超时**（② `EnvHealth.kt:365-370`）；`resourceCheck` 读 /proc 采样。
3. **无缓存**：每次展开（② `HomeScreen.kt:181-187`）、展开态每次 ON_RESUME（② `:262-264`）都从零全跑一遍。
4. **全有或全无渲染**：结果未回填前卡片显示“环境体检中…”（② `:391-396`），然后 11 行**同时**出现——这就是“突然出信息、有点吓人”。

**无感化方案（纯 Kotlin，不动判定逻辑）**：

| # | 措施 | 做法 | 解决什么 |
|---|---|---|---|
| 1 | 缓存优先（stale-while-revalidate） | 上次结果留内存（可选落盘）；展开即渲染旧值，后台刷新，只更新变化的行 | 慢、空白、吓人 |
| 2 | 并行采集 | `coroutineScope { ITEMS.map { async(Dispatchers.IO) { … } } }`，墙钟耗时 = 最慢一项，不再是总和 | 慢 |
| 3 | 流式上屏 | 每项完成即发射（Flow / 逐项 state），快项先出；行级淡入，尊重系统减弱动效 | 突然出信息 |
| 4 | 分级刷新 | 快项（文件 stat，毫秒级）每次展开都跑；慢项（磁盘遍历、资源采样）30–60 秒内不重复 | 慢、重复等待 |
| 5 | 慢项旁路 | TCP 超时 1.2s → 600ms，且只配给“慢车道”，永不挡快行 | 慢 |

**Rust 帮不上忙，理由（②+③）**：

- 这套检查是 **I/O 与网络 bound**（文件元数据 syscall、/proc 读、一次 TCP 连接），不是 CPU bound——Rust 让 I/O 和网络延迟变小不了。
- 项目自己测过 native vs Java：SHA256 走 Rust 收益 **<2%**（② `EnvHealth.kt:436-438` 引 ERRATA）——那可是 CPU 密集型，收益都比这大。
- 唯一可能加分的是**目录遍历**：`dirSizeMb` 已经走 native（② `SystemInfoProvider.kt:266-272`，`CoreNative.dirSizeBytes`，边界只跨一次），但磁盘体检那条路（`StorageAudit` → `fileLengths`）没走。把审计切到 native 遍历可能砍掉最大的一块——但这是“改用已有的 native 函数”，不是“用 Rust 重写体检”，且**要先测量确认遍历真是瓶颈**（③）。
- 对照项目既定裁定：单函数跨 JNI 搬大块数据永远亏；“用 Rust 重写 EnvHealth”会是许多次小 JNI 跨越，正是最亏的形态。

**结论**：无感化 = 缓存 + 并行 + 流式 + 分级刷新（纯 Kotlin，确定性收益，估 1–2 天）；Rust 只在目录遍历一处待测量后可能加分。

### 5.5 数字类「先空后蹦」全点位与统一处方（2026-10-12 用户反馈「缓存的真实的具体数字也有这个现象」）

同一个病（异步测量 → 先占位 → 算完整体替换）在数字类界面还有 8 处（② 代码原文）：

| # | 位置 | 现象 | 证据 |
|---|---|---|---|
| 1 | 设置 Hub「存储与缓存」行 | 三个数字先显示 `…`（`mbText(-1)`），算完后**同时**变成真实 MB | `SettingsScreen.kt:119-121/151-165/170/188` |
| 2 | 存储页「存储占用」 | 三行「统计中…」→ 三个数字同时出现；审计明细**整列表**同时出现 | `SettingsStorageActivity.kt:191-193/198-220` |
| 3 | 存储页「缓存清理」 | 整卡「统计中…」→ 各目录尺寸成批出现 | `SettingsStorageActivity.kt:348-363` |
| 4 | 存储页「安装包缓存」 | 「统计中…」→ 数字 | `SettingsStorageActivity.kt:566` |

| 6 | 卸载确认弹窗 | 「尺寸统计中…」→ 两行尺寸文字出现 | `HomeScreen.kt:931-941` |

| 8 | 常驻通知内存行 | 「统计中」→「N MB」 | `SessionService.kt:246` |

**统一处方（纯 Kotlin，与 5.4 同族）**：

1. **落盘上次值**：测量结果写 SharedPreferences（项目已有 6 个 SP 文件，加一个即可），冷启动也有真实数字可显——这是“无感”的地基。
2. **旧值即显 + 就地更新**：有旧值就显示旧值（次级色或极小「约」字表示是上次的），新值到达时**只改那一个数字**，配 ~150ms 高亮/淡入，尊重系统减弱动效。
3. **逐项独立**：三个数字各自到位各自亮，不等齐（rootfs 先亮、cache 后亮完全可接受）。
4. **列表 stale-while-revalidate**：审计明细/包缓存列表保留上次内容，按 key diff 更新变化行，不整块重绘。
5. 治本提速：目录测量切到**已有的** native `dirSizeBytes`（② `SystemInfoProvider.kt:266-272`，边界只跨一次）；`StorageAudit`/`CacheCleaner.measure` 目前走 Java `fileLengths`（② `StorageAudit.kt:132/338` → `CacheCleaner.kt:537-545`）。先测后切（③）。

> 体验判据：用户任何一刻都不该看到「…」或「统计中…」占位（除非这台设备从未测出过值）；数字变化应是“这一个数在变准”，不是“一片数突然出现”。
