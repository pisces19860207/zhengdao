## 一、结论速览

**第一方代码（Kotlin / C / Rust）可以合法闭源。** 依据两条，都已在仓库内取证：

1. 唯一的 **GPL 组件 proot** 是「官方发行二进制、assets 内置、运行时释放为**独立可执行文件**调用」
   ——聚合分发，不链接、不混源（`PROVENANCE.md:52`；红线见 `PROVENANCE.md:64-69`：
   **只能 `exec`，绝不能 `dlopen` / `loadLibrary`**，且该红线**与文件名、目录无关**）。
   **法理依据（2026-10-11 补引，FSF 原文口径）**：FSF《GNU GPL 常见问题》的经典判据 ——
   **如果主程序与插件之间只用 `fork` 与 `exec` 通信，那么插件就是独立程序，主程序的许可证
   对它不施加任何要求**（<https://www.gnu.org/licenses/gpl-faq.html#GPLPlugins>；
   「聚合分发」口径见 <https://www.gnu.org/licenses/gpl-faq.html#MereAggregation>）。
   proot 正是这条：assets 内置官方二进制 → 运行时释放为独立文件 → 由 App 以独立进程
   `exec` 调用。**一旦改成 `dlopen`，关系就从「聚合」变成「衍生作品」**，整个 App 被 GPL 传染。
2. 终端渲染层聚合的 **Termux `terminal-emulator` / `terminal-view` 是 Apache-2.0，不是 GPL-3.0**
   （上游仓库整体 GPLv3，但这两个库属 Exceptions 例外；见 `PROVENANCE.md:58-62` 的许可证勘误）。
   Apache-2.0 **不传染**，义务是**四条**：**4(a) 随附许可证副本** ＋ 4(b) 标注修改
   ＋ 4(c) 保留版权与归属声明 ＋ 4(d) NOTICE（**不适用**：上游没有 NOTICE 文件）。
   逐条对照与正文位置见 `THIRD-PARTY-LICENSES.md` 末节与 `licenses/Apache-2.0.txt`。

> 判断口径：**GPL 会要求开源第一方代码，Apache-2.0 不会**——这条直接决定核心代码能否闭源，
> 属不可出错项（`docs/ERRATA.md:38-39`）。

## 五、变更规程（以后照做）

1. **新增第三方组件** → 同步更新 `PROVENANCE.md`（组件表 ＋ 必要时新章节）、`THIRD-PARTY-LICENSES.md`
   （含「需要随附哪几份正文」）与 `licenses/`（**新增正文要同时更新 `licenses/README.md` 的
   SHA256 与取回日期**），并回到本文件第二节加一行。
2. **换 proot / 字体等随包分发的二进制或资产** → 按 `PROVENANCE.md` 各自的「升级流程」走
   （取新版 → 算 SHA256 → 更新证件与 assets → 真机回归 → 提交），并同步更新官方 `.deb` 摘要。
3. **每次准备发版前**，把第三节九条门禁过一遍；**任何一条为否，先补文件内证据再落账**
   （流程见 `PROVENANCE.md`「落账流程」一节）。
4. **换 `LICENSE` / 改闭源策略属重大操作** → 必须先经项目所有者确认（本文件与
   `THIRD-PARTY-LICENSES.md` 的红线声明）。
