# 闭源切换清单（2026-10-11）

> **这份文件是什么**：把「本项目若要闭源 / 商业化分发，哪些组件允许、哪些必须履行什么义务」集中成一张
> 可逐项打勾的清单。它是**策略文档**，不是许可证审计的原始登记，也不是法律意见。
> **分工**：原始登记在仓库根 `PROVENANCE.md`（来源、上游版本、逐文件修改、红线）与
> `THIRD-PARTY-LICENSES.md`（随包分发物的第三方声明）；本文件只做「闭源决策视角」的归纳与门禁。
> 三份文件如有冲突，**以 `PROVENANCE.md` / `THIRD-PARTY-LICENSES.md` 为准**（它们是取证现场）。

## 一、结论速览

**第一方代码（Kotlin / C / Rust）可以合法闭源。** 依据两条，都已在仓库内取证：

1. 唯一的 **GPL 组件 proot** 是「官方发行二进制、assets 内置、运行时释放为**独立可执行文件**调用」
   ——聚合分发，不链接、不混源（`PROVENANCE.md:52`；红线见 `PROVENANCE.md:64-69`：
   **只能 `exec`，绝不能 `dlopen` / `loadLibrary`**，且该红线**与文件名、目录无关**）。
2. 终端渲染层聚合的 **Termux `terminal-emulator` / `terminal-view` 是 Apache-2.0，不是 GPL-3.0**
   （上游仓库整体 GPLv3，但这两个库属 Exceptions 例外；见 `PROVENANCE.md:58-62` 的许可证勘误）。
   Apache-2.0 **不传染**，义务仅为保留 LICENSE / NOTICE 与标注修改。

> 判断口径：**GPL 会要求开源第一方代码，Apache-2.0 不会**——这条直接决定核心代码能否闭源，
> 属不可出错项（`docs/ERRATA.md:38-39`）。

## 四、开放项（未完成 / 未逐项核实）

- **proot 的构建 commit 尚未记录**：红线第 6 条要求记录（用于源码要约的可复现性，`PROVENANCE.md:191`），
  但 `PROVENANCE.md:106-121` 目前只有版本号与四个文件的 SHA256。**待补**：拿到 Termux 官方包对应的构建
  commit（或 packages.termux.dev 的构建元数据）后写入该节。
- **rootfs 内各 Debian 包的版权文件未逐包核**：`THIRD-PARTY-LICENSES.md` §7 已登记发行版来源与整体口径，
  但没逐包点数（rootfs 是 200 MB 级、上千个包，逐包核成本高）。**未实测·推断**：Debian 官方镜像的包都带
  `copyright`，闭源分发时义务是"保留"而非"逐条引用"，因此**当前不阻塞**；真要坐实可在 rootfs 内跑
  `grep -rl "License" /usr/share/doc | wc -l` 之类做抽样。
- **闭源后 release 资产（rootfs tarball 等）的下载可用性**：rootfs 走 GitHub Release 资产，闭源只改源码
  可见性，不影响资产下载；但**若将来换成私有 release**，需重新确认 App 端下载与校验链路（未验）。

## 五、变更规程（以后照做）

1. **新增第三方组件** → 同步更新 `PROVENANCE.md`（组件表 ＋ 必要时新章节）与 `THIRD-PARTY-LICENSES.md`，
   并回到本文件第二节加一行。
2. **换 proot / 字体等随包分发的二进制或资产** → 按 `PROVENANCE.md` 各自的「升级流程」走
   （取新版 → 算 SHA256 → 更新证件与 assets → 真机回归 → 提交）。
3. **每次准备发版前**，把第三节八条门禁过一遍；**任何一条为否，先补文件内证据再落账**
   （流程见 `PROVENANCE.md`「落账流程」一节）。
