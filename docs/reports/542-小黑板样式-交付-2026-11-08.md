### 为什么这三个色不进 `ui/theme/Color.kt`

`ContrastGuardTest` 有一条硬门禁：**`Color.kt` 里不许再有绿色常量**（§2.1 色数收敛，语义绿「已就绪」已删）。A 案的绿不是语义色，是一块**实体板子的物性色** ⇒ 照玄览底栏 `XuanLanPalette` 的房型另开 `ui/baopu/BoardPalette.kt`，并用门禁钉住**只许小黑板那一屏引用**（`BoardStyleGateTest` 扫全 main 源码：除色板自身，只有 `GovernanceCenterScreen.kt` 提到它）。语义色板里仍然一个绿都没有。

### 截图证据（不只"看值"，还看像素）

模拟器 zdga（Android 16，1080×2400，软件渲染）截图上直接采样，三档色**逐值命中**：

```
#1F3B2F 29,328 像素   ← 板面底
#F2F1E6    856 像素   ← 板面正文与「清空」
#C9C9BE    297 像素   ← 顶上那行、上限、占位
```

对比度（WCAG 相对亮度当场重算，与 `ContrastGuardTest` 同一把尺）：

| 配对 | 比值 | 门槛 |
|---|---|---|
| 板面正文 / 板面底 | **10.73 : 1** | AA 4.5 ✔ |
| 板面小字 / 板面底 | **7.29 : 1** | AA 4.5 ✔ |
| 负例：次墨 `#57544C` / 板面底 | 1.61 : 1 | ✘（证明这把尺不恒真） |

`BoardPaletteContrastTest` 把这个算式写成了四例门禁（三值逐字相等 ＋ 两条 AA ＋ 一条负例）。

## 2. 可见性：免解锁，但不念名字

### 2.1 机制（唯一一条可见性链上多一个 `||`）

`ToolGroup.UNLOCK_FREE_SILENT = {board_read, board_write, governance_state}`（唯一定义处）。

| 出口 | 变化 |
|---|---|
| `isVisibleTool` | 组锁着也可见／可调（用户两道开关照旧先判，压在它前面） |
| `filteredReasonOf` | 同进同退（`FilteredReasonConsistencyTest` 的「可见 ⇔ 原因为空」仍成立） |
| `capabilities` 名册 | **两处都不念名字**：组内工具行、「当前可见工具（N 个）」行 |
| `ToolGroupTable.checkCoverage` | 名单里的名字必须真在分组表里，写错一个字母 ⇒ 装配期直接抛（fail closed） |

### 2.2 为什么不塞进既有两条通路

- **不塞 `defaultVisibleTools`（157 那条）**：它被 `register()` 的只读闸钉死，写类进去装配期就炸（`board_write` 是写）；
- **不塞 `DEFAULT_VISIBLE` 的某个组（如 CORE）**：会破「默认可见 ≤12」那张硬卡，也会让名册把三件念成 CORE 成员——判据④要的正好相反。

### 2.3 三条没松

1. **用户开关优先**：关掉 FILES 组，三件一起消失（有单测）；
2. **注册与矩阵保留**：仍是 FILES 组成员，`RiskMatrix` 两行（R0 / R1）原样，设置页逐件开关仍可用；
3. **落点不变**：仍只写 `<工作区>/产物/.board.md`，`BoardStore` 仍是唯一碰盘处（新增的 `updatedAt()` 也在它里面）。

### 2.4 顺手改掉的两句假话

两件工具的描述原本写着「（这个工具在 FILES 组：看不到就先 capabilities 解锁）」——542 起这句是假的，已改成「免解锁：组锁着也照样可调，不用 capabilities 申请」。**工具描述是注入面**，留着假指引会让模型去申请一个根本不必申请的组。

## 6. 真机（模拟器）上抓到的一个真 bug——已修，并补了门禁

第一版在**截图上**才发现：右下「清空」不见了。`uiautomator dump` 里连节点都没有——不是颜色问题，是**布局**问题：
`BoardText` 自带 `Modifier.fillMaxWidth()`，而它也用在同一行的底部 `Row` 里 ⇒ 它吃满整行，`Spacer(weight)` 与按钮被挤到可视区之外。

- 修法：`BoardText` 去掉 `fillMaxWidth()`（正文换行不靠它，`Text` 本来就按父约束换行）；
- 补门禁：`BoardStyleGateTest.BoardText不许fillMaxWidth_否则右下清空被挤到屏外`（变异 M5 已验证会红）；
- 教训与 428 N2 同型：**同一件事在"值对不对"与"东西在不在"之间，只有截图能判后者**——所以判据①的"含截图"不是形式。

## 8. 裁量与挂账（请验收方裁）

1. **「12sp」落成了 13sp**。用户给的是「`#C9C9BE` 12sp」，但律令字阶只有 34/22/17/15/13/10 六档，**没有 12**；同一句里更强的约束是「字号一律用律令既有 token」⇒ 取了最接近的 `labelMedium`（13sp）。1sp 的差在 1× 下肉眼不可分；**要字面上的 12sp 就改一行**（`BoardTitleLine` 的 `style`），随手改的代价是把第七个字号带进树里。**这条请裁。**
2. **截图来自模拟器，不是真机**。本机 `adb devices` 空（无设备会话），用 AVD `zdga`（Android 16，1080×2400）安装本单 debug 包后截图；模拟器时区是 GMT，所以图上「最近更新 14:28」＝本机 22:28。真机要复看的话，就三眼：板面色、顶上那行、右下清空。
3. **判据③ 的证据是 JVM 行为级，不是"模型真的调了一次"**。这台模拟器没有模型配置（顶栏「未配置」），发不出一次真请求；能做到的最高等级是：真注册表 ＋ 真 `executor` ＋ 真落盘 ＋ `tools` 数组里确有它（不是桩）。「模型自己想起来用它」这条留给有模型的环境。
4. **设置页仍把两件列在 FILES 组里**（显示为"待点头"）。按判据④只约束 `capabilities` 输出，没动设置页——那里是**唯一能单独关掉它**的地方，藏掉反而让人没法收。**副作用**：设置页会把这两件画在"未解锁"的组下，与"其实已经能用"有不一致；要不要在设置页给它们单独标一档（如"免解锁"）需要动 `BaopuToolArea` 与它的 4 条门禁，本单没做。**挂账。**
5. **体检单的「默认可见」口径没跟着改**。`HealthCheckTest.toolCensus` 仍按"组 ∈ {CORE, EDIT}"算默认可见 ⇒ 体检单里这三件被算作"不默认可见"。那是诊断单不是门禁，改它要动 `ToolProbe` 的构造与那张单子的两处断言，本单没做。**挂账。**
6. **detekt 预算里有一条历史指纹漂移**：`CyclomaticComplexMethod|RunRules.kt|confirmSummary#1` 在当前树上存在、预算清单里没有（本单未碰 `RunRules.kt`）；总量 335 = 335、按规则分布也等值，闸报的是"通过"，漂移只作诊断。
7. **空板时「清空」不可点**。判据②要的是"三样齐"＝**看得见**；空板点它只会弹一个"清空一件不存在的东西"的确认框，所以压暗不可点（按钮仍在，截图可见）。若要求"处处可点"，去掉 `enabled = view.clearEnabled` 一行即可。
