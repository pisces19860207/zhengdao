## 1. 目标对象（`.goal.json` 的形状）

| 字段 | 形状 | 谁给 |
|---|---|---|
| `sentence` | 一句话目标（≤160 字，原文不转述） | 模型带 `goal.sentence` |
| `criteria[]` | `{text, kind, path?}`；`kind=file` ⇒ 收尾时机器去查 `path` 在不在（**可机械验证**）；`kind=human` ⇒ 只能人判 | 模型带，判定层校验 |
| `boundaries[]` | `{text, denyTools[], denyPaths[]}`；点名了才机械可比（越界闸据此停），只写一句话就只靠模型自律 | 模型带 |
| `budget` | `maxSteps`（必填 ≥1）＋ `maxMinutes`（可选，0＝不限时） | 模型带 |
| `state` | 五值闭集：`active` 进行的／`achieved` 已达成／`failed` 未达成／`pending_review` 待验收／`stopped` 已停下 | 收口判出来的（`achieved` 只由 PASS 换来） |
| `pledgeId` | 军令状快照 id（**外键**） | 冻结那一刻填 |
| `total` / `done` / `used` | 状里的项数 ／ 有结局的项数 ／ 已用工具步数 | 快照＋收口＋板子数 |

**为什么没有「步骤清单」字段**：目标只挂一份外键，步骤总数与进度都来自军令状（347 的快照与收口读数）。这就是判据「军令状只一份」的**结构保证**——不是靠注释约定，是目标里根本没有第二个清单可写（`GoalModeTest.目标本体没有清单字段_只有状的外键` 反射钉死）。

落点 `<工作区>/产物/.goal.json`：**点号开头** ⇒ 不计入「产物 N 件」（512／322 同口径）；写盘先写 `.goal.json.tmp` 再改名（同 `BoardStore` 房型），半份目标比没有目标更糟。

## 2. 五步怎么落地（派工单 §做 ①–⑤）

| 步 | 落点 | 做了什么 |
|---|---|---|
| ① 立目标 | `plan/GoalMode.kt`：`GoalRules.parse` ＋ `GoalBoard.freeze`；`agent/PlanController.kt`：`submit` 的写法门 ＋ `goalLandingNote` | `update_plan` 多一个可选键 `goal`（**与 `pledge` 同一次调用**，不新开单、不新开工具）；空判据／没有一条可机械验证／没状 ⇒ 拒，错误原文回灌教改法 |

| ③ 每步对照 | `RunEngine.goalStepGate`（挂在 `preExecutionGate`，每次串行工具调用前）＋ `GoalRules.stepCheck` | 越界（不做清单点名的工具／路径前缀）⇒ **停并问**（不执行，原话让模型先问用户）；超预算（步数或时长）⇒ **停并报**（不执行，原话让模型把现状报上来）；`ask_user`／`update_plan` 任何时刻放行 |
| ④ 完成判三态 | `RunEngine` 收尾；`GoalRules.judge` / `stateOf` / `settleNotice` | 右相的判据表**复用 332 的 `verify.Status`**（PASS/FAIL/UNVERIFIABLE，不写第二套）：文件类判据由机器真去查工作区；PASS ⇒「已达成」，有任何一条只能人判 ⇒「待验收」，机械判据没兑现 ⇒「未达成」并指名哪条 |
| ⑤ 账本可见 | `agent/tools/GovernanceStateTool.kt` 的 `goal` 段（第七段，`v` 1→2）；`GovernanceCenterRules.goal`；`GovernanceCenterScreen.GoalSection` | 出口给一行成品字 `目标：… / 进度 3/5 步 / 预算用 40%`；百分数**只在 `GoalRules.percentText` 一处算**，屏幕与判据层都只抄字（322 判据②的「零算术」门禁照旧绿） |

**续跑（用户追加要求的「收口续跑」）**：

- 进度与已用步数**每次计划落库成功就写盘**（`GoalBoard.noteProgress`）——只写立目标那一次的话，进程一重启就「进度归零、预算重新计」，正好是本单要治的病；
- 续跑分支（`seedPledge`）在同一处 `GoalBoard.attach(spillRoot())` 把盘上那份接回来：**读不到就是没目标**（不编一份），读到了进度与预算照旧；
- `seedFromStore`（进程重启回种）**不清目标**——清了等于完成度归零；只有「新一轮（新请求）」才清（`newRound`）。

## 6. 没做的 / 移交（如实列，不粉饰）

1. **「达成/失败数据进 495/517」——本批只做到「数据落地、可读」，没接它们的聚合口径。**
   现状：达成/失败落在 `产物/.goal.json`（`state`）＋ 收尾 notice ＋ `run_log` 一行，经 `governance_state.goal` 可读。
   为什么不接：495 读的是触发账本、517 读的是深度读数，两边的**聚合口径是它们自己的判据**（`triggerEvalOf` 的 score、`EvidenceFacts.last` 的结论），擅自在目标这一侧塞一列会**污染评测分数与深度定档**——那是「看着做了、其实改了别人的尺子」。接入点已量好：给 `TriggerRow` 加一列 `goalMet: Boolean? = null`（向后兼容、老读侧零影响）即可，登记为移交项。
2. **目标模板**：按派工单「只出候选（灰度后才用）」，本批**没有实现**模板库，也没写死任何模板——它要过灰度才允许用，提前落成代码就是「先用后批」。
3. **467 预留段**：`PlanController.kt` 458 的 taskId 回填那一整段未动；等 467 合入 main 后 rebase，再在那一段补 `contractDigest` 相关行（本批的 `goal` 解析在它**之前**的 hunk 里，两者不重叠）。
4. **真机未跑**：本批判据全部在 JVM 层可测（判据层零 Android、闸与屏幕各有门禁）；真机验收建议一条链：说「目标模式」→ 看它带 `goal` 立目标 → 让它调一个在不做清单里点名的工具（应被停并要求问人）→ 收尾看治理中心那一行是否显示「已达成/待验收」。
5. **屏幕只做了「一行字」**：没有做目标的编辑/取消入口（改目标属于「跟用户说清为什么换」，走对话，不做按钮——少一个误触就少一次完成度失真）。
