## 0. 为什么要做

用户原话：「有些人百年用不到某些工具。」25 个工具每轮全塞给模型 ⇒ prompt 变长、模型容易被低频工具干扰；而逐个开关是**用户手工维护**，不是「默认就收起来、需要时解锁」。

## 1. 行为（v1）

1. **分组**：给每个工具加 `group` 字段（`core` / `edit` / `browser` / `library` / `media` / `card` / `plan`）。分组表**只有一份**（放 ToolRegistry，UI 从它读）。
2. **默认可见**：`core` 与 `edit` 默认可见；其余组默认**不可见**（不是禁用——模型根本看不到）。
3. **解锁工具**：新增 `capabilities`（FREE）：无参数 ⇒ 返回「当前可见组 / 可解锁组 + 每组一句话」；带 `enable: ["browser","card"]` ⇒ 本会话内解锁，返回解锁后的组清单。
4. **生效范围**：解锁状态**按会话**持久（写 `session` 或单独小表，二选一，在报告里写清）；新会话回到默认。用户既有开关仍然优先：组被用户关掉 ⇒ `capabilities` 也不能解锁（如实回「被用户关闭」）。
5. **诚实**：模型调未解锁工具时，回「该工具组未解锁：先调 capabilities」，不静默。
6. **设置页**：工具开关区顶部加「默认只显示核心工具；低频组按需解锁」说明 + 每组的开关（与单工具开关并存），状态读同一份 group 表。

## 2. 验收（判据）

- 默认发给模型的 tools 数组 **≤ 12 个**（core+edit+capabilities），其余不出现；
- `capabilities` 在表里，且能列出组与解锁状态；
- 调 `capabilities(enable=["browser"])` 后，下一轮 tools 数组出现 browser 组；
- 用户关掉的组：`capabilities` 不解锁，返回原因；
- 新会话回到默认（默认可见组数量与首轮一致）；
- 源码门禁：tools 数组只由「可见组 ∩ 用户开关」计算，不许另起第二条过滤链；
- 纯函数：`visibleTools(catalog, settings, unlockedGroups)` 可直接 JVM 测（给 3 组用例：默认/解锁/用户关闭）。
- 全量单测 0 失败 0 错误，跳过不恶化；lint 预算不升。
