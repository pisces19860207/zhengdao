## 二、派工单 A（🔴 必修）—— 失败态「重试」必须能把 serve 拉起来

### 落点（已核验）
- `app/src/main/java/com/example/zhengdao/ui/taiji/TaijiScreen.kt:326-329`
  ```kotlin
  state.phase is TaijiPhase.Failed ->
      FailedPane((state.phase as TaijiPhase.Failed).message) {
          scope.launch { repo.open(OcRuntime.scope, sessionId = null) }
      }
  ```
  ⇒ 只调 `repo.open(...)`，**没有任何 `startServe`**。
- 拉 serve 的现成入口：`app/src/main/java/com/example/zhengdao/oc/OcManager.kt:420` `fun startServe(ctx: Context): String?`
  **幂等**（`TaijiScreen.kt:268-273` 注释：serve 已在跑时解析密码并写 `OcManager.servePassword` 后返回；未跑则拉起）。
- 相关假设文档 `app/src/main/java/com/example/zhengdao/oc/OcConnectionPolicy.kt:20`/`:83` 写着「失败态 → 重开（`FailedPane` 的「重试」就是靠这条）」——**该假设漏了「serve 已经死了」这一分支**，本刀要把它补上并改注释。

### 验收判据（三条，缺一不可）
1. serve 不在跑时：失败态点「重试」⇒ serve 被拉起、**连接恢复**（不再无限失败）。
2. serve 在跑时：点「重试」**不产生第二个 serve 进程**（幂等，不许双绑）。
3. `startServe` 是阻塞调用（裸 `HttpURLConnection` + 起进程）⇒ **不得在主线程调**。

### 测试要求
- 把「失败态重试应当采取的动作」抽成**可 JVM 单测的纯函数**（放 `oc/OcConnectionPolicy.kt` 一带），锁正例 **+ 负例自证**（见 ERRATA **E-133**：门禁判据写死局部变量名的写法会被等价改写绕过，**必须有负例**）。

### 红线
- 不动熔断阈值与语义：`oc/OcConnectionPolicy.kt:88` `RECONNECT_GIVE_UP = 8`、`oc/SseClient.kt:221` 的「连续 10 场连上即关」。
- 不动版本号（`app/build.gradle.kts` 的 `appVersionName` / `versionCode`）、不动 `.github/**`、不动 `docs/` 台账类文件（入账是我的活）。
- 不顺带重构；只改必要行。

### 排期建议
本单与 **P1-6（serve 关停策略③）同域同文件族**，建议**并入 P1-6 那一刀一起交**（P1-6 让 serve 更容易处于"已被关掉"的状态，本单正是它的配套补丁），可少跑一轮真机验证。

### 真机验收（我来跑，workbuddy 不用管）
同签名 debuggable QA 包流程现成：`ZHENGDAO_KEYSTORE_*` 环境变量指向发版 jks + `assembleDebug` ⇒ 与线上包**同签名 + debuggable**，`install -r` 覆盖升级**数据不丢**，`run-as` 直读 `filesDir/logs/`。

## 三、派工单 B（🟠 第㉒刀）—— 冻结态收尾取证（先取证，后决定改不改）

### 背景
真机实测：`SIGSTOP`（T 态）冻结的 oc serve，R-17 四步收尾全流程走完（`app/src/main/java/com/example/zhengdao/oc/OcManager.kt:543-552` → `shutdownProcess`：`destroy()` → 2000ms → `destroyForcibly()` → 再等），日志「强制收尾完成」已留痕，但 `ps` 里进程**仍是 T 态存活**；随后**外部 `kill -9` 立即收掉**（count=0）。

### 任务性质
**先取证，后决定。禁止盲改。** 允许的产出有两种，二选一，必须附证据：
- (a) 结论「平台语义如此」⇒ 不改行为，只补留痕/文档；
- (b) 结论「我们打错了目标」⇒ 再给**最小**修法。

### 必须取到的四件证据
1. **pid 对照**（重点怀疑项）：`destroyForcibly()` 作用的对象与 `ps` 里 T 态 pid **是否同一个**。proot 链会 fork/exec loader，`serveProcess` 句柄可能只是包装进程 ⇒ 若是，则 R-17 收尾一直在打错目标，**这是真缺陷**，不是平台怪癖。
2. 全链现场：`ps -o pid,ppid,stat,cmd`（guest 内 + App 侧都要）＋ `dumpsys activity processes`。
3. Java 侧 pid 留痕：在收尾路径打一行 pid 到 RunLog（只加日志，不改行为）。
4. 可复现脚本：设备侧 **nohup 盯梢器**在新 serve 出现时立即 `SIGSTOP`。
   ⚠️ 两个已踩过的坑：① 用 `&` 起的后台进程会随工具会话被回收 ⇒ 必须 `nohup` 落脚本；② 脚本内用 **run-as**，不要用 shell uid（否则 `kill` 被拒，实测 `Operation not permitted`）。

### 红线
- 不改熔断/超时阈值，不顺带重构，不动版本号。
- 取证阶段的临时文件收尾时清理干净（保持设备现场可复跑）。
