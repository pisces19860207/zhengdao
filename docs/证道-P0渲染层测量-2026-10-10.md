## 0. 一句话

**`TerminalRenderer.render()` 一帧 2.3 ms（framestats `draw` 相位），占 16.67 ms 预算的 14%；中文与英文无可测差异；掉帧掉在 GPU/合成侧与主线程解析侧，不在绘制。**
⇒ **换渲染层（Compose）不会让任何一帧变快。** P2 的价值是结构、审美与可维护性，不是性能。

**P1-a 之后的补充（E-087，②③）**：上面那个 2.3 ms 是**显示列表记录**口径；直接在 `onDraw()` 里计时是 **2.5–19.8 ms（中位 ≈5 ms）**，也就是说 Java 侧 41 行循环其实要花几毫秒 —— 但**没有任何便宜办法把它省掉**：`View.invalidate(Rect)` 只减少光栅化，`onDraw` 收到的 `canvas.getClipBounds()` **永远是整个 View**（真机实测每帧 `rows=41/41 clip=Rect(0, 0 - 1228, 2094)`）。想按脏区真的省下循环，只有自带保留位图 + 显式脏区（SurfaceView `lockCanvas(dirty)` / 保留 Bitmap blit / 自己持位图的 Compose Canvas）——**这是 P2 重写唯一有依据的性能收益点**。

### 1.1 洪水场景重测（2026-10-10 第二轮 → 第三轮复核，P1-a 包上做，① 真机）

上一轮「洪水 6 秒只有 100 帧」的窗口**落在洪水结束之后**：`seq 1 2000000` 在 guest 侧 `real` 只有 **1.702 s**（见下表第三轮），6 s 窗口里跑的基本只剩 600 ms 的光标闪烁 —— 所以那条「主线程被解析占满」是误读，**已正式撤回**。第三轮改用「逐 2–3 s 采样应用 CPU + 读累积帧数」的复核口径（窗口不再依赖固定 6 s）：

| 探针 | 命令 | 结果 |
|---|---|---|
| 基线（不经过终端） | `time (base64 /dev/zero \| head -c 10000000 > /dev/null)` | `real 0m0.086s` |
| 10 MB 打到 pty | `time (base64 /dev/zero \| head -c 10000000)` | `real 0m0.735s`（user 0.028 / sys 0.210），App CPU 无可见尖峰 |
| 洪水 A：`seq 1 2000000`（≈14 MB） | `clear; time seq 1 2000000` | guest **`real 0m1.702s`**（user 0.025 / sys 1.311）；App CPU t0 2480 ms → t=3 s **+920 ms**、此后每 2–3 s 只 +50 ms；头 3 秒 ≈108 帧（**≈36 fps**）、51 s 共 195 帧；**janky 0** ⇒ **≈64 ms CPU/MB**，洪水在头 3 秒就被消化完 |
| 洪水 B：200 MB `base64` | `clear; time (base64 /dev/zero \| head -c 200000000)` | App CPU t0 4420 ms → t=16 s **+9360 ms**、之后转平（+20 ms/s）；帧 142 → **939（≈52 fps）**；**janky 0** ⇒ **≈47 ms CPU/MB** |

**读数**：① 复核口径下，能造出的最重洪水（200 MB / 16 s）也没把主线程压垮 —— **52 fps、janky 0、零 deadline miss**；`seq` 那一波（14 MB）在头 3 秒就被消化掉（≈36 fps）。② 按 47–64 ms CPU/MB 折算，单次 64 KB `append` ≈ **3–4 ms**，离 16.67 ms 的帧预算差一个数量级 ⇒ **「解析占满主线程、渲染挨饿」不成立，正式撤回**。

**同时暴露一个口径坑**：**静止屏上的 janky / 帧总时长不可信**。静止屏只有每 600 ms 一次的闪烁帧，稀疏帧的 `FrameCompleted − IntendedVsync` 会把「等 vsync + 悬浮窗合成」的排队时间算进去，于是量出 janky 100%、p50 30–42 ms；而帧密集时（洪水）同一台机器是 janky 0 / p50 5 ms。**结论：判断「卡不卡」要看帧密集场景，不要用静止屏的百分位。**

## 3. P1 修正方向（用户 2026-10-10 拍板的优先级）

> 用户原话（m24462）：「**P1 优先级：光标局部失效 → 解析离开主线程 → 6 类职责拆分 → 5 条已有 bug**」

### P1-a 光标局部失效

**证据（②）**
- `app/src/main/java/com/termux/view/TerminalView.java:1413-1429` `TerminalCursorBlinkerRunnable.run()`：`:1420-1422` 翻转 `mCursorVisible` 并 `mEmulator.setCursorBlinkState(...)`，`:1423` `invalidate()`（**全屏**），`:1427` `finally` 里无条件 `postDelayed(this, mBlinkRate)`。
- `:1388-1394` `stopTerminalCursorBlinker()` 是唯一的取消入口；调用点只有 `:1300`（`setTerminalCursorBlinkerRate`）与 `:1357`（`setTerminalCursorBlinkerState`）。
- `:1532` `onDetachedFromWindow()` **没有**调 `stopTerminalCursorBlinker()` —— 同一方法里专门处理了另一个 PopupWindow 泄漏，所以这里更像漏掉。⇒ 审计 🟡-5「光标闪烁 Runnable 永不停止」：`TerminalCursorBlinkerRunnable` 是**非静态内部类**（隐式持有 `TerminalView` → Context），每进一次终端页留一条 600 ms 永久空转循环。

**改法**
1. 把 `:1423` 的 `invalidate()` 换成 `invalidate(cursorRect)`：用 `mEmulator.getCursorRow()/getCursorCol()` + `mTopRow` 与 `mRenderer.getFontWidth()/getFontLineSpacing()` 算出光标格矩形（左右各留 1 px 余量，容纳 BAR/UNDERLINE 两种光标样式）。
2. 三种情况**回退全屏 `invalidate()`**：光标被禁用 / 回滚了历史（`mTopRow != 0`，光标不在屏上）/ 算出的矩形为空或越界。
3. `onDetachedFromWindow()`（`:1532`）补 `stopTerminalCursorBlinker()` —— 顺带修掉审计 🟡-5。
4. 只在 P1-a 范围内**不改** `TerminalRenderer`（它按行迭代、由 Canvas 裁剪掉脏区外的绘制）；局部失效省的是**合成与 GPU 侧**，正是 P0 量出来的瓶颈。
   > **改法第 4 条与配套的「按 clip 裁行」已作废**（见下面「实施结果」与 ERRATA E-087）：clip 恒为整屏，裁行代码不生效，已撤回。第 1 条（`invalidate(光标格)`）保留 —— 它省下的是光栅化，值得留，只是量不到 CPU 收益。

**实施结果（2026-10-10 真机，PGT-AN10 / Android 16）**

落到 `feature/terminal-view-refactor-p1` 的 P1-a 改动（`app/src/main/java/com/termux/view/TerminalView.java` 4 处）：

| # | 改动 | 目的 |
|---|---|---|
| 1 | `TerminalCursorBlinkerRunnable.run()` 的 `invalidate()` → 新增的 `invalidateCursorCell()` | 闪烁只失效光标那一格（宽字符留 2 格 + 上下 2 px 余量）；光标被隐藏 / `mTopRow != 0` / 越界 / 尺寸未就绪一律回退整屏 |
| 2 | `stopTerminalCursorBlinker()` 里补 `mTerminalCursorBlinkerRunnable = null` | 断开 `Handler → Runnable → View → Activity` 引用链（审计 🟡-5） |
| 3 | `onDetachedFromWindow()` 开头补 `stopTerminalCursorBlinker()` | 上游漏掉，每进出一次终端页留一条 600 ms 永久空转循环 |
| 4 | `onAttachedToWindow()` 末尾补 `setTerminalCursorBlinkerState(true, false)` | 与第 3 条配对：否则"离开再回来"光标不再闪（该方法内部先 stop 再 start，幂等） |

**数字（同一台机器、同一屏内容：ZH `cat /root/AGENTS.md \| head -60`、键盘收起、同一悬浮视频窗）**

| 口径 | 改前（存量 v2.0.9 release） | 改后（benchmark 包，同签名覆盖安装） |
|---|---|---|
| 30 s 光标闪烁的应用 CPU | **980 ms**（98 ticks） | 1050 ms / 1000 ms（两次窗口） |
| 30 s 帧数 | **51 帧（1.7 fps）** | 51 帧 / 51 帧 |
| janky / legacy | 28 / 51、31 | 30 / 51、32（两次窗口） |

⇒ **CPU、帧数、掉帧三项都没有可测变化**（差异在噪声内）。原因就是上面那条：局部 `invalidate` 只减少光栅化，`onDraw` 的 41 行循环一次不少，主线程仍每 600 ms 走一遍。

**因此 P1-a 的真实收益**：① 修掉审计 🟡-5 的引用链泄漏（这条是确定收益）；② 每次闪烁的 GPU 光栅化面积从整屏降到一格（量不到 CPU，但方向正确）；③ 顺手得到两条硬结论（clip 恒整屏；`onDraw` 中位 ≈5 ms），直接决定 P2 该怎么做。

**真机验证与"无残影"检查**：闪烁 30 s 期间屏幕内容正确（无残影、无花屏）；键盘收起后 `dumpsys input_method` 的 `mInputShown=false`；覆盖安装后 Debian 环境与 tmux 会话完好（`install -r` 同 debug key，用户数据未丢）。

**验收**
- 编译 + `:app:testDebugUnitTest` 全绿；
- 真机：闪烁无残影（切到 tmux 状态栏、中文屏两种内容各看 30 秒）、滑动 + 闪烁同时进行不花屏；
- 数字：同场景 `gfxinfo` 帧数 / GPU 相位与 P0 基线对比（落 ERRATA）；
- 泄漏：连续进出终端页 10 次，观察 `adb shell dumpsys meminfo com.example.zhengdao | grep Views` 不线性增长（③ 判据）。

### P1-b 解析离开主线程

**现状（②）**：`app/src/main/java/com/termux/terminal/TerminalSession.java:133-148` 的读线程只把 pty 字节读进 `mProcessToTerminalIOQueue` 并 `sendEmptyMessage(MSG_NEW_INPUT)`；真正的解析在**主线程** `:337-347` `MainThreadHandler.handleMessage()` → `mEmulator.append(mReceiveBuffer, bytesRead)` → `:224-226` 回调 `mClient.onTextChanged(this)`。⇒ ~~洪水时主线程被字节状态机占满（P0 ①：帧只有 5 ms，却只有 16.7 fps）~~　**这句推断已被 E-088 正式撤回**（复核：`seq 1 2000000` 头 3 秒消化完、janky 0；200 MB 长洪水 **939 帧 ≈52 fps / janky 0**）—— 保留在此仅为留痕，**不要**据此认定解析是瓶颈。解析确实在主线程，但**它没有造成症状**（见下方裁决）。

**两条路线（需拍板后动）**
- **B1 专用解析线程 + 快照/锁纪律**：`append` 挪到工作线程，`mEmulator`/`TerminalBuffer` 的**所有**访问点加锁（渲染 `onDraw`、`getColumnAndRow`、`resize`、`paste`、鼠标转发、选区、`getText`）。收益最大（主线程彻底不被解析占用），**风险最大**：动的是 vendored 的 `com/termux/`，且渲染路径每帧持锁。
- **B2 更新路径减负（不改线程模型）**：`append` 仍在主线程，但把「读队列 → append → 回调」按时间片合并、把 `notifyScreenUpdate()` 的触发频率与帧对齐。收益中等、风险小。

**原建议**：先做 **B2** 并量数字（同 `seq 1 2000000` 场景对比 fps）；**B1 单独走一次评审**（它要动 vendored 代码 + 定锁纪律，不能塞进 P1 的「零风险」里）。⚠️ 动 `com/termux/` 前先备份；不破坏 `PROVENANCE.md` 记录。

**裁决（2026-10-10 实测后）：B1 与 B2 都不做 —— 理由是「没有症状」，不是「没有工作量」。**

复核口径：逐 2–3 s 采应用 CPU（`/proc/<pid>/stat` 的 utime+stime ×10 = ms）+ 读**累积**帧数（`gfxinfo`），每波洪水前 `reset`。

| 探针（P1-a 补丁包上真机实跑） | 命令 | 结果 |
|---|---|---|
| 基线（不经过终端） | `time (base64 /dev/zero \| head -c 10000000 > /dev/null)` | `real 0m0.086s` |
| 10 MB 打到 pty | 同上去掉重定向 | `real 0m0.735s`（user 0.028 / sys 0.210） |
| 洪水 A：`seq 1 2000000`（≈14 MB） | `clear; time seq 1 2000000` | guest `real 0m1.702s`；App CPU t0 2480 → t=3 s **+920 ms**，之后每 2–3 s 仅 +50 ms；头 3 秒 ≈108 帧（≈36 fps）、51 s 共 195 帧；**janky 0** |

读数与裁决：

- **症状不存在**：能造出的最重洪水（200 MB / 16 s）下，App 全程 **≈52 fps、janky 0、Frame deadline missed 0**；`seq` 那一波（14 MB）在**头 3 秒**就被消化完（≈36 fps）。没有任何可复现的用户可见症状（掉帧、卡顿、回显延迟）可以拿来当验收标准。
- **代价与风险是实打实的**：B1 要动 vendored `com/termux/` 的线程模型与**锁纪律** —— `mEmulator`/`TerminalBuffer` 的每个访问点（渲染 `onDraw`、`getColumnAndRow`、`resize`、`paste`、鼠标转发、选区、`getText`）都得进锁，等于把风险从「解析可能慢」换成「每帧渲染可能被锁阻塞」，而渲染正是那条只有 2.3 ms 的核心路径；B2 改投递节奏，在没有症状的前提下**收益无法被度量**（也就无法验收）。
- **裁决原则**：P1 的定位是「零风险搬运 + 修可复现 bug」。**没有症状的性能改造不进 P1**。B1/B2 降级为「**有证据再来**」的储备项，触发条件（满足任一即立项）：
  ① 真机上抓到 `janky > 0` **且** `append`/`onTextChanged` 逐帧耗时 > 8 ms 的日志；② 单次 `paste`/超大 burst 造成可感知回显延迟（如敲键到回显 > 100 ms）；③ 用户报「输出洪水时掉帧/发烫」。
- **留给将来的参照基线**：App 侧端到端吞吐 ≈ **47–64 ms CPU / MB（≈15–21 MB/s）**。将来若真要动 P1-b，就用这个数字当对照，而不是拿「体感」当依据。

```powershell
# 进终端（TerminalActivity 是 exported=false，只能这样进）
& $adb shell monkey -p com.example.zhengdao -c android.intent.category.LAUNCHER 1
& $adb shell input tap 656 2775          # 底部「终端」Tab
& $adb shell input keyevent 4            # 收键盘（Activity 不 finish）

& $adb shell input keyevent 66           # 回车
# 量（framestats 必须连调两次，第二次才有数据段）
& $adb shell dumpsys gfxinfo com.example.zhengdao reset
& $adb shell dumpsys gfxinfo com.example.zhengdao framestats > $null
& $adb shell dumpsys gfxinfo com.example.zhengdao framestats
```
