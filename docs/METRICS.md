## 〇、三条总规矩（全表适用）

| # | 规矩 | 怎么在代码里成立 |
|---|---|---|
| R1 | **分母 <10 ⇒ `unknown`**，只报「分子／分母」，**不出现百分比** | `Ratio.known = denom >= Metrics.MIN_DENOM(10)`；`Ratio.text()` 在 `known=false` 时不拼 `%` |
| R2 | **口径先落盘再看数** | 本文件先提交；负例「看数后改口径」由窗口口径用例钉住（滚动窗 vs 日历窗） |
| R3 | **同一份数据两次算出同一个数** | `Metrics.compute` 纯函数：不读时钟、不用随机、按 id 去重、证据排序去重；输入列表顺序不影响结果（有幂等用例） |

**分母禁忌**：任何指标的分母**不得是 `意见判定.jsonl` 的条数**（274 意见账）。
理由（用户 2026-10-29 明令）：拿意见条数当分母，系统只要"少报"就能让读数好看——279 已定「少报就少抽」的循环不能再来一次。
四率的分母一律取**外部事实**（动作／任务／判决／检查项），意见账只作旁证，不作分母。

**窗口一律滚动**（`now - N 天`），不按日历周/月切：日历周会让周一 0 点出现额度跳变与重复计数（279 裁定① 同一条理由）。

| `skip` | 跳过率 | 巡按判「查不了」（`no_data`）的检查项数 | 巡按跑过的检查项数（每跑一次六项） | 滚 7 天 | 239 `巡按记录.jsonl` |

### 1.1 违规率（v1）

- **分子**：208 账本窗口内，`kind = auto_act` 的行里，**被某条 `rollback_of` 指到**的那几条（按原行 id 去重）。
- **分母**：同一窗口内全部 `auto_act` 行。
- **为什么是它（v1 的实话）**：276 还没把「有证据的违规」单独记一类账，275 `ProgressivePenalty` 只有判定层、没有落账。
  现在仓库里唯一可查的"做错了"事实是**被撤销**。所以 v1 只能量到「免问动作被撤销的比例」；276 落违规账之后升 v2。
- **与 I4 免问回滚率不是同一层**：I4 按**动作痕迹实例**算（日志），这里按**账本行**算（决策）。两层都对，各管各的，不合并。
- 证据 id：`decision:<原行 id>`。

### 1.2 误判率

- 与 239 `PassRate.of` **同源同算法**（`DecisionReview.latestPerRecord`，窗口按判定时刻、不按被纠动作时刻），不另写一套。
- 证据 id：`decision:<record_id>`（判「错」的那几条）。

### 1.3 干预率

- **分母**：`run_log` 窗口内出现过的 (session_id, step) 去重数（不分工具、读写都算）。
- **分子**：同窗口内出现 `state = 'AwaitConfirm'` 的 (session_id, step) 去重数。
- 为什么按 (会话, 步) 去重：同一步可能落多行日志（摆卡一行、执行一行），按行数会重复放大。
- 证据 id：`call:<session>#<step>`。

### 1.4 跳过率

- **定义**：勘验**因无数据/无持久口跳过的检查项**占全部检查项的比例。
- **分母**：窗口内 `巡按记录.jsonl` 每条的 `findings` 条数之和（一次巡按六项）；**无 `findings` 字段的老行不计入**，并在读数行的备注里写明跳过了几次。
- **分子**：其中 `verdict = 'no_data'` 的条数。
- **为什么不取意见账**：见 R 段「分母禁忌」。跳过率测的是「制度有多少检查项根本没查成」，分母是检查项（外部事实），不是意见条数。
- 证据 id：`patrol:<巡按 id>#<check>`。

## 二、技能成功率（L2／255）

- **key**：`skill_success`
- **源**：`技能/<名>/验收.json`（`schema = zl-accept/1`），项目层与全局层**两层目录都读**。
- **窗口**：滚 30 天（255 `SkillAcceptance.WINDOW_MS`），用 255 自己的 `windowOf` 取样本（不另算窗口）。
- **成功** `ok = true`；**失败** `ok = false`；**降级** = 该技能 `demotedAt` 落在窗口内。
- **成功率** = Σ成功 ÷ Σ样本（跨技能合并）；单技能同式。
- **分母 <10 ⇒ `unknown`**：与 255 `MIN_SAMPLES = 10` 同数，别处不另立一个数。
- 同一 `opId` 只算一次（255 记账幂等；读数不重复放大）。
- 读数行的备注给：技能数、窗口内降级数。
- 证据 id：`skill:<层>/<名>#<opId>`（判失败的样本）。

### 3.1 任务成功率（终稿，**已落码：第二批**）

- **成功** = 该任务**终态**同时满足三条：①无回滚 ②无重启续跑 ③无未处理失败。
- **任务** ＝ `run_trace.run_id`（一次运行；与 I4 的 `taskCount` 同口径）。
- **已结束** ＝ 该 run 最后一行状态 ∈ {OK, FAILED, TIMEOUT, CANCELLED}。
  「最后一行」＝按 `run_trace.id` 升序的最后一条（自增主键＝真发生顺序；**不按 `started_at`**——批准路径补的那行 `started_at = 0`）。
  - 最后一行是 `CONFIRM` ＝还在等你批，**不算结束**；
  - 其余状态（`REJECTED`／`SKIPPED`）**也不算结束**（v1 保守：判不准就不进分母）。
- **无未处理失败** ＝ 最后一行不是 FAILED/TIMEOUT/CANCELLED；**FAILED 之后同 run 还有后续 OK 行**＝被重试救回来了，算「无未处理失败」
  ——判法就是「最后一行是不是 OK」：最后一行 OK 时，前面任何一次 FAILED 后面都已有 OK 兜住。
- **无回滚** ＝ 该 run 的时间跨度（首行 `started_at` → 末次活动时刻）内、同会话**没有** `rollback_of` 账行
  （账本不带 `run_id`，只能按会话＋时间归属，这是 v1 的粗口径：run 结束后才补记的回滚**不算**在它头上）。
- **无重启续跑** ⚠ 库里没有续跑标记（`RunEngine.kt:294` 原话「续跑是新 run」）⇒ **v1 不判这一条**。要判得在落库时记 `resumed_from`，属别的批。
- ⚠ **在跑的 run 没有 run 级终态行**：`run_trace` 只按步收口（`RunTrace.settleStep`），run 结束时不再补一行
  ⇒ 正在跑的任务，最后一行也是上一步的 `OK`，**可能被算成已结束**。v1 如实记；要精确得有 run 级收尾行（别的批）。
- **新旧数不可比**：分母从「子任务」换成「任务」，换之前那些数**不能**和换之后的比（用户 2026-10-29 明令）。
- **读数行备注（原文钉住，删字＝用例红）**：
  `续跑未判（缺标记）；新旧数不可比（旧口径按子任务算）；在跑任务可能被算成已结束（无 run 级终态行）`
- 子任务级另叫 `e1_subtask_done`（诊断），**两个名字不许混用**。

### 3.2 人介入率（终稿，**已落码：第一批**）

- **工具请求** ＝ `run_trace` 里 `tool <> ''` 的行，按 **(run_id, step, tool, args_hash) 四元组**去重后的一个请求。
  为什么要去重：同一步批准后会**补第二行**（`RunEngine.kt:3629` 挂起时记 CONFIRM、批准后按真结果再记一行），按行数算会把一次请求算成两次。
  为什么不用 (run_id, step) 两元组：批编排一个 step 能连跑多个工具调用（`RunEngine.kt:1953` 段循环）⇒ 两元组会把一步里的 3 个请求算成 1 个。四元组里 tool 与 args_hash 都相同的行才是同一次请求。
  **2026-10-29 修订：由 (run_id, step) 改为四元组**（用户裁定⑤；改前口径已交付，改的理由见上句实测）。
- **摆过确认卡** ＝ 该请求的行里**出现过** `status = CONFIRM`，**或该请求的 `tool = ask_user`**（不是"最后落成 CONFIRM"——批准后那行还在）。
  `ask_user` 本身就是一张卡、但它不产生 CONFIRM 轨迹行（卡在工具自身执行体里），漏掉它会把"人介入"**低估**——低估比高估危险（会让人以为不用管）。**2026-10-29 裁定⑦**。
- 任务级另叫 `e1_task_needs_confirm`（辅助），**不许与人介入率混用**。

### 3.3 不可逆动作占比（终稿，**已落码：第一批**）

- **不再用 `reversible = false` 当判据**（它含 `read_scope`／`eval_verdict`／`rollback_of`／`skill_demoted` 等非破坏动作，会多算）。
- 改用**破坏动作白名单**（§三·乙，写死在代码里；新增动作必须显式加名并改本文件）。
- 分子＝已执行请求中 `tool ∈ 白名单` 的数；分母＝已执行工具请求数（去重口径同 3.2，「已执行」＝该请求有一行 `status = OK`）。

### 3.4 写侧账实不符率（终稿，**已落码：第一批**，只改名）

- **保持代码现值**：分母＝**核对过的**写侧动作数（`AuditGapCheck.compare` 的 `checked`），分子＝漏行数。
- 名字改为 **写侧账实不符率**（key 不变 `e1_ledger_mismatch`）；「差条数 ÷ 总条数」那种读法**作废**。
- 账本窗口内没有 `auto_act` 行时 `checked = 0` ⇒ 自动 `unknown`（不许报 0%）。

### 3.5 平均纠偏次数与两个新名字（**已落码：第二批**）

- **平均纠偏次数**是均值不是率：分母（任务数）<10 同样 `unknown`，不印「0.3 次/任务」。
- **子任务完成率**（诊断）只认终态：`PENDING/RUNNING` 不进分母；`sub_task` 只在多 Agent 分解路径上有行，日常单链路径为空 ⇒ 多半 `unknown`（这是"没有数据"的实话）。
  算式＝旧 `任务成功率` 那段**整段搬过来**（语义一字未改），旧位置换成任务级算法。
- **需介入任务占比**（辅助）与人介入率同源不同层：**同一张工具请求表按 `run_id` 聚合**——
  **分子**＝窗内有过摆卡请求（`CONFIRM` 行或 `ask_user`，判法同 §3.2）的 run 数；
  **分母**＝窗内**出现过工具请求**的 run 数（没有请求就不存在「需介入」，不把纯思考的 run 拉进分母）。
- 读数行备注（原文钉住）：
  - 子任务完成率：`诊断口径（子任务级），不是任务成功率`
  - 需介入任务占比：`任务级（有过摆卡即算），与人介入率不同层`
- 证据 id：`task:<run_id>`／`decision:<id>`／`trace:<会话>#<步>`。

### 3.6 取数映射与两个缺口（v1）

1. **工具请求去重**：见 3.2，**四元组 (run_id, step, tool, args_hash)**；`run_trace.tool = ''` 的行（THINK／COMPRESSING 边界）不算请求。

   **它的窗口判据也同 #4：`MAX(started_at, ended_at) >= ?`**（2026-10-30 她裁定「与本批同源，并入本批」）。按 `started_at` 开窗会把批准补记那行（`started_at = 0`、`status = OK`）整条读丢 ⇒ 该请求的 `hasOk` 恒假 ⇒ **不可逆动作占比**把「摆了卡、批了、真执行了」的破坏动作全当成没执行，分子分母同少（率往哪边偏不一定，但覆盖度是假的）。**只改窗口过滤这一处**：时刻投影仍取 `MAX(started_at)`（同组的 `CONFIRM` 行有真起点），别的字段一字节没动。
2. **缺口①「覆盖写」判不出**：`run_trace` 只存 `args_hash`、不存参数 ⇒ 读时不知道目标文件当时在不在。

3. **缺口②「重启续跑」判不了**：见 3.1，v1 不判、备注写明。
4. **run 级取数**：`runSummaries()` 把 `run_trace` 行按 `run_id` 聚合成一个 run——
   首行 `started_at` 作回滚归属起点、末次活动（`started_at`／`ended_at` 取大）作窗口依据、按 `id` 升序的状态序列作终态判定输入。

## 四、M9 幻觉抽检

- **key**：`m9_hallucination`
- **抽检量**：每周 k = 20 条对话结论（滚 7 天窗口）。
- **三态**（人判，调用方递进来）：
  - `mismatch`：与源不符（数字／文件／状态对不上）；
  - `verified`：与源相符；
  - `unverifiable`：无法验证（源不在手边／结论本身不可核）。
- **可验证幻觉率** = `mismatch ÷ (mismatch + verified)`。
- **无法验证不进分母、也不进分子**：它既不是通过也不是失败，塞进去就是把「没核成」洗成「准确率高」。
- 分母 <10 ⇒ `unknown`。
- 读数行的备注给：抽了几条、无法验证几条、是否抽满 k=20。
- **判词从哪来**：本批不落新账——`InspectReadOnlyGateTest` 的账本白名单不在 281 租约里，写第三本账要改那个测试（属别的批）。
  所以 M9 是**纯函数**：判词由调用方递进来；持久化与抽检入口另立一批。
