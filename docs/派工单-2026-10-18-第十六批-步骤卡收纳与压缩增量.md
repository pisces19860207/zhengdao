## 0. 一句话

- **第一件**：抱朴页现在把每次工具调用都摊在对话里、永不收；一轮结束时自动收成一行（`N 步 · 用时 · 失败 M`），**点开才展开每一步明细**，手机默认收起。最终回答文字照旧常显。
- **第二件**：压缩从「每次都把全部旧消息重发一遍」改成「**只压还没压过的**」，并且单次有上限、摘要做增量——否则长会话越压越慢、最后必然失败。

## 2. 规格 · 第一件：步骤卡收纳（四段）

### 2.1 A 段：按「轮」分组

- 一轮 = 「一条 user 消息」到「下一条 user 消息之前」的所有 part（assistant 文本 + tool 卡 + 压缩细条不动）。
- 分组**只在 UI 层做**（纯函数：`groupRounds(messages): List<Round>`），数据源仍是 `message`/`part`，**不新增表、不改 schema**。
- 最近一条 user 消息之后的「当前轮」**永远展开**（正在干活的要看得见）；已完成的历史轮才收。

### 2.2 B 段：一轮结束后自动收成一行

- 收起的行文案（中英各一条字符串，走 `strings.xml`，不拼中文）：
  - 中文：`干了 %1$d 步 · 用时 %2$s · 失败 %3$d`
  - 英文：`%1$d steps · %2$s · %3$d failed`
- 用时来源：该轮 `run_log` 里首末 `created_at` 之差（**没有 run_log 行** ⇒ 用「消息时间差」兜底；都没有就不显示用时，别显示 `0s` 假装知道）。
- 失败数：该轮 `run_log.ok = 0` 的行数（**没有数据 ⇒ 显示 0**，因为「不知道」和「没失败」在 UI 上都是 0，别加符号）。
- 当前在跑（`engineState` ∈ THINKING/ACTING/AWAIT_CONFIRM/COMPRESSING）⇒ **该轮保持展开**，不收。

### 2.3 C 段：点开看明细

- 点收起行 ⇒ 展开该轮每一步：`工具名 / 耗时 / 结果（ok/拦/失败）/ 错误原文（截断 200 字，可点开全文）`。
- 展开/收起状态**记住**（同一轮内 `remember(note.key)` 即可，不必落库）。
- **确认卡、问人卡、记忆候选卡永远不许被收**（它们是「要人动手」的东西，收起来就是事故）。

### 2.4 D 段：默认收起

- 首次进入会话页，所有**已完成**的历史轮一律收起（用户要的「手机上默认关闭」）。
- 不要「全部展开/全部收起」按钮（本单不加新控件，只加一行可点的摘要）。

## 2B. 规格 · 第二件：压缩增量（五条）

1. **扣掉已压**：`CompressionRunner.runOnce` 增 `skipIds: Set<String> = emptySet()` 参数；选区之后按 `it.id !in skipIds` 过滤。**与 `ContextAssembler.pendingOldMessageCount` 同口径**（它已经用 `compressedIds` 扣过一次），不许另写一套判定。
2. **引擎传参**：`RunEngine.runCompression` 调用 `runOnce` 时传 `compressedIds`（就是 `RunEngine.kt:209` 那个字段）。组装跳过、条数判据、压缩选区三处从此同源。
3. **单次上限**：`RunRules.COMPRESS_MAX_MESSAGES_PER_RUN = 200`。扣除后超过上限时**只压最旧的 200 条**（**不许整批拒绝**——整批拒绝会让长会话永远压不动，等于把压缩锁死）。
4. **摘要增量（二选一，交付报告写明选了哪个）**：
   - **甲案**：请求里分两段——「上一版摘要」（若已有）＋「本轮新增对话」，要求模型输出**合并后的完整摘要**；
   - **乙案**：不拼上一版进请求，只压新段，产出后与旧摘要**按「旧 + 新」顺序拼接**。
   两案都必须保证：**旧摘要的实质内容不能丢**（乙案拼接即天然满足），且**总长度受既有上限约束**；超限时先丢最旧的段，并在日志里写一句「摘要超限，丢弃最旧段」。
5. **老调用行为不变**：不传 `skipIds`（默认空集）时，选区与请求体与改前**完全一致**（这条必须有判据）。

## 2C. 追加二：压缩链还有三处断线（2026-10-18 接线审计发现，**和第二件同一个文件，顺手修**）

> 来源：`docs/接线审计-2026-10-18.md` §2/§3，蓝总管已用 `git grep` 复核。

**C1（最严重·丢上下文）`RunEngine.kt:462` 的局部变量把成员遮蔽了。**

```kotlin
// :212 成员
private var compressionSummary: String? = null
// :462 同一函数里又声明了一个同名局部
var compressionSummary: String? = null
// :501 传的是这个局部
compressionSummary, compressedIds, compressedIds,
```

后果：压过一次之后，**下一条用户消息**（含进程重启后）摘要段就空了；而 `compressedIds` 仍是成员、还在让 assemble 跳过旧消息 ⇒ **模型上下文断档**。`restoreCompression()`（`:235`）塞回成员也白塞——每次进 run 都被局部覆盖成 null。
**修法**：删掉 `:462` 那个局部（或改名），一律用成员；并在 run 开始时**不要**重置它（会话切换/新会话才重置）。
**判据 J12**：同一会话连跑两次 run，第二次 assemble 的 prompt 必须仍含摘要段；重启恢复后同样。

**C2（悄悄烧钱）压缩通道选择被丢弃，永远走主通道。**

- `Compressor.buildRequest(…, provider: Provider)`（`Compressor.kt:97`）：**函数体从不引用 provider**；
- `CompressionRunner` 的 `complete` 闭包签名 `(messages, maxTokens, temperature)` **不含 provider**（`:58`），`:117` 把 `choice.provider` 只喂给了 `buildRequest`（而它不用）；
- `RunEngine.kt:221-222` 的闭包用 `LlmClient(provider)`——**引擎当前通道**；
- `freeAvailable = { true }`（`CompressionRunner.kt:68`）**从未注入** ⇒ 降级分支不可达；
- 日志却写“内置免费通道”。

后果：用户切到付费通道后，**压缩也走付费**，账上却记“免费”。
**修法**：把 `choice.provider` 传进 `complete`（改签名或包一层），`RunEngine` 里按传入的 provider `new LlmClient(provider)`；`freeAvailable` 接真实探针（拿不到就按 true，但**必须注入**）。
**判据 J13**：默认走内置免费通道（断言 LlmClient 收到的 provider 是 BUILTIN_FREE）；`freeAvailable=false` 时走主通道并带降级标记。

**C3（越刷越坏）`BaopuChatController.kt:679` 每次 refresh 都 `restoreCompression()`。**

库里存的是**最后一条** compression 记录，restore 会把引擎里**运行期累积的** `compressedIds` 覆盖成那一条 ⇒ 二次压缩后，前一批旧消息重新进 prompt。
**修法**：refresh 只在「没有活跃 run」时 restore，或 restore 取并集而非覆盖。
**判据 J14**：运行期连续两次压缩后，`compressedIds` 是两次的并集（不被 refresh 缩水）。

## 5. 负例（自己造红再改回绿）
