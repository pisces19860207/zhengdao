## 0. 一页纸（给不看代码的人）

这一批要做三件事，都是纯逻辑，不联网、不碰真机：

1. **认脸**：拿到一个文件，说出它是哪套格式。三套指 **风月AI**（自制文字游戏平台）、**Tavo**（另一个平台）、**SillyTavern**（酒馆）。另外酒馆的角色卡是 **PNG 图片**，卡的内容藏在图片里的文本块。
2. **体检**：说出这张卡哪儿会出事。不只是「值超范围」，更要说出「这条世界书永远不会被触发」这种**语义级**的毛病。
3. **酒馆 PNG 导出/读回**：把卡塞进 PNG、再读出来，**一个字节都不能变**。

**这一批不做**：三套格式互转、界面预览、改用户工作区里的原卡。

### 三条必须先建立的世界观

**① 进口看扩展名，判脸看内容。这两件事必须分开写，不能混。**

- **进口（准入）**：只收 `.json` 和 `.png`。用户口径（2026-10-19）：**导入必须是 `.json`**；`.txt` 只是他自己看稿方便，产品不照顾。
- **判脸（判定）**：进了门之后，是风月还是 Tavo 还是酒馆，**只看内容**，不看文件名。

为什么不能反过来（不能"按扩展名判格式"）：`制卡总纲/*.txt`、`素材库/*.txt` 这 10 个文件扩展名是 `.txt`，内容和 `成品世界书素材库/*.json` 是同一套风月结构；只看扩展名会把它们判成"不是卡"。反过来，`tavo整理/raw/regex_id_mapping_final.json` 名字带 `regex`、扩展名 `.json`，内容却是一张 `{uid: id}` 映射表，**不是卡**。
⇒ 判据 0：**门禁在调用方（只看扩展名），判定在解析器（只看字节）。解析器本身不许读文件名。**

**② 三套格式不是「同一张表换个字段名」，是三种世界观。**
最容易翻车的三组（详见 §3 对照表）：

| 你以为一样 | 实际 |
|---|---|
| 开关 | 风月 `enable`、Tavo `enabled`、酒馆 **`disable`（反义）** |
| 关键词 | 风月是**一个字符串**（`_or_水@wb@火`）、Tavo/酒馆是**数组** |
| `depth` | 三套都有这个字，**语义不同**：风月是扫描深度、酒馆是注入深度、Tavo 另有 `injectionDepth`（还有 999 哨兵值） |

**③ 「没数据」不等于「没问题」。**
没给提示词/前置词/后置词时，不能报「0 条永不触发」，要报「未判」。
这条在机构上叫**空值纪律**，B 段必须实现，否则体检会给人假安全感。

## 1. 术语与证据等级

### 1.1 术语

| 词 | 含义 |
|---|---|
| **认脸** | 判定一个文件属于哪套格式，输出判定＋依据＋置信度 |
| **条目** | 世界书里的一条（风月 `world_book[i]`、Tavo `entries[i]`、酒馆 `entries[uid]`） |

## 2. 认脸（`CardFormat`）

### 2.0 准入：扩展名门禁（在调用方做，不在解析器里做）

**产品口径**：导入只收 **`.json`** 和 **`.png`**。

| 扩展名 | 处理 |
|---|---|
| `.json` / `.JSON`（大小写不敏感） | 进 JSON 分支 |
| `.png` / `.PNG` | 进 PNG 分支 |
| 其它一切（含 `.txt`、`.md`、无扩展名） | **拒绝**，不进解析器 |

拒绝话术（逐字）：

```
只支持 .json 和 .png 两种文件。如果是 .txt，请先改回 .json 再导入。
```

**三条纪律**：

1. **门禁只看扩展名，解析器只看字节。** `CardFormat` 的函数签名只有字节，**不许传文件名进去**——否则「按内容判」这条会在实现里悄悄退化成「按名字猜」。
2. **测试样本里的 `.txt` 不算产品支持面。** 那 10 个 `.txt` 只用于**本规格的样本核对**（证明同一套结构可能出现在别的扩展名下）；F 系列用例一律用 `.json`。
3. **`.json` 进门后仍要按内容判**：一个叫 `xxx.json` 的文件可能是 Tavo 卡、可能是映射表、可能根本不是卡。门禁只负责「别让明显不对的文件进来」，不负责「判对」。

### 2.1 输入与输出

**输入**：一个文件的**字节**（不要只给路径——B 段要能对内存里的字节判）。路径只用于报错信息，**不参与判定**。
**禁止**：写盘、改盘、移动文件。认脸是**纯只读**操作。

**输出**（字段名 B 段照抄，顺序无所谓，类型固定）：

```
FormatVerdict {
  format:      FormatKind          // 见 2.2 枚举
  subtype:     string?             // 子类型，见 2.2
  confidence:  HIGH | LOW          // 见 2.6
  evidence:    string[]            // 命中的判据，逐条人类可读，例："顶层键 world_book 是数组"
  conflicts:   string[]            // 同时成立的互斥特征，见 2.5
  defaultsApplied: string[]        // 补过的默认值，风月专用，见 2.4
  entryCount:  int?                // 能数就数（风月/Tavo/酒馆世界书）
  keysSeen:    string[]            // 判不出时必填：看过的顶层键，最多 20 个，见 2.7
  embeddedJson:string?             // 仅 PNG：解出来的原始 JSON 字符串（未 parse）
  pngTextKeys: string[]            // 仅 PNG：见到的文本块关键字
}
```

`FormatKind` 枚举（**只有这 8 个值，不许自创**）：

| 值 | 中文名 | 说明 |
|---|---|---|
| `FENGYUE` | 风月AI | 顶层 `world_book` |
| `TAVO_BOOK` | Tavo 世界书 | 顶层 `entries` 数组 |
| `TAVO_CHAR` | Tavo 角色卡 | 顶层 `{kind,id,name,updatedAt,data}` |
| `TAVO_REGEX` | Tavo 正则 | 同上但 `entries` 元素含 `findRegex` |
| `TAVO_PRESET` | Tavo 预设 | 同上但含 `basicPrompts`/`active` |
| `ST_WORLD` | 酒馆原生世界书 | 顶层 `entries` 字典 |
| `ST_CARD_PNG` | 酒馆角色卡（PNG） | PNG 签名 ＋ 文本块 |
| `UNKNOWN` | 未知 | 判不出 |

`subtype` 取值：

| format | subtype | 判据 |
|---|---|---|
| `FENGYUE` | `TEMPLATE` | 顶层另有 `_comment`（数组）[实：15/22 文件] |
| `FENGYUE` | `PLAIN` | 只有 `world_book` [实：7/22] |
| `ST_CARD_PNG` | `V3` / `V2` | 按读到的块：有 `ccv3` ⇒ `V3`；只有 `chara` ⇒ 按解出的 `spec` 填 `V2`/`V3`，无 `spec` ⇒ `V2`（[推]，见 §8） |
| 其它 | `null` | — |

### 2.2 判定算法（按顺序，命中即停）

**这一步的顺序就是优先级，不许重排。** 后面 2.5 的冲突裁决全部由这个顺序实现。

```
判(字节 B):
  # 第 0 步：PNG 先判，因为 PNG 字节当文本解必失败
  if B 的前 8 字节 == 89 50 4E 47 0D 0A 1A 0A:
      return 判PNG(B)                      # 见 2.3，可能返回 ST_CARD_PNG 或 UNKNOWN

  # 第 1 步：当文本读
  s = UTF-8 解码(B)                        # 允许 BOM；解码失败 ⇒ UNKNOWN(理由=NON_UTF8)
  j = JSON 解析(s)                          # 失败 ⇒ UNKNOWN(理由=NOT_JSON)
  if j 不是 JSON 对象:                      # 数组/标量
      return UNKNOWN(理由=NOT_OBJECT)

  # 第 2 步：P1 风月 —— 最高优先级
  if j 含 "world_book" 且 j.world_book 是数组:
      return FENGYUE(子类型见 2.2.1)
      # 注意：不再看 entries，即使同时存在也归风月（见 2.5 冲突 C1）

  # 第 3 步：P3/P4 Tavo 资产 —— 四件套比「entries 的形态」更专有
  if j 同时含 "kind" 且 "id" 且 "name" 且 "updatedAt":
      if j 含 "data" 且 data 是对象:
          return TAVO_CHAR
      if j 含 "entries" 且 entries 是数组:
          if 元素含 "findRegex":      return TAVO_REGEX
          if 顶层含 "basicPrompts" 或 "active" 或元素含 "content"+"role": return TAVO_PRESET
          return TAVO_BOOK(子类型标 TAVO_ASSET_UNKNOWN)   # 仍是 Tavo，但子类判不出
      return UNKNOWN(理由=TAVO_SHAPE_INCOMPLETE)          # 有 kind 四件套但既无 data 又无 entries

  # 第 4 步：P2 只有 entries
  if j 含 "entries":
      if entries 是数组:  return TAVO_BOOK
      if entries 是字典:  return ST_WORLD
      return UNKNOWN(理由=ENTRIES_NOT_COLLECTION)

  # 第 5 步：什么都不是
  return UNKNOWN(理由=NO_SIGNATURE_KEY, keysSeen=前 20 个顶层键)
```

**为什么 Tavo 资产（第 3 步）要排在 `entries` 形态（第 4 步）之前**：
Tavo 的正则/预设**也有 `entries` 数组**，元素里也有 `content`。如果先按「entries 是数组 ⇒ Tavo 世界书」判，正则和预设会被误判成世界书。四件套 `kind/id/name/updatedAt` 是 Tavo 资产独有的，用它先分流才不误判。这是**顺序敏感**的地方，B 段不许调换。

#### 2.2.1 风月子类型

`_comment` **存在且是数组** ⇒ `TEMPLATE`；否则 `PLAIN`。
[实] `_comment` 在样本里 100% 是字符串数组（如 9 个元素）。若 `_comment` 存在但不是数组 ⇒ 仍判 `FENGYUE`，但 `conflicts` 里加一条「`_comment` 不是数组」。

### 2.3 PNG 分支（`判PNG`）

```
判PNG(B):
  if B 长度 < 8 或签名不符: return UNKNOWN(理由=NOT_PNG)   # 实际到不了这里，签名已在上面验过
  块表 = 逐块解析(B)        # 见 §5.2；解析失败 ⇒ UNKNOWN(理由=PNG_CHUNK_BROKEN, 附字节偏移)
  文本 = 收集块表里所有 tEXt 的 (关键字 → 文本)
  if "ccv3" ∈ 文本 或 "chara" ∈ 文本:
      kw = 有 ccv3 ? "ccv3" : "chara"
      raw = base64解码(文本[kw])        # 失败 ⇒ UNKNOWN(理由=BASE64_BAD)
      s   = UTF-8 解码(raw)             # 失败 ⇒ UNKNOWN(理由=PAYLOAD_NOT_UTF8)
      j   = JSON 解析(s)                # 失败 ⇒ UNKNOWN(理由=PAYLOAD_NOT_JSON)
      if j 不是对象:                     # 失败 ⇒ UNKNOWN(理由=PAYLOAD_NOT_OBJECT)
      return ST_CARD_PNG(embeddedJson=s, pngTextKeys=文本的所有关键字)
  else:
      return UNKNOWN(理由=PNG_NO_CARD_BLOCK, pngTextKeys=所有文本块关键字)
      # 逐字话术见 2.7「这不是酒馆角色卡」
```

**要点**：
- 只有 `tEXt` 算数。`iTXt`/`zTXt` **不读**（3/3 实测样本全是 `tEXt`；见 §8-11 的理由与验证方法）。
- `embeddedJson` 必须是**解码后的原始字符串**，不许 `parse` 后再 `toString()`——那样会丢键顺序、改转义、把 `\u4e2d` 变成「中」。
- 两块都在时**取 `ccv3`**。理由[实]：本机 3 张样本卡里有 1 张（记为 PNG-2）的 `chara` 是 V2、`ccv3` 是 V3，两块字节数同为 20152 但内容不同（`spec` 字段不同，`data` 键集合 16/16 相同）。取错块会导致「读出来是旧版本」。
- 两块都在但内容不同 ⇒ `conflicts` 加一条「chara 与 ccv3 内容不一致，已取 ccv3」。

### 2.4 风月省略默认值（必须在解析阶段就地补）

[实] 607 条里 `value_type`/`value_configs` **只有 94 条带**（94/607）。而且这 94 条**全部**是 `value_type=0`、`value_configs=[]`（**没有一条真正的概率模式实例**，见 §8-1）。

规则：
1. 缺失 `value_type` ⇒ 补 `0`，`defaultsApplied` 加 `"value_type"`。
2. 缺失 `value_configs` ⇒ 补 `[]`，`defaultsApplied` 加 `"value_configs"`。
3. **补了默认值不能产生任何 finding**。F2 就是盯这条。
4. `value_type=0` 且 `value_configs` 非空 ⇒ 这是**矛盾**，报 WARN（不是错误：平台可能容忍）。

### 2.5 冲突裁决（同时成立时谁赢）

**总原则：优先级由 2.2 的顺序定义，不另设规则。** 下表是顺序的推论，B 段照此实现并在报告里写出 `conflicts`：

| 编号 | 同时出现 | 判定 | 置信度 | conflicts 里写什么 |
|---|---|---|---|---|
| C1 | `world_book` ＋ `entries` | **风月**（P1 赢） | HIGH | 「world_book 与 entries 并存，按风月处理」 |
| C2 | `world_book` ＋ `kind/id/name/updatedAt` | **风月**（P1 赢） | HIGH | 「风月结构与 Tavo 资产四件套并存」 |
| C3 | `kind` 四件套 ＋ `entries` 是字典 | **Tavo 资产**（第 3 步赢） | LOW | 「Tavo 四件套与字典形态 entries 并存，形态异常」 |
| C4 | `entries` 是数组 ＋ 元素含 `findRegex` 但无四件套 | **TAVO_BOOK** | LOW | 「像正则但缺 Tavo 四件套」 |
| C5 | `entries` 是字典 ＋ 元素含 `keywords/content`（Tavo 味） | **ST_WORLD**（键类型说了算） | HIGH | 「元素字段像 Tavo，但 entries 是字典」 |
| C6 | 顶层是纯 `{uid: 整数}` 字典（如映射表） | **UNKNOWN** | — | 「疑似 id 映射表，不是卡」 |

C5 的依据[实]：Tavo 的 `entries` **602/602 全是数组**；酒馆的 `entries` **69/69 全是字典且键全为整数**。所以「容器类型」比「元素字段」更可靠。

### 2.6 置信度

| 置信度 | 什么时候 |
|---|---|
| `HIGH` | 命中 P1 / P2（容器类型明确）/ P3 的 `data` 分支 / PNG 两块之一解码成功 |
| `LOW` | 命中 C3 / C4 这类「特征打架」的情况；或 Tavo 资产判不出子类（`TAVO_ASSET_UNKNOWN`）；或只有单一弱特征（例如只有 `entries` 字典但一条entry都没有） |
| （不适用） | `UNKNOWN` 没有置信度 |

**空容器例外**：`entries` 是空数组/空字典时，仍按类型判（Tavo/ST），但置信度降到 `LOW`，并加 evidence「容量为 0，无元素可交叉验证」。

### 2.7 错误话术（逐字，B 段照抄）

| 情形 | 返回话术（用户可见） |
|---|---|
| 不是 JSON 也不是 PNG | `认不出这个文件：既不是 PNG 图片，也不是合法的 JSON 文本。` |
| JSON 不是对象 | `认不出这个文件：JSON 最外层不是对象（是数组或单值），三套卡都不是这种形状。` |
| 有 `entries` 但容器类型不对 | `认不出这个文件：entries 既不是数组也不是对象。` |
| 判不出 | `认不出这个文件是什么格式。看过的顶层键：<前 20 个，逗号分隔>。` |
| PNG 无卡块 | `这不是酒馆角色卡：PNG 里找不到 chara 或 ccv3 文本块。` |
| PNG 有卡块但解不开 | `这是 PNG，但卡数据解不开：<base64 解码失败／不是 UTF-8／不是 JSON>。` |
| PNG 结构坏 | `PNG 文件结构损坏：第 <n> 个数据块（偏移 <off>）读不下去。` |

**禁止**：
- 禁止在判不出时返回「最像的那个」。宁可知未知。
- 禁止把 `keysSeen` 写成空数组（判不出时必须给键名清单）。
- 禁止把「文件不存在／没权限」包装成「格式未知」——那是 IO 错误，要分开报。

## 3. 三套字段与取值域

> **读法**：每一行都给「合法域」（校验器认的）和「实测域」（样本里真出现过的）。
> 两者不一致时**以合法域为准校验，以实测域为准解释**——实测域窄，不代表别的值非法。
> 样本基数见 §1.3。带 ⚠️ 的行是三套之间最容易被写混的字段。

### 3.1 风月AI —— 12 字段（607 条）

## 4. 体检（`CardCheck`）

### 4.1 输入、输出与级别

**输入**：
1. 认脸结果 `FormatVerdict`（必须先认脸，不认脸不体检）
2. 可选：系统文本三段 —— `prompt`（提示词）／`pre`（前置词）／`post`（后置词），**可分别缺省**
3. 可选：`detailHtml`（「详细介绍」里的 HTML 文本），用于判 B 类

**输出**：

```
CheckReport {
  findings: Finding[]
  stats: {
    entries: int
    byFormat: string
    cCount: int?          // 永不触发条数；未判时必须是 null，不是 0
    unjudgedCount: int?   // 未判条数
    notApplicableCount: int
  }
  skipped: {check: string, reason: string}[]   // 跳过的检查与原因，必须显示
  systemTextGiven: {prompt: bool, pre: bool, post: bool}
}

Finding {
  level:   ERROR | WARN | INFO
  code:    string        // 见 4.2/4.3 的表，固定词表
  entry:   EntryRef      // 定位，见下
  field:   string?       // 出问题的字段名
  message: string        // 面向用户的一句话（中文，逐字模板见 4.5）
  evidence: string       // 证据，截断到 60 字；不含整条正文
}

EntryRef {
  index: int?      // 0 起：数组用下标，字典用「按整数 uid 排序后的序号」
  sort:  int?      // 风月 sort
  uid:   string?   // 酒馆 entries 的键 / Tavo identifier
  key:   string?   // 风月 key 原串（最多 30 字）；Tavo/酒馆取 key[0]
}
```

**级别口径**（B 段不许自行升降）：

| 级别 | 什么时候 | 用户看到的效果 |
|---|---|---|
| `ERROR` | 平台会拒收、导入必失败、或明确会被判「积分刺客」 | 必须修 |
| `WARN` | 能存但行为可能不对（永不触发、可能互相压制、矛盾配置） | 建议修 |
| `INFO` | 只是「没设置，按默认」或「不适用」 | 知悉即可 |

### 4.2 字段级检查（三套各一张表）

**总规则**：
- **「缺字段」与「取值越界」必须分开报**（不同 `code`）——它们的修法完全不同。
- 每套只跑自己那张表。给 Tavo 跑风月的位掩码校验 = 满屏假错误。
- 类型不符一律 `ERROR`（这是最硬的错），取值越界也是 `ERROR`，缺必填 `ERROR`。
- **空值不等于错**：酒馆那三个 `null` 字段必须走 INFO，不能走 ERROR。

### 4.3 语义级三件（本批真正的价值）

#### 4.3.1 关键词过宽（积分刺客）

**只在风月上跑**。Tavo/酒馆没有 `_or_`/`@wb@` 协议，硬套会全判错。

**判定算法**：

```
判过宽(条目 e) -> Finding?:
    k = e.key
    if k 不是 string: return null            # 类型错已在字段级报过，不重复报

    # 第 1 步：只剥开头的前缀，剥一次，不递归
    prefix = 无
    if k 以 "_or_" 开头:  prefix = OR;  body = k[4:]
    elif k 以 "_and_" 开头: prefix = AND; body = k[5:]
    else:                 prefix = NONE; body = k

    # 第 2 步：按字面量 "@wb@" 切（不是正则！
    tokens = body.split("@wb@")

    # 第 3 步：逐 token 判「单字」
    for t in tokens:
        core = t.strip()                     # 去掉首尾空白（含全角空格）
        if core == "": continue              # 空 token 不参与（另有 FY_EMPTY_KEY）
        if 码点数(core) == 1:
            if prefix == OR:  return ERROR(FY_KEY_TOO_BROAD)
            if prefix == AND: return WARN(FY_KEY_TOO_BROAD_AND)
            # 无前缀：风月平台默认行为未实测，降为 WARN
            return WARN(FY_KEY_TOO_BROAD_IMPLICIT)
    return null
```

**「单字」的精确定义**（B 段照此实现，不许加码）：

| 问题 | 规格答案 | 依据 |
|---|---|---|
| 一个汉字算单字吗 | **算** | [实] 100 个单字 token 全是汉字 |
| 一个 ASCII 字母算吗 | **算** | 同一条规则，不特判语种 |
| 一个数字算吗 | **算** | 同上 |
| 一个标点/emoji 算吗 | **算**（码点数 1） | 同上 |
| 大小写怎么处理 | **不折叠**。`A` 是单字，`a` 也是 | 折叠只影响「是否同一个词」，不影响「长度」 |
| 全角/半角 | 不转换；`ｉ` 是 1 个码点 ⇒ 单字 | 规格只数码点 |
| 组合字符（e + ́） | **按码点数**，`e` + 组合符 = 2 个码点 ⇒ **不算单字** | 这是已知的漏报口子，见 §8-10 |
| 带空格的 token（`"水 "`） | 先 `strip()` 再数 | [实] 样本里 0 个带空格 token，但夹具要有 |

**为什么 `_or_` 是 ERROR、`_and_` 是 WARN**：`_or_` 是「任一命中即触发」，单字几乎必中 ⇒ 每条消息都在烧 token；`_and_` 要求同时命中，单字会显著抬高触发门槛、多半导致永不触发，风险方向相反但同样是坑。[推] 平台对两者的处罚口径未实测（§8-5）。

**计数要求**：`stats` 里要给 `broadKeyCount`，F5 要能看到「58 条里有 100 个单字 token」这类量级。实测基数：**58 条 / 100 个单字 token**（607 条口径）。

#### 4.3.2 永不触发（A / B / C 类）

**这条最容易写错，错法只有一种：拿系统文本去判所有条目。**
[实] 风月 607 条里 **`key_region=2`（只扫玩家输入）的有 161 条**，`key_region=4`（只扫 AI）的有 67 条。这 228 条**天然不吃系统文本**，如果一并判 C，会一次性误报 228 条假「永不触发」。

**第 0 步：先算「可判域」**

```
可判(e) =
  风月:  (e.key_region & 1) != 0          # 只有「吃系统文本」的条目才可判
  Tavo:  e.strategy == "keyword" 且 e.enabled != false   # constant 常驻、关闭的都不参与
  酒馆:  e.constant == false 且 e.disable == false    # 常驻 / 已关闭都不参与
```

不可判的条目，逐条给 INFO（不是 WARN）：

| 情形 | code | 话术 |
|---|---|---|
| 风月 `key_region=2` | `FY_NOT_APPLICABLE_REGION` | `不参与判定：这条只扫玩家输入，不看系统文本。` |
| 风月 `key_region=4` | `FY_NOT_APPLICABLE_REGION` | `不参与判定：这条只扫 AI 正文。` |
| Tavo `strategy=constant` | `TV_NOT_APPLICABLE_CONSTANT` | `不参与判定：这条是常驻条目，每轮都会注入。` |
| 酒馆 `constant=true` | `ST_NOT_APPLICABLE_CONSTANT` | 同上 |
| 酒馆 `disable=true` | `ST_NOT_APPLICABLE_DISABLED` | `不参与判定：这条是关闭状态。` |

**第 1 步：三级判定（只对可判条目）**

```
判触发(条目 e, 系统文本 T, 详细介绍 HTML H):
    # T = prompt + "\n" + pre + "\n" + post（只拼给了的那几段）
    tokens = 该条目的关键词列表
             风月: split(e.key) 去前缀、按 @wb@ 切、strip、去空
             Tavo: e.keywords ++ e.secondaryKeywords
             酒馆: e.key ++ e.keysecondary

    if tokens 为空:
        return C            # 没有词 ⇒ 永远不可能触发（Tavo 空 keywords / 酒馆空 key）

    if T 完全没有给（三段都缺）:
        return 未判          # ★ 空值纪律：不许返回 C，不许把计数写成 0

    if 任一 token 命中(T):
        return A

    # ---- 分水岭：这一套格式有没有「详细介绍 HTML」这条通道 ----
    if H 给了:
        if 任一 token 命中(H): return B
        return C
    else:
        if 格式是 风月:  return 未判（B 类待定）   # 风月有配置器 HTML，没给就不能断言
        else:            return C                  # Tavo / 酒馆没有 HTML 通道，不命中就是 C
```

**为什么这里要按格式分叉（关键）**：

| 格式 | 有「详细介绍 HTML」通道吗 | 没给 HTML 时 | 理由 |
|---|---|---|---|
| **风月** | **有** —— 「详细介绍」里是玩家配置器 HTML，可能出现角色名、选项文字 | **未判** | 命不中系统文本，仍可能被 HTML 命中（B 类） |
| **Tavo** | **没有** —— 世界书 JSON，没有配置器 HTML 字段 | **判 C** | 没有第二条命中通道，「系统文本不中」＝ 永不触发 |
| **酒馆** | **没有** —— 同上 | **判 C** | 同上 |

⇒ 这条分叉是让「C 类计数非零」在 Tavo/酒馆上**真正成立**的地方。若不分叉，C 类只可能在「风月＋给了 HTML」这一种组合下出现，等于把体检的主功能关掉了。

**命中（`命中(token, text)`）的精确定义**：

| 问题 | 规格答案 | 理由 |
|---|---|---|
| 子串还是词边界 | **子串**（`text.contains(token)`） | [实] 风月没有 `matchWholeWord` 字段，平台侧行为未实测；用词边界会大量假 C |
| 区分大小写吗 | **先按原样匹配；不中再做一次大小写不敏感匹配；两次都不中才算不中** | 保守优先，宁可漏报 C，不可误报 C |
| 中文怎么算 | 子串即可（中文无词边界概念） | — |
| 正则条目（`match_type=3`） | **不参与本判定**，标 `未判`（正则无法用子串近似） | [实] 样本 0 条，但夹具要有 |
| token 里的 `\` 等 | 按**字面量**处理，不编译正则 | 关键词不是正则 |

**第 2 步：计数与呈现**

```
stats.cCount = C 类条数
stats.unjudgedCount = 未判条数
stats.notApplicableCount = 不适用条数
三者之和 == 可判总数 + 不适用总数 == 全部条目数
```

**硬纪律（F6 专盯）**：
- 没给系统文本 ⇒ `cCount = null`（不是 0），`unjudgedCount = 全部可判条目数`，报告里写「未判 N 条」。
- 给了系统文本 ⇒ C 类**必须逐条列出**（EntryRef ＋ code ＋ 命中的反面证据：`所有 N 个词都没有出现在系统文本里`）。计数为 0 时必须显示「0」而不是省略这一项。
- **不许**把「无法判」写成「没问题」。

#### 4.3.3 同名 / 同键冲突

**目的**：同一本书里两条关键词一样、触发区域又重叠 ⇒ 平台可能只让其中一条进上下文（互相压制）。

```
判冲突(全部条目):
    按「归一化 key」分组：
        风月: split(e.key) → token 列表，保留顺序（不排序）
        Tavo: e.keywords（保留顺序）
        酒馆: e.key（保留顺序）
    同组内两两比较：
        if 一方的 key_region & 另一方的 key_region != 0:
            → WARN(KEY_COLLISION)
        else:
            → INFO(KEY_COLLISION_DISJOINT_REGION)   # 有交集才有可能压制
    另外：token 集合相同但顺序不同 → INFO(KEY_ORDER_DIFF)
```

**「重叠」的精确算法**：按位与 `!= 0`。

| 组合 | `a & b` | 结论 |
|---|---|---|
| 3 与 3 | 3 | 重叠 |
| 3 与 2 | 2 | 重叠 |
| 2 与 4 | 0 | **不重叠** |
| 7 与任何非 0 | ≠0 | 重叠 |

**Tavo/酒馆怎么办**：它们没有 `key_region`，视为「全区域重叠」（即只要 key 完全相同就报 WARN）。
**依据**：两者都有 `scanDepth` 但语义是「扫最近 N 条消息」，区域是固定的，不做位掩码 [推]。

**边界**：
- 空 key 不参与（29 条酒馆空 key、160 条 Tavo 空 keywords 会互相「撞」——这是噪声，不是冲突）。
- 只报 `key` 完全相同；**大小写不同视为不同**（不折叠），因为平台匹配是否折叠未实测。
- 风月实测：607 条 key 有 564 个不同值 ⇒ **有 43 处重复**，F 系列用例要能在合成夹具里复现这个形态。

#### 4.3.4 `sort` 重复（风月专有，WARN）

`sort` 是插入顺序，重复会导致顺序不确定。实测风月 `[0,99]` 里 96 个不同值 ⇒ 有重复。
判定：同一文件内 `sort` 值出现 ≥2 次 ⇒ 每个重复组报一条 WARN，`evidence` 写「sort=7 出现 3 次（条目 2、15、31）」。

### 4.4 空值纪律（贯穿全部检查）

| 情形 | 正确行为 | 错误行为（会被 F6 抓） |
|---|---|---|
| 没给系统文本 | C 类「未判」+ 计数 null | 报「0 条永不触发」 |
| 风月没给详细介绍 HTML | B 类「未判」 | 直接判 C |
| Tavo/酒馆没给 HTML | **照判 C**（它们没有 HTML 通道） | 也标「未判」⇒ C 类永远报不出来 |
| 条目 `key_region` 不吃系统文本 | 「不适用」 | 判 C |
| 酒馆字段是 `null` | 「未设置，按默认」INFO | 报「缺字段」ERROR |
| 风月缺 `value_type` | 补默认，不报 | 报「缺字段」 |
| 正则条目 | 「未判」 | 用子串硬判出 C |

| code | 话术模板 |
|---|---|

## 5. 酒馆 PNG：按字节写规格

> 这一节是「照字节实现」的，不是「按库实现」的。B 段只许用 JDK：`java.util.zip.CRC32`、`java.util.Base64`、`javax.imageio`（仅夹具）、`java.nio`。
> 不许引入第三方 PNG/图片库。

### 5.1 一个 PNG 文件的字节长什么样

```
偏移 0    8 字节   签名  89 50 4E 47 0D 0A 1A 0A     （\x89 P N G \r \n \x1a \n）
偏移 8    开始逐块排列，直到 IEND
```

每个块的布局（**全部大端**，big-endian）：

```
 +----------------+----------------+-------------------+----------------+
 |  length (4B)   |  type (4B)     |  data (length B)  |  CRC (4B)      |
 +----------------+----------------+-------------------+----------------+
    不含自身与 type     ASCII            length 字节        覆盖 type+data
```

- `length` = **data 的字节数**，不含 length 字段自己、不含 type、不含 CRC。
- `type` = 4 个 ASCII 字母（`IHDR`/`IDAT`/`tEXt`/`IEND`…）。
- 一个块总长 = `12 + length`。
- `IEND` 的 `length` 必须是 **0**（实测 3/3 的 `tail_len=0`）。

实测三张卡的块序列（**[实]**；样本卡按文件大小降序匿名为 PNG-1/2/3，**不记文件名、不记角色名**）：

```
PNG-1（2,135,730 B）  IHDR(13) → IDAT(740006) → tEXt(697822) → tEXt(697821) → IEND(0)
PNG-2（  551,901 B）  IHDR(13) → IDAT(511505) → tEXt(20158)  → tEXt(20157)  → IEND(0)
PNG-3（   46,572 B）  IHDR(13) → IDAT(44512)  → tEXt(990)    → tEXt(989)    → IEND(0)
```

> 三张的 `tEXt` 都是 `chara` 在前、`ccv3` 在后（长度差 1 字节，是关键字长度差）。PNG-1/PNG-3 两块同源（V3）；PNG-2 两块版本不同，见 §2.3。

> ⚠️ **关键实测修正**：三张卡的 `tEXt` 全在 **`IDAT` 之后**、`IEND` 之前。
> 合并单原来写的「在 `IHDR` 之后插入」是**按规范允许性推的**，不是样本实际形态。
> 本规格的取舍见 §5.5。

### 5.2 `tEXt` 块的精确布局

```
data 部分 = keyword (1–79 字节，Latin-1) + 0x00 + text (0 或多字节，Latin-1)
```

| 项 | 规定 |
|---|---|
| `keyword` | `chara` 或 `ccv3`，**5 或 4 个 ASCII 字节** |
| 分隔符 | **恰好一个** `0x00`；关键字内不许出现 `0x00` |
| `text` | `base64(JSON 的 UTF-8 字节)`；**纯 ASCII** |
| `text` 长度 | **无上限**（实测有一块 697,816 字节）；`length` 字段是 4B，理论上限 2³²−1 |
| 换行 | **不许有**任何 `\n`/`\r`（实测 6/6 块 `has_nl=false`） |
| 填充 | 标准 base64 字母表（`A–Z a–z 0–9 + /`），**带 `=` 补齐**；不是 URL-safe（实测 `urlsafe=false`） |

**为什么 `tEXt` 够用、不写 `iTXt`/`zTXt`**：

| 块 | 编码 | 能不能用 | 本规格 |
|---|---|---|---|
| `tEXt` | Latin-1 文本 | ✅ base64 是 ASCII 子集，**永远安全** | **只写这个** |
| `iTXt` | UTF-8，可压缩 | 规范允许，但实测 3/3 样本**一个都没有**；旧版酒馆是否读 `iTXt` 未验证 | ❌ 不写 |
| `zTXt` | 压缩 Latin-1 | 规范里有，但它压缩的是文本；酒馆实测不用 | ❌ 不写 |

> 读的一侧：**只认 `tEXt`**。遇到 `iTXt`/`zTXt` 不解析、跳过，并在 `pngTextKeys` 里如实列出「见到了 iTXt（未使用）」。
> 理由：宁可说「读不出」，也不要用一条没验证过的路径去解别人的卡。

### 5.3 CRC-32

```
CRC = CRC32( type 的 4 字节 || data 的 length 字节 )     # 不含 length 字段本身
```

参数（与 `java.util.zip.CRC32` 完全一致）：

| 参数 | 值 |
|---|---|
| 多项式（反射） | `0xEDB88320` |
| 初值 | `0xFFFFFFFF` |
| 输入/输出反射 | 是（`java.util.zip.CRC32` 内部已处理） |
| 最终异或 | `0xFFFFFFFF` |
| 覆盖范围 | **type + data**，**不含 length** |

Java 写法（唯一允许的算法）：

```
CRC32 c = new CRC32();
c.update(typeBytes, 0, 4);
c.update(dataBytes, 0, length);
long v = c.getValue();          // 已是最终值，不要再自己异或
```

> [实] 三张卡 6 个 `tEXt` 块 + 3 个 `IHDR` + 3 个 `IDAT` 的 CRC 全部复算通过（用 Python `binascii.crc32(type+data)`，与 Java `CRC32` 同一算法）。
> F7 要用 `java.util.zip.CRC32` **独立复算**，不许调用导出代码里的同一个函数来「自证」。

### 5.4 写入算法（`CardPng.export`）

**输入**：`jsonString`（String，**不是对象**）、`baseImage`（可选字节）、`outPath`
**输出**：写入的 `outPath`

```
导出(jsonString, baseImage?, outPath):
    # 1) 拒绝覆盖（F9）
    if outPath 已存在:
        return 失败("目标已存在，未覆盖：" + outPath)

    # 2) 准备 payload —— 绝不 parse
    jsonBytes = jsonString 按 UTF-8 严格编码        # 不做任何 normalize
    payload   = Base64 标准编码(jsonBytes)          # 不换行！用 Base64.getEncoder()，不要 getMimeEncoder()
    charaText = payload
    ccv3Text  = payload                              # 两块写同一份（见 5.6 的理由）

    # 3) 准备底图
    base = baseImage 或 内置 1×1 白图                # 见 5.7
    if base 不是合法 PNG: return 失败("底图不是 PNG")

    # 4) 找插入点：IEND 块开头
    iendOffset = 扫块直到 type=="IEND" 的偏移        # 扫不到 ⇒ 失败("底图结构损坏")
    head = base[0 : iendOffset]                      # 含 IHDR/IDAT/其它块，原样保留
    tail = base[iendOffset : ]                       # 从 IEND 开始，原样保留

    # 5) 拼两个 tEXt 块
    block1 = 造tEXt("chara", charaText)
    block2 = 造tEXt("ccv3",  ccv3Text)

    # 6) 写新文件（源图一个字节都不改）
    写文件(outPath, head || block1 || block2 || tail)

    return 成功(outPath)
```

`造tEXt(keyword, text)`：

```
造tEXt(kw, txt):
    dataBytes = kw 的 ASCII 字节 || 0x00 || txt 的 ASCII 字节
    return 大端4B(dataBytes.length) || "tEXt" 的 ASCII || dataBytes || 大端4B(CRC32("tEXt" + dataBytes))
```

**为什么放 `IEND` 之前（即 `IDAT` 之后）而不是 `IHDR` 之后**：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| `IHDR` 之后 | 想读卡的人不用读完像素数据，定位快 | 要在 IDAT 大数据（最大 74 万字节）**前面**插入 ⇒ 必须重写整幅图，且与 3/3 样本形态相反 | ❌ |
| **`IDAT` 之后 / `IEND` 之前** | **追加式**：前面字节原样照抄，只写两个块 + IEND；与 3/3 实测样本一致 | 读的人要扫完整文件（但扫块本来就是顺序的，不额外读像素） | ✅ |

> PNG 规范允许 `tEXt` 出现在 `IHDR` 之后、`IEND` 之前的任何位置（**只要不插在多个 `IDAT` 中间**）。两种都合法，选后者是为了「与样本一致 + 追加式写入不动大块」。
> 读的一侧必须两种位置都吃 —— 见 §5.5 第 1 步「全文件扫块」。

**禁止**：
- 禁止修改源图字节（不许 `Files.write(base, ...)`）。
- 禁止覆盖已存在的目标（不许 `StandardOpenOption.TRUNCATE_EXISTING`、不许 `REPLACE_EXISTING`）。
- 禁止对 JSON 做 `parse → toString()`、`JsonObject` 重组、格式化、转义归一。
- 禁止用 `Base64.getMimeEncoder()`（它会每 76 字符插换行）。

### 5.5 读回算法（`CardPng.read`）

```
读回(pngBytes):
    # 第 1 步：全文件扫块（不假设位置、不假设只有两个文本块）
    if 前 8 字节 != PNG 签名: return 失败("这不是 PNG")
    blobs = {}
    off = 8
    while off < len(pngBytes):
        if 剩余不足 8 字节: return 失败("PNG 结构损坏：块头截断 @off")
        len = 大端4B(bytes[off .. off+3])
        typ = bytes[off+4 .. off+7] 的 ASCII
        if 剩余不足 12+len: return 失败("PNG 结构损坏：块数据截断 @off")
        data = bytes[off+8 .. off+7+len]
        crcStored = 大端4B(bytes[off+8+len .. off+11+len])
        if typ == "tEXt":
            kw, txt = 在第一个 0x00 处切分(data)      # 没有 0x00 ⇒ 跳过并记 INFO
            blobs[kw] = txt                          # 同名块后者覆盖前者（记录 INFO）
        off += 12 + len
        if typ == "IEND": break

    # 第 2 步：按优先级取块
    if "ccv3" in blobs:          kw, txt, prio = "ccv3", blobs["ccv3"], 1
    elif "chara" in blobs:       kw, txt, prio = "chara", blobs["chara"], 2
    else:                        return 失败("这不是酒馆角色卡：PNG 里找不到 chara 或 ccv3 文本块。")

    # 第 3 步：解码（严格）
    raw = Base64 解码(txt)                     # 失败 ⇒ 失败("卡数据解不开：base64 解码失败")
    s   = raw 按 UTF-8 严格解码               # 失败 ⇒ 失败("卡数据解不开：不是 UTF-8")
    j   = 尝试 JSON 解析(s)                    # 失败 ⇒ 失败("卡数据解不开：不是 JSON")
    if j 不是对象:                             # 失败("卡数据解不开：JSON 最外层不是对象")

    # 第 4 步：报告
    return 成功(s, 块名=kw, 优先级=prio, pngTextKeys=blobs 的所有键)
```

**读的硬规定**：

| 规定 | 理由 |
|---|---|
| **不假设 `tEXt` 在哪个位置**，从偏移 8 扫到 `IEND` | 实测在 IDAT 后，但规范允许在两处；别家工具（含我们自己写的）可能不同 |
| **`ccv3` 优先于 `chara`** | [实] 样本卡 PNG-2 的 `chara` 是 V2、`ccv3` 是 V3，内容不同；取 `chara` 会读到旧版本 |
| 两块都在但内容不同 ⇒ 用 `ccv3` ＋ 报 INFO「两块不一致」 | 沉默取一个会让人以为卡是对的 |
| 同名块出现多次 ⇒ 后者覆盖，报 INFO | 规范没说重复怎么办；最后一版通常是最新写入 |
| **不校验 CRC 就拒绝**：CRC 错只报 WARN，数据照解 | 现实里 CRC 错的卡还能用；直接拒绝会让用户失去可读性。但**导出侧必须写对 CRC**（F7） |
| 解不出 ⇒ **明确失败**，不许返回空 JSON | F10 专盯 |

**为什么导出时两块写同一份**：
[实] 3 张卡里 2 张两块完全相同（都是 V3），1 张不同（`chara`=V2、`ccv3`=V3）。我们没有 V2 生成器，写两份不同内容只会制造「两个版本」的假象。写同一份 = 两块都可用，读的一侧按 `ccv3` 优先，行为一致。

### 5.6 往返判定（F8，不可放宽）

**定义**：`导出(s) → 读回() == s`，字符串**逐字相等**（`String.equals`，不是 `equalsIgnoreCase`，不是「JSON 语义相等」）。

```
往返(s):
    png = 导出(s, null, tmpPath)
    (r, 块名) = 读回(png)
    assert r.equals(s)        # ← 就这一条，没有备选口径
```

**为什么这条必须这么硬**：
1. 我们全程**不 parse**，所以键顺序、中文、`\uXXXX` 转义、空格、换行**天然**保持。一旦相等不成立，只可能是 B 段偷懒做了 parse/dump 或用了 MIME base64。
2. 这条同时钉住了编码：任何 UTF-8 编解码不一致都会立刻暴露。
3. 「语义相等」当验收 = 放水：键顺序变了、`\u4e2d` 变成「中」，用户下次读出来的文件就和他存的不一样了。

**编码细节（B 段必须照此实现）**：

| 环节 | 规定 |
|---|---|
| 源 JSON 文件的读入 | 按字节读 → UTF-8 **严格**解码（`CodingErrorAction.REPORT`）。**BOM 保留为 U+FEFF，不剥离** |
| 导出 | `jsonString.getBytes(UTF_8)`（严格） |
| base64 | `Base64.getEncoder().encodeToString(bytes)`（标准、带 padding、无换行） |
| 读回 | `Base64.getDecoder().decode(txt)` → `new String(bytes, UTF_8)` |
| 比较 | `String.equals` |

> BOM 为什么不剥：往返判定比的是「你存进去的那串字符」。剥了 BOM，读回来就少一个字符，`equals` 必红。若产品上要剥 BOM，必须在**入口**剥一次，并让往返以剥后的串为准 —— 本批选「不剥」，最简单、最可证。

**非 UTF-8 源文件**：直接报错「源文件不是 UTF-8，无法无损导出」。**不许**用 `new String(bytes)` 让它替换成 `�`——那样往返比对会「看起来成功但内容已经毁了」。

### 5.7 内置底图（没有给 `baseImage` 时）

**规矩**：不许把一张 PNG 常量数组硬编码进源码（体积、可审计性都差），也不许读外部资源。**用 `javax.imageio` 现画 1×1**：

```

    img.setRGB(0, 0, 0xFFFFFF)
    ByteArrayOutputStream out = ...
    ImageIO.write(img, "png", out)
    return out.toByteArray()
```

产物必然是合法 PNG（含 `IHDR`/`IDAT`/`IEND`），然后走 §5.4 的同一套插入逻辑。

> 夹具若想「手拼字节」，规则在 §6.3；但**产品代码只用 ImageIO 现画**，不拼常量。

J3 的三条目变体：`strategy=keyword`，`keywords` 分别为 `["甲"]`、`["乙"]`、`["丙"]`，其余字段同 J3。

**输入**：`prompt="甲出现了"`，**不给 HTML**（Tavo 本来也没有这条通道）。

| 条目 | 期望 |
|---|---|
| 0（甲） | A |
| 1（乙） | **C** |
| 2（丙） | **C** |

⇒ `stats.cCount = 2`（**非零**）、`stats.unjudgedCount = 0`

### 6.3 PNG 夹具（F7–F10 用）

**规则**：**用 `javax.imageio` 现画 1×1**，不要硬编码 PNG 字节常量。

```
造底图():
    BufferedImage img = new BufferedImage(1, 1, TYPE_INT_RGB)
    img.setRGB(0, 0, 0xFFFFFF)
    ByteArrayOutputStream o = new ByteArrayOutputStream()
    ImageIO.write(img, "png", o)
    return o.toByteArray()
```

**P1 · 导出用**：`造底图()` ＋ `J4.toString()`（**注意：夹具里可以 `toString()`，产品代码里绝对不行**——夹具只验结构，不验键顺序）

**P2 · 无卡块的 PNG**（F10）：就是 `造底图()` 本身，不插任何 `tEXt`

**P3 · 有卡块但 base64 坏**：手工插一个 `tEXt`，关键字 `chara`，文本 `"!!!not-base64!!!"`

**P4 · 有卡块但 payload 不是 JSON**：`tEXt` 关键字 `chara`，文本 = `Base64("hello")`

**P5 · `chara` 与 `ccv3` 不一致**（验优先级）：
- `chara` ← `Base64` of `{"spec":"chara_card_v2","data":{"name":"旧"}}`
- `ccv3` ← `Base64` of `{"spec":"chara_card_v3","data":{"name":"新"}}`
- 期望读回 `ccv3` 那份，并报 INFO「两块不一致」

> 这些夹具的 PNG 都是**几十字节到几百字节**，全部运行时生成，不进仓库、不进资源目录。

### 6.4 夹具命名与组织建议（给 B 段）

| 建议 | 理由 |
|---|---|
| 一个夹具一个常量，命名 `FX_J1_FENGYUE_PLAIN`、`FX_N4_OR_SINGLE` | F 用例与夹具一一对应，返修时不用找 |
| JSON 用文本块（text block）写，不用 `JsonObject` 拼 | 拼出来的容易「顺手 normalize」，与「逐字」纪律冲突 |
| PNG 夹具每次测试现生成，不落盘 | 落盘就会有「谁把真实卡塞进 resources」的风险 |
| 断言用**精确字段**（`assertEquals("FY_DEPTH_RANGE", f.code)`），不用 `contains("depth")` | 后者会把相邻字段的报错当成通过 |

## 7. 验收用例 F1–F11（B 段照抄成单测）

> 每条给：**输入 → 期望（逐字或字段级）→ 什么情况算红 → 负例（故意改坏哪里会让它红）**。
> 完整可抄版本见 `docs/格式层规格-判据表F1-F11-2026-10-19.md`。

### F1 · 七种样本各判对

- **输入**：J1–J7 七个夹具（§6.1），全部走 `.json` 门禁。
- **期望**：`format` 与 `subtype` 逐一对上 §6.1 的表；每条 `evidence` 非空。
- **算红**：任一夹具 format 错、subtype 错、或 `TAVO_REGEX`/`TAVO_PRESET` 被判成 `TAVO_BOOK`。
- **负例**：把 §2.2 第 3 步（Tavo 四件套）挪到第 4 步之后 ⇒ J6/J7 变 `TAVO_BOOK` ⇒ 红。

### F2 · 风月省略默认值不误报

- **输入**：J1（无 `value_type` / `value_configs`）。
- **期望**：`defaultsApplied` 含两项；`findings` 中**不含** `FY_MISSING_FIELD`（field=value_type/value_configs）；`entryCount=1`。
- **算红**：出现任何指向这两个字段的 ERROR，或 `format` 变成 `UNKNOWN`。
- **负例**：把「缺失即报缺字段」写进解析器 ⇒ 红。

### F3 · 判不出 ⇒ 未知 ＋ 键名

- **输入**：N2（`{"foo":1,"bar":[1,2],"baz":{"x":true}}`）。
- **期望**：`format=UNKNOWN`；`keysSeen` = `["foo","bar","baz"]`；话术逐字含「看过的顶层键：foo, bar, baz」。
- **算红**：`format` 是任何一个具体格式；或 `keysSeen` 为空；或话术里没有键名。
- **负例**：在 `UNKNOWN` 分支加一句「按最接近的风月处理」⇒ 红。

### F4 · 四个越界值

- **输入**：N3-a/b/c/d 四个变体。
- **期望**：分别且仅分别产出 `FY_PROBABILITY_RANGE` / `FY_DEPTH_RANGE` / `FY_KEY_REGION_RANGE` / `FY_MATCH_TYPE_RANGE`，各一条 ERROR，`entry.index=0`。
- **算红**：漏报任一；或一条变体里冒出 2 条以上 ERROR（说明校验口径串了）；或级别不是 ERROR。
- **负例**：删掉位掩码 1–7 的校验 ⇒ N3-c 红。

### F5 · `_or_` 单字

- **输入**：N4（三条：`_or_水@wb@火`、`_and_水@wb@火`、`_or_水滴@wb@火焰`）。
- **期望**：`FY_KEY_TOO_BROAD`（ERROR，第 0 条）、`FY_KEY_TOO_BROAD_AND`（WARN，第 1 条）、第 2 条无 finding；`broadKeyCount=2`。
- **算红**：把「水滴」也判成单字（长度算错）；或把 `_and_` 也判 ERROR（级别错）；或第 2 条误报。
- **负例**：删掉单字检查 ⇒ 红；把「单字」实现成「len(token)==1 字节」⇒ 中文永远不命中 ⇒ 红。

### F6 · C 类计数与条号（含「没给系统文本」）

- **输入**：N5 五条 ＋ **四种**输入组合（给系统文本无 HTML／给系统文本＋HTML／三段全缺／Tavo 卡不给 HTML）。
- **期望**：
  - 风月、给系统文本无 HTML：`cCount=0`（**要显示 0**）、`unjudgedCount=2`、`notApplicableCount=2`
  - 风月、给系统文本＋HTML：`cCount=1`，且 `EntryRef.index=1`
  - 风月、三段全缺：`cCount=null`（**不是 0**）、`unjudgedCount=3`
  - **Tavo、给系统文本、不给 HTML**：`cCount` **必须非零**（Tavo 没有 HTML 通道，不命中即 C）——这一组是让「C 类计数非零」真正成立的用例
- **算红**：把 `key_region=2/4` 的两条算进 C（会变成 `cCount=2` 或 `4`）；或没给系统文本时 `cCount=0`；或 C 类不列条号；或 Tavo 那组报「未判」而不是 C。
- **负例**：把可判域判断（`key_region & 1`）删掉 ⇒ 第二组 `cCount` 变 3 ⇒ 红；把「风月/非风月」分叉删掉 ⇒ Tavo 那组全变未判 ⇒ 红。

### F7 · PNG 导出：CRC 与结构

- **输入**：P1（1×1 底图 ＋ J4 的 JSON 字符串）。
- **期望**：
  1. 输出文件前 8 字节是 PNG 签名
  2. 块序列含 `IHDR`、至少一个 `IDAT`、`tEXt(chara)`、`tEXt(ccv3)`、`IEND`（顺序：IEND 必须最后）
  3. 每个块用 `java.util.zip.CRC32` 独立复算（`update(type)` + `update(data)`）与文件里存的 CRC 相等
  4. `IEND` 的 length 为 0
  5. 原有 `IHDR`/`IDAT` 的字节与底图**逐字节相同**
- **算红**：任一 CRC 对不上；或缺 `ccv3`；或 `IEND` 不在最后；或 IDAT 被重编码（字节变了）。
- **负例**：故意把 CRC 写成 `0` 但导出仍返回成功 ⇒ 读回侧复算必须拦住 ⇒ 红。

### F8 · PNG 往返逐字

- **输入**：一个含中文、含 `\uXXXX` 转义、含特殊键顺序的合成 JSON 字符串（例：`{"z":1,"a":"\u4e2d","m":"中"}`，故意 z 在前）。
- **期望**：`读回(导出(s)).equals(s) == true`。
- **算红**：不相等。任何不相等都是**实现问题**，不是用例问题。
- **负例**：把导出改成 `parse → toString()` ⇒ 键顺序变（`{"a":..,"m":..,"z":..}`）⇒ 红；用 `getMimeEncoder()` ⇒ 读回时 base64 带换行 ⇒ 红。

### F9 · 目标已存在 ⇒ 拒绝

- **输入**：先建一个占位文件 `out.png`（内容随意），再导出到同一路径。
- **期望**：返回失败，话术含「目标已存在，未覆盖」；`out.png` 内容**一个字节没变**；源底图也没变；不产生临时文件残留。
- **算红**：覆盖成功；或"先删后写"（内容变了也算红）；或抛出未捕获异常。
- **负例**：把写入改成 `REPLACE_EXISTING` ⇒ 红。

### F10 · 非酒馆 PNG ⇒ 明确报错

- **输入**：P2（无 `tEXt`）、P3（base64 坏）、P4（payload 不是 JSON）。
- **期望**：三种都返回**失败**，话术分别逐字对上 §5.8；**不许**返回空字符串/空 JSON/`{}`。
- **算红**：返回了 `""` 或 `"{}"` 或 `null` 但标成功。
- **负例**：把「没有块」实现成 `return ""` ⇒ 红。

### F11 · `card_inspect` 只读

- **输入**：源码级检查 ＋ 行为检查。
- **期望**：
  1. 源码里 `card_inspect` 路径上**没有任何** `writeText` / `writeBytes` / `delete` / `renameTo` / `createNewFile` / `Files.write`
  2. 跑一次 inspect 前后，对源文件做 sha256，**必须相同**
  3. `card_export` 路径上没有「覆盖已存在文件」的分支（F9 已行为验证，这里补源码级）
- **算红**：出现任一写操作；或 sha256 变了。
- **负例**：在 inspect 里加一句「顺手把规范化后的 JSON 写回」⇒ 红。

## 9. 给 B 段的三句话交接（最容易翻车的三条）

1. **§2.2 的判定顺序不许改**：`world_book` → Tavo 四件套 → `entries` 形态。把「`entries` 是数组」写在最前面，Tavo 的正则/预设会全被判成世界书（F1 的 J6/J7 就是为了钉这个）。
2. **§4.3.2 先算「可判域」再判 A/B/C**：风月 607 条里有 161 条 `key_region=2`、67 条 `key_region=4`，它们根本不吃系统文本。直接拿提示词去判，会一次性误报 228 条假「永不触发」（F6 专盯）。
3. **PNG 全程不 parse JSON**：导出收的是字符串，直接 `getBytes(UTF_8)` → base64 → 写块；读回是 base64 → 字符串。中间只要有一次 `parse → toString`，F8 的「逐字相同」必红，而且红得很难查（键顺序变了但内容看着没错）。
